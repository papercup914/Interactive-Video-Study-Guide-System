방대한 코드베이스를 전수 조사했습니다. 유지보수 관점에서 **심각도 순**으로 정리합니다.

## 🔴 CRITICAL (현재 생산환경에서 이미 위험하거나 곧 깨지는 것)

### C1. 이중 시스템 공존 — 레거시 `app.py`(Streamlit)과 `backend/`(FastAPI) 병존
- `app.py`(337줄)는 `from services import video, llm`, `from storage import json_handler`를 임포트하지만 **이들 모듈은 현재 디렉토리에 거의 없거나** 이전 API 시그니처(`llm.generate_answer(context, question, provider)` 3-인자)를 사용합니다.
- 반면 실제 서비스는 `services/llm.py`(921줄)와 `backend/services/llm.py`가 따로 있고, `app.py`는 `services/video.py`의 `get_video_title()`을 호출하지만 해당 함수는 `backend/services/video.py`에 존재하지 않습니다.
- **즉 `app.py`는 현재 코드와 어긋난 채 방치된 데드코드**입니다. 실행하면 `get_video_title` AttributeError로 깨집니다.

**권고:** `app.py`, `services/`, `storage/`, `patch_history.py`, `test_models.py`, `summary*.py` 등 Streamlit 레거시를 `.archive/`로 옮기거나 명시적 삭제. 루트에 두 시스템이 섞여 있어 신규 기여자가 어느 것이 진짜인지 헷갈립니다.

### C2. `requirements.txt` 불일치 (Dockerfile이 깨짐)
- 루트 `requirements.txt`는 141바이트짜리 Streamlit 의존성 7줄뿐입니다.
- 실제 백엔드는 `backend/requirements.txt`에 FastAPI/셀러리 등이 있음.
- **`Dockerfile.backend:24`는 `COPY backend/requirements.txt` 후 `backend/requirements.txt`를 읽으므로** 실제로는 동작하나, 루트 `requirements.txt`는 완전히 **쓸모없는 중복**입니다.
- 루트 파일에 `streamlit`이 포함되어 있어 CI/배포 스크립트가 루트 것만 보면 잘못된 의존성을 설치할 위험이 있습니다.

**권고:** 루트 `requirements.txt` 삭제 → `backend/requirements.txt`를 단일 진실의 소스로 승격.

### C3. 마이그레이션 로직이 `job_manager.py` 모듈 임포트 시점에 실행
- `job_manager.py:12` `Base.metadata.create_all(bind=engine)`와 `:15-31`의 `ALTER TABLE` 자동 마이그레이션이 **모듈 import 시점**에 실행됩니다.
- 이는 부작용이 큰 안티패턴: import만 해도 DB가 변경되고, SQLite/PostgreSQL 분기 문자열 비교(`"sqlite" in str(engine.url)`)가 취약하며, 예외를 무차별 `except Exception: pass`로 삼킵니다.

**권고:** Alembic 도입. 최소한 `import`가 아닌 앱 스타트업/마이그레이션 스크립트로 분리.

### C4. `let` / `finally` 로직 버그 — `process_audio` 반환값 불일치
`llm.py:194-294`의 `process_audio`:
- 캐시 히트 시 215줄에서 `return cached_text`
- 289줄 `return transcript` 아래 **291-294줄에 도달 불가능한 코드**(`with open(...)` 후 `return transcript`)가 있음. 정상 흐름에서는 이미 289줄에서 리턴하므로 291-294는 데드코드입니다.
- 하지만 더 심각한 것은 캐시 저장을 `if transcript:` 블록(282-287)과 그 뒤 291-294 두 곳에서 중복 시도하는 흐름입니다.

**권고:** 290줄 이후 데드코드 제거. 캐시 저장 로직 단일화.

### C5. `generate_outline` 캐시 오염 — 논리적 결함
`llm.py:430-432`: 함수가 예외 없이 정상 종료되면 항상 `sections`를 캐시에 기록하지만, 만약 `sections == ["전체 내용 요약"]`(427-428줄 fallback)인 경우에도 캐시가 기록됩니다. 즉 **LLM 실패로 생성한 빈 fallback 목차가 영구 캐시되어** 이후 요청들이 잘못된 목차를 재사용합니다.

**권고:** fallback 섹션은 캐시하지 않거나 별도 마킹.

## 🟠 HIGH (유지보수성·확장성을 해치는 구조 문제)

### H1. `task_serializer: json`과 Celery 태스크 시그니처 불일치
`celery_app.py:22` `"task_serializer": "json"`인데, `guide.py:69`는 `celery_generate_guide_task.delay(job_id, request_data, file_paths)`로 3개 인자를 전달하고 `tasks.py:213`은 `@celery_app.task(bind=True)` 데코레이터로 `self`를 받습니다. JSON 직렬화 + `bind=True` 조합은 `self`와 인자가 섞여 미묘한 버그를 유발할 수 있습니다. 뿐만 아니라:

### H2. 비동기 태스크 실행 방식이 두 갈래로 혼재
- `guide.py:69`: Celery로 태스크 dispatch (`.delay()`)
- `admin.py:309`: `asyncio.create_task(run_batch_pregeneration_pipeline(batch_id))` — Celery 태스크(`celery_batch_pregenerate_task`)가 **정의되어 있음에도 사용하지 않고** FastAPI 이벤트 루프에 직접 태스크를 매달음.

**문제:** `async_generate_guide`(guide 경로)는 Celery 워커에서, 배치 파이프라인(admin 경로)은 API 서버 프로세스 이벤트 루프에서 실행됩니다. 서버 재시작 시 배치 작업이 유실되고, 메모리/CPU가 API 프로세스에 몰립니다.

**권고:** 배치도 `celery_batch_pregenerate_task.delay(batch_id)`로 통일.

### H3. LLM 하드코딩된 모델명/버전이 난무
- `gemini-3.6-flash`, `gemini-3.5-flash`, `gemini-3.5-flash-lite` 등이 `FALLBACK_GEMINI_MODELS`(llm.py:28-34), `SELECTED_GEMINI_VERSION` 기본값, docker-compose `SELECTED_GEMINI_VERSION=gemini-3.6-flash` 등에 **복수 개소 하드코딩**.
- 프론트 `page.tsx:405`는 기본 provider를 `"google/gemini-3.6-flash"`로 두는데, 백엔드 `is_gemini_provider`(llm.py:126)는 `"gemini" in p or "google" in p` 매칭이라 아슬아슬하게 맞아떨어짐. provider 문자열 규약이 코드 곳곳에서 암묵적으로 다름(`"Google Gemini"` vs `"google/gemini-3.6-flash"` vs `"OpenAI (GPT-4o)"` vs `"gpt-4o"`).

**권고:** 모델/프로바이더 상수를 단일 config 모듈로 중앙화. provider 문자열은 enum/normalize 함수로 정규화.

### H4. 대규모 함수 & 프롬프트 인라인
- `llm.py`가 **921줄 단일 파일**이며, 프롬프트 템플릿이 함수 안에 통짜 인라인(f-string)으로 박혀 있음(line 341, 458, 500, 667, 750, 801, 852 등).
- 프롬프트 수정 시 코드와 섞여 diff 추적이 어렵고 재사용 불가. `async_generate_chapter_content` 하나가 227줄.

**권고:** 프롬프트를 `prompts/` 디렉토리나 상수로 분리. 핵심 기능 단위로 파일 분할.

### H5. 광범위한 `except:` / `except Exception: pass`
- `job_manager.py` 곳곳 `except:` (빈 except, 14+회)가 JSON 파싱 실패를 모두 삼킴.
- `video.py`, `source.py`도 `except Exception:` 후 무시 패턴 다수.
- **조용한 데이터 유실**: 잘못된 JSON이 저장되면 조용히 `None`/`{}`/`[]`로 대체되어 원인 추적 불가.

**권고:** 최소 `except Exception as e:` + 로깅. bare `except:`는 전면 금지.

### H6. `debug.py`, `debug_mermaid.py`, `fix_mermaid.py`에 하드코딩된 job_id와 DB 경로
- `backend/data/debug.py`와 `debug_mermaid.py`가 특정 `job_5305ef89...` ID를 하드코딩, `fix_mermaid.py:5`는 `backend/data/jobs.db` 경로 하드코딩.
- 일회성 디버그 스크립트가 `backend/data/`에 섞여 있음.

**권고:** `scripts/`로 이동하거나 삭제. 하드코딩 제거.

### H7. 타이밍/레이트리밋 폴링은 `time.sleep` + 무한루프
- `video.py` Innertube, `llm.py` Gemini file upload, `source.py` PDF 업로드 등에서 `while ... PROCESSING: time.sleep(3)` **무한 폴링** — 상한이 없어 파일이 영구 PROCESSING 상태에 머물면 무한 대기.

**권고:** 최대 폴링 횟수/타임아웃 상한 추가.

- Unsplash 기본 이미지 URL `...c639042777db?q=80&w=800...`이 `image.py`, `guide.py`(3회), `page.tsx`, `guide/page.tsx`에 반복. 상수화 필요.

### M3. `evaluator.py`와 `rag.py`는 사실상 미사용 (죽은 코드)
- `evaluator.py`의 `evaluate_learning_profile`은 `guide.py:184 process_latest_note_evaluation`에서 "Evaluation feature disabled (Option B Rollback)" 주석으로 비활성화.
- `rag.py`(ChromaDB)는 어디에서도 import되지 않음. `requirements.txt`에도 `chromadb`가 없음. **import 시 `chromadb` 미설치로 즉시 터지는 orphan 모듈**.

### M4. `.env` 키 누락 — `NEMOTRON_`만 있고 실제 값은 미완
- `.env`에 `NEMOTRON_`(접두사만)로 잘린 키가 존재. `llm.py:141`은 `NEMOTRON_3_ULTRA_API_KEY`를 읽지만 실제 키가 온전한지 확인 필요.

### M5. 테스트 파일 미완성
- `backend/test_auth.py`(77줄), `test_redis.py`, `test_cache.py`는 존재하나 `backend/main.py` 테스트 러너도, pytest 설정도 없음. 프론트 `src/tests/*` 8개 파일이 있으나 `package.json`에는 `test:admin` 스크립트만 있고 전체 실행 스크립트(`test`)가 없음.

### M6. `created_at`/`updated_at`이 `String` + `datetime.now().isoformat()`
- `models.py` 전 모델에서 날짜를 **문자열**로 저장. SQLAlchemy `DateTime`이 아니라 `String`. 정렬/범위 쿼리/표준화가 어렵고, DB 내에서 시간 비교 불가. UTC 통일도 없음.
