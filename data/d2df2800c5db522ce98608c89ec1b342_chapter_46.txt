# 📚 챕터 3: 도메인 전문성을 위한 도구/스킬/서브 에이전트 설계 원칙
## — '뇌(판단)'와 '손(실행)'을 분리하여 안전하고 빠른 전문가 에이전트 만들기

안녕하세요! 지난 시간에는 에이전트가 **'생각(루프)'**과 **'도구(툴)'**를 어떻게 조화시키는지 배웠습니다. 오늘은 한 걸음 더 나아가, **"실제 현업(도메인)에서 믿을 수 있는 전문가 에이전트를 만들려면 어떻게 설계해야 할까?"**라는 질문에 답해보려 합니다.

오늘 강의에서 강사님은 **'인시던트 대응(Incident Response)'**이라는 아주 고통스러운 개발자의 현실적인 문제를 예로 드셨죠. 새벽 3시에 서버가 터져서 잠결에 로그를 뒤지던 경험, 상상만 해도 아찔합니다. 이 문제를 해결하기 위해 **'클로드 매니지드 에이전트(Claude Managed Agents)'**라는 플랫폼 위에서 에이전트를 직접 만들어보는 실습을 진행하셨는데요, 그 과정에서 **에이전트 설계의 핵심 원칙 3가지(에이전트/환경/세션 구조, 서버 사이드 루프, 뇌와 손의 분리)**가 자연스럽게 드러납니다.

어려운 인프라 용어 대신, 우리 주변의 **'레스토랑 주방'**에 비유해서 아주 천천히, 자세히 뜯어보겠습니다. 자, 앞치마 두르고 주방으로 들어가 볼까요? 🍳

---

### 1. 실습 준비: '나만의 주방' 차리기 (환경 설정)

강사님은 본격적인 설계 이야기를 하기 전에, 실습용 코드를 내려받고 실행하는 과정을 보여주셨습니다.

> **"저장소 클론 → 가상환경 진입 → 의존성 설치 → API 키 입력 → 앱 실행 (`streamlit run app.py`)"**

이 과정은 **요리사가 자기 칼을 갈고, 도마를 씻고, 재료(API 키)를 냉장고에 채워 넣는 '주방 오픈 준비'**와 똑같습니다. 
*   **GitHub 저장소**: 검증된 레시피북(코드 베이스)
*   **가상환경(`venv`, `conda`)**: 나만의 독립된 조리대 (다른 요리랑 재료 섞이지 않게 격리)
*   **API 키 (`ANTHROPIC_API_KEY`)**: 최고급 식재료 구매권 (이게 없으면 요리 불가)
*   **`streamlit run app.py`**: "자, 장사 시작해!" 하고 문 여는 스위치

> **💡 개념 돋보기: 왜 '가상환경'을 쓸까요?**
> > 내 컴퓨터(글로벌 환경)에는 이미 다른 프로젝트용 파이썬 라이브러리가 깔려 있을 수 있습니다. 프로젝트마다 필요한 라이브러리 버전이 다를 수 있죠(예: 프로젝트 A는 Django 3.0, 프로젝트 B는 Django 4.0). 가상환경은 **"이 프로젝트 전용의 깨끗한 조리대"**를 만들어주는 격리 공간입니다. 여기선 `requirements.txt`라는 '필수 재료 목록'만 딱 설치해서 쓰니 충돌 걱정 끝!

### 2. 시나리오: 새벽 3시, 주방에 불이 났다! (인시던트 대응)

강사님이 **"소프트웨어 엔지니어라면 새벽 2~3시, 휴가 중에도 온콜(On-call) 전화를 받고 뛰어가야 하는 고통을 알 것"**이라고 하셨죠.

*   **상황**: 서버(주방 가스불)가 꺼지거나 이상 신호(메트릭/로그/배포 기록)가 감지됨.
*   **사람의 고통**: 잠결에 눈을 비비며 로그(주문서), 메트릭(온도계), 배포 내역(레시피 변경 이력)을 뒤져 원인 찾기 → 조치 → 보고서 작성.
*   **에이전트의 역할**: 이 **'고통스러운 심부름꾼'** 역할을 에이전트가 대신해 주는 것. 
    *   "클로드야, 너가 대신 로그 보고 원인 찾아서 고치고, 나한테 요약만 해줘. 나 자게."
    *   더 나아가: 에이전트가 다 해결해서 **인간이 아예 안 깨게 하는 것**이 궁극적 목표.

### 3. 핵심 설계도: 에이전트 3대 요소 (뇌, 손, 근무표)

실습 코드(`agent.py`)를 열어보니, 에이전트를 구성하는 세 가지 핵심 클래스가 나옵니다. 강사님은 이를 **뇌(Brain), 손(Hands), 연결 고리(Session)**로 비유하셨습니다.

#### ① `Agent` (에이전트) = **'헤드 셰프 (Head Chef)'** — **뇌, 판단, 페르소나**
*   **정의**: "너는 누구야? 뭐 할 줄 알아? 어떤 스타일로 일해?"를 정의하는 설계도.
*   **구성 요소**:
    *   **모델(Model)**: 셰프의 **두뇌 용량/경력** (Claude Sonnet, Opus 등).
    *   **MCP 서버 / 스킬(Skills)**: 셰프가 가진 **전문 자격증/비법 노트** ("나 쿠버네티스 잘 다뤄", "나 SQL 쿼리 짱 잘 써").
    *   **페르소나(시스템 프롬프트)**: 셰프의 **성격/원칙** ("안전 제일이야", "빠르게 고치는 것보다 원인 분석이 우선이야").
*   **역할**: 상황을 보고 **생각(Reasoning)해서 계획(Plan) 짜기**. "음, 로그 보니 메모리 누수네. 그럼 재시작하고 덤프 떠서 분석하자."

> **💡 개념 돋보기: '스킬(Skill)'과 'MCP 서버'는 셰프의 '전문 도구 가방'입니다.**
> > 에이전트에게 "너 이거 할 줄 알지?"라고 가르치는 대신, **검증된 기능 덩어리(스킬)**를 플러그인처럼 꽂아주는 것입니다. "쿠버네티스 클러스터 재시작 스킬", "데드락 분석 스킬" 처럼요. MCP(Model Context Protocol) 서버는 이 스킬들이 돌아가는 **표준화된 외부 작업실**이라고 보시면 됩니다. 셰프가 주방 안에 모든 도구를 다 둘 수 없으니, 전문 도구는 옆 건물 '도구 창고(MCP 서버)'에 두고 필요할 때 꺼내 쓰는 거죠.

#### ② `Environment` (환경) = **'격리된 전문 주방 (Sandbox Kitchen)'** — **손, 실행, 상태**
*   **정의**: 에이전트가 **실제로 칼질하고 불 쓰는 물리적 공간**.
*   **특징**: 
    *   파일 시스템 있음 (재료 보관 창고)
    *   터미널/쉘 있음 (조리 도구)
    *   네트워크 있음 (외부 식자재 마트랑 연결)
    *   **중요!**: **샌드박스(Sandbox) = 격리된 공간**. 여기서 불내도 내 진짜 집(로컬 PC/프로덕션 DB)엔 불 안 번짐.
*   **역할**: 헤드 셰프(에이전트)가 "이거 해!"라고 지시하면(Tool Call), 실제로 명령어 치고 파일 수정하고 API 호출해서 **결과(Observation) 돌려주기**.

> **💡 개념 돋보기: 왜 '환경'을 별도로 둘까요? (핵심 설계 원칙 1)**
> > 초창기 에이전트 프레임워크(예: 초기 Claude Code 등)는 **'뇌(루프)'와 '손(도구 실행)'이 한 몸(같은 컨테이너/프로세스)**이었습니다. 셰프가 주방 안에서 직접 칼도 들고 불도 때고 생각도 하는 거죠. 이게 편해 보이지만, **큰 문제가 있습니다.** (뒤에서 자세히 다룹니다)

#### ③ `Session` (세션) = **'근무 교대표 / 작업 지시서 (Shift Ticket)'** — **연결, 지속성, 스트리밍**
*   **정의**: **"이 셰프(에이전트 인스턴스)가 저 주방(환경)에서 지금부터 일 시작해!"**라고 이어주는 **런타임 컨텍스트**.
*   **역할**:
    *   에이전트 인스턴스 + 환경 인스턴스 = **1:1 매칭** (한 셰프가 두 주방 동시에 못 봄)
    *   사용자(나) ↔ 에이전트 사이의 **이벤트 스트리밍 파이프** (생각 과정, 도구 호출 결과, 최종 답변이 실시간으로 흘러옴)
    *   상태 유지: "아까 그 인시던트 어떻게 됐지?"라고 물으면 세션이 맥락 기억해줌.

### 4. '매니지드 에이전트'의 마법: 주방 관리는 매니저가! (서버 사이드 루프)

강사님이 **"클로드 매니지드 에이전트의 핵심: 에이전트 루프가 서버 사이드에서 돈다"**고 강조하셨습니다.

*   **기존 방식 (로컬/클라이언트 사이드 루프)**: 
    *   내 노트북에서 `while True:` 루프 돌리며 에이전트 실행.
    *   **문제**: 노트북 덮으면 에이전트 죽음 💀, 배터리 나가면 죽음 🔋, 네트워크 끊기면 죽음 📡, 내 컴퓨터 자원(CPU/RAM) 다 잡아먹음 💻.
    *   프로토타입 → 프로덕션 갈 때 **'내구성(Durability)', '신뢰성(Reliability)', '확장성(Scaling)'** 내 손으로 다 구현해야 함. 지옥문 열림 🔥.

*   **매니지드 에이전트 방식 (서버 사이드 루프)**:
    *   **내 노트북은 그냥 '리모컨(UI/CLI)' 역할만 함**.
    *   **진짜 뇌(추론 루프)는 클라우드 서버(Anthropic 인프라)에서 24/365 돌고 있음**.
    *   내가 노트북 덮어도, 와이파이 끊겨도, 휴대폰으로 접속해도 **세션은 그대로 살아있음**. 작업 내역, 상태, 컨텍스트 **완벽 보존**.
    *   **비유**: 나는 **'식당 사장'**이고, 클로드 매니지드 에이전트는 **'믿음직한 총주방장 + 시설 관리팀'**.
        *   나는 "오늘 메뉴 이거야"라고 지시만 하면(프롬프트/태스크),
        *   주방장(서버 사이드 루프)이 알아서 재료 주문하고(툴 호출), 요리하고(실행), 그릇 담고(결과 반환), 홀 서빙까지(스트리밍) 다 함.
        *   나는 집 가서 자도 됨. 내일 와도 요리 진행 중인 거 그대로 이어서 볼 수 있음.

> **💡 개념 돋보기: '프로토타입에서 프로덕션으로'의 골짜기(Death Valley) 건너기**
> > 많은 개발자가 로컬에서 "우와, 에이전트 되네!" 하고 좋아하다가, 실제 서비스 올리려고 보니 **상태 저장, 재시작 복구, 동시 접속 처리, 보안 격리, 로깅/모니터링** 등 인프라 지옥에 빠집니다. 매니지드 에이전트는 이 **'인프라 지옥'을 플랫폼이 다 떠안아주는 서비스**입니다. 개발자는 **'도메인 로직(무엇을 할 것인가)'**만 짜면 됩니다.

### 5. 오늘의 하이라이트: **'뇌(루프)'와 '손(도구 실행)'의 분리 (Decoupling)** ⭐⭐⭐

이 챕터의 **가장 중요한 설계 원칙**입니다. 강사님이 "이 설계 결정이 안전성, 신뢰성, 지연 시간 모든 걸 바꿨다"고 하신 바로 그 부분입니다.

#### 🚫 과거 방식: 뇌와 손이 한 몸 (Coupled Agent Loop + Tool Execution)
*   **구조**: 에이전트 루프(생각) 돌리는 컨테이너 안에 **파일 시스템 접근 도구, 쉘, DB 클라이언트, 크리덴셜(비밀키) 등 모든 권한이 다 들어있음**.
*   **비유**: **'셰프가 주방 안에서 생각도 하고, 칼질도 하고, 금고(비번/키)도 직접 열고, 가스밸브도 직접 만지는 구조'**.
*   **문제점 1: 보안/자격 증명 유출 (Credential/Security Nightmare)**
    *   셰프(에이전트)가 해킹당하거나 환각(Hallucination)으로 이상한 명령 내리면? → **금고 털리고, 가스 폭발하고, 프로덕션 DB 날림**. 권한이 너무 큼.
    *   격리하려면 매번 무거운 컨테이너(가상머신) 띄워야 함 → 느리고 비쌈.
*   **문제점 2: 지연 시간 (Latency / Time To First Token - TTFT)**
    *   새 요청(세션) 올 때마다 **"새 주방(컨테이너) 짓고 → 가스 연결하고 → 도구 셋팅하고 → 셰프 불러들이고"** 해야 함.
    *   이 **'주방 준비 시간(Cold Start)'** 때문에 사용자는 첫 대답 받기까지 오래 기다림 (P95 기준 90% 이상 지연 발생).

#### ✅ 현재 방식 (클로드 매니지드 에이전트): 뇌와 손의 완전 분리 (Decoupled Brain vs. Hands)

| 구성 요소 | 역할 | 비유 | 위치 |
| :--- | :--- | :--- | :--- |
| **Agent Loop (Brain)** | 추론, 계획, 도구 선택, 상태 관리 | **'본사 전략실 / 헤드셰프 사무실'** | **서버 사이드 (클라우드, 고성능, 상시 대기)** |
| **Environment (Hands)** | 실제 코드 실행, 파일 조작, API 호출, DB 쿼리 | **'격리된 지점 주방 / 샌드박스 컨테이너'** | **별도 격리 환경 (필요할 때만 띄움, 권한 최소화)** |

*   **작동 원리**:
    1.  **전략실(루프)**: "이 인시던트 해결하려면 `kubectl logs` 좀 봐야겠다." → **도구 호출 요청(MCP 프로토콜) 보냄**.
    2.  **네트워크**: 안전하게 암호화된 채널로 요청 전달.
    3.  **지점 주방(환경)**: 요청 받음 → **권한 최소화된 샌드박스 안에서만** `kubectl logs` 실행 → 결과 텍스트만 전략실로 보냄.
    4.  **전략실(루프)**: 결과 받아 보고 → "아하, OOM Killer네. 그럼 재시작 스킬 써야지." → 다음 지시 내림.

#### 🎉 분리가 가져다준 4가지 선물 (Benefits)

> **💡 개념 돋보기: 뇌-손 분리(Decoupling)가 만든 기적들**
> > 1.  **🛡️ 안전성 (Safety & Security)**: 전략실(뇌)엔 **비밀키(크리덴셜)가 아예 없음**. 해커가 뇌를 털어도 금고 열쇠 못 구함. 주방(손)은 권한 최소화(Least Privilege)된 샌드박스라, 터져도 그 주방만 터짐. **자격 증명 관리, 암호화, 샌드박싱이 구조적으로 해결됨.**
> > 2.  **⚡ 속도 (Latency / TTFT 90% 감소!)**: 뇌(루프 서버)는 **항상 켜져 있음 (Warm)**. 새 요청 와도 '주방 짓기' 안 함. 그냥 **이미 떠 있는 가벼운 주방(환경) 하나 붙여서(Attach) 바로 일 시키면 끝**. P95 지연 시간 90% 이상 단축됨. 사용자는 "띠용, 바로 답 오네?" 함.
> > 3.  **🛠️ 신뢰성/내구성 (Reliability/Durability)**: 뇌는 클라우드 인프라가 책임지고 99.99% 가용성 보장. 주방(환경) 하나 고장 나면? **뇌는 그대로 두고 주방만 갈아 끼우면 됨**. 세션 상태(대화 맥락)는 뇌가 가지고 있으니 작업 이어서 가능.
> > 4.  **🧩 유연성/확장성 (Flexibility)**: 파이썬 주방, 자바 주방, 쿠버네티스 전용 주방, 읽기 전용 주방... **용도별로 다양한 '손(환경)'을 골라 붙일 수 있음**. 뇌는 그대로 두고 손만 교체/추가 가능. **도메인별 특화 환경(Sub-agent/Environment) 설계의 기반이 됨.**

### 6. 실습 코드 뜯어보기: 완성된 셰프 모셔오기 (`agent.py` vs `agent_complete.py`)

강사님은 빈 껍데기(`agent.py`)에 완성본(`agent_complete.py`)에서 조각조각 복사해 붙이며 에이전트를 완성해 나가는 방식을 쓰셨습니다. 이건 **'레시피북 보고 하나씩 따라 하며 요리 배우는 과정'**과 같습니다.

**복사해 붙일 핵심 컴포넌트들 (레시피 순서):**
1.  **`Agent` 클래스 정의**: "너는 인시던트 대응 전문가야. 모델은 손넷 써. 스킬은 쿠버네티스, 로그 분석, 메트릭 조회 장착해." (페르소나/능력 부여)
2.  **`Environment` 클래스 정의**: "작업할 주방은 파이썬 샌드박스야. 네트워크 허용하고, `kubectl` 깔아두고, 읽기 전용 모드 옵션 넣어." (실행 환경 세팅)
3.  **`Session` 생성 로직**: "자, 이 셰프 저 주방에 투입. 세션 ID 발급하고, 사용자한테 스트리밍 연결해줘." (런타임 연결)
4.  **메인 루프/핸들러**: 사용자 입력 받 → 세션에 태스크 던짐 → 이벤트 스트리밍으로 중간 과정/결과 보여줌.

> **💡 튜터의 팁: "한 번에 다 이해하려 하지 마세요."**
> > 강사님 말씀대로 `agent_complete.py`에서 **한 조각씩 복사해서 `agent.py`에 붙여 넣고, 저장하고, 실행해보며 "어? 여기서 이러네?"** 하고 확인하는 게 최고입니다. 전체 그림은 복잡해 보여도, **하나하나 나누면 그냥 '설정값 채우기'랑 '함수 호출하기'뿐입니다.**

### 7. 마무리 요약: 도메인 전문가 에이전트 설계 체크리스트 ✅

오늘 배운 원칙을 바탕으로, **내 도메인(금융, 의료, 쇼핑몰, 게임 서버 등)에 맞는 전문가 에이전트**를 만들 때 체크해볼 목록입니다.

| 설계 단계 | 핵심 질문 | 오늘 배운 원칙 적용 |
| :--- | :--- | :--- |
| **1. 페르소나/두뇌 (Agent)** | 우리 도메인 전문가처럼 생각하게 하려면?<br>어떤 모델? 어떤 스킬(MCP) 세트? | **Agent = 페르소나 + 모델 + 스킬 세트**<br>도메인 지식은 '스킬'로 모듈화해 꽂기 |
| **2. 손/실행 환경 (Environment)** | 어디까지 만지게 할까? 어디는 위험한가?<br>파일 시스템? DB 쓰기? 외부 API? | **Environment = 격리된 샌드박스 + 최소 권한**<br>**뇌(루프)엔 비밀키/중요 권한 절대 주지 말기** |
| **3. 연결/지속성 (Session)** | 사용자와 어떻게 대화 이어갈까?<br>중간에 끊겨도 복구되게 하려면? | **Managed Agent(서버 사이드 루프) 활용**<br>인프라 걱정 말고 도메인 로직에만 집중 |
| **4. 성능/보안 아키텍처** | 첫 응답 느리지 않게 하려면?<br>보안 사고 터지면 어떻게 격리할까? | **뇌-손 분리(Decoupling) 필수**<br>Warm 루프 서버 + 일회용/경량 환경 컨테이너 조합 |

### 🎓 튜터의 한 마디

> **"에이전트를 만든다"는 건 단순히 "프롬프트 잘 짜기"가 아닙니다.**  
> 오늘 강의에서 본 것처럼, **'누가(에이전트) 어디서(환경) 어떻게(세션) 일하게 할 것인가'라는 아키텍처 설계**가 진짜 실력입니다. 특히 **'뇌(판단 로직/자격증명)와 손(실행 환경/권한)을 물리적으로 분리하는 것'**은 이제 선택이 아니라 **프로덕션 레벨 에이전트의 필수 생존 전략**이 되었습니다.

> 실습하실 때 `agent.py` 채워 나가면서, **"아, 여기가 셰프 고용하는 곳이구나", "여기가 주방 짓는 곳이구나", "여기가 주방에 주문 넣는 곳이구나"** 하고 상상해보세요. 코드 한 줄 한 줄이 다 의미를 가질 겁니다.
