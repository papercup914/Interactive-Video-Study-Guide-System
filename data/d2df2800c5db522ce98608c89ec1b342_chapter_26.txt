# 챕터 3. 기존 패턴: 에이전트 루프와 도구 실행의 긴밀한 결합 (Claude Code 등에서 유효)

---

안녕하세요, 여러분! 지난 시간에는 '에이전트(두뇌)', '환경(손)', '세션(작업대)'이라는 세 가지 핵심 구성 요소가 어떻게 조립되어 하나의 완성된 AI 비서를 만드는지 큰 그림을 그려보았습니다. 오늘은 본격적으로 **"왜 클로드 매니지드 에이전트(Claude Managed Agents)는 이 세 가지를 굳이 분리했는가?"**라는 아주 중요한 설계의 비밀, 즉 **'아키텍처의 진화'**에 대해 파헤쳐 보려고 합니다.

이해를 돕기 위해 우리가 매일 겪는 **'식당 주방'** 이야기로 출발해 볼까요?

---

## 1. 옛날 방식: '슈퍼 셰프'가 모든 것을 하는 주방 (긴밀한 결합)

상상해 보세요. 아주 유명한 1인 식당이 있습니다. 여기에는 **'슈퍼 셰프' 단 한 명**이 있습니다. 이 셰프는 요리 레시피를 짜는 **'두뇌'** 역할도 하고, 직접 칼질을 하고 팬을 돌리는 **'손(도구 실행)'** 역할도 동시에 합니다.

### 🍳 이 주방의 하루 일과 (에이전트 루프 + 도구 실행 결합)

1.  **손님 주문 접수 (사용자 요청):** "김치찌개 1인분요!"
2.  **생각하기 (에이전트 루프 - LLM 추론):** "음, 김치찌개엔 묵은지가 필요하고, 돼지고기 넣고, 두부도 썰어야지. 국물 맛을 내려면 육수도 우려야 해."
3.  **행동하기 (도구 실행 - Tool Use):**
    *   냉장고에서 김치 꺼내기 (`get_kimchi` 도구 호출)
    *   도마에서 돼지고기 썰기 (`chop_pork` 도구 호출)
    *   가스불 켜고 냄비 올리기 (`turn_on_stove` 도구 호출)
    *   국물 맛보기 (`taste_soup` 도구 호출)
4.  **다시 생각하기 (에이전트 루프):** "아, 간이 좀 싱겁네. 소금 더 넣자."
5.  **다시 행동하기 (도구 실행):** 소금 뿌리기 (`add_salt` 도구 호출)
6.  **완료 및 서빙:** "손님, 김치찌개 나왔습니다!"

이 방식에서 **'생각하는 머리(에이전트 루프)'**와 **'움직이는 손(도구 실행/컨테이너)'**은 **한 몸(같은 프로세스, 같은 컨테이너)**에 붙어 있습니다. 셰프가 생각을 멈출 수 없는 것처럼, **요리하는 동안에는 이 주방(컨테이너)이 계속 켜져 있어야 하고, 셰프가 점유하고 있어야 합니다.**

이것이 바로 **기존 패턴, 즉 '에이전트 루프와 도구 실행의 긴밀한 결합(Tight Coupling)'**입니다. **Claude Code(클로드 코드)**가 바로 이 방식을 따릅니다.

> **💡 개념 돋보기: '긴밀한 결합(Tight Coupling)'이란?**
> > 두 개의 구성 요소가 서로 강하게 의존하여, 한쪽이 변하면 다른 쪽도 즉시 영향을 받고, **물리적으로나 논리적으로 분리하기 어려운 상태**를 말합니다. 우리 식당 비유에서는 **"셰프(두뇌)와 주방 설비(손/도구)가 한 공간에 묶여 있어, 셰프가 일하는 동안 주방 전체를 독점한다"**는 뜻입니다.

---

## 2. 왜 Claude Code는 이 방식을 고집할까? (장점: 강력한 권한 위임)

"그럼 왜 불편한데 이 방식을 쓰나요?"라고 물으실 수 있습니다. 분명한 이유가 있습니다. **'신뢰'와 '편의성'** 때문입니다.

### 🛠️ 내 노트북 위에서의 '완벽한 자율성'

여러분이 `Claude Code`를 로컬 컴퓨터에서 켜서 코딩을 시킨다고 상상해 보세요.
*   **"이 파일 좀 읽어줘"** → 클로드가 내 하드디스크의 `src/main.py`를 직접 읽음 (`read_file` 도구)
*   **"여기에 버그 고쳐줘"** → 클로드가 직접 내 파일을 수정하고 저장함 (`edit_file` 도구)
*   **"테스트 돌려봐"** → 클로드가 내 터미널에서 `pytest` 명령어를 직접 실행함 (`run_command` 도구)

이때 클로드(에이전트 루프)는 **내 컴퓨터의 파일 시스템, 터미널, 네트워크 등 모든 '손(도구)'에 직접, 즉각적으로 접근**해야 합니다. 생각(코드 분석) → 행동(파일 수정) → 결과 확인(테스트 실행) → 다시 생각... 이 루프가 **초 단위, 밀리초 단위로 수없이 빠르게 돌면서** 내 로컬 환경 곳곳을 휘젓고 다녀야 하죠.

이럴 때는 **'두뇌'와 '손'이 한 몸처럼 붙어 있는 게(결합) 훨씬 효율적**입니다. 중간에 "잠깐, 손아, 너 내 파일에 접근하려면 권한 확인 좀 하고 와" 같은 통신 과정이 끼어들면 개발 흐름이 뚝뚝 끊겨 버리니까요. **내 안전한 내 컴퓨터 안에서, 내가 허락한 슈퍼 셰프에게 주방 열쇠를 통째로 맡기는 것**과 같습니다. 그래서 **Claude Code 같은 '로컬 개발 도구'에서는 이 '긴밀한 결합'이 여전히 최고의 선택**입니다.

> **💡 개념 돋보기: 왜 Claude Code는 결합되어 있는가? (로컬 환경의 특권)**
> > *   **지연 시간 제로(Zero Latency):** 네트워크 통신 없이 메모리 안에서 바로 도구 호출 가능.
> > *   **완전한 상태 공유:** 현재 열려 있는 파일, 터미널 히스토리, 환경 변수 등 '컨텍스트'를 공유하기 쉬움.
> > *   **강력한 권한:** 사용자 로컬 머신의 루트 권한에 준하는 접근 제어 가능 (사용자가 `chmod 777` 준 것과 유사).
> > *   **대상:** **신뢰된 사용자의 개인 워크스테이션(로컬)**. 여기는 내 집 주방이라 내가 다 책임지면 됨.

---

## 3. 하지만 '프로덕션(운영 환경)'에서는 치명적입니다 (단점: 보안, 확장성, 지연)

자, 이제 상황을 바꿔 봅시다. 이 '슈퍼 셰프' 시스템을 **우리 회사의 핵심 서버실(프로덕션 환경)**에 갖다 놓는다고 상상해 보세요. 여기서 문제가 터지기 시작합니다.

### ⚠️ 문제 1: "주방 열쇠를 아무나 줬다간 큰일 난다" (보안 & 자격 증명 탈취)

로컬에서는 내 컴퓨터니까 괜찮지만, 회사 서버에는 **데이터베이스 비밀번호(AWS Key, DB Password), 고객 개인정보, 결제 연동 키** 같은 **'마스터 키(자격 증명/Credentials)'**가 곳곳에 있습니다.

*   **결합된 구조에서는:** 에이전트(셰프)가 도구(손)를 쓰려면 **주방 전체(컨테이너/서버 환경)에 접근 권한이 있어야 합니다.**
*   **위험 시나리오:** 해커가 프롬프트 인젝션(Prompt Injection)으로 셰프를 홀려서 "`cat /etc/secrets/aws_credentials` (비밀번호 파일 읽어줘)"라고 시키면? **셰프가 순순히 읽어줍니다.** 왜냐면 셰프와 주방이 한 몸이라, 주방 구석구석(환경 변수, 시크릿 파일)에 접근하는 게 '도구 실행'의 일환이니까요.
*   **샌드박스(Sandbox, 격리) 불가능:** "너는 요리만 해, 냉장고 뒤 비밀 금고는 건드리지 마"라는 **물리적 분리가 안 됩니다.** 셰프가 냉장고(파일 시스템) 문을 여는 행위 자체를 막을 수 없으니까요.

> **💡 개념 돋보기: '자격 증명(Credentials) 유출'과 '샌드박싱(Sandboxing)'의 딜레마**
> > *   **자격 증명(Credentials):** API 키, DB 비번, SSH 키 등 '접근 권한'을 증명하는 비밀 문자열.
> > *   **샌드박싱(Sandboxing):** "이 놀이터(모래상자) 안에서만 놀아. 밖에는 나가지 마."라고 **실행 환경을 격리**하는 보안 기술.
> > *   **결합된 구조의 비극:** 에이전트 루프(두뇌)가 도구 실행 환경(손/컨테이너) 안에 **함께 갇혀(결합되어) 있음** → 두뇌가 해킹당하면 손(도구)을 통해 **격리된 샌드박스 바깥의 비밀 금고까지 털어갈 수 있음**. "두뇌와 손을 분리해서, 두뇌는 비밀 금고 위치를 모르게 해야 한다"는 발상이 여기서 나옵니다.

### ⚠️ 문제 2: "손님 올 때마다 주방 짓고 셰프 고용하느라 문전성시인데 문 못 연다" (지연 시간 & 확장성)

이게 더 치명적입니다. **'첫 토큰 생성 시간(Time To First Token, TTFT)'** 문제입니다.

**시나리오:** 새벽 3시, 장애 알람이거나 혹은 블랙프라이데이 세일로 **동시에 1,000명의 사용자가 "장애 복구해줘!"**라고 요청을 보냈습니다.

**결합된 구조(기존 에이전트 하네스)에서는:**
1.  요청 1개당 **전용 컨테이너(주방) 1개**를 새로 띄워야 함 (Docker 컨테이너 기동, Python 환경 로딩, 의존성 설치, 에이전트 프로세스 시작...).
2.  이 **'주방 짓는 시간(Cold Start)'이 수초~수십 초** 걸림.
3.  1,000개 요청 → 1,000개 컨테이너 동시 기동 시도 → **서버 자원 고갈(Out of Memory), 네트워크 병목, 스케줄러 과부하**.
4.  사용자는 **"생각 중입니다..."**라는 화면만 30초 동안 쳐다봄 (TTFT 폭증).

영상에서는 이 문제를 **"에이전트 루프와 도구 실행이 같은 박스(컨테이너)에 있으니, 세션 하나당 컨테이너 하나를 띄워야 해서 지연이 발생한다"**고 정확히 짚어줍니다. 심지어 **"P95(상위 5% 느린 요청) 기준으로 TTFT가 90% 이상 감소했다"**는 놀라운 수치를 제시하는데, 이는 **"주방(컨테이너)을 미리 지어놓고(풀링/Pooling), 셰프(두뇌)만 파견 보내는 구조로 바꿨기 때문"**입니다.

> **💡 개념 돋보기: TTFT(Time To First Token) & P95 지표, 왜 중요할까?**
> > *   **TTFT (Time To First Token):** 사용자가 요청을 보낸 후, **첫 번째 응답 글자(토큰)가 화면에 찍히기까지 걸린 시간**. "로딩 중..." 스피너가 도는 시간입니다. 사용자 체감 속도의 핵심.
> > *   **P95 (Percentile 95):** "상위 5% 느린 경우"를 뜻함. 평균(Mean)은 빨라 보여도, **가장 답답한 순간(장애 대응 시 트래픽 몰릴 때)의 경험**을 보장하려면 P95, P99를 봐야 함.
> > *   **90% 감소의 의미:** 기존 10초 걸리던 첫 응답이 1초로 단축됨. 장애 대응 골든 타임(보통 5~15분) 안에서 에이전트가 개입하려면 **반응 속도는 생존의 문제**임.

### ⚠️ 문제 3: "셰프가 노트북 덮으면 요리 다 날아가" (내구성 & 상태 관리)

영상에서는 **"랩탑을 덮거나(Close laptop), 강제 새로고침(Hard refresh) 하면 모든 게 유지된다"**는 말을 하는데, 이는 역설적으로 **기존 결합 구조에서는 이게 안 됐음**을 의미합니다.

*   결합 구조: 에이전트 프로세스(두뇌)가 컨테이너(손) 안에서 돌고 있음 → 사용자 브라우저/터미널이 끊기면(웹소켓 끊김) → **프로세스가 죽거나 좀비 상태가 됨** → 중간 상태(생각 중이던 체인, 열려 있던 파일 핸들) **증발**.
*   운영 환경에서는 "에이전트가 3일 걸려 장문 리포트 쓰는 중인데 네트워크 잠깐 끊겼다고 처음부터 다시 써라" 하면 안 됨. **내구성(Durability), 신뢰성(Reliability)**이 필수.

---

## 4. 요약: '긴밀한 결합'의 명암 (Design Trade-off)

자, 이제 이 챕터의 핵심인 **'기존 패턴(긴밀한 결합)'의 정체**를 완벽히 이해하셨을 겁니다. 표로 정리하며 마무리하겠습니다.

| 구분 | **긴밀한 결합 (Tight Coupling)**<br>_예: Claude Code, 로컬 에이전트 프레임워크_ | **분리된 구조 (Decoupled)**<br>_예: Claude Managed Agents (현재 배우는 대상)_ |
| :--- | :--- | :--- |
| **구조** | **에이전트 루프(두뇌) + 도구 실행(손/컨테이너) = 단일 프로세스/컨테이너** | **에이전트 루프(서버 사이드) ↔ 환경(독립 컨테이너/샌드박스) = 네트워크로 연결** |
| **최적 용도** | **로컬 개발, 개인 생산성 도구, 신뢰된 단일 사용자 환경** | **멀티 테넌트 SaaS, 프로덕션 워크로드, 비신뢰 코드 실행, 고가용성 필요** |
| **장점** | • 초저지연 (로컬 함수 호출 수준)<br>• 강력한 권한 위임 (로컬 FS/Shell 완전 접근)<br>• 구현 단순함 (상태 공유 쉬움) | • **보안/샌드박싱 강력** (두뇌가 비밀 모름)<br>• **확장성/지연 최적화** (컨테이너 풀링, TTFT 90%↓)<br>• **내구성/신뢰성** (세션 지속, 랩탑 닫아도 유지) |
| **단점** | • 보안 취약 (프롬프트 인젝션 시 전체 시스템 장악)<br>• 확장성 한계 (세션당 컨테이너 기동 비용)<br>• 상태 휘발성 (클라이언트 종속) | • 네트워크 왕복 지연 존재 (RTT 비용)<br>• 상태 동기화 복잡도 증가 (Event Streaming 필요)<br>• 인프라 운영 복잡도 높음 (Managed 서비스가 해결해줌) |

## 5. 튜터의 한 마디: "도구는 용도에 맞게"

여러분, **"긴밀한 결합이 나쁘다"**는 말이 **절대 아닙니다**.
*   내 로컬에서 `Claude Code`로 리팩토링할 때는 **'결합된 슈퍼 셰프'**가 최고입니다. 빠르고, 내 파일 다 만지고, 내 터미널 다 쓰니까요.
*   하지만 **"고객 데이터가 오가는 운영 서버에서, 수천 명이 동시에 쓰는 장애 대응 에이전트를 돌릴 때"**는요? **'분리된 구조(두뇌 따로, 손 따로)'**가 정답입니다.

클로드 매니지드 에이전트가 왜 **"에이전트 루프는 서버 사이드에서 돌리고, 환경(손)은 따로 떼어냈는가?"** — 이 챕터의 모든 내용은 바로 이 **'프로덕션 레디(Production Ready)'라는 목표**를 향한 치열한 고민의 결과물입니다.

다음 챕터에서는 이 **'분리된 구조(Decoupled Architecture)'**가 실제로 코드 레벨에서 어떻게 구현되는지, `Agent` 클래스와 `Environment` 클래스, 그리고 `Session`이 어떻게 유기적으로 연결되는지 **실전 코드와 함께** 낱낱이 파헤쳐 보겠습니다. 여러분의 '주방'이 이제 **'안전하고, 빠르고, 24시간 꺼지지 않는 프로 주방'**으로 업그레이드되는 순간입니다. 기대해 주세요!
