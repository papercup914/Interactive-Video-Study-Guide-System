# 📝 챕터 2. 두 번째 검증 에이전트 구현: 블로그 포스트 검증 체커 (Blog Post Validation Checker)

안녕하세요! 지난 시간에는 **플래너(Planner)**가 설계를 하고, **체커(Checker)**가 이를 검토하며 **최대 3번까지 재시도**하는 '안전장치 루프'를 만드는 법을 배웠습니다. 설계도가 완벽해질 때까지 계속 고쳐 쓰는 과정이었죠?

이번 챕터에서는 그 **완벽해진 설계도(아웃라인)**를 바탕으로 **실제 글(블로그 포스트)**을 쓰는 **'블로그 라이터(Blog Writer)'**를 고용하고, 쓴 글이 **제대로 작성되었는지 다시 한번 검사하는 '블로그 포스트 검증 체커(Blog Post Validation Checker)'**를 추가하는 전 과정을 아주 자세히 들여다보겠습니다.

---

## 1. 글쓰기 전문가 고용하기: 블로그 라이터 (Blog Writer) 에이전트

자, 이제 **`blog_outline`**이라는 공유 창고에 **완벽하게 검증된 아웃라인(목차/설계도)**이 들어있습니다. 이제는 이 설계도를 보고 **실제 블로그 글을 써줄 작가**가 필요합니다.

### 🍳 비유: "설계도(아웃라인)를 받아 정찬 코스 요리(블로그 포스트)를 만드는 수석 셰프"

*   **아웃라인(설계도):** "에피타이저 -> 메인(스테이크, 사이드) -> 디저트" 순서와 각 요리의 핵심 포인트만 적힌 메모지.
*   **블로그 라이터(수석 셰프):** 이 메모지만 보고, 손님(독자)에게 내놓을 **완성된 플레이팅(마크다운 글)**을 만듭니다.
*   **공유 상태 `blog_post`:** 완성된 요리가 놓인 **서빙 테이블(임시 보관소)**.

### 🛠️ 블로그 라이터에게 주는 구체적인 주문서 (Instruction/프롬프트)

이 셰프(에이전트)에게 그냥 "요리해"라고만 하면 안 됩니다. 우리 독자가 누구인지, 어떤 스타일을 원하는지 **아주 구체적인 가이드라인(Instruction)**을 줘야 합니다. 영상 스크립트에서는 다음과 같은 주문서를 셰프에게 건넸습니다.

> **📋 셰프에게 주는 특별 주문서 (System Prompt 역할)**
> 1.  **손님(대상 독자)은 '소프트웨어 엔지니어'다.** -> 기초 설명(예: "변수가 뭐예요?")은 **생략**하고, 실무적인 인사이트(팁, 이유, 노하우)만 집중적으로 다뤄라.
> 2.  **'어떻게(How)'만 쓰지 말고 '왜(Why)'도 설명해라.** -> 코드만 던져주지 말고, 왜 이 방식을 선택했는지 배경 지식까지 담아라.
> 3.  **짧은 코드 조각(Code Snippet)은 도움이 될 때만 넣어라.** -> 장황한 전체 코드 말고, 핵심 로직만 보여주는 '샘플' 정도만.
> 4.  **아웃라인의 구조(제목, 소제목)를 그대로 따라 마크다운(Markdown) 형식으로 써라.** -> `# 제목`, `## 소제목` 구조를 맞춰라.

이 주문서를 받은 **블로그 라이터 에이전트**는 `blog_outline`을 읽고, 위 규칙을 지키며 **완성된 초안(Draft)**을 써서 공유 창고의 **`blog_post`**라는 칸에 저장합니다.

> **💡 개념 돋보기: 에이전트에게 '페르소나(Persona)'와 '제약 조건(Constraints)' 주기**
> > **"야, 글 좀 써줘"**라고 하면 AI는 초등학생 일기처럼 쓰거나, 교수님 논문처럼 씁니다.
> > **"당신은 10년 차 시니어 개발자야. 독자는 3년 차 주니어 개발자야. 존댓말 쓰지 말고 반말로, 실무 팁만 딱딱 끊어서 줘. 코드는 5줄 이내로."**
> > 이렇게 **'누가(Who), 누구에게(To Whom), 어떻게(How), 무엇을 피할지(Don'ts)'**를 정의해주는 것이 **프롬프트 엔지니어링의 핵심**이자, 에이전트가 일을 잘하게 만드는 비결입니다.

## 2. 쓴 글도 검사받아야 한다: 블로그 포스트 검증 체커 (Blog Post Validation Checker)

자, 셰프가 요리(`blog_post`)를 다 만들어 서빙 테이블에 올렸습니다. 바로 손님(사용자)에게 내보내면 될까요?

**절대 안 됩니다.** 주방장이 실수로 **소금을 안 넣었거나(내용 누락)**, **에피타이저가 메인 요리랑 안 맞거나(구조 불일치)**, **디저트가 없는(결론 누락)** 상태일 수 있으니까요.

그래서 우리는 **'품질 관리 매니저(QA Manager)'** 역할을 할 **두 번째 체커, 즉 '블로그 포스트 검증 체커'**를 투입합니다.

### 🕵️ 비유: "서빙 직전, 플레이팅된 요리를 체크리스트 들고 검수하는 꼼꼼한 매니저"

*   **대상:** `blog_post` (완성된 초안).
*   **도구:** **체크리스트(검증 기준)**.
*   **결과:** **"OK (합격)"** 또는 **"Retry (재작성)"**.

### 📋 매니저의 체크리스트 (검증 기준 4가지)

영상 스크립트에 따르면, 이 매니저는 다음 4가지를 **반드시** 확인합니다.

#### ① 도입부(Introduction)가 있는가? 🚪
*   **비유:** 식당에 들어왔을 때 **"어서 오세요, 오늘의 특선 메뉴는 ~~입니다"** 하고 안내하는 **호스트 멘트**가 있는가?
*   **기술적 의미:** 글이 무슨 주제를 다룰지, 왜 읽어야 하는지 독자의 흥미를 끌고 맥락을 잡아주는 첫 단락이 존재하는지 확인.

#### ② 아웃라인과 섹션이 일치하는가? 🗺️
*   **비유:** **메뉴판(아웃라인)**에 "1. 스테이크, 2. 파스타"라고 적혀 있는데, 실제 상차림(본문)에는 "1. 스테이크, 2. 샐러드"만 나와 있으면 안 된다. **약속된 코스가 다 나왔는지** 확인.
*   **기술적 의미:** `blog_outline`에 정의된 `## 제목들`이 `blog_post` 본문에 **빠짐없이, 순서대로, 같은 이름으로** 존재하는지 대조.

#### ③ 결론(Conclusion)이 있는가? 🏁
*   **비유:** 식사가 끝날 때 **"맛있게 드셨나요? 요약하자면 오늘 핵심은 ~~였습니다. 다음에 또 오세요"** 라며 **마무리 인사**를 하는가?
*   **기술적 의미:** 글을 읽고 난 독자가 "그래서 뭐가 중요해?"라고 묻지 않도록, 핵심 요약과 다음 액션(Call to Action) 등이 담긴 마무리 단락 필수.

#### ④ 설명이 명확한가? (Clear Explanations) 💡
*   **비유:** 요리 설명이 **"맛있어요"**에서 끝나는 게 아니라, **"이 소스는 48시간 숙성한 토마토로 만들어 신맛이 덜하고 감칠맛이 납니다"** 처럼 **이해하기 쉽게 구체적**인가?
*   **기술적 의미:** 단순히 나열식이 아니라, **이유(Why)와 맥락(Context)**이 포함되어 있어 대상 독자(소프트웨어 엔지니어)가 끄덕이며 읽을 수 있는 깊이 있는 설명인지 평가.

## 3. 검증 결과에 따른 흐름 제어: "OK" vs "Retry"

매니저(체커)가 체크리스트를 다 훑고 난 후, **판정**을 내립니다. 이 판정은 단 두 가지입니다.

### ✅ Case 1: "OK" (합격) - **공정 종료**
> **"모든 체크리스트 통과. 이 요리는 손님상에 내도 됩니다."**
> *   `blog_post`는 최종 완성본으로 확정.
> *   워크플로우(그래프)의 다음 단계(예: 저장, 발행, 알림 등)로 넘어감.

### 🔄 Case 2: "Retry" (재작성) - **피드백과 함께 라이터에게 돌려보내기**
> **"3번(결론)이 빠졌어요. 4번(설명)도 코드만 있고 왜 쓰는지 설명이 부족해요. 다시 요리해 주세요."**
> *   체커는 단순히 "다시 해"가 아니라, **무엇이 틀렸는지 구체적인 피드백(이유)**을 함께 보냅니다.
> *   이 피드백을 받은 **블로그 라이터(셰프)**는 `blog_outline`을 다시 보고, **피드백을 반영해 `blog_post`를 수정/덮어쓰기** 합니다.
> *   수정된 `blog_post`는 다시 **체커에게 가서 검사**받습니다. (루프 형성)

> **💡 개념 돋보기: '단순 재시도'가 아닌 '피드백 기반 개선 루프' (Feedback Loop)**
> > 지난 챕터의 플래너-체커 루프가 **"다시 생각해봐(Re-plan)"**였다면, 이번 라이터-체커 루프는 **"이 부분 고쳐써(Rewrite with Feedback)"**입니다.
> > *   **플래너 루프:** 사고의 구조(설계) 수정.
> > *   **라이터 루프:** 표현의 품질(구현) 수정.
> > 이렇게 **단계별로 다른 성격의 검증 루프**를 두는 것이 실전 에이전트 시스템을 견고하게 만듭니다. "설계는 맞는데 글쓰기에서 실수했네?"를 잡아내기 위함이죠.

## 4. 전체 흐름 통합: 설계 검증 -> 작성 -> 작성 검증

이제까지 배운 내용을 **하나의 큰 그림(파이프라인)**으로 연결해 보겠습니다. 이 흐름이 바로 우리가 만드는 **'자동 블로그 글쓰기 공장'**의 핵심 라인입니다.

```mermaid
graph TD
    A[시작: 주제 입력] --> B{플래너 에이전트}
    B --> C[아웃라인 초안 생성\nblog_outline]
    C --> D{아웃라인 체커\n(1차 검증)}
    D -- "Retry (최대 3회)" --> B
    D -- "OK" --> E[블로그 라이터 에이전트]
    E --> F[블로그 포스트 초안 생성\nblog_post]
    F --> G{블로그 포스트 체커\n(2차 검증 - 이번 챕터 핵심!)}
    G -- "Retry + 피드백" --> E
    G -- "OK" --> H[최종 완성: blog_post 확정]
    H --> I[다음 단계: 저장/발행 등]
```

### 🧐 단계별 상세 해설

1.  **플래너 (Architect):** "이 주제로 글을 쓰려면 1) 배경, 2) 핵심 기술, 3) 비교, 4) 결론 순서로 쓰자" -> `blog_outline` 저장.
2.  **아웃라인 체커 (Structural Inspector):** "순서 괜찮아? 빠진 거 없어? 대상 독자에 맞어?" -> **최대 3번** 플래너에게 돌려보내며 **설계도 품질 확보**.
3.  **블로그 라이터 (Writer/Chef):** 검증된 `blog_outline`을 읽고, **"시니어 개발자 페르소나"**로 **실전 코드와 왜(Why) 중심**의 `blog_post` 마크다운 작성.
4.  **블로그 포스트 체커 (Content QA / 이번 챕터 주인공):** 완성된 `blog_post`를 **줄 단위로 읽으며 4대 체크리스트(도입, 구조일치, 결론, 명확성) 검사**.
    *   통과 -> **최종 산출물 확정!**
    *   실패 -> **"3번 결론 누락, 2번 섹션에서 '이유' 설명 부족"** 같은 **구체적 피드백**과 함께 라이터에게 **재작성 명령**.

## 5. 실전 구현 시 고려할 꿀팁 (Implementation Tips)

영상에는 코드가 안 나왔지만, 이 로직을 코드(LangGraph, LangChain 등)로 구현할 때 **꼭 챙겨야 할 포인트**들을 비유와 함께 정리해 드립니다.

### 🛑 1. 무한 루프 방지: "최대 재시도 횟수" 설정하기
*   **비유:** 셰프가 아무리 해도 매니저 마음에 안 들어 100번 다시 요리하면 식당 문 닫습니다.
*   **구현:** `state`에 `retry_count` 변수 두고, 체커 노드 진입 전 `if retry_count >= 3: break (또는 에러 처리)` 로직 필수.
*   **왜?** LLM이 환각(Hallucination)으로 "내가 고쳤어"라고 하고 안 고치는 경우, 혹은 기준이 너무 높아서 영원히 통과 못 하는 경우 방지.

### 📝 2. 체커의 출력 형식 통일: Structured Output (JSON/Pydantic)
*   **비유:** 매니저가 "이거 이상해"라고 말로만 하면, 셰프는 어디가 이상한지 모릅니다. **체크리스트 양식지(결과지)**에 체크하고 코멘트 적어서 줘야 합니다.
*   **구현:** 체커 에이전트의 출력을 **단순 문자열("OK", "Retry")이 아닌, 구조화된 객체**로 받으세요.
    ```python
    class CheckResult(BaseModel):
        status: Literal["ok", "retry"]
        feedback: str  # "Retry"일 때만 채워짐. 예: "결론 단락이 없습니다. 핵심 요약 3줄 추가 바람."
        missing_sections: List[str] = [] # 어떤 섹션이 빠졌는지 리스트
    ```
*   이 `feedback` 필드를 **라이터 에이전트의 다음 프롬프트에 `이전 피드백: {feedback}` 형태로 주입**해야 '피드백 루프'가 동작합니다.

### 🎯 3. 프롬프트에 '부정 제약 조건(Negative Constraints)' 넣기
*   라이터 프롬프트에 **"절대 하지 말 것"**을 명시하세요.
    *   "기초 문법 설명 금지 (독자는 시니어임)"
    *   "마크다운 외 다른 포맷(HTML, 일반 텍스트) 출력 금지"
    *   "아웃라인에 없는 새로운 섹션 임의 추가 금지"
*   체커가 이걸 검사하기 쉽게, 라이터가 애초에 안 어기게 만들기 위함입니다.

### ⚖️ 4. 체커의 '엄격함 수준(Strictness)' 조절
*   프롬프트에서 `"꼼꼼하게 검사해"` vs `"큰 틀만 봐줘"` 차이는 큽니다.
*   **초기 개발 시:** 엄격하게(Strict) 설정 -> 에러 많이 잡힘 -> 프롬프트/로직 개선.
*   **운영/배포 시:** 적당히(Moderate) 설정 -> 속도/비용 절감, 사소한 문체 차이로 Retry 안 나게.
*   **팁:** 체커에게 **"너는 까다로운 시니어 에디터야. 하지만 사소한 오타나 오타는 넘겨줘. 구조와 논리만 봐."** 라고 역할 부여.

## 6. 요약하며: 왜 '두 번'이나 검사하는가? (두 마리 토끼 잡기)

혹시 **"아웃라인 체커 있는데 왜 또 체커 만드나요? 귀찮게..."** 라고 생각하셨나요?

이건 **'설계 품질'**과 **'구현 품질'**은 **완전히 다른 차원**이기 때문입니다.

| 구분 | 1차: 아웃라인 체커 (Planner Checker) | 2차: 블로그 포스트 체커 (Writer Checker) |
| :--- | :--- | :--- |
| **검사 대상** | **구조/설계도** (`blog_outline`) | **실제 결과물/본문** (`blog_post`) |
| **검사 관점** | 논리 흐름, 빠진 주제, 중복, 독자 레벨 적합성 | 문단 구성(도입/결론), 아웃라인 준수 여부, 설명 깊이, 포맷 |
| **비유** | **건축 도면 검토:** "방 3개 맞나? 동선 괜찮나? 구조 계산 맞나?" | **준공 검사/인테리어 점검:** "도면대로 방 3개 지어졌나? 문은 달렸나? 마감재 괜찮나? 누수 없나?" |
| **잡는 실수** | 플래너의 **사고 오류**, 기획 누락 | 라이터의 **표현 오류**, 지시 불이행, 환각, 포맷 위반 |

> **💡 개념 돋보기: 'Shift Left(시프트 레프트)'와 'Shift Right'의 조화**
> > 소프트웨어 공학에서 **'Shift Left(왼쪽으로 이동)'**는 **초기 단계(설계/코딩)에서 버그를 잡자**는 뜻입니다. 1차 체커가 바로 이겁니다.
> > 하지만 **'Shift Right(오른쪽으로 이동/Production 검증)'**도 필요합니다. **실제 런타임(최종 산출물)에서만 보이는 버그(문체, 포맷, 컨텍스트 누락)**를 잡기 위함이죠.
> > **우리는 둘 다 합니다.** 그래서 믿을 수 있는 에이전트 시스템이 되는 것입니다.
