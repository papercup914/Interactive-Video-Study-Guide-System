# 다음 학습 단계 안내: MCP(Model Context Protocol) 서버 연동을 통한 에이전트 기능 확장

자, 여러분! 드디어 Google ADK를 이용해서 첫 번째 AI 에이전트를 터미널 위에서 직접 돌려보는 데 성공하셨습니다. 방금 우리는 에이전트에게 "AI 에이전트의 탑 10 활용 사례에 대한 블로그 글을 써줘"라고 요청했고, 서브 에이전트들이 협업해서 계획하고, 작성하고, 결과를 터미널에 뿜어내는 모습까지 생생하게 지켜봤죠. 코드 한 줄 한 줄이 어떻게 유기적으로 연결되는지, 아이디어가 어떻게 실제 작동하는 프로그램으로 탄생하는지 그 전 과정을 함께 걸어왔습니다.

정말 수고 많으셨습니다! 🎉

하지만 잠깐, 여기서 멈추기엔 우리가 만든 에이전트가 너무 아깝지 않나요? 지금 우리 에이전트는 **'자신의 머릿속 지식만으로만 답하는 똑똑한 박사님'** 같은 상태입니다. 세상에나, 박사님이 아무리 똑똑해도 **'도구(칼, 도마, 오븐, 인터넷 검색, 내 컴퓨터의 파일, 데이터베이스)'**를 쓸 줄 모르면 요리도 못 하고, 최신 뉴스도 못 찾아주고, 내 엑셀 파일도 못 읽어주잖아요?

이번 챕터에서 배울 **MCP(Model Context Protocol) 서버 연동**이 바로 그 **'박사님에게 손발(도구)을 달아주는 마법'**입니다. 자, 이제 우리 에이전트를 '생각만 하는 존재'에서 **'실제로 일하는 비서'**로 진화시켜 볼까요?

---

## 1. 왜 MCP가 필요할까? - '박사님'에게 '손발'을 달아주자

### 🍳 일상 비유: '주방 없는 요리사'의 비극
상상해 보세요. 세계 최고의 레시피를 줄줄 외우고, 식재료의 궁합을 완벽하게 꿰뚫고 있는 **'미슐랭 3스타 셰프(우리 에이전트)'**가 있습니다. 근데 이 셰프에게 **주방도 없고, 칼도 없고, 냉장고도 없고, 그저 빈 방에 의자만 하나** 놓여 있다고 해볼까요?

여러분이 "김치찌개 좀 끓여줘"라고 주문하면, 셰프는 **"아, 김치찌개요? 돼지고기 200g, 김치 300g, 두부 반 모, 고춧가루 2큰술... 레시피는 완벽하게 알려드릴 수 있어요!"**라고 **말만** 할 수 있습니다. **직접 끓여서 그릇에 담아 줄 수는 없는 거죠.** 이게 바로 **'도구(Tools)가 없는 LLM/에이전트'의 한계**입니다.

우리가 방금 만든 ADK 에이전트도 마찬가지였습니다. "블로그 글 써줘" 하니까 **글 쓰는 '능력(지식)'**만 써서 텍스트를 뱉어냈지, **"구글 검색해서 최신 트렌드 좀 찾아와"**, **"내 노션(Notion) 페이지 읽어와"**, **"이메일로 보내줘"**, **"엑셀 파일로 저장해줘"** 같은 **'현실 세계의 행동(Action)'**은 못 했습니다.

### 💡 개념 돋보기: LLM의 근본적 한계 - '세상과 단절된 뇌'
> **💡 핵심 포인트: LLM(Large Language Model)은 기본적으로 '입력된 텍스트를 받아 다음 토큰을 예측하는 확률 모델'입니다.**
> *   **학습 시점 고정:** 학습이 끝난 시점 이후의 최신 정보(오늘 뉴스, 어제 주가, 방금 바뀐 API 문서)를 모릅니다.
> *   **외부 세계 접근 불가:** 내 컴퓨터의 파일 시스템, 회사의 데이터베이스, 슬랙(Slack), 지메일(Gmail), 구글 캘린더 등에 **직접 접속할 수 없습니다.** (코드 실행 환경이 주어지지 않는 한)
> *   **상태 없음(Stateless):** 이전 대화 내용을 스스로 기억하지 못합니다(컨텍스트 윈도우에 넣어줘야 함).
>
> **결론:** LLM 혼자서는 '생각'만 할 뿐, '행동'할 수 없습니다. **도구(Tools) = 함수 호출(Function Calling)** 이 필요합니다.

## 2. 기존 방식의 고통: '직접 만드는 도구'의 지옥

그럼 지금까지는 어떻게 에이전트에게 도구를 쥐여줬을까요? 개발자가 **직접 파이썬 함수로 하나하나 다 만들어서** 에이전트에게 "이 함수가 있어. 이러이러할 때 써."라고 등록해줬습니다.

### 🛠️ 일상 비유: '맞춤형 수제 공구' 만들기
여러분이 셰프(에이전트)에게 **'감자 깎는 칼'**, **'양파 다지는 기계'**, **'고기 써는 칼'**, **'국자'**, **'거품기'**... 이 모든 도구를 **직접 철공소 가서 주문 제작**해서 쥐여주는 것과 같습니다.
*   **"셰프님, 이 칼은 감자만 깎는 칼이에요. 양파는 안 돼요."**
*   **"이 국자는 된장국용이에요. 김치찌개엔 좀 작을 수 있어요."**
*   새 레시피(새로운 기능)가 생길 때마다? **새로운 도구를 또 주문 제작해야 합니다.**

**문제점:**
1.  **개발자 번아웃:** 도구 하나 만들 때마다 함수 정의 → 스키마 작성(이름, 설명, 파라미터 타입) → 에러 핸들링 → 테스트 → 에이전트 등록... 이 지루한 과정을 반복해야 함.
2.  **재사용성 제로:** 내가 만든 '구글 검색 도구'를 동료 개발자가 쓰려면 내 코드 복사해서 붙여넣고 환경 변수 설정하고... 버전 관리도 각자 따로.
3.  **표준 부재:** A회사 에이전트는 `search_google(query: str)` 이고, B회사는 `google_search(keyword: str, max_results: int)`... 이름이랑 파라미터가 다 달라서 호환 안 됨.

## 3. MCP(Model Context Protocol) 등장: '범용 도구함'의 표준화

이 아비규환을 해결하려고 **앤트로픽(Anthropic, 클로드 만든 회사)**에서 **"야, 도구 연결하는 거 왜 이렇게 복잡해? 그냥 **'전기 콘센트'**처럼 표준화하자!"** 하고 만든 것이 바로 **MCP(Model Context Protocol)**입니다.

### ⚡ 일상 비유: '전기 콘센트'와 '멀티탭'의 혁명
*   **에이전트(LLM) = 가전제품 (청소기, 드라이기, 선풍기, 에어프라이어...)**
*   **도구(기능) = 전기 에너지 (모터 돌리기, 열 내기, 바람 불기...)**
*   **MCP 서버 = 멀티탭 / 벽면 콘센트**
*   **MCP 프로토콜 = 220V 플러그 모양 표준 (구멍 2개, 전압 220V, 주파수 60Hz)**

**MCP 이전:** 청소기 만들 때마다 발전소 짓고, 전선 직접 따서 연결함. (개발자 하드코딩)
**MCP 이후:** 청소기(에이전트)에는 그냥 **'표준 플러그(MCP Client)'**만 달면 됨. 벽면 **'콘센트(MCP Server)'**에 꽂기만 하면 **'전기(도구/데이터/리소스)'**가 바로 공급됨!

> **💡 개념 돋보기: MCP의 3대 핵심 구성 요소 (The Big Three)**
> MCP 서버가 에이전트에게 제공하는 '전기'의 종류는 딱 3가지로 표준화되어 있습니다.
>
> 1.  **Tools (도구/액션) - "뭐 좀 해줘" (Write/Action)**
>     *   *기능:* 외부 시스템에 **변경**을 가하거나 **실행**하는 함수.
>     *   *예시:* `send_email`, `create_github_issue`, `update_notion_page`, `run_sql_query(INSERT/UPDATE)`, `post_tweet`.
>     *   *비유:* **'청소기 모터 돌리기', '드라이기 열 내기'** -> 실제 세상에서 **일(Work)을 수행**.
>
> 2.  **Resources (리소스/데이터) - "뭐 좀 보여줘" (Read/Data)**
>     *   *기능:* 에이전트가 **읽기만** 할 수 있는 정적/동적 데이터 소스. URI(주소) 체계를 가짐.
>     *   *예시:* `file:///home/user/docs/report.pdf`, `postgres://db/users/schema`, `api://github/repos/anthropic/mcp/README.md`.
>     *   *비유:* **'냉장고 안 재료 목록 보기', '레시피 책 펼쳐보기'** -> **정보 제공(Read-only)**.
>
> 3.  **Prompts (프롬프트/워크플로우) - "이렇게 해줘" (Template/Workflow)**
>     *   *기능:* 재사용 가능한 **프롬프트 템플릿**이나 **작업 흐름(워크플로우)**. 사용자나 에이전트가 "이 상황엔 이 프롬프트 써"라고 호출.
>     *   *예시:* `code_review_prompt`, `debug_error_workflow`, `write_blog_post_template`.
>     *   *비유:* **'김치찌개 레시피 카드', '손님 접대 매뉴얼'** -> **일하는 방식/절차 표준화**.

## 4. MCP 아키텍처: 클라이언트-서버 구조의 아름다움

MCP는 **클라이언트-서버(Client-Server)** 구조를 따릅니다. 이게 왜 중요하냐고요? **'관심사의 분리(Separation of Concerns)'**가 되기 때문입니다.

### 🏗️ 일상 비유: '배달 앱(클라이언트)'과 '맛집(서버)'의 관계
*   **MCP Host (배달 앱 플랫폼 / 예: Claude Desktop, Cursor, 우리 ADK 앱):**
    *   사용자와 만나는 인터페이스. "유저가 뭐 해달래?"라고 파악하고, 적절한 서버에 주문 넣음.
*   **MCP Client (배달 앱 안의 '주문 기능' 모듈):**
    *   Host 안에 내장된 작은 프로그램. 서버와 **1:1로 전용 통신라인(세션)**을 유지하며 JSON-RPC 메시지 주고받음.
*   **MCP Server (맛집 / 예: GitHub 서버, Filesystem 서버, Slack 서버, PostgreSQL 서버):**
    *   **진짜 일을 하는 곳.** 특정 도메인(깃허브, 파일시스템, 슬랙)의 기능을 `Tools`, `Resources`, `Prompts`로 포장해 둠.
    *   여러 Client(여러 에이전트 앱)가 동시에 접속해도 됨. **상태 유지(Stateful) 가능.**

> **💡 개념 돋보기: 왜 '서버'인가? (로컬 vs 원격)**
> MCP 서버는 **내 컴퓨터 로컬(Local)에서 프로세스로 돌릴 수도 있고**, **클라우드 원격(Remote) 서버일 수도 있습니다.**
> *   **Local Server (STDIO 전송):** 내 터미널에서 `npx @modelcontextprotocol/server-github` 처럼 실행. 내 파일 읽기, 내 디비 접속 등 **보안/속도 중요할 때**.
> *   **Remote Server (SSE/Streamable HTTP 전송):** 웹 주소(`https://mcp.mycompany.com`)로 접속. 팀 전체가 공유하는 **공용 도구(회사 위키, 공용 DB, 공용 API)** 연동 시.
> *   **핵심:** 에이전트(Client) 입장에선 **로컬이든 원격이든 똑같이 `tools/list` 호출하면 도구 목록이 옵니다.** 프로토콜이 추상화해줬으니까요!

## 5. 실전 예고: ADK 에이전트에 MCP 서버 '꽂아보기'

자, 이제 이론은 충분합니다. 다음 영상(우리가 지금 준비하는 이 학습 단계)에서 우리는 **실제로 손코딩**을 해볼 겁니다.

### 🎯 우리가 할 미션: "내 로컬 파일 시스템을 읽고, 요약해서, 깃허브 이슈로 등록해주는 에이전트 만들기"

**시나리오:**
1.  내 컴퓨터 `~/project/ideas/` 폴더에 `new_feature.txt` 파일이 있음 (내 아이디어 메모).
2.  에이전트에게 **"아이디어 폴더 읽고, 핵심 요약해서, 우리 팀 깃허브 레포에 '신규 기능 제안' 이슈로 올려줘"**라고 명령.
3.  에이전트는 **MCP Filesystem Server** 꽂아서 파일 읽고(Resource/Tool) -> **MCP GitHub Server** 꽂아서 이슈 생성(Tool).

**필요한 MCP 서버 2개 (이미 세상 누군가가 다 만들어 놨음! 우리가 만들 필요 없음!):**
1.  **`@modelcontextprotocol/server-filesystem`** (공식 제공): 내 로컬 폴더 접근 권한 주고 파일 읽기/쓰기/리스트 도구 제공.
2.  **`@modelcontextprotocol/server-github`** (공식 제공): GitHub 토큰만 주면 이슈 생성, PR 생성, 코드 검색 등 도구 제공.

### 🛠️ 실습 로드맵 (다음 영상에서 다룰 내용)

| 단계 | 작업 내용 | 비유 |
| :--- | :--- | :--- |
| **1. 사전 준비** | Node.js 설치 확인, GitHub Personal Access Token 발급 (repo 권한) | **전기 공사(인프라)** 하기, **멀티탭 콘센트 구멍** 뚫기 |
| **2. MCP 서버 실행 (CLI)** | `npx @modelcontextprotocol/server-filesystem ~/project/ideas` <br> `npx @modelcontextprotocol/server-github` (환경변수 `GITHUB_TOKEN` 설정) | **맛집(서버) 오픈** 준비. "영업 시작!" 문 걸어두기. |
| **3. ADK 코드 수정** | `MCPToolset` 클래스 임포트 -> `StdioServerParameters`로 서버 실행 명령 연결 -> `root_agent`의 `tools` 파라미터에 리스트로 추가 | **가전제품(에이전트)에 '표준 플러그' 달기** -> **멀티탭(서버)에 꽂기** |
| **4. 실행 및 검증** | `adk run` -> "아이디어 폴더 읽고 깃허브 이슈 올려줘" 프롬프트 입력 -> 터미널에서 도구 호출 로그(`Calling tool: read_file` -> `Calling tool: create_issue`) 실시간 확인 -> 깃허브 가서 이슈 생성됐는지 확인 | **스위치 ON!** -> **청소기 돌고, 드라이기 불고** -> **집안 깨끗(업무 완료)** |

## 6. 개념 정리: 왜 ADK에서 `MCPToolset`을 쓸까?

구글 ADK 문서를 보면 `MCPToolset`이라는 클래스가 있습니다. 이 친구가 하는 일이 진짜 **'어댑터(Adapter)'** 역할입니다.

> **💡 개념 돋보기: `MCPToolset` 내부 동작 원리 (알면 든든한 블랙박스 열기)**
> ```python
> from google.adk.tools.mcp_tool.mcp_toolset import MCPToolset, StdioServerParameters
> 
> # 1. 서버 실행 파라미터 정의 (어떤 명령어로 서버 프로세스 띄울지)
> server_params = StdioServerParameters(
>     command='npx',                    # 실행 명령어
>     args=['-y', '@modelcontextprotocol/server-filesystem', '/path/to/folder'], # 인자들
>     env={'SOME_SECRET': 'value'}      # 필요시 환경변수 주입
> )
> 
> # 2. 툴셋 생성 (이게 바로 '플러그' 역할)
> # 내부적으로 비동기적으로 서버 프로세스 띄우고, 초기화(initialize) 핸드셰이크 하고,
> # tools/list 호출해서 도구 목록 받아와서 ADK Tool 객체 리스트로 변환해줌.
> mcp_toolset = MCPToolset(connection_params=server_params)
> 
> # 3. 에이전트에 장착
> root_agent = Agent(
>     ...
>     tools=[mcp_toolset] # 리스트로 넣으면 끝! (단일 도구처럼 동작하지만 실은 도구 묶음)
> )
> ```
>
> **이 한 줄(`tools=[mcp_toolset]`)이 하는 일:**
> 1.  **프로세스 스폰(Spawn):** `npx ...` 명령어로 자식 프로세스(서버) 실행.
> 2.  **핸드셰이크(Initialize):** JSON-RPC `initialize` 요청 보내고 서버 능력(Capability) 확인.
> 3.  **도구 발견(List Tools):** `tools/list` 요청 -> 서버가 `[{name: "read_file", ...}, {name: "write_file", ...}]` 응답.
> 4.  **래핑(Wrapping):** 각 도구 스키마를 ADK의 `BaseTool` / `FunctionTool` 호환 객체로 감쌈.
> 5.  **실행 위임(Delegate):** 에이전트가 `read_file` 호출하면 -> `MCPToolset`이 JSON-RPC `tools/call`로 서버에 전달 -> 서버가 실제 파일 읽고 결과 반환 -> 에이전트에게 리턴.

**개발자는 그냥 `tools=[mcp_toolset]` 한 줄만 쓰면, 수천 줄짜리 파일 시스템 연동 코드, 깃허브 API 연동 코드, 인증 토큰 관리 코드... 이 모든 게 **자동으로, 안전하게, 표준대로** 연결됩니다.** 이게 바로 MCP의 힘입니다.

## 7. 마무리하며: '도구 쓰는 에이전트'의 세상으로

여러분, 지금까지 우리는 **'생각하는 에이전트'(ADK 기본 구조)**를 만들었습니다.
이제부터 우리는 **'행동하는 에이전트'(MCP 연동)**를 만들 겁니다.

이건 단순히 "라이브러리 하나 더 배우는 것"이 아닙니다.
**내 에이전트가 내 컴퓨터의 파일을 읽고, 내 회사의 데이터베이스를 쿼리하고, 슬랙으로 알림 보내고, 지라 티켓 만들고, AWS 인프라 조작하고...** 이 모든 게 **'표준 플러그 하나 꽂는 것'**으로 해결되는 **'에이전트 생태계의 표준'**을 배우는 것입니다.
