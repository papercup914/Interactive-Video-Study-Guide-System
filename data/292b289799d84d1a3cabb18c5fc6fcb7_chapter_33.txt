# 챕터 4. 아웃라인 구조 준수(제목, 헤딩) 및 완성된 초안을 'blog_post' 상태에 저장

---

자, 이제 드디어 **'글쓰기 본편'**에 들어왔습니다. 앞선 챕터에서 우리는 기획자(플래너)가 뼈대(아웃라인)를 짜고, 검수자(체커)가 "이 정도면 합격!"이라고 도장 찍어주는 과정까지 자동화했습니다. 이제는 이 **승인된 설계도(아웃라인)를 바탕으로 실제 집(블로그 글)을 지어줄 '시공 기사(블로그 라이터)'**가 등장할 차례입니다.

그런데 그냥 "지어줘"라고 시키면 안 됩니다. **"설계도에 나온 방 개수대로 방을 만들었니?", "제목은 1단 제목(`#`), 소제목은 2단 제목(`##`)으로 정확히 맞췄니?"** 같은 엄격한 건축 법규(구조 준수)를 지키게 해야 하고, 다 지어진 집 열쇠를 **'blog_post'라는 금고(공유 상태)**에 잘 보관해둬야 다음 공정(최종 검수)으로 넘길 수 있겠죠?

이번 챕터에서는 이 **'견고한 시공 과정(Loop Agent) → 실제 시공(Blog Writer) → 결과물 저장(State Management)'**이 어떻게 코드 레벨에서 구현되는지, 비전공자도 이해하기 쉽게 식당 주방 비유로 낱낱이 파헤쳐 보겠습니다.

---

## 1. '혹시 모르니 세 번은 확인하자': 견고한 기획 루프 (Robust Blog Planner)

스크립트 앞부분은 **"플래너(기획자)와 체커(검수자)를 `Loop Agent`라는 반복 기계 안에 넣어서, 최대 3번까지 재시도하게 만든다"**는 내용입니다.

### 🍳 일상 비유: 깐깐한 주방장과 수석 셰프의 '레시피 승인 회의'

상상해 보세요. **주방장(Planner)**이 신메뉴 레시피(아웃라인)를 짰습니다. 그런데 이 레시피가 바로 메뉴판에 올라가면 안 됩니다. **수석 셰프(Checker)**가 맛보고 "간이 안 맞는데?", "구성이 부실해"라며 퇴짜 놓을 수 있어야 합니다.

*   **1차 시도:** 주방장이 레시피 제출 → 수석 셰프 시식 → **"다시 짜와 (Retry)"**
*   **2차 시도:** 주방장 수정 제출 → 수석 셰프 시식 → **"아직 부족해 (Retry)"**
*   **3차 시도:** 주방장 심기일전 제출 → 수석 셰프 시식 → **"좋아, 합격 (OK)!"**

이 **'제출 → 검수 → 퇴짜/합격' 사이클을 최대 3번 반복하는 기계**가 바로 **`Robust Blog Planner`(견고한 블로그 플래너)**라는 **루프 에이전트(Loop Agent)**입니다.

> **💡 개념 돋보기: 루프 에이전트 (Loop Agent)란?**
> > **루프 에이전트(Loop Agent)**는 **"특정 조건이 만족될 때까지 하위 에이전트들을 계속 반복 실행하라"**는 명령만 수행하는 **'관리자 에이전트'**입니다. 스스로 생각해서 글을 쓰거나 검수하지 않습니다. 단지 **"플래너 돌려 → 체커 돌려 → 체커가 OK라고 할 때까지(최대 3회) 이 순서 반복해"**라는 **플로우(Flow) 제어**만 담당하는 일종의 **'반복문(while문) 매니저'** 같은 존재입니다.

### 왜 최대 3번일까? (안전망의 미학)

LLM(거대 언어 모델)은 가끔 **'환각(Hallucination)'**을 일으키거나, 지시사항 중 **'제목은 반드시 H1으로 시작한다'** 같은 세부 규칙을 깜빡 잊을 수 있습니다. 한 번만 시키고 끝내면, 실수 하나가 그대로 최종 결과물이 되어 버립니다. 

이 **3회 재시도 루프**는 **"인간도 실수하는데 AI라고 안 하겠냐? 기회는 세 번 줄게. 세 번 다 틀리면 그때는 나도 손 놔야지"**라는 **방어적 프로그래밍(Defensive Programming)** 기법이자, **신뢰성을 높이는 가장 저렴한 보험**입니다.

## 2. 드디어 등장한 '글쓰기 장인': 블로그 라이터 (Blog Writer) 에이전트

자, `Robust Blog Planner` 루프가 "OK"를 외치며 끝났다면, 이제 공유 상태(`Shared State`)의 **`blog_outline` 슬롯에는 '검수 완료된 완벽한 설계도'가 들어있습니다.**

이제 **`Blog Writer`(블로그 라이터)**라는 새로운 에이전트가 투입됩니다. 이 친구의 역할은 딱 하나입니다. **`blog_outline`을 읽고 → 진짜 사람이 읽을 만한 '완성된 마크다운 블로그 글'로 풀어써서 → `blog_post` 슬롯에 저장하는 것.**

### 🍳 일상 비유: 설계도만 보고 뚝딱 집을 짓는 '모듈러 주택 시공팀'

*   **입력 재료 (Input):** `blog_outline` (승인된 설계도: "1. 서론, 2. 본론-코드 예시 포함, 3. 결론" 같은 목차 구조)
*   **시공 매뉴얼 (Instruction/시스템 프롬프트):** "너는 시공팀이야. 대상은 **소프트웨어 엔지니어**야. 기초 문법 설명 같은 건 **생략**해. **'어떻게(How)'만 말고 '왜(Why)'도 설명해. 코드 조각(Code Snippet)도 적절히 넣어. 그리고 **설계도의 헤딩 구조(`#`, `##`)를 절대 어기지 마.**"
*   **산출물 (Output):** 완성된 마크다운 파일 (`.md`)
*   **보관 장소 (State Key):** `blog_post` (공유 상태의 '완성품 보관함')

### 프롬프트 엔지니어링 관점에서 본 '시공 매뉴얼(Instruction)' 분석

스크립트에 나온 `Blog Writer`에게 주어진 지시사항(Instruction)을 하나씩 뜯어보며 왜 이렇게 적었는지 비유로 이해해 봅시다.

| 지시사항 (Instruction) | 의미 | 🍳 주방 비유 |
| :--- | :--- | :--- |
| **`Assume audience is software engineers`**<br/>(대상을 SW 엔지니어로 가정) | 독자 수준 설정. "변수가 뭐예요?" 같은 기초 설명 금지. | **"이 손님은 미슐랭 셰프야. '소금이 짠 맛을 낸다'는 설명 하지 말고, '이 소금은 게랑드 소금이라 미네랄 풍미가 다르다'고 말해."** |
| **`Skip the basics`**<br/>(기초 생략) | 시간 낭비 방지, 글의 밀도 높이기. | **"기본 반찬(김치, 물) 설명하지 말고 메인 요리(스테이크) 조리법에 집중해."** |
| **`Focus on practical insights`**<br/>(실용적 통찰 중심) | 이론 나열이 아닌 '현장 팁' 위주. | **"교과서 레시피 말고, 주방에서 20년 일하며 터득한 '불 조절 노하우'를 적어."** |
| **`Explain both the how and the why`**<br/>(어떻게 + 왜 설명) | 코드만 보여주지 말고 의도/이유 설명. | **"이 재료를 왜 지금 넣는지(Why), 어떻게 볶아야 하는지(How) 둘 다 적어."** |
| **`Include short code snippets`**<br/>(짧은 코드 조각 포함) | 이해 돕는 시각적 자료. | **"글만 쓰지 말고, 핵심 소스(데모 접시) 사진도 작게 넣어."** |
| **`Follow outline structure with proper headings`**<br/>(아웃라인 구조/헤딩 준수) | **가장 중요!** 목차 구조(`#`, `##`) 강제 준수. | **"설계도에 '안방'이라 적혔으면 '안방'으로 지어. '큰방'이라고 멋대로 바꾸지 마. 벽(헤딩 레벨) 위치도 정확히 맞춰."** |

> **💡 개념 돋보기: 헤딩 구조(Heading Structure) 준수의 기술적 의미**
> > 마크다운에서 `# 제목`, `## 소제목`, `### 세부제목`은 단순한 **폰트 크기 조절이 아닙니다.** 이것은 **문서의 의미론적 계층 구조(Semantic Hierarchy)**를 정의합니다.
> > 
> > *   **검색엔진(SEO) 크롤러**는 이 헤딩 태그를 읽고 "아, 이 문서의 주제는 이거고, 소주제는 저거구나"를 파악합니다.
> > *   **스크린 리더(시각장애인 보조기기)**는 헤딩을 이용해 문서 목차를 음성으로 탐색하게 해줍니다.
> > *   **자동화 파이프라인(다음 챕터의 체커 등)**은 정규식(Regex)이나 파서로 `# `, `## ` 패턴을 찾아 "목차 구조가 설계도와 일치하는가?"를 기계적으로 검증합니다.
> > 
> > 그래서 `Blog Writer`에게 **"Proper Headings(적절한 헤딩)을 지키라"**고 지시하는 것은, **"예쁘게 써라"**가 아니라 **"기계가 읽고 검증 가능한 표준 포맷으로 써라"**라는 **엔지니어링적 제약 조건**인 것입니다.

## 3. 완성된 초안, 'blog_post' 금고에 보관하기 (State Management)

`Blog Writer`가 밤새워(사실은 몇 초 만에) 글을 다 썼습니다. 이제 이 결과물을 어디에 두어야 할까요? 로컬 변수에 담아두면 다음 에이전트(체커)가 못 찾습니다. **반드시 공유 상태(Shared State)라는 '공용 금고'의 정해진 슬롯(`blog_post`)에 넣어야 합니다.**

### 🍳 일상 비유: 완성된 요리를 '출하대(Pass)'에 올리기

레스토랑 주방에는 **'출하대(Pass)'**라는 곳이 있습니다. 요리사(Writer)가 접시에 담아 **"완성됐어!"** 하고 올려두면, 홀 매니저(Checker/다음 단계)가 와서 접시 상태 확인 후 손님에게 서빙합니다.

*   **State Key: `blog_post`** = **출하대 위의 '완성된 접시' 위치 라벨**
*   **Value: Markdown String** = **접시 위에 놓인 '완성된 요리(글 본문)'**

코드 상에서는 대략 이런 흐름이 됩니다 (의사코드/Pseudo-code):

```python
# Blog Writer 에이전트 내부 로직 (개념도)
def run_blog_writer(shared_state):
    # 1. 금고에서 설계도(아웃라인) 꺼내오기
    outline = shared_state.get("blog_outline") 
    
    # 2. LLM에게 시공 매뉴얼(Instruction) + 설계도 주며 글쓰기 요청
    prompt = f"""
    [시공 매뉴얼]
    - 대상: 시니어 소프트웨어 엔지니어
    - 스타일: 실용적, How/Why 병기, 코드 스니펫 포함
    - 제약: 아웃라인 헤딩 구조(#, ##) 엄수
    
    [설계도]
    {outline}
    
    위 설계도대로 블로그 글 초안을 마크다운으로 작성해줘.
    """
    full_markdown_draft = llm.generate(prompt)
    
    # 3. 완성된 초안을 금고의 'blog_post' 슬롯에 저장 (이게 핵심!)
    shared_state["blog_post"] = full_markdown_draft
    
    return "초안 작성 완료, blog_post에 저장됨."
```

이 **`shared_state["blog_post"] = ...`** 한 줄이 없다면? 이 파이프라인은 **'단절된 섬'**이 됩니다.Writer가 글을 써도 Checker가 읽을 수 없고, Publisher가 발행할 수 없습니다. **상태(State) 공유는 멀티 에이전트 시스템의 '혈관'**과 같습니다.

## 4. 다음 공정 예고: 블로그 포스트 검증 체커 (Blog Post Validation Checker)

스크립트 마지막에 **"Next up, we're going to add another checker, this time for the post. It's called blog post validation checker. It looks at blog_post and check..."** 라며 문장이 끊깁니다.

이것은 **'시공 완료 → 품질 검수(QA)'**로 넘어가는 완벽한 연결고리입니다.

*   **1단계 검수 (이전 챕터):** **설계도(아웃라인) 수준** 검수 → "목차 구조가 맞니? 빠진 주제 없니?"
*   **2단계 검수 (다음 챕터):** **완성품(본문) 수준** 검수 → "본문 내용이 설계도대로 채워졌니? 코드 예시가 정말 돌아가는 코드니? 헤딩 레벨이 중간에 깨지진 않았니?"

`Blog Writer`가 `blog_post`에 글을 저장해둔 **바로 그 순간**, `Blog Post Validation Checker`가 금고에서 `blog_post`를 꺼내 읽고 **"합격/불합격"**을 판단할 준비를 마친 것입니다.

## 📝 챕터 요약 및 핵심 체크포인트

이번 챕터에서 우리는 **'설계도 승인 루프' → '실제 시공(글쓰기)' → '결과물 보관'**이라는 **소프트웨어 공학의 표준 워크플로우(Plan → Do → Check 준비)**가 에이전트 시스템에서 어떻게 구현되는지 보았습니다.

1.  **Robust Blog Planner (Loop Agent):** "실수할 수 있으니 3번까지 기회 준다"는 **안전망(Safety Net)**. 플래너와 체커를 `while (retry < 3 && not ok)` 루프로 감싼 관리자 에이전트.
2.  **Blog Writer (Worker Agent):** 지시사항(Instruction)을 **'시공 매뉴얼'** 삼아, `blog_outline`을 읽고 **마크다운 본문**을 생성하는 **실행 에이전트**. 특히 **헤딩 구조 준수**는 기계적 검증을 위한 필수 제약 조건임.
3.  **State Key `blog_post`:** 완성된 초안을 다음 단계(Validation Checker)가 찾아갈 수 있게 **공유 메모리에 저장하는 키(Key)**. 이 저장이 없으면 파이프라인이 끊김.
4.  **다음 단계 예고:** 저장된 `blog_post`를 대상으로 **내용 충실도, 코드 정확성, 구조 일치 여부**를 검사할 `Blog Post Validation Checker`가 대기 중.

> **💡 한 줄 인사이트**
> **"좋은 에이전트 시스템은 '똑똑한 에이전트 한 명'이 아니라, '실수해도 잡아주는 루프(Loop)'와 '결과물을 확실히 넘겨주는 상태(State)'로 완성된다."**

---

자, 이제 설계도는 승인됐고(`Robust Planner`), 집도 다 지어졌습니다(`Blog Writer` → `blog_post`). 다음 챕터에서는 이 집을 **'입주 가능 판정(Validation Checker)'** 내리는 과정, 즉 **완성된 글의 품질을 코드 레벨에서 어떻게 자동 검증하는지** 파헤쳐 보겠습니다. 기대해 주세요!
