# 🧠 챕터 3. 언어 모델의 단계별 추론 과정: 생각 → 도구 호출 → 관찰 → 다음 단계 결정

안녕하세요! 지난 시간에는 AI 에이전트가 **"단순히 대답만 하는 챗봇이 아니라, 스스로 판단하고 행동하는 소프트웨어"**라는 것을 배웠습니다. 그런데 이 '판단하고 행동한다'는 게 대체 내부적으로 어떻게 돌아가는 걸까요? 오늘은 그 **'생각의 엔진'**이라 불리는 **단계별 추론 과정(Reasoning Loop)**을 아주 느긋하게, 마치 요리사가 요리하는 과정을 지켜보듯 뜯어보겠습니다.

---

## 1. 한 번에 '짠!' 하고 답하지 않아요: '한 호흡' 쉬어가기

우리가 학교 다닐 때 수학 문제를 풀던 시절을 떠올려 보세요. 선생님이 "자, 이 문제 풀어봐"라고 하셨을 때, 답만 덜렁 적어내면 **"과정 좀 적어!"**라고 혼나지 않았나요? 답이 어떻게 나왔는지 **'생각의 흔적(과정)'**이 중요했기 때문입니다.

전통적인 언어 모델(LLM)은 마치 **'찍신(찍어서 맞히는 신동)'** 같았습니다. 질문을 받으면 고민하는 척하다가(사실은 확률 계산만 하고) 바로 **한 번에 최종 답변을 '탁!' 뱉어냈죠.** 그러다 보니 복잡한 계산이 필요하거나, 최신 정보가 필요하거나, 여러 단계를 거쳐야 하는 문제에서는 엉뚱한 소리(환각, Hallucination)를 하곤 했습니다.

하지만 **AI 에이전트(특히 ReAct 패턴을 쓰는 녀석들)**는 다릅니다. 이 친구들은 **"잠깐만, 나 지금부터 생각을 단계별로 적어가면서 풀게."**라고 선언합니다. 즉, **'생각(Thought) → 행동(Action) → 관찰(Observation) → 다음 생각(Next Thought)...'** 이라는 **루프(Loop, 순환 구조)**를 돌면서 문제를 해결해 나갑니다.

> **💡 개념 돋보기: '한 번에 답하기' vs '단계별로 풀기' (Single-shot vs. Chain-of-Thought/ReAct)**
>
> *   **전통적 LLM (Single-shot):** 문제를 보자마자 답만 뱉음. (예: "123 x 456 = 56,088") → 중간에 틀리면 되돌릴 수 없음.
> *   **에이전트 (ReAct Loop):** "자, 일단 123 x 400부터 해볼까? → 49,200. 그다음 123 x 50은? → 6,150. 마지막 123 x 6은? → 738. 다 더하면... 56,088!" → **중간 검증 가능, 도구(계산기) 사용 가능, 실수 수정 가능.**

## 2. ReAct 패턴: '생각'과 '행동'을 결합하다 (Synergizing Reasoning and Acting)

이 멋진 아이디어를 정립한 유명한 논문이 있습니다. 바로 **"ReAct: Synergizing Reasoning and Acting in Language Models" (2002년, 구글 리서치 등)**입니다. 제목에서 알 수 있듯 **Reasoning(추론/생각)**과 **Acting(행동/도구 사용)**을 **시너지(Synergy, 상승효과)** 나게 합쳤다는 뜻이죠.

논문의 핵심 주장은 단순하지만 강력합니다.
> **"언어 모델은 한 번에 텍스트를 생성하는 게 아니라, 단계별로 추론하고(Thought), 도구를 호출하고(Action), 결과를 보고(Observation), 다음 단계를 결정(Next Thought)하는 사이클을 돌아야 한다."**

이게 바로 **'ReAct 루프(ReAct Loop)'**입니다. 자, 이제 이 4단계를 **'맛집 탐방 블로거'**가 되어 하나씩 체험해 봅시다.

## 3. ReAct 루프 4단계 완전 정복: "오늘 점심 어디 갈까?"

상황을 설정해 볼게요. 사용자가 에이전트에게 **"강남역 근처에 주차 편하고, 분위기 좋은 데이트 코스 맛집 추천해 줘."**라고 물었습니다. 에이전트는 이 복잡한 요청을 한 번에 답하지 않고, 다음과 같이 '일기'를 쓰듯 처리합니다.

### ① 단계: 생각 (Thought) — "작전 회의 시간"
> **에이전트 속마음:** *"음, 사용자가 '강남역', '주차 편한 곳', '분위기 좋은 곳', '데이트 코스'라는 키워드를 줬네. 내 지식만으로는 실시간 주차 가능 여부나 현재 예약 상황을 모를 테니, **'지도/장소 검색 API(도구)'**를 써서 후보군을 찾아야겠다. 먼저 '강남역 맛집 주차 가능'으로 검색해 보자."*

*   **비유:** 요리사가 냉장고를 열며 **"오늘 손님이 매운 거 좋아한다던데, 고추장 소스 어떤 거 쓰면 좋을까? 일단 장 보러 가야겠다"**라고 **작전 짜는 단계**입니다. 아직 행동하지 않고 **'어떤 도구를 쓸지, 뭘 검색할지' 머리 속으로 시뮬레이션**하는 시간입니다.

### ② 단계: 도구 호출 / 행동 (Action / Tool Call) — "실행에 옮기기"
> **에이전트 행동:** `search_places(query="강남역 맛집 주차 가능 분위기 좋은", location="강남역", radius=500)`
> *(실제로 구글 맵 API나 네이버 지도 API를 호출하는 코드를 실행함)*

*   **비유:** 요리사가 **시장에 가서 "고추장 1kg 주세요, 신선한 거로 골라주세요"라고 주문하는 행위** 그 자체입니다. 생각만 하면 안 되고, **외부 도구(API, 계산기, 코드 실행기, 검색 엔진 등)를 실제로 호출**해야 합니다. 이 단계에서 에이전트는 **함수(Function) 이름과 입력 값(Arguments/Parameters)을 정해 시스템에 명령**합니다.

### ③ 단계: 관찰 (Observation) — "결과물 확인하기"
> **시스템이 돌려준 결과 (Observation):**
> ```json
> [
>   {"name": "정돈", "address": "강남역 1번 출구 앞", "parking": "발렛 가능 (유료)", "vibe": "조용한 일식 돈가스"},
>   {"name": "삼성당", "address": "강남역 지하상가 연결", "parking": "건물 주차 2시간 무료", "vibe": "힙한 퓨전 한식"},
>   {"name": "출동스시", "address": "강남역 11번 출구", "parking": "주차 불가 (대중교통 권장)", "vibe": "가성비 스시 오마카세"}
> ]
> ```
> **에이전트 속마음:** *"오, 3곳이 나왔네. 근데 '출동스시'는 주차 불가라 사용자 조건(주차 편함)에 안 맞네. '정돈'은 발렛인데 유료고, '삼성당'은 건물 주차 2시간 무료네. 사용자가 '데이트 코스'라고 했으니 분위기 좋은 '삼성당'이나 '정돈' 위주로 추리면 되겠다."*

*   **비유:** 요리사가 시장에서 사 온 **고추장을 맛보며 "음, 이거 좀 짜네? 아니면 딱 맞네?" 하고 상태를 확인하는 단계**입니다. 도구가 돌려준 **원시 데이터(Raw Data, JSON, 텍스트, 에러 메시지 등)를 '눈으로 보고' 사실 그대로 받아들이는 과정**입니다. 여기서 **판단이나 해석을 하지 않고, 일단 '관찰'만** 합니다.

### ④ 단계: 다음 단계 결정 (Next Thought / Decision) — "그럼 이제 어쩌지?"
> **에이전트 속마음:** *"자, 관찰 끝났으니 이제 사용자에게 줄 최종 답변을 정리해야지. '삼성당'이 주차 무료에 분위기도 좋아 1순위, '정돈'은 발렛 가능하지만 유료라 2순위로 제시하고, '출동스시'는 주차 어렵다고 빼고 설명해야겠다. 이제 최종 답변 생성 도구(또는 그냥 텍스트 생성)를 호출하자."*

*   **비유:** 요리사가 재료 확인 끝냈으니 **"자, 이제 이 고추장으로 제육볶음 양념장을 만들자! 레시피대로 볶으면 되겠다"**라고 **다음 행동 계획을 세우는 단계**입니다. 이 결정에 따라 다시 ①번 **생각(Thought)**으로 돌아가 **"최종 답변 작성하기"**라는 새로운 생각을 하고, ②번 **행동(Action: 최종 답변 출력)**으로 이어지거나, 정보가 부족하면 **"리뷰 더 찾아보기"**라는 새로운 도구를 또 호출할 수도 있습니다. 이게 바로 **루프(Loop)**입니다!

## 4. 왜 이렇게 복잡하게 '루프'를 돌까요? (핵심: 제어권의 이동)

여러분, **"그냥 한 번에 생각 다 하고, 도구 한 번만 쓰고, 답 주면 안 돼?"**라고 생각할 수 있습니다. 물론 간단한 건 그렇습니다. 하지만 **복잡한 현실 세계**에서는 그렇지가 않아요.

### 🎯 비유: 내비게이션 vs. 베테랑 택시 기사

*   **전통적 LLM (한 번에 답하기) = 구형 내비게이션:** 출발 전 "최적 경로 계산 완료! 이 길로 가세요." → **중간에 사고 나면? 도로 공사하면? → "경로 재탐색 중..." 하며 멍해지거나, 엉뚱한 길로 안내함.**
*   **ReAct 에이전트 (루프 돌기) = 베테랑 택시 기사 아저씨:**
    1.  **생각:** "지금 강남대로 꽉 막혔을 시간인데..."
    2.  **행동 (눈/귀/내비 확인):** "교통 상황 CCTV 확인, 라디오 교통 정보 청취."
    3.  **관찰:** "아, 서초IC에서 사고 났네. 우회로 타야겠다."
    4.  **다음 결정:** "그럼 논현로로 빠져서 한남대교 타자."
    5.  **(다시 루프) 생각/행동/관찰...** → **실시간으로 최적 경로 갱신하며 목적지 도착!**

**ReAct 루프의 핵심은 '제어권(Control)'이 모델에게 있다는 겁니다.**
*   모델이 **"아, 정보 부족해? 그럼 검색 도구 써야지."** (생각)
*   모델이 **"검색어는 이걸로."** (행동)
*   모델이 **"결과 보니 이건 아니네? 다시 검색하자."** (관찰 → 다음 생각)

이 **'스스로 판단해서 다음 스텝을 결정하는 자율성(Autonomy)'**이 바로 에이전트를 에이전트답게 만드는 마법입니다.

## 5. 실전 코드에서는 어떻게 생겼나요? (ADK에서의 구현 힌트)

구글 ADK(Agent Development Kit)를 쓰면 이 루프를 우리가 일일이 `while True:` 문으로 짜지 않아도 됩니다. 프레임워크가 **'에이전트 런타임(Agent Runtime)'** 안에서 이 루프를 자동으로 돌려줍니다.

우리가 할 일은 **"어떤 도구(Tools)를 줄 것인가?"**와 **"시스템 프롬프트(System Prompt)로 '너는 생각-행동-관찰 루프를 돌아라'라고 지시하는 것"**뿐입니다.

```python
# 개념적인 ADK 코드 구조 (실제 실행 코드는 다음 챕터에서!)

from google.adk.agents import Agent
from google.adk.tools import google_search # 도구 예시

# 1. 도구 준비 (요리사의 칼, 도마, 프라이팬)
tools = [google_search]

# 2. 에이전트 정의 (요리사 채용 계약서 작성)
root_agent = Agent(
    model="gemini-2.0-flash", # 뇌(LLM)
    name="restaurant_finder_agent",
    instruction="""
    너는 맛집 추천 에이전트다.
    사용자 요청을 받으면:
    1. 생각(Thought): 어떤 정보가 필요한지 분석한다.
    2. 행동(Action): google_search 도구를 써서 실시간 정보를 찾는다.
    3. 관찰(Observation): 검색 결과를 읽고 조건에 맞는지 확인한다.
    4. 다음 단계 결정: 정보 부족하면 다시 검색, 충분하면 최종 답변 작성.
    이 과정을 반복(Loop)하라.
    """,
    tools=tools # 도구 상자 건네주기
)

# 3. 실행 (요리 시작!)
# runner.run(agent=root_agent, user_message="강남역 주차 편한 맛집")
```

> **💡 개념 돋보기: ADK가 대신 해주는 '루프 관리' (The Agent Runtime Loop)**
>
> 우리가 `runner.run()`을 호출하면 내부적으로 대략 이런 일이 벌어집니다.
> ```text
> [사용자 입력] 
>      ↓
> [LLM 생성] → "Thought: 주차 정보 필요함. Action: google_search('강남역 주차 맛집')"
>      ↓ (ADK가 파싱해서 도구 실행)
> [도구 실행] → google_search(...) → 결과 반환
>      ↓
> [LLM 생성] → "Observation: 검색 결과 3건 확인. Thought: 삼성당이 조건 맞음. Action: 최종 답변 생성"
>      ↓
> [최종 답변 출력] → 사용자에게 전달
> ```
> **개발자는 루프 코드를 짜는 게 아니라, '도구'와 '지시문(Instruction)'만 잘 설계하면 됩니다!**

## 6. 요약하며: '생각의 근육'을 키우는 과정

오늘 배운 **ReAct 루프(Thought → Action → Observation → Next Thought)**는 AI 에이전트가 **"생각하는 기계"**에서 **"일하는 기계"**로 진화하는 핵심 메커니즘입니다.

1.  **Thought (생각):** "뭘 해야 하지? 어떤 도구 쓰지?" — **기획/전략**
2.  **Action (행동):** "도구야, 일해라!" — **실행/외부 세계와의 상호작용**
3.  **Observation (관찰):** "결과가 이렇네? 에러네? 성공이네?" — **피드백/현실 확인**
4.  **Next Thought (다음 결정):** "그럼 이제 이렇게 하자." — **학습/계획 수정**

이 과정이 **한 번으로 끝날 수도 있고, 10번, 20번 반복될 수도 있습니다.** 에이전트가 "아, 이거 정보 부족한데?"라고 느끼면 다시 검색하고(Thought→Action→Observation), "계산이 틀렸네?"라고 느끼면 다시 계산기를 두드립니다.

다음 챕터에서는 이 추론 과정을 가능하게 하는 **'도구(Tools)'의 정체**와, 에이전트에게 **'너는 이런 도구를 이렇게 써라'라고 가르치는 프롬프트 엔지니어링(시스템 인스트럭션)** 비법을 본격적으로 파헤쳐 보겠습니다. 자, 이제 에이전트에게 **'손발(도구)'**을 달아줄 차례입니다! 🛠️🚀
