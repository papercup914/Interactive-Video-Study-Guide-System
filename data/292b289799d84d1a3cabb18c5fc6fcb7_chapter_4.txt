# 챕터 2. 최신 AI 에이전트의 구성 요소: 추론, 계획, 메모리, 자율성

안녕하세요! 지난 챕터에서는 AI 에이전트가 **"단순히 대답만 하는 챗봇이 아니라, 스스로 판단하고 행동하는 소프트웨어"**라는 큰 그림을 그려보았습니다. 이번 챕터에서는 이 '스스로 판단하고 행동하는' 엔진룸을 열어보고, **추론(Reasoning), 계획(Planning), 메모리(Memory), 자율성(Autonomy)**이라는 네 가지 핵심 부품이 어떻게 맞물려 돌아가는지 아주 꼼꼼하게 뜯어보겠습니다.

어려운 용어가 나와도 걱정하지 마세요. 우리가 매일 겪는 **'요리'와 '식당 운영'** 이야기로 모두 풀어드릴게요. 자, 앞치마를 두르고 주방으로 들어가 볼까요?

---

## 1. '대답만 하는 알바생' vs '주방장 님' : 챗봇과 에이전트의 결정적 차이

스크립트에서 가장 먼저 나온 이야기는 이겁니다.
> *"At the simplest level, an agent is software that doesn't just answer, it can decide and take action."*
> (가장 단순하게 말하면, 에이전트는 단순히 대답만 하는 소프트웨어가 아닙니다. 결정하고 행동할 수 있습니다.)

### 🍳 비유: 분식집 시나리오

상상해 보세요. 여러분이 분식집 사장님입니다.

**케이스 A: 기존 챗봇 (수동적인 알바생)**
*   손님: "김치볶음밥 하나 주세요."
*   알바생(챗봇): **"네, 김치볶음밥 하나 나왔습니다!"** (메뉴판에 적힌 설명만 읽어줌)
*   손님: "계란 후라이 추가요."
*   알바생: **"네, 계란 후라이 추가 나왔습니다!"** (또 설명만 함)
*   손님: "근데 밥이 좀 딱딱한데요?"
*   알바생: **"죄송합니다. 김치볶음밥은 맛있습니다."** (맥락 파악 못 하고 매뉴얼만 반복)

> **💡 개념 돋보기: 기존 LLM(대형 언어 모델) / 챗봇의 한계**
> > **기존 모델은 '예측 기계'입니다.** 방대한 텍스트를 읽고 "다음에 올 말이 뭘까?"를 확률적으로 예측해서 **'텍스트 한 덩어리(응답)'를 한 번에 뱉어냅니다.** 주방에서 요리하는 과정(도구 사용, 상태 확인, 수정)을 전혀 모릅니다. 그냥 "요리 완성!"이라는 문장만 생성하는 거죠.

**케이스 B: AI 에이전트 (프로 주방장 님)**
*   손님: "김치볶음밥 하나 주세요. 근데 밥이 좀 질게 해주시고, 김치는 잘게 다져주세요."
*   주방장(에이전트): (머릿속으로 생각 시작)
    1.  **추론:** "아, 밥 질게 하려면 물 더 넣고 볶아야지. 김치 잘게 다지려면 칼질 더 해야겠다."
    2.  **계획:** "먼저 김치 다지고 -> 팬 달구고 -> 밥 넣고 물 살짝 부어 볶고 -> 계란 후라이 올리고 -> 그릇 담기."
    3.  **행동(도구 사용):** 칼(도구) 꺼내 김치 다지기 -> 프라이팬(도구) 달구기 -> 주걱(도구) 으로 볶기.
    4.  **관찰:** "어? 밥이 좀 탔네? 물 더 부어 살리자."
    5.  **수정(재추론):** 계획 수정 -> 물 추가 -> 다시 볶기.
    6.  **완료:** "자, 손님 맞춤형 김치볶음밥 완성!"

> **💡 개념 돋보기: AI 에이전트의 핵심 - '사이클(Cycle)'**
> > **에이전트는 '한 방에 답을 내지 않습니다.'**  
> > **생각(추론) → 행동(도구 호출) → 결과 확인(관찰) → 다시 생각(수정)**  
> > 이 **무한 루프(사이클)**를 돌면서 일을 완성합니다. 마치 주방장이 요리 중간중간 간을 보고, 불을 조절하고, 재료를 추가하는 과정과 **완전히 똑같습니다.**

## 2. 현대 에이전트의 설계도: ReAct (Reasoning + Acting) 패러다임

스크립트에서는 구글 연구자들이 발표한 유명한 논문 **'ReAct: Synergizing Reasoning and Acting in Language Models'**을 인용하며, 이 사이클의 정체를 밝힙니다.

> *"Language models shouldn't just generate text in one go. They can actually reason step-by-step, take an action like calling a tool or API, observe the results, and then decide what to do next."*
> (언어 모델은 한 번에 텍스트를 생성만 해선 안 됩니다. 단계별로 추론하고, 도구나 API를 호출하는 행동을 취하고, 결과를 관찰한 뒤, 다음에 무엇을 할지 결정할 수 있습니다.)

### 🍳 비유: 요리 레시피 vs 요리사의 실전 노하우

*   **기존 모델 (레시피 책):** "1. 재료 준비 2. 볶기 3. 완성." -> **고정된 순서만 따름. 예외 상황(탄 것, 싱거운 것) 대처 불가.**
*   **ReAct 에이전트 (주방장의 머리):**
    *   **Thought (생각/추론):** "지금 김치 색깔 보니 좀 탔네? 물 넣어야겠다."
    *   **Action (행동):** `주걱으로_휘젓기(강도=약함)`, `물_붓기(양=한국자)`
    *   **Observation (관찰):** "연기 안 나고 윤기 나네. 간 볼까?" -> `맛보기_실행()`
    *   **Observation Result:** "싱겁다."
    *   **Next Thought:** "간장 한 바퀴 둘러야지."
    *   **Next Action:** `간장_두르기`

> **💡 개념 돋보기: ReAct (Reasoning + Acting) = '생각하며 움직이는 것'**
> > **Reasoning (추론/사고):** "현재 상황이 이렇고, 목표는 저긴데, 지금 내 도구함엔 뭐가 있지? 뭘 먼저 해야 하지?" **언어 모델이 자연어로 생각을 '말로' 꺼내는 과정**입니다. (Chain-of-Thought, 생각의 사슬)
> > **Acting (행동/도구 사용):** 생각을 현실로 옮기는 단계. **파이썬 코드 실행, 구글 검색 API 호출, 이메일 보내기, 데이터베이스 조회** 등 외부 세계와 상호작용하는 모든 행위입니다.
> > **Observation (관찰):** 행동의 결과값(에러 메시지, 검색 결과, 계산 값)을 다시 모델의 컨텍스트(입력)로 넣어주는 피드백 루프입니다.
> > **이 세 가지가 합쳐져서 '자율성'의 기반이 됩니다.**

## 3. 에이전트의 4대 심장: 추론, 계획, 메모리, 자율성

스크립트 끝부분에서 정의가 끊겼지만, 이렇게 마무리됩니다.
> *"...systems with reasoning, planning, and memory with enough autono..."*
> (추론, 계획, 메모리를 갖춘, 충분한 자율성을 가진 시스템...)

이 네 가지가 왜 '심장'인지, 식당 운영에 비유해 하나씩 해부해 보겠습니다.

---

### ① 추론 (Reasoning): "상황 판단하고 논리 짜기" - **주방장의 머리**

스크립트에서는 *"figures out what steps need to be taken"* (어떤 단계가 필요한지 파악한다)고 했죠.

**🍳 식당 상황:**
손님이 "매운 거 못 먹는데 김치찌개 먹고 싶어요"라고 했어요.
*   **단순 모델:** "김치찌개 레시피: 김치, 돼지고기, 고춧가루..." (고춧가루 그대로 넣음 -> 망함)
*   **추론 능력 있는 에이전트:**
    1.  **제약 조건 파악:** "매운 거 못 먹음 = 고춧가루/청양고추 금지."
    2.  **대안 탐색:** "그럼 맵지 않게 하려면? -> 고춧가루 빼고 된장/간장으로 간 맞추기, 김치 씻어서 쓰기."
    3.  **논리 구성:** "김치 씻기 -> 물 끓이기 -> 된장 풀기 -> 김치/고기 넣고 끓이기."

> **💡 개념 돋보기: 추론의 종류 - '생각의 사슬(Chain-of-Thought)'과 '트리 탐색(Tree of Thoughts)'**
> > **Chain-of-Thought (CoT):** "생각을 단계별로 글로 적으며 풀기." (수학 문제 풀 때 연산 과정 적듯) -> *가장 기본적이고 강력한 추론 기법.*
> > **Tree of Thoughts (ToT):** "여러 가지 경우의 수를 가지치기하며 생각하기." (체스 두듯 '이러면 저렇고, 저러면 이렇고' 시뮬레이션) -> *복잡한 계획 세울 때 씀.*
> > **에이전트는 이 '추론' 과정을 자연어로 출력하며 스스로를 디버깅합니다.** "아, 내가 아까 김치 안 씻었네? 다시 씻자." 이 자기 수정(Self-Correction)이 추론의 꽃입니다.

---

### ② 계획 (Planning): "큰 그림 그리기, 작업 쪼개기" - **총주방장의 오더 시트**

스크립트에는 직접 언급 안 됐지만, 제목에 있고 정의에 나옵니다. 추론이 '한 단계 생각'이라면, 계획은 **'전체 로드맵 짜기'**입니다.

**🍳 식당 상황:**
단체 손님 20명 예약 들어옴. 메뉴: 샐러드, 파스타, 스테이크, 디저트.
*   **계획 없는 에이전트:** 샐러드 다 만들 -> 파스타 다 만들 -> 스테이크 굽기 -> (손님 기다리다 감) -> 디저트 만들기. **비효율 끝판왕.**
*   **계획 있는 에이전트 (Planner):**
    1.  **작업 분해 (Decomposition):** [샐러드 준비], [파스타 소스 끓이기], [스테이크 고기 재우기], [디저트 플레이팅]로 나눔.
    2.  **의존성 파악 & 순서 정하기 (Scheduling):**
        *   고기 재우기(30분 소요) -> **가장 먼저 시작!**
        *   소스 끓이기(20분) -> 고기 재우는 동안 병행.
        *   샐러드(10분) -> 서빙 직전 신선하게.
        *   스테이크 굽기(5분) -> 손님 입장 타이밍에 맞춰 마지막에.
    3.  **자원 할당:** 나(주방장)는 스테이크 담당, 알바생 A는 샐러드, 알바생 B는 파스타 면 삶기. **(멀티 에이전트 협업의 기초!)**

> **💡 개념 돋보기: 계획 모듈의 구현체 - 'Task Planner' / 'Orchestrator'**
> > 코드 레벨에서는 보통 **`Planner` 클래스**나 **`Graph` 구조(DAG: Directed Acyclic Graph)**로 구현됩니다.
> > *   **입력:** 사용자 목표("여행 계획 짜줘"), 사용 가능한 도구 리스트(항공권 검색, 호텔 예약, 지도 API).
> > *   **출력:** JSON 형태의 실행 계획표.
> > ```json
> > {
> >   "goal": "제주도 2박 3일 여행",
> >   "steps": [
> >     {"id": 1, "task": "항공권 조회", "tool": "flight_api", "depends_on": []},
> >     {"id": 2, "task": "호텔 조회", "tool": "hotel_api", "depends_on": []},
> >     {"id": 3, "task": "일정 짜기", "tool": "map_api", "depends_on": [1, 2]} // 비행기/호텔 정해져야 동선 짬
> >   ]
> > }
> > ```
> > 이렇게 **'의존성 그래프'**를 그려서 병렬 처리할 건 병렬로, 순차 처리할 건 순차로 최적화하는 게 계획의 핵심입니다.

---

### ③ 메모리 (Memory): "경험 쌓고, 맥락 기억하기" - **주방장의 비법 노트 & 단골 장부**

스크립트 정의에 `memory`가 명시되어 있습니다. 에이전트에게 메모리가 없다면? **금붕어**입니다. 3초 뒤면 까먹어요.

**🍳 식당 상황:**

| 메모리 종류 | 주방 비유 | 에이전트 기술 구현 | 역할 |
| :--- | :--- | :--- | :--- |
| **단기 기억 (Short-term / Working Memory)** | **오늘 주문 받은 종이(오더지)** | **Context Window (컨텍스트 윈도우)**, `Conversation History` | 현재 대화 턴, 바로 직전 도구 호출 결과, 현재 계획 단계 기억. "방금 항공권 검색했으니 이제 호텔 찾을 차례지." |
| **장기 기억 (Long-term Memory)** | **비법 레시피 노트, 단골 손님 취향 장부** | **Vector DB (Chroma, Pinecone, FAISS)**, `RAG (Retrieval-Augmented Generation)` | 과거 대화 요약, 사용자 선호도(매운 거 싫어함), 도메인 지식(회사 규정, 제품 매뉴얼), 성공/실패 케이스 학습 데이터. |
| **절차적 기억 (Procedural Memory)** | **몸에 밴 칼질, 불 조절 노하우** | **Fine-tuning**, **Prompt Engineering (System Prompt)**, **Few-shot Examples** | "너는 여행 전문가야", "도구 호출할 땐 JSON만 출력해" 같은 시스템 프롬프트, 예시 코드들. 배워서 몸에 익힌 스킬. |

> **💡 개념 돋보기: 왜 '벡터 DB(Vector DB)'가 장기 기억인가?**
> > 컴퓨터는 텍스트를 숫자 리스트(벡터/임베딩)로 바꿔 저장합니다. "김치찌개"와 "된장찌개"는 의미가 가까우니 벡터 공간상에서 **거리가 가깝게** 배치됩니다.
> > 사용자가 "저번에 맛있던 그 국물 요리 레시피 줘"라고 하면(쿼리 벡터), DB에서 **가장 가까운 벡터(유사도 검색)**를 찾아 "김치찌개 레시피"를 꺼내줍니다. 이게 **RAG(Retrieval-Augmented Generation)**의 핵심이고, 에이전트의 '외장 하드'이자 '장기 기억'입니다.

---

### ④ 자율성 (Autonomy): "인간 개입 없이 목표까지 완주하기" - **주방장에게 열쇠 맡기기**

스크립트 마지막: *"...with enough autonomy"* (충분한 자율성을 가지고).

**🍳 식당 상황:**
*   **자율성 낮음 (Co-pilot):** 주방장):** 주방장이 "양파 다져!"라고 일일이 지시해야 움직임. 양파 다지고 나서 "다 했어요, 다음 뭐 할까요?"라고 묻음. **인간(사용자)이 핸들을 잡고 있음.**
*   **자율성 높음 (Auto-pilot / Agent):** 사장님이 "오늘 저녁 장사 알아서 잘해줘"라고만 함.
    *   주방장: 재고 확인 -> 메뉴 구성 -> 발주 넣기 -> 알바생 스케줄 짜기 -> 조리 -> 품질 검수 -> 마감 정산 -> 내일 준비.
    *   **중간에 불 났거나(에러), 재료 떨어졌거나(예외 상황) -> 스스로 판단해서 소방서 부르거나, 메뉴 변경하거나, 사장님께만 긴급 보고.**
    *   **최종 목표(맛있는 음식 팔아서 매출 내기) 달성할 때까지 스스로 루프 돌림.**

> **💡 개념 돋보기: 자율성의 레벨 (Level of Autonomy) - 사람의 개입 정도**
> > 에이전트라고 다 같은 자율성이 아닙니다. **Human-in-the-loop** 설계가 중요합니다.
> > *   **Level 1: 도구 사용자 (Tool User)** - 사용자가 "검색해줘"라고 할 때만 검색 도구 씀. (추론/계획 약함)
> > *   **Level 2: 작업 실행자 (Task Executor)** - "여행 계획 짜줘" 하면 계획 짜고 도구 여러 번 써서 결과물 내옴. 중간에 사용자 확인 받음.
> > *   **Level 3: 자율 에이전트 (Autonomous Agent)** - "우리 회사 매출 올려줘" 같은 **모호한 고위 목표**만 주면, KPI 분석 -> 전략 수립 -> 실행 -> 모니터링 -> 수정 **반복**. 인간은 '승인'만 하거나 '예외 상황'만 처리.
> > *   **안전 장치 (Guardrails):** 자율성이 높을수록 **'돌발 행동 방지'**가 필수. "돈 다 써서 주식 사라", "DB 삭제해라" 같은 위험 행동을 막는 **규칙 엔진, 권한 분리, 예산 한도 설정** 등이 반드시 코드 레벨로 들어가야 합니다.

## 4. 종합: 네 가지 요소가 한 몸처럼 돌아가는 모습 (The Agent Loop)

이제 이 네 조각을 합쳐서 **'에이전트 메인 루프(Main Loop)'**라는 하나의 심장 박동으로 보겠습니다. 이 코드 구조는 나중에 ADK 실습할 때 뼈대가 됩니다.

```text
[사용자 목표 입력] "제주도 여행 계획 짜줘. 예산 50만 원, 렌터카 필수."
       │
       ▼
┌──────────────────────────────────────────────────────┐
│ 1. PLANNER (계획 수립)                                │
│    - 목표 분해: 항공권, 숙소, 렌터카, 일정, 예산 체크 │
│    - 의존성 그래프 생성 (DAG)                         │
│    - 메모리에서 '사용자 선호도(해산물 좋아함)' 조회    │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│ 2. REASONING & ACTION LOOP (추론-행동 루프) - ReAct  │
│                                                       │
│  [Step 1: 항공권 검색]                               │
│   Thought: "예산 50만 중 항공권 20만 쓰면 나머진 30만"│
│   Action:  flight_api.search(date, budget=200k)      │
│   Observation: "왕복 18만 원 짜리 발견. 남은 예산 32만"│
│   (메모리 업데이트: 남은 예산 32만 원 확정)           │
│                                                       │
│  [Step 2: 렌터카 검색]                               │
│   Thought: "렌터카 필수. 남은 예산 32만 중 10만 배정" │
│   Action:  car_api.search(compact, budget=100k)      │
│   Observation: "가장 싼 게 12만 원... 예산 초과!"     │
│   Thought: "초과했네? 항공권 더 싼 거 찾거나, 숙소 줄여야겠다" │
│   Action:  flight_api.search_cheaper()  (재시도/대안) │
│   ... (목표 달성될 때까지 루프 반복)                  │
└──────────────────────────────────────────────────────┘
       │
       ▼
┌──────────────────────────────────────────────────────┐
│ 3. MEMORY CONSOLIDATION (기억 정리)                   │
│    - 성공한 여행 일정 벡터 DB에 저장 (다음 추천용)     │
│    - "이 사용자는 가성비 중시, 렌터카 필수" 프로파일 업데이트 │
└──────────────────────────────────────────────────────┘
       │
       ▼
[최종 결과물 반환] "짜잔! 48만 원에 맞춘 완벽 일정표입니다."
```

## 5. 챕터 마무리: 이제 우리는 '주방 설계자'가 됩니다

자, 지금까지 최신 AI 에이전트의 4대 구성 요소를 **분식집 주방**에 비유해 아주 깊게 파고들었습니다.

1.  **추론(Reasoning):** "이 상황엔 뭘 어떻게 해야 하지?" (순간순간의 판단력)
2.  **계획(Planning):** "전체 코스를 어떻게 짜지?" (큰 그림 그리기, 효율성)
3.  **메모리(Memory):** "지난번에 뭐 했더라? 손님 취향이 뭐더라?" (경험과 지식의 축적)
4.  **자율성(Autonomy):** "사장님 부르지 말고 나 혼자 끝까지 해치우자." (목표 지향적 완주 능력)

이 네 가지가 **ReAct(추론+행동+관찰) 사이클** 위에서 **메모리**를 읽고 쓰며, **계획**에 따라 움직이고, **자율성**의 수준만큼 인간의 개입 없이 돈다. 이게 바로 **'최신 AI 에이전트'**의 해부도입니다.
