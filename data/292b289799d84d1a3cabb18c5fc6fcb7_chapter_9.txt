# 🧩 문제 유형에 따라 딱 맞는 에이전트 패턴을 고르는 법: 우리 팀에 맞는 '일잘러' 인턴 뽑기

지난 시간에는 AI 에이전트가 **'생각하고(Reasoning) → 행동하고(Acting) → 지켜보고(Observing) → 고쳐나가는(Adjusting)'** 사이클을 돌며 자율적으로 일한다는 걸 배웠습니다. 그런데 모든 인턴이 똑같은 스타일로 일하지 않듯, 에이전트도 **'일하는 스타일(패턴)'**이 제각각 다릅니다.

우리가 식당을 차린다고 상상해 볼까요? 주방에서 일할 직원을 뽑는데, **"무조건 레시피대로만 움직이는 직원"**, **"눈앞의 상황에만 즉각 반응하는 직원"**, **"처음부터 끝까지 큰 그림을 그리고 계획 짜는 직원"** 중 누가 우리 식당 사정에 맞을지 고민해야 합니다. 바로 이 고민이 **'에이전트 패턴 선택'**입니다.

영상에서는 이 패턴을 크게 **세 가지(순차적, 반응적, 계획적/심사숙고형)**로 나누어 설명하고 있는데요, 하나씩 일상 비유와 함께 아주 자세히 뜯어보겠습니다.

---

## 1. 순차적 에이전트 (Sequential Agents): "레시피만 보고 요리하는 신입 주방장"

> **🔍 개념 돋보기: 순차적 에이전트 (Sequential Agents)**
> *   **핵심 원리:** **정해진 순서(Step 1 → Step 2 → Step 3...)대로 무조건 실행**합니다.
> *   **장점:** **예측 가능(Predictable)하다.** 실수할 여지가 적고, 디버깅(오류 찾기)이 쉽습니다.
> *   **단점:** **융통성이 없다(Rigid).** 중간에 예외 상황이 터져도 "내가 할 일은 3번까지야" 하고 멈춰버립니다.
> *   **적합한 상황:** **절차가 법이나 규정에 고정되어 있어** 절대 순서가 바뀌면 안 되는 업무.

### 🍳 일상 비유: '라면 끓이기 매뉴얼'만 달달 외운 알바생
상상해 보세요. 여러분이 편의점 사장님인데, 새 알바생에게 **"물 끓이고 → 면 넣고 → 스프 넣고 → 3분 끓이고 → 그릇에 담아라"**라는 **종이 매뉴얼(고정된 코드/프롬프트 체인)**을 쥐여줬습니다.

이 알바생(순차적 에이전트)은 아주 착실합니다. 
1.  **Step 1:** 냄비에 물 붓기 (완료)
2.  **Step 2:** 물 끓을 때까지 기다리기 (완료)
3.  **Step 3:** 면 투하 (완료)
4.  **Step 4:** 스프 투하 (완료)...

**하지만 문제가 생깁니다.** 
*   손님이 **"저 매운 거 못 먹어요, 스프 반만 넣어주세요"**라고 해도? → **못 알아듣습니다.** 매뉴얼엔 '스프 한 봉지 다 넣기'라고 적혀 있으니까요.
*   물이 끓어넘치는데? → **모릅니다.** 'Step 2: 기다리기' 중이니까 그냥 기다립니다.
*   면이 다 익었는데 스프가 없다면? → **멈춥니다.** Step 4를 못 하니까 전체 공정이 올스톱됩니다.

이게 바로 **'순차적 에이전트'**의 민낯입니다. **"이거 하면 저거 해, 저거 하면 이거 해"**라는 **고정된 파이프라인(조립 라인)** 위에 올려놓은 것과 똑같습니다. 

### 💡 언제 써먹나요?
*   **데이터 전처리 파이프라인:** "CSV 읽기 → 결측치 채우기 → 정규화 하기 → DB 저장하기" (순서가 절대 안 바뀜)
*   **규정 준수 워크플로우:** "계약서 조회 → 법적 필수 조항 체크 → 승인 도장 찍기" (법이 정한 순서라 바꿀 수 없음)
*   **단순 반복 자동화:** "매일 오전 9시 → 어제 매출 크롤링 → 엑셀 정리 → 슬랙 알림 보내기"

> **💡 튜터의 팁:** "우리 업무는 **'예외 상황'이 거의 없고, **'순서가 생명'**이야!" 라면 주저 말고 **순차적 패턴**을 쓰세요. 구현도 제일 쉽고, 유지보수도 편합니다. `LangChain`의 `LCEL (LangChain Expression Language)` 체인이나 `RunnableSequence`가 딱 이 패턴입니다.

## 2. 반응적 에이전트 (Reactive Agents): "눈앞의 손님 주문만 보고 즉석 요리하는 베테랑 셰프"

> **🔍 개념 돋보기: 반응적 에이전트 (Reactive Agents)**
> *   **핵심 원리:** **미리 짜인 계획 없이, '지금 이 순간의 상태(State/Observation)'만 보고 즉각 행동(Action) 결정**합니다. `ReAct(Reasoning + Acting)` 루프를 매 턴마다 돕니다.
> *   **장점:** **유연하다(Flexible).** 예측 못한 상황(도구 오류, 사용자 말 바꾸기, 데이터 변경)에 즉각 대처합니다.
> *   **단점:** **근시안적(Short-sighted)이다.** 큰 그림 없이 당장의 최적해만 쫓다 보니, 전체적으로 비효율적이거나 목표에서 벗어날 수 있습니다. (예: 냉장고 문을 열기 위해 밥솥 뚜껑을 여는 식)
> *   **적합한 상황:** **상황이 시시각각 변하고, 다음 단계가 무엇인지 미리 알 수 없는** 탐색/대화/긴급 대응 업무.

### 🍳 일상 비유: '냉장고 파먹기' 달인, 즉흥 요리사
이번엔 미슐랭 스타 셰프를 모셨습니다. 레시피 책? 그런 거 안 봅니다. 
*   **상태 확인:** "어? 냉장고에 김치랑 돼지고기 남았네? 김치찌개 각이네."
*   **행동 결정:** "그럼 김치 볶고 → 물 붓고 → 고기 넣고 → 끓이자." (계획 세우기 X, 바로 실행)
*   **관찰:** "어라? 국물이 짜네? 물 더 붓자." (즉각 수정)
*   **다음 행동:** "두부도 있네? 썰어 넣자."

이 셰프(반응적 에이전트)는 **'계획'이라는 걸 안 세웁니다.** 그냥 **눈앞의 재료(현재 상태)** 보고 **직감(LLM 추론)**으로 **"이거 해!"** 하고 도구(칼, 불, 국자)를 씁니다. 손님이 중간에 "아, 나 두부 싫어해"라고 하면? **"아 넵, 두부 빼고 달걀 풀게요"** 하고 바로 방향 틀어버립니다. 

하지만 **단점**도 명확합니다. 
*   "김치찌개 끓이려고 물 끓이는 중인데, 갑자기 '아, 밥도 해야지!' 생각나서 밥솥 누르고, 국 끓이던 불 끄고... 결과적으로 김치찌개도 태우고 밥도 설익게 되는 상황"이 옵니다. **큰 그림(전체 최적화)이 없어서 중구난방이 될 수 있죠.**

### 💡 언제 써먹나요?
*   **고객 상담 챗봇:** 사용자가 "환불해줘" → "이유가?" → "사이즈 커서" → "교환은?" → "아니 환불" ... 대화 흐름이 전혀 예측 불가함.
*   **게임 AI / 로봇 제어:** 적 출현 → 피하기 → 반격 → 아이템 줍기 (매 프레임마다 상황이 바뀜)
*   **코딩 어시스턴트 (단일 함수 수준):** "에러 났다 → 로그 보니 NullPoint → if문 추가 → 다시 실행" (즉각적 피드백 루프)

> **💡 튜터의 팁:** 반응적 에이전트는 **'도구(Tool) 리스트'**를 얼마나 잘 갖춰줬느냐가 생명입니다. 김치찌개 하려면 `칼`, `도마`, `냄비`, `불조절` 도구가 다 있어야 하듯, 에이전트에게 **"너 지금 상태에서 쓸 수 있는 도구는 이거야(API 리스트)"**라고 **시스템 프롬프트에 명확히 명시**해줘야 헤매지 않습니다. `LangGraph`의 `React Agent` 노드나 `AutoGPT` 초창기 스타일이 이 패턴에 가깝습니다.

## 3. 계획적/심사숙고형 에이전트 (Deliberate / Planning Agents): "여행 일정표부터 짜고 떠나는 꼼꼼한 여행 플래너"

> **🔍 개념 돋보기: 계획적 에이전트 (Deliberate / Planning Agents)**
> *   **핵심 원리:** **실행 전, '목표(Goal)'를 달성하기 위한 전체 단계(Plan/Task List)를 먼저 수립**합니다. 계획을 세우는 단계(Planning)와 실행하는 단계(Execution)가 **분리**되어 있습니다.
> *   **장점:** **전략적이다(Strategic).** 복잡한 의존성(순서 의존, 리소스 배분)을 관리하며, 전체 최적화를 노립니다. 중간에 계획 수정(Re-planning)도 가능합니다.
> *   **단점:** **초기 지연(Latency) 발생.** 계획 짜는 데 시간/토큰 비용이 듭니다. 계획이 틀리면 처음부터 다시 짜야 할 수도 있습니다(비용↑).
> *   **적합한 상황:** **여러 단계가 얽혀 있고, 순서가 중요하며, 리소스(비용, 시간, API 호출 수) 관리가 필요한** 복합 미션.

### 🍳 일상 비유: '유럽 3주 배낭여행' 짜주는 여행 플래너
영상 스크립트에서 나온 **'여행 예약(Booking Travel)'** 예시가 교과서적입니다. 
여러분이 "유럽 3주 여행 가고 싶어"라고 말했을 때, 반응적 에이전트(즉흥 셰프)는 **"그럼 파리 비행기부터 끊자!"** 하고 예약 사이트부터 켭니다. 그런데 파리 도착하니 숙소 없고, 스위스 가려니 기차표 매진이고... 난리 납니다.

**계획적 에이전트(여행 플래너)**는 다릅니다. 
1.  **🧠 사고/계획 단계 (Planning Phase - 아직 행동 안 함):**
    *   목표 분석: "3주, 예산 500만 원, 볼거 많음, 체력 안 좋음"
    *   제약 조건 체크: "비자 필요? 성수기? 환율?"
    *   **전체 로드맵 작성:** 
        > 1단계: 비자/여권 준비 (D-30 ~ D-15)  
        > 2단계: 항공권 왕복 예약 (D-14)  
        > 3단계: 도시별 이동 경로/교통편 확정 (유레일 패스 vs 저가항공)  
        > 4단계: 도시별 숙소 예약 (이동 동선 고려)  
        > 5단계: 필수 관광지 티켓 선예약 (루브르, 콜로세움 등)  
        > 6단계: 짐 싸기/환전/보험 (D-1)
2.  **⚙️ 실행 단계 (Execution Phase):**
    *   1단계 완료 → 2단계 진행... 
    *   **중간 모니터링:** "어? 3단계에서 파리-로마 비행기 값이 2배 올랐네? → **재계획(Re-planning):** 기차로 바꾸고 일정 하루 늘리자."

이게 바로 **'심사숙고(Deliberation)'**입니다. **"일단 저질러놓고 수습하자"**가 아니라, **"머릿속으로 시뮬레이션 돌려보고, 가장 효율적인 경로를 확정 짓고, 그제야 움직인다"**는 거죠.

### 💡 언제 써먹나요?
*   **복잡한 리서치/리포트 작성:** "경쟁사 분석 보고서 써줘" → (계획: 산업 정의 → 주요 플레이어 10곳 선정 → 재무/기술/마케팅 데이터 수집 → 비교 표 작성 → 인사이트 도출 → 초안 작성 → 검수)
*   **멀티스텝 코드 생성/리팩토링:** "이 레거시 시스템 마이크로서비스로 분리해줘" → (계획: 모듈 의존성 분석 → 경계 분리 설계 → API 계약 정의 → 서비스별 구현 → 통합 테스트 → 배포 파이프라인 수정)
*   **자동화된 비즈니스 프로세스 (RPA 대체):** "매월 말 정산 마감 프로세스 돌려" → (계획: 원장 마감 → 부가세 신고 데이터 추출 → 오류 검증 → 세무사 전달 → 신고 완료 알림)

> **💡 튜터의 팁:** 계획적 에이전트를 구현할 땐 **'플래너(Planner)'**와 **'실행자(Executor)'**를 **별도의 에이전트(또는 노드)**로 분리하는 게 정석입니다. `LangGraph`에서는 `StateGraph` 안에서 `planner_node`가 `Plan` 객체(리스트)를 상태에 저장하면, `executor_node`가 하나씩 꺼내서 수행하고 결과를 다시 상태에 쌓는 구조로 만듭니다. 이때 **'계획 수정(Re-plan)' 노드**를 루프로 연결해두면 실패 시 자동 복구까지 가능해집니다.

## 🧠 튜터의 마무리 조언: "섞어 쓰세요, 하이브리드로!"

현실 세계의 복잡한 문제는 **하나의 패턴만으로 해결되지 않습니다.** 가장 강력하고 실용적인 아키텍처는 **패턴을 계층적으로 조합(Hierarchical Composition)**하는 겁니다.

> **🏗️ 실전 아키텍처 예시: "자동 주식 분석 리포트 에이전트"**
> 1.  **최상위: 계획적 에이전트 (마스터 플래너)**
>     *   목표: "삼성전자 분기 분석 리포트 작성"
>     *   계획 수립: ① 재무제표 크롤링 → ② 뉴스/공시 감성 분석 → ③ 경쟁사 비교 → ④ 차트 기술적 분석 → ⑤ 종합 인사이트 도출 → ⑥ PDF 생성
> 2.  **중간: 순차적 에이전트 (서브 파이프라인)**
>     *   ①번 '재무제표 크롤링'은? → **순차적**: DART API 호출 → 파싱 → 검증 → DB 저장 (순서 고정, 예외 없음)
>     *   ⑥번 'PDF 생성'은? → **순차적**: 마크다운 변환 → 템플릿 적용 → PDF 렌더링 → 업로드
> 3.  **하위: 반응적 에이전트 (툴 사용자)**
>     *   ②번 '뉴스 감성 분석' 중 "관련 뉴스 검색" 단계 → **반응적**: 검색어 뭐 칠까? → 결과 안 좋으면? → 키워드 바꿔서 재검색 (즉각 루프)
>     *   ④번 '차트 분석' 중 "지표 계산" → **반응적**: 데이터 구멍 나면? → 보간법 써서 채우기 (상황 대응)

이렇게 **'큰 그림은 계획적으로(Planning)', '반복되는 단위 작업은 순차적으로(Sequential)', '예측 불가능한 도구 사용은 반응적으로(Reactive)'** 설계하는 것이 **'잘 나가는 프로덕션 레벨 에이전트'**를 만드는 비결입니다.

다음 챕터에서는 이 패턴들을 코드 레벨에서 어떻게 구현하는지, 특히 **LangGraph**를 이용해 **상태(State)를 중심으로 그래프를 그리는 법**을 본격적으로 파헤쳐 보겠습니다. 기대해 주세요! 🚀
