# 두 번째 서브 에이전트 구현: 블로그 라이터(Blog Writer) — 튼튼한 설계를 위한 검증 루프와 글쓰기 담당자 영입

안녕하세요! 지난 시간에는 블로그 글의 **설계도(아웃라인)**를 그려주는 첫 번째 서브 에이전트, '블로그 아웃라인 플래너'를 만들었습니다. 그런데 설계도를 그리는 사람이 "아, 소개 빼먹었다", "결론 안 썼네" 하며 실수하면 어떻게 될까요? 그대로 다음 단계로 넘어가면 엉망진창인 글이 탄생하겠죠.

이번 챕터에서는 **"실수를 자동으로 잡아주는 검수 시스템(Loop Agent)"**을 구축하고, 드디어 **실제 본문을 써줄 '블로그 라이터(Blog Writer)'**를 영입하는 과정을 아주 자세히, 일상 비유와 함께 풀어보겠습니다.

---

## 1. 첫 번째 에이전트 마무리: "내 작품은 여기다" — `output_key`의 비밀

지난 시간에 `BlogOutlinePlanner` 에이전트를 만들면서 `output_key`를 `'blog_outline'`로 설정했었죠? 이 한 줄이 왜 그렇게 중요한지, **'공용 칠판(Shared State)'** 비유로 완벽하게 이해해 봅시다.

### 🍳 비유: 식당 주방의 '공용 주문서 보드'

상상해 보세요. 아주 바쁜 식당 주방입니다.
*   **에이전트 1(플래너):** 헤드 셰프가 오늘의 특선 메뉴 **레시피(아웃라인)**를 적습니다.
*   **에이전트 2(검수관/라이터):** 부주방장이나 라인 쿡이 그 레시피를 보고 요리(본문 작성/검수)를 해야 합니다.

만약 헤드 셰프가 레시피를 종이에 적어 **자기 주머니에 넣어버리면** 어떨까요? 부주방장은 "셰프, 레시피 어디 있어요?"라고 소리쳐야 하고, 셰프는 "아, 여기 있네" 하며 건네줘야 합니다. 이게 **`output_key`가 없을 때** 상황입니다. 매번 "내 결과물 좀 받아가세요"라고 명시적으로 넘겨줘야 하니 번거롭고 실수하기 쉽죠.

하지만 **`output_key = 'blog_outline'`**을 설정하면?
> **헤드 셰프가 레시피를 완성하자마자, 주방 중앙의 '공용 주문서 보드(Shared State)'의 '오늘의 특선 레시피' 칸에 척! 붙여놓는 것**과 같습니다.

그러면 뒤에 오는 어떤 요리사(다음 에이전트)든 **보드만 보면** "아, 오늘 레시피가 이거네?" 하고 즉시 작업을 시작할 수 있습니다. 굳이 셰프를 찾지 않아도 되니 **자동화된 파이프라인**이 돌아가는 것이죠.

> **💡 개념 돋보기: `output_key`와 Shared State (공유 상태)**
>
> *   **Shared State (공유 상태/공용 칠판):** 여러 에이전트가 데이터를 주고받는 **공통의 메모장**입니다. 파이썬의 `dict`(딕셔너리)처럼 `{'키': '값'}` 형태로 데이터가 저장됩니다.
> *   **`output_key`:** 현재 에이전트가 작업한 **결과물을 공용 칠판의 '어떤 이름(key)'으로 저장할지** 정해주는 설정입니다.
> *   **자동 전달의 마법:** ADK(에이전트 개발 키트)는 에이전트가 일을 마치면 `output_key`에 지정된 이름으로 자동으로 State에 저장해줍니다. 다음 에이전트는 별도 코드 없이 State에서 그 키로 값을 읽어오기만 하면 됩니다.
> *   **왜 중요한가?** 에이전트 간의 **결합도(Coupling)를 낮춰줍니다.** "너에게 직접 줄게"가 아니라 "칠판에 적어둘게, 알아서 봐"가 되니까 에이전트끼리 서로의 존재를 몰라도 협업이 가능해집니다.

## 2. 두 번째 에이전트 등장: 깐깐한 '품질 검수관' — Outline Validation Checker

설계도를 그리는 플래너가 아무리 똑똑해도, 가끔 "제목 빠뜨림", "섹션 3개만 씀(4~6개 필요)", "결론 없음" 같은 실수를 할 수 있습니다. 사람으로 치면 **'퇴고 안 하고 출판사 보낸 원고'** 같은 꼴이 되겠죠.

그래서 우리는 **두 번째 서브 에이전트, `OutlineValidationChecker`(아웃라인 검증 검수관)**를 둡니다. 이 친구는 글을 **쓰지 않습니다. 오직 '검사'만 합니다.**

### 📋 비유: 까다로운 '편집장' 또는 '건축 감리사'

*   **플래너(건축가):** "자, 5층 건물 설계도 그렸어요! (근데 1층만 그렸을 수도 있음)"
*   **검수관(감리사/편집장):** 설계도를 펼쳐 들고 **체크리스트**를 들고 검사합니다.
    *   ✅ 제목 있나?
    *   ✅ 서론(도면 설명) 있나?
    *   ✅ 본론 섹션 4~6개 있나?
    *   ✅ 결론(마무리) 있나?
*   **판정:**
    *   **전부 통과 → "OK"** (도장 쾅! 다음 단계로 넘김)
    *   **하나라도 빠짐 → "RETRY" + 사유** ("야, 3층 설계도 빠졌어. 다시 그려와!")

### 🛠️ 구현 상세: 프롬프트(Instruction)로 '규칙' 심어주기

이 에이전트는 별도의 도구(Tool)가 필요 없습니다. **LLM 자체의 추론 능력**만으로 "상태에 있는 아웃라인이 규칙에 맞나?"를 판단하게 합니다. 핵심은 **`instruction`(지시문)에 규칙을 아주 구체적으로 박아넣는 것**입니다.

```python
# 개념적 코드 구조 (실제 코드는 영상 참고)
outline_checker = LlmAgent(
    name="OutlineValidationChecker",
    model="gemini-2.0-flash", # 빠르고 똑똑한 모델 추천
    instruction="""
    당신은 블로그 아웃라인 품질 검수관입니다.
    공용 상태(State)에 저장된 'blog_outline'을 읽으세요.
    
    [필수 체크리스트]
    1. 제목(Title)이 있는가?
    2. 서론(Introduction)이 있는가?
    3. 본문 섹션(Sections)이 4개 이상 6개 이하인가?
    4. 결론(Conclusion)이 있는가?
    
    [출력 규칙 - 반드시 둘 중 하나만 출력하세요!]
    - 모두 만족하면: "okay" (소문자, 따옴표 없이 딱 이 단어만)
    - 하나라도 부족하면: "retry" (소문자) + 줄바꿈 후 구체적으로 뭐가 빠졌는지 설명
    
    예시:
    okay
    
    또는
    
    retry
    섹션이 3개뿐입니다. 4~6개 사이로 늘려주세요. 결론도 누락되었습니다.
    """,
    # 이 에이전트는 결과를 State에 저장할 필요 없음 (판단만 하면 되니까)
    # output_key 생략 가능 또는 별도 키 사용
)
```

> **💡 개념 돋보기: '구조화된 출력(Structured Output)' 강제하기**
>
> 여기서 **"반드시 'okay' 또는 'retry' 단어만 출력하라"**고 지시한 것이 포인트입니다.
> *   LLM은 기본적으로 말이 많습니다. "네, 검토해보니 제목이 빠졌네요. 다시 쓰셔야겠어요."라고 장황하게 말하면, **다음 단계(루프 제어 로직)가 이 말을 이해 못 합니다.** 코드는 `if result == "okay":` 이렇게 비교하니까요.
> *   즉, **에이전트끼리 대화할 때는 '사람 말'이 아닌 '기계가 읽는 신호(프로토콜)'를 쓰게 해야 합니다.** 이건 프롬프트 엔지니어링의 핵심 기법 중 하나입니다. **"출력 포맷을 강제하여 파싱(Parsing) 에러를 원천 차단한다"**고 이해하시면 됩니다.

## 3. 이 둘을 묶는 '무한 루프(안전망)' — Loop Agent: Robust Blog Planner

자, 플래너(작가)와 검수관(편집장)이 준비됐습니다. 이제 이 둘을 **"통과할 때까지 반복해!"**라고 시키는 **관리자(매니저)**가 필요합니다. 그게 바로 **`LoopAgent`**입니다.

### 🔄 비유: "합격할 때까지 재시험 보는 학원 시스템" 또는 "불량품 걸러내는 컨베이어 벨트"

*   **일반 에이전트(Sequential Agent 등):** 1번 → 2번 → 3번 → **끝**. (중간에 틀려도 그냥 감)
*   **Loop Agent:** **시작 → (플래너 → 검수관) → [판단: Okay?] → Yes → 끝 / No → 다시 처음으로 (플래너 → 검수관) → ...**

이게 바로 **'견고한(Robust) 블로그 플래너'**를 만드는 비결입니다.

### ⚙️ 작동 흐름 (Step-by-Step)

1.  **Loop Agent 시작** (최대 3회 반복 제한 설정: `max_iterations=3`)
2.  **1차 시도:**
    *   **Planner 실행:** State에 `blog_outline` 작성.
    *   **Checker 실행:** State의 `blog_outline` 읽고 검사.
    *   **결과 확인:**
        *   `okay` → **루프 탈출(성공)!** 다음 단계(Writer)로 넘어감.
        *   `retry` → **루프 지속(실패).** 카운트 1 증가.
3.  **2차 시도 (재시도):**
    *   **Planner 실행:** *여기서 핵심!* 플래너는 **이전 State(실패한 아웃라인 + Checker의 "retry 사유")를 그대로 봅니다.**
    *   즉, 플래너는 "아, 내가 섹션 3개만 썼구나. 편집장이 4~6개 하랬지? 고쳐쓰자." 하고 **수정된 아웃라인**을 State에 **덮어쓰기(Update)** 합니다.
    *   Checker 다시 검사 → `okay`면 탈출, `retry`면 3차 시도.
4.  **3차 시도 (최후의 기회):** 동일 반복.
5.  **3회 초과 시:** 루프 강제 종료 → 에러 처리 또는 사람 개입 요청.

### 🛠️ 구현 포인트: `sub_agents` 리스트 순서와 `max_iterations`

```python
# 개념적 코드 구조
robust_planner = LoopAgent(
    name="RobustBlogPlanner",
    max_iterations=3,  # 🛡️ 안전장치: 무한 루프 방지 (비용 폭주/시간 낭비 막음)
    sub_agents=[
        blog_outline_planner,      # 1순위: 작가 (초안 작성/수정)
        outline_validation_checker # 2순위: 검수관 (판정)
    ]
    # LoopAgent는 sub_agents를 순서대로 반복 실행하며,
    # 마지막 에이전트(Checker)의 출력/상태를 보고 계속할지 멈출지 결정하는 로직이 내장되어 있거나
    # 별도의 '조건 확인 에이전트'를 두기도 합니다. 
    # (영상에서는 Checker의 출력이 'okay'면 멈추는 로직이 LoopAgent 내부에 구현되거나
    #  후처리 로직으로 연결된 것으로 보입니다.)
)
```

> **💡 개념 돋보기: LoopAgent vs SequentialAgent — "조건부 반복"이 핵심이다**
>
> | 특징 | **SequentialAgent (순차 에이전트)** | **LoopAgent (루프 에이전트)** |
> | :--- | :--- | :--- |
> | **흐름** | 일직선: A → B → C → **끝** | 순환: (A → B) → 조건 체크 → **다시 A → B** ... |
> | **제어권** | 무조건 한 번씩 실행 | **조건 만족 시까지 반복** |
> | **State 활용** | 다음 에이전트에 전달만 함 | **이전 결과를 피드백 삼아 수정(Refinement)함** |
> | **비유** | 조립 라인 (한 번 지나가면 끝) | **연습 → 테스트 → 불합격 → 보충 수업 → 재테스트** |
> | **안전장치** | 필요 없음 | **`max_iterations` 필수!** (없으면 무한 루프로 요금 폭탄/정지) |
>
> **왜 `max_iterations=3`인가?**
> LLM은 확률적이라 같은 실수를 반복할 수 있습니다. 3번 해도 안 고쳐지면 프롬프트나 모델 문제일 확률이 높으니, 사람(개발자)에게 넘기는 게 낫습니다. **"기계에게 무한 재시도 권한을 주지 마라"**는 철칙입니다.

## 4. 드디어 본문 작성자 영입! — 세 번째 에이전트: Blog Writer

자, 이제 **"검증된 완벽한 설계도(아웃라인)"**가 State의 `blog_outline`에 안전하게 저장되었습니다. 이제 이 설계도를 보고 **실제 블로그 글(본문)을 써줄 '블로그 라이터(Blog Writer)'**를 만들 차례입니다.

영상 스크립트는 "Now we create another agent called blog writer. This one takes the..." 여기서 끊기지만, 앞선 흐름으로 볼 때 구현 사항은 명확합니다.

### ✍️ 비유: 설계도만 보고 집 짓는 '시공사(건설사)'

*   **Robust Planner (건축가 + 감리사):** "자, 5층 건물 설계도 검수 완료됐어. State에 올려놨으니까 시공사는 이거 보고 지어."
*   **Blog Writer (시공사):** 설계도(`blog_outline`)를 State에서 꺼내 읽고, **각 섹션별로 살(내용)을 붙여 완전한 글(Full Blog Post)을 만듦.**

### 🛠️ Blog Writer 에이전트 설계 명세서 (예상 구현)

```python
blog_writer = LlmAgent(
    name="BlogWriter",
    model="gemini-2.0-flash", # 창의적 글쓰기에는 flash나 pro 적절히 선택
    instruction="""
    당신은 전문 블로그 작가입니다.
    공용 상태(State)에서 'blog_outline' 키로 저장된 **검증 완료된 아웃라인**을 읽으세요.
    
    [작성 규칙]
    1. 아웃라인의 제목(Title)을 글의 제목으로 사용하세요.
    2. 서론(Introduction): 독자의 흥미를 끌고 글의 개요를 설명하세요.
    3. 본문(Sections): 아웃라인의 각 섹션 제목과 핵심 포인트를 바탕으로, **풍부한 예시, 비유, 데이터, 스토리텔링**을 곁들여 최소 3~5문장 이상의 깊이 있는 단락으로 확장하세요.
    4. 결론(Conclusion): 핵심 내용을 요약하고, 독자에게 액션(댓글, 공유, 구독 등)을 유도하는 마무리를 하세요.
    5. 톤앤매너: 친근하고 전문적인 '튜터' 말투(존댓말, 설명조)를 유지하세요.
    6. 마크다운(Markdown) 형식(arkdown) 문법(## 제목, **볼드**, 리스트 등)을 적극 활용해 가독성을 높이세요.
    
    [출력]
    완성된 블로그 글 전체를 **하나의 텍스트 블록**으로 출력하세요.
    별도의 설명이나 인사말 없이 본문만 출력합니다.
    """,
    output_key="final_blog_post" # 🎯 최종 결과물을 State에 'final_blog_post' 키로 저장!
)
```

> **💡 개념 돋보기: `output_key="final_blog_post"` — 파이프라인의 '최종 산출물'**
>
> *   플래너는 `blog_outline` (중간 산출물)
> *   라이터는 `final_blog_post` (최종 산출물)
> *   이렇게 **단계별로 키 이름을 다르게** 주면, State에는 `{ "blog_outline": "...", "final_blog_post": "..." }` 형태로 **히스토리가 쌓입니다.**
> *   나중에 디버깅할 때 "어? 아웃라인은 제대로 나왔는데 본문이 이상하네?" 하면 State만 보면 바로 원인 파악 가능합니다. **데이터 계보(Data Lineage)**가 자연스럽게 생기는 셈이죠.

## 5. 전체 흐름 정리: '견고한 블로그 작성 파이프라인' 탄생

이제 우리가 만든 **메인 에이전트(루트 에이전트)**의 `sub_agents` 리스트는 이렇게 구성됩니다.

```mermaid
graph TD
    Root[Root Agent: BlogMaster] --> RobustPlanner[LoopAgent: RobustBlogPlanner]
    RobustPlanner --> Planner[LlmAgent: BlogOutlinePlanner]
    RobustPlanner --> Checker[LlmAgent: OutlineValidationChecker]
    Planner -->|작성/수정| State[(Shared State\nblog_outline)]
    Checker -->|검사\nokay/retry| State
    Checker -.->|retry 시| Planner
    Checker -->|okay 시| Writer[LlmAgent: BlogWriter]
    Writer -->|최종 글 작성| State[(Shared State\nfinal_blog_post)]
```

1.  **사용자 요청** → Root Agent 수신
2.  **RobustBlogPlanner (Loop) 가동**
    *   Planner가 아웃라인 초안 작성 → State 저장
    *   Checker가 검사 → `retry`면 Planner에게 피드백 주고 재시도 (최대 3회)
    *   `okay`면 루프 종료, **검증된 아웃라인 State에 확정**
3.  **BlogWriter 가동**
    *   State의 확정된 아웃라인 읽기
    *   본문 전체 작성 → `final_blog_post` 키로 State 저장
4.  **Root Agent** → 사용자에게 `final_blog_post` 전달하며 종료

## 6. 마무리하며: "왜 이렇게 복잡하게 만드나?" — 엔지니어링의 본질

여러분, 혹시 **"그냥 프롬프트 한 번에 '블로그 써줘' 하면 되지 않나?"**라는 생각 안 드셨나요?

물론 간단한 건 됩니다. 하지만 **'프로덕션 레벨(실제 서비스 수준)'**로 가면 이야기가 달라집니다.
*   **일관성:** 매번 다른 구조, 다른 톤앤매너 → 브랜드 신뢰도 하락.
*   **완성도:** 섹션 빠짐, 결론 없음 → 독자 이탈.
*   **디버깅:** 어디가 문제인지 모름 → 수정 불가.

이번 챕터에서 배운 **`output_key`(자동 전달), `LoopAgent`(자동 검증/재시도), 역할 분리(Planner/Checker/Writer)**는 **"LLM의 환각과 실수를 시스템 차원에서 방어하고, 안정적인 품질을 보장하는 소프트웨어 공학 기법"**입니다.

이제 여러분은 단순한 '프롬프트 작성자'가 아니라, **'에이전트 시스템 아키텍트'**의 첫걸음을 뗀 것입니다. 다음 챕터에서는 이 파이프라인을 실제 코드로 돌려보고, Streamlit 같은 UI에 붙여 **'나만의 AI 블로그 작성 서비스'**로 런칭하는 방법을 알아보겠습니다. 기대하셔도 좋습니다! 🚀
