# Chapter 3. Session (세션): 에이전트와 환경을 연결하기 — 에이전트 인스턴스를 환경에서 구동하고 이벤트 스트리밍하기

자, 앞서 우리는 **'에이전트(Agent)'**라는 **'똑똑한 두뇌(브레인)'**를 만들었고, **'환경(Environment)'**이라는 **'튼튼한 손발(핸드)'**을 준비했습니다. 이제 이 둘을 어떻게 연결해서 실제 일을 시킬까요? 그냥 "너, 저기 가서 일해"라고 말로만 시키면 안 됩니다. 두뇌가 손발에게 구체적인 지시를 내리고, 손발이 작업한 결과를 다시 두뇌에게 실시간으로 보고하는 **'통로'**가 필요하죠. 바로 이 통로의 이름이 **'세션(Session)'**입니다.

이번 챕터에서는 이 세션이 도대체 무엇인지, 왜 우리가 세션이라는 개념을 따로 떼어내서 관리해야 하는지, 그리고 이 세션 덕분에 우리가 밤새 서버를 켜두지 않아도 되고, 보안 걱정 없이 안심하고 에이전트를 쓸 수 있게 되는 마법 같은 원리까지 아주 낱낱이 파헤쳐 보겠습니다.

## 1. 세션: 두뇌와 손발을 잇는 '작업 현장'이자 '라이브 중계선'

상상해 보세요. 여러분이 **'사장님(사용자)'**이고, **'유능한 매니저(에이전트/두뇌)'**를 고용했다고 칩시다. 그리고 매니저가 실제 일을 처리할 **'현장 사무실(환경/손발)'**도 마련해 주었습니다. 그런데 매니저가 본사(클라우드)에 있고, 현장 사무실은 별도의 건물에 있다면? 사장님인 여러분은 지금 현장에서 무슨 일이 벌어지고 있는지 알 길이 없습니다. 매니저가 "다 했어요"라고만 말하고 끝내면, 중간에 무슨 일을 했는지, 에러는 없었는지, 지금은 어느 단계인지 알 수 없겠죠.

> **💡 개념 돋보기: 세션(Session)이란?**
> **세션은 '에이전트 인스턴스가 환경 내에서 구동되는 구체적인 실행 단위'이자, '사용자와 에이전트/환경 사이에서 오가는 모든 이벤트(생각, 도구 호출, 결과, 최종 답변)를 실시간으로 스트리밍해 주는 양방향 통신 채널'입니다.**
> 쉽게 말해, **"지금부터 이 매니저(에이전트)가 저 현장(환경)에서 이 작업(태스크)을 수행하는 하나의 완결된 작업 단위(세션)"**를 의미합니다. 세션이 시작되면 에이전트는 환경에 들어가서 살림을 차리고(인스턴스 스핀 업), 일을 시작하며, 그 모든 과정을 사용자에게 생중계(이벤트 스트리밍)합니다.

### 세션의 3가지 핵심 역할

세션은 단순히 '연결'만 하는 것이 아니라, 다음 세 가지 아주 중요한 책임을 집니다.

#### ① 인스턴스화(Instantiation): "매니저를 현장에 파견 보낸다"
코드상에서 `session = Session(agent=my_agent, environment=my_env)` 같은 식으로 세션을 생성하는 순간, **추상적으로만 존재하던 에이전트 정의(클래스/설정)가 실제 메모리 위에 올라가는 살아있는 '인스턴스(Instance)'가 되어 환경 속에 입장**합니다. 마치 게임에서 캐릭터를 선택하고 '게임 시작'을 눌러 맵 위에 내 캐릭터가 소환되는 것과 똑같습니다. 세션이 없다면 에이전트는 설계도에 불과하고, 환경은 빈 건물에 불과합니다.

#### ② 이벤트 스트리밍(Event Streaming): "현장 상황을 실시간 중계한다"
이게 정말 중요합니다. 에이전트가 환경에서 일을 할 때(생각하고 -> 툴 쓰고 -> 결과 보고 -> 다시 생각하고), 그 **모든 중간 과정(이벤트)들이 세션을 타고 사용자(또는 프론트엔드 UI)에게 실시간으로 흘러옵니다.**
*   `Event: Agent Thinking...` (에이전트 생각 중)
*   `Event: Tool Call - read_logs()` (로그 읽기 도구 호출)
*   `Event: Tool Result - "Error 500 at line 102"` (도구 결과 반환)
*   `Event: Agent Thinking...` (결과 보고 다시 생각)
*   `Event: Final Answer` (최종 답변)

이 스트리밍 덕분에 우리는 스트림릿(Streamlit) 같은 UI에서 **타이핑하듯 나타나는 답변**을 볼 수 있고, "아, 지금 로그를 뒤지고 있구나", "이제 데이터베이스를 쿼리하는구나" 하며 진행 상황을 육안으로 확인할 수 있습니다. 세션이 이 파이프 역할을 안 해주면, 사용자는 그저 멍하니 돌고 있는 로딩 스피너만 쳐다봐야 합니다.

#### ③ 생명주기 관리(Lifecycle Management): "작업의 시작과 끝을 책임진다"
세션은 시작(`create`/`start`)되고, 작업이 돌고(`run`/`stream`), 끝납니다(`close`/`terminate`). 세션이 끝나면 환경에 할당됐던 리소스(컨테이너, 메모리, 네트워크 연결 등)를 깔끔하게 반납합니다. 이건 나중에 '비용 절감'과 '신뢰성' 파트에서 더 깊게 다룰 아주 핵심적인 포인트입니다.

## 2. 실습 코드로 보는 세션의 탄생: `agent.py` 안에서

영상 속 실습 코드(`agent.py` → `agent_complete.py` 복사 과정)를 보며 세션이 어떻게 코드 레벨에서 구성되는지 눈여겨봅시다. 강연자는 "이제 세션으로 에이전트와 환경을 묶자"라고 하며 코드를 채워 넣습니다.

```python
# agent_complete.py 의 핵심 부분 발췌 (이해하기 쉽게 재구성)

from claude_agent_sdk import Agent, Environment, Session, StreamlitUI # 가상의 SDK 임포트

# 1. 두뇌 정의 (앞서 배운 Agent)
my_agent = Agent(
    model="claude-3-5-sonnet",
    system_prompt="당신은 사고 대응 전문가입니다...",
    skills=[investigate_logs, check_deployments, query_metrics],
    mcp_servers=[github_mcp, datadog_mcp]
)

# 2. 손발 정의 (앞서 배운 Environment)
# 여기선 로컬 도커 컨테이너나 원격 샌드박스가 환경이 됨
my_environment = Environment(
    type="docker", 
    image="incident-response-env:latest",
    env_vars={"DATADOG_API_KEY": "..."} # 민감 정보는 환경 쪽에만!
)

# 3. 🌟 세션 생성 및 실행: 두뇌 + 손발 = 작업 단위(세션)
# 이 한 줄(또는 블록)이 바로 '마법'의 시작입니다.
session = Session(
    agent=my_agent,       # 이 세션에서 일할 두뇌
    environment=my_environment # 이 세션에서 쓸 손발/작업장
)

# 4. 사용자 요청(태스크)을 세션에 태워 실행 + 스트리밍
user_task = "새벽 3시에 알람 떴음: 결제 API 500 에러 급증. 원인 분석하고 조치 제안해줘."

# 세션.run() 또는 세션.stream() 호출 시 이벤트 제너레이터 반환
for event in session.stream(user_task):
    # 이 event 가 바로 실시간 중계 데이터!
    if event.type == "thinking":
        print(f"🤔 에이전트 생각: {event.content}")
    elif event.type == "tool_call":
        print(f"🛠️ 도구 호출: {event.tool_name}({event.args})")
    elif event.type == "tool_result":
        print(f"📥 도구 결과: {event.result}")
    elif event.type == "final_answer":
        print(f"✅ 최종 보고: {event.content}")
```

**여기서 놓치지 말아야 할 포인트:**
*   **`Session` 객체 생성 시점**에 비로소 "이 에이전트가 저 환경에서 일한다"는 **결합(Binding)**이 일어납니다.
*   **`session.stream(...)`** 메서드가 **제너레이터(Generator)**를 반환하며 `yield`를 통해 이벤트를 하나씩 뱉어냅니다. 이 덕분에 프론트엔드(Streamlit)는 `for event in session.stream(): st.write(event)` 같은 식으로 **블로킹 없이 실시간 UI 업데이트**가 가능해집니다.

> **💡 개념 돋보기: 왜 `run()`이 아니라 `stream()`인가?**
> 일반적인 함수 호출(`run`)은 일이 다 끝날 때까지 기다렸다가 결과만 돌려줍니다(동기식). 하지만 에이전트 작업은 몇 분, 몇 십 분이 걸릴 수도 있는 긴 여정입니다. `stream()`은 **'이벤트 스트림(Event Stream)'**을 반환하여, **작업이 진행되는 *도중*에도 중간중간 상태를 사용자에게 보여줄 수 있게 해줍니다.** 이게 바로 '체감 속도(Time to First Token)'를 빠르게 느끼게 해주는 비결이자, 사용자 경험(UX)의 핵심입니다.

## 3. 클로드 매니지드 에이전트(Claude Managed Agents)의 '신의 한 수': 서버 사이드 에이전트 루프 & 세션의 영속성

여기서 영상에서 강연자가 **"이게 진짜 중요한 디자인 결정이다"**라고 강조한 부분이 나옵니다. 바로 **에이전트 루프(Agent Loop)가 서버 사이드(클라우드 관리 인프라)에서 돌아간다**는 사실입니다. 이 말이 왜 세션과 연결되어 그렇게 중요할까요?

### 기존 방식(로컬/임베디드 루프)의 고통: "노트북을 닫으면 다 죽는다"

기존에 우리가 랭체인(LangChain), 오토젠(AutoGen), 크루에이아이(CrewAI) 등으로 로컬에서 에이전트 돌릴 때를 떠올려 보세요.
*   내 노트북(또는 내 서버)에서 파이썬 프로세스(`python agent.py`)가 **에이전트 루프(생각 → 도구 호출 → 결과 처리 → 다시 생각...)**를 직접 돌립니다.
*   도구 실행(환경)도 같은 프로세스 안이거나 같은 머신 안에서 일어납니다(강결합).

**이때 치명적인 문제들:**
1.  **내구성(Durability) 제로:** 내가 실수로 창을 닫거나(`Ctrl+C`), 노트북 덮개를 덮거나, 와이파이가 끊기거나, 배터리가 나가면? **그대로 프로세스 사망.** 지금까지 생각한 거, 진행 중이던 거 다 날아가고 처음부터 다시 해야 함.
2.  **확장성(Scaling) 악몽:** 동시 사용자 100명이 몰리면? 내 서버 100대 띄워야 함. 세션마다 파이썬 프로세스 하나씩 붙여야 하니 메모리/CPU 관리 지옥.
3.  **신뢰성(Reliability) 낮음:** 프로세스 중간에 OOM(Out of Memory) 터지거나 미처 잡지 못한 예외 터지면 세션 끝. 재시도 로직 내가 다 짜야 함.

### 클로드 매니지드 에이전트 방식: "세션은 클라우드에서 불사신으로 산다"

클로드 매니지드 에이전트에서는 **에이전트 루프(사고 회로)를 Anthropic의 관리형 인프라(Server-side)에서 돌립니다.** 사용자의 코드(클라이언트)는 단지 **`Session` 객체를 생성하고, 태스크를 던지고, 이벤트 스트림을 받아보기만** 하면 됩니다.

> **💡 개념 돋보기: 서버 사이드 에이전트 루프 (Server-side Agent Loop)**
> **에이전트의 '생각하기(LM 추론) → 도구 결정 → 도구 결과 수용 → 다시 생각하기'라는 핵심 루프가 사용자의 머신이 아닌, Anthropic의 고가용성/고확장성 클라우드 인프라에서 실행됨을 의미합니다.**
> 사용자(클라이언트)는 단지 **세션 ID**를 가지고 **"이 세션에 이 태스크 좀 넣어줘(`session.stream(task)`)"**라고 요청만 보내면 됩니다. 클라우드 측에서 알아서 에이전트 인스턴스를 깨우고, 환경을 붙여주고, 루프를 돌리고, 이벤트를 스트리밍으로 쏴줍니다.

**이게 세션 관점에서 주는 선물들:**

| 기능 | 로컬 루프 방식 | 클로드 매니지드 세션 방식 |
| :--- | :--- | :--- |
| **노트북 덮개 닫기 / 새로고침** | **세션 즉사(데이터 유실)** | **세션 생존!** 클라우드에서 계속 돌고 있음. 나중에 다시 `session_id`로 붙어서 이어보기 가능. |
| **장시간 작업 (수시간)** | SSH 세션 끊김, 타임아웃, 프로세스 킬 위험 | **무한 대기 가능.** 클라우드가 알아서 관리. |
| **장애 복구 (Resilience)** | 사용자가 직접 구현 (체크포인팅, 재시도) | **플랫폼 레벨 제공.** 인프라 단에서 자동 재시도, 페일오버. |
| **상태 저장 (State Persistence)** | 사용자가 DB/파일에 직렬화 저장 구현 | **자동 영속화.** 대화 이력, 툴 호출 이력, 중간 상태 자동 저장. |
| **비용/리소스** | 놀고 있어도 내 서버 리소스 점유 | **실행한 만큼만 과금(Serverless 느낌).** 유휴 시 리소스 반납. |

**비유로 정리하자면:**
*   **기존 방식:** 내가 **직접 운전기사(에이전트 루프)를 고용해서 내 차(내 서버/노트북)에 태워 현장(환경)으로 보냄**. 기사가 피곤해하면(에러), 차 고장 나면(크래시), 내가 다 책임져야 함. 내가 집에 가면(노트북 끔) 기사도 퇴근함.
*   **매니지드 세션 방식:** 나는 **'우버/택시 앱(세션 클라이언트)'만 켜고 "여기 기사(에이전트)랑 차(환경) 좀 보내줘"라고 호출(세션 생성)**. 기사는 **우버 본사(클라우드 인프라)** 소속 프로 기사라서, 내 폰 끄고 자도(**노트북 덮개 닫아도**) 기사는 목적지까지 안전하게 운전해서 **결과(이벤트 스트림)**를 앱으로 실시간 중계해 줌. 중간에 차 고장 나도(**인프라 장애**) 우버가 알아서 다른 차 붙여줌.

## 4. '분리(Decoupling)'의 위력: 손발(환경/도구)을 두뇌(에이전트 루프)에서 떼어내다

영상 후반부에서 강연자가 **"이전에는 에이전트 루프와 도구 실행이 한 박스(컨테이너/프로세스)에 꽉 묶여 있었다(Tightly Coupled)"**고 말하며, 이걸 분리했더니 **TTFT(Time To First Token, 첫 토큰 생성 시간)가 P95 기준으로 90% 이상 줄어들었다**고 자랑하는 대목이 나옵니다. 이건 세션 아키텍처 관점에서 **핵심적인 성능/보안 혁신**이니 꼭 이해하고 넘어가야 합니다.

### 기존: '만능 컨테이너' 방식 (Monolithic Agent Container)
```text
[ 내 세션 컨테이너 (단일 프로세스/박스) ]
┌─────────────────────────────────────────────┐
│  🧠 에이전트 루프 (LLM 추론, 프롬프트 조립)   │
│  🛠️ 도구 실행기 (Python, Bash, Docker CLI)   │
│  🔐 비밀 키/자격 증명 (AWS Key, DB PW...)    │
│  📁 파일 시스템 접근 (전체 루트 권한 가능)    │
└─────────────────────────────────────────────┘
```
*   **문제 1: 보안(자격 증명 누출)** — 에이전트가 "파일 읽기" 도구를 쓰라고 했는데, 프롬프트 인젝션 등으로 해커가 `/etc/shadow`나 `.env` 파일을 읽게 시키면? **한 방에 털림.** 두뇌가 손발(도구 실행기)을 직접 조종하니 손발이 가진 모든 권한(루트, 시크릿)을 두뇌가 다 가짐.
*   **문제 2: 지연 시간(Latency/TTFT)** — 세션 하나 뜰 때마다 **무거운 컨테이너(도구 실행 환경 포함)를 통째로 띄워야 함.** `docker run --rm -v ... python agent.py` 치고 컨테이너 부팅 + 파이썬 임포트 + 모델 로딩 + 루프 진입... 이거 다 합치면 **첫 토큰 나오기까지 수초~수십 초**. 사용자는 흰 화면만 봄.
*   **문제 3: 리소스 낭비** — 에이전트가 "생각만" 하고 있을 때(LLM 추론 대기 중)에도 무거운 도구 실행 환경(도커 데몬, 런타임, 라이브러리)이 메모리 차지하고 앉아 있음.

### 클로드 매니지드 방식: '두뇌(클라우드) ↔ 손발(샌드박스 환경)' 완전 분리 (Decoupled)

```text
[ 클라우드 매니지드 인프라 (Server-side) ]        [ 사용자/고객 환경 (Environment/Sandbox) ]
┌──────────────────────────────────┐      gRPC / HTTP API       ┌────────────────────────────┐
│  🧠 에이전트 루프 (경량, 무상태)    │ ◀──────────────────────▶ │  🛠️ 도구 실행 샌드박스        │
│  - 프롬프트 조립                  │   Tool Call / Result       │  - 격리된 컨테이너/VM       │
│  - LLM 추론 (초고속 GPU 클러스터) │   (구조화된 JSON)          │  - 최소 권한 (Least Priv)   │
│  - 상태 관리 (세션 영속성)         │                            │  - 자격 증명 없음!           │
└──────────────────────────────────┘                            └────────────────────────────┘
        ▲                                                                     ▲
        │                                                                     │
        │                     세션(Session) 이벤트 스트림                      │
        │                   (Server-Sent Events / WebSocket)                   │
        ▼                                                                     ▼
┌──────────────────────────────────┐
│  👤 사용자 클라이언트 (Streamlit)  │
└──────────────────────────────────┘
```

#### 이 분리가 주는 3가지 기적

**1. 🚀 TTFT(첫 토큰 지연 시간) 90% 단축 — "생각만 하는 건 초경량이라서"**
*   세션 시작 시 **무거운 도구 실행 환경(도커 이미지 풀, 런타임 초기화)을 켤 필요가 없습니다.**
*   클라우드 측 에이전트 루프 프로세스는 **이미 떠 있는 상태(Warm Pool)**이거나, 아주 가벼운 프로세스라 **밀리초 단위로 기동**합니다.
*   사용자가 `session.stream("일 해")` 치는 순간 → 클라우드 루프 즉시 가동 → **첫 `thinking` 이벤트 또는 첫 토큰이 즉시 스트리밍**됨.
*   도구 쓸 때만 원격 환경에 `Tool Call` RPC 날리면 됨. **도구 실행 시간만큼만 환경 리소스 쓰고 반납**하면 되니 비용도 절감.

**2. 🔒 보안/샌드박싱(Sandboxing) 완전 정복 — "두뇌는 열쇠를 모른다"**
*   **에이전트 루프(두뇌) 프로세스에는 어떤 API 키도, DB 비번도, SSH 키도 없습니다.** 그냥 "툴 호출해줘"라는 JSON 메시지만 보낼 뿐.
*   **실제 자격 증명과 민감 리소스는 '환경(손발/샌드박스)' 쪽에만 안전하게 격리되어 저장**됩니다. (예: 환경 변수 주입, 시크릿 매니저 마운트)
*   설령 에이전트가 해킹당해(프롬프트 인젝션) "시크릿 다 내놔"라고 해도, 두뇌 프로세스 메모리엔 시크릿이 **애초에 없으니 털릴 게 없습니다.**
*   손발(환경)도 **최소 권한 원칙(Least Privilege)**으로 런타임에 격리됨(예: gVisor, Firecracker, K8s PodSecurityPolicy). "로그 읽기" 툴만 등록돼 있으면 파일 시스템 다른 곳 절대 못 건드림.

**3. ⚖️ 유연한 환경 구성 — "두뇌는 하나, 손발은 여러 벌"**
*   같은 에이전트(두뇌)를 **개발용 로컬 도커 환경**, **스테이징용 쿠버네티스 잡**, **프로덕션용 방화벽 뒤 전용 VM** 등에 **세션 생성 시점에 동적으로 붙여서** 쓸 수 있습니다.
*   `Session(agent=my_agent, environment=prod_env)` vs `Session(agent=my_agent, environment=local_env)` 단 한 줄 차이.

## 5. 실습 시나리오 '새벽 3시 사고 대응'으로 보는 세션 라이프사이클

영상에서 강연자가 스트림릿 앱 켜고 "이제 사고 대응 에이전트 돌려보자"고 하는 그 장면, 바로 **세션의 탄생부터 죽음까지**를 보여주는 완벽한 예시입니다.

### 단계별 세션의 여정

#### 1️⃣ 세션 생성 (`Session(agent, env)`) — "출동 준비 완료"
*   사용자(당신)가 스트림릿 페이지 열거나 `session = Session(...)` 코드 실행.
*   클라우드 매니지드 인프라: **"세션 ID `sess_abc123` 발급. 에이전트 루프 프로세스 할당(또는 웜풀에서 차출). 환경 `incident-env`와 연결 파이프라인 구축."**
*   아직 아무 일도 안 함. 그냥 '대기 중' 상태.

#### 2️⃣ 태스크 투입 & 스트리밍 시작 (`session.stream("결제 API 500 에러...")`) — "현장 투입"
*   사용자 입력이 세션을 타고 클라우드 루프로 들어감.
*   **이벤트 1: `thinking`** — "음, 결제 API 500이면 일단 최근 배포 내역부터 봐야지." (스트림릿에 생각 말풍선 뜸)
*   **이벤트 2: `tool_call: check_recent_deploys()`** — 루프가 환경 쪽에 RPC 보냄.
*   **환경(손발) 작동:** 격리된 샌드박스에서 `kubectl rollout history` 또는 GitHub API 호출 실행. **여기서 자격 증명(GitHub Token) 사용됨. 두뇌는 모름.**
*   **이벤트 3: `tool_result: "v2.3.1 배포 후 에러율 급증"`** — 결과가 다시 루프로 돌아옴.
*   **이벤트 4: `thinking`** — "아, v2.3.1에 DB 커넥션 풀 크기 줄인 커밋 있네. 메트릭 확인해보자."
*   **이벤트 5: `tool_call: query_datadog_metrics("db.connections")`** — 또 환경에 RPC.
*   ... (루프 반복) ...
*   **이벤트 N: `final_answer`** — "원인: v2.3.1 배포 시 DB 커넥션 풀 100→10 축소. 조치: 롤백 또는 풀 사이즈 복구 PR 생성 권장."

#### 3️⃣ 사용자 개입 (Human-in-the-loop) — "세션은 살아있다"
*   강연자가 "이거 PR 만들어줘"라고 채팅 치면? **같은 세션 ID로 새 메시지 투입.**
*   세션은 **이전 대화 맥락(히스토리)을 그대로 가진 채** 이어서 루프 돌림. 새로운 세션 안 파도 됨.

#### 4️⃣ 세션 종료/일시정지 — "노트북 덮어도 됨"
*   작업 다 끝나고 브라우저 탭 닫음(`session.close()` 호출 또는 GC).
*   클라우드: "세션 `sess_abc123` 상태 영구 저장(DB). 환경 리소스(샌드박스 컨테이너) 종료/반납. 에이전트 루프 프로세스 웜풀로 반환 또는 종료."
*   **내일 출근해서 같은 세션 ID로 `session.resume()` 또는 새 세션에 이전 히스토리 넘기면** 바로 어제 그 상황부터 이어서 가능.

## 6. 요약하며: 세션, 에이전트, 환경의 '황금 삼각형' 정리

이번 챕터의 핵심은 **세션(Session)이 단순히 '연결고리'가 아니라, '에이전트(두뇌)'와 '환경(손발)'이라는 두 개의 분리된 컴포넌트를 하나의 **'실행 가능한 작업 단위(Unit of Work)'로 엮어주고, 그 작업의 전 과정을 사용자에게 **'실시간 스트림'으로 중계하며, 클라우드 네이티브하게 **'영속성/신뢰성/보안/확장성'을 모두 보장해 주는 총괄 매니저**라는 점입니다.

| 구성 요소 | 비유 | 핵심 책임 | 클로드 매니지드에서의 위치 |
| :--- | :--- | :--- | :--- |
| **Agent (에이전트)** | **🧠 두뇌 / 매니저** | 페르소나, 모델, 스킬, 프롬프트, 추론 로직 | **Server-side (Managed)** — 사용자 코드엔 정의만 있음. 실행은 클라우드에서. |
| **Environment (환경)** | **🛠️ 손발 / 현장 사무실** | 도구 실행, 파일 시스템, 네트워크, **자격 증명/시크릿 보관** | **Customer-side (Bring Your Own)** — 사용자 계정/클라우드/온프렘 어디든 가능. 격리된 샌드박스. |
| **Session (세션)** | **📞 작업 지시서 + 무전기 + 생중계 카메라** | 인스턴스화, 이벤트 스트리밍, 생명주기 관리, 상태 영속화 | **Control Plane (Managed)** — 클라우드가 세션 오케스트레이션 담당. 사용자는 `session.stream()`만 호출. |

> **💡 마지막 개념 돋보기: "세션 = 프로덕션 레디 에이전트의 최소 단위"**
> 프로토타입에서는 `while True: agent.step()` 로컬 루프로 충분합니다. 하지만 **'프로덕션(실제 서비스)'**으로 가려면 다음이 필수입니다:
> 1.  사용자 요청 들어올 때마다 **격리된 세션**으로 격리 실행 (멀티테넌시).
> 2.  네트워크 끊겨도 **세션 상태가 살아있음** (내구성).
> 3.  에이전트 해킹당해도 **시크릿 안 털림** (보안/분리).
> 4.  첫 응답까지 **1초 안 걸림** (지연 시간/TTFT).
> 5.  트래픽 몰려도 **자동 스케일아웃** (확장성).
>
> 이 모든 것을 **코드 한 줄(`Session(...)`) 변경 없이 인프라 레벨에서 해결해 주는 것**이 바로 클로드 매니지드 에이전트의 세션 아키텍처입니다. 이제 여러분은 `agent.py`에 `Session` 객체 넣고 `stream()` 돌리는 것만으로, 엔터프라이즈급 인시던트 대응 에이전트를 **'배포'가 아닌 '실행'**만으로 가질 수 있게 된 겁니다.
