# 챕터 11. 핸즈온 워크숍: 인시던트 대응 에이전트 구축 — 내 손으로 '야간 당직 요정' 만들기

자, 드디어 이론 수업은 끝났습니다. 이제 진짜 재미있는 시간, **'핸즈온 워크숍(Hands-on Workshop)'** 시간이에요. 지금까지 "에이전트가 이렇게 똑똑하다", "이렇게 안전하다"는 얘기만 들었는데, 오늘은 우리가 직접 **'새벽 3시에 날 깨우지 않고 서버를 고쳐주는 나만의 AI 당직 요정'**을 만들어 볼 거예요.

이번 챕터는 강연자분이 라이브 코딩으로 보여주신 **'인시던트 대응 에이전트(Incident Response Agent)'**를 단계별로 뜯어보며, "아, 이게 그 원리였구나!" 하고 무릎을 칠 수 있도록 아주 친절하고 상세하게 안내해 드릴게요. 노트북 켤 준비 되셨죠? 자, 시작합니다!

## 1. 왜 하필 '인시던트 대응'인가? — 개발자의 악몽, 새벽 3시의 전화

강연자분이 워크숍을 시작하며 제일 먼저 꺼낸 이야기가 있어요. 바로 **소프트웨어 엔지니어의 '악몽'** 이야기죠.

> "여러분이 소프트웨어 엔지니어라면, 새벽 2시나 3시, 심지어 휴가 중인데도 전화가 울려서 잠이 깨는 경험을 해봤을 거예요. 온콜(On-call, 당직) 근무 중이니까 서버가 죽거나 서비스에 장애가 생기면 **즉시** 대응해야 하거든요. 이건 엔지니어 인생에서 가장 고통스러운 부분 중 하나죠."

상상해 보세요. 따뜻한 이불 속에서 꿈나라 여행 중인데, 핸드폰이 요란하게 울려요. 화면을 보니 **[긴급] 서버 다운 - CPU 100%**. 눈 비비며 노트북 열고, 대시보드 켜고, 로그(`logs`) 뒤지고, 메트릭(`metrics`) 그래프 보고, 최근 배포(`deployments`) 내역 뒤지면서 "대체 무슨 일이지?" 하고 머리를 싸매는 거죠. 커피 마시며 새벽을 새우는 그 장면, 바로 **'인시던트 대응(Incident Response)'**의 현실입니다.

이번 워크숍의 목표는 이 **고통스러운 '사람의 새벽 노동'을 'AI 에이전트'에게 떠넘기는 것**입니다. 

> ### 💡 개념 돋보기: 인시던트 대응(Incident Response)이란?
> > **일상 비유: 병원 응급실 당직 의사**
> > 서비스가 '환자'라면, 인시던트는 '응급 환자'입니다. 서버가 다운되거나 에러율이 치솟는 건 환자가 심정지 온 것과 같아요. 온콜 엔지니어는 **응급실 당직 의사**예요. 밤새 대기하다가 환자(장애) 생기면 바로 달려가 진단(로그/메트릭 분석)하고 처치(재배포/재시작/롤백)해야 하죠. 이번에 만들 에이전트는 **'초능력 인턴 의사'**를 고용하는 셈입니다. 의사가 자고 있어도 인턴이 1차 진단하고, 간단한 처치는 알아서 하고, 큰일 나면 의사에게 "선생님, 여기 좀 보세요"라고 요약 보고만 올려주는 거죠.

## 2. 워크숍의 재료 준비: '에이전트 키트' 다운로드받기

강연자분이 "자, 이제 노트북 여세요"라고 하시며 띄운 화면, 바로 **GitHub 저장소(Repository)** 주소예요. 우리가 만들 에이전트의 **설계도와 재료가 담긴 상자**라고 보시면 돼요.

### 2-1. 저장소 복제하기 (Git Clone)
터미널(명령창)을 열고 아래 명령어를 칩니다. 이건 **"깃허브 창고에서 '에이전트 만들기 키트' 상자 하나를 내 컴퓨터로 통째로 복사해 와"**라는 뜻이에요.

```bash
git clone [강연자분이_알려준_URL_주소]
```

### 2-2. 작업 방으로 들어가기 (cd 명령어)
복사가 끝났으면 그 폴더 안으로 들어가야죠. 강연자분 말씀대로 `Ship Your First Manage Agent` 폴더로 이동합니다.

```bash
cd Ship\ Your\ First\ Manage\ Agent
# (윈도우라면 백슬래시 \ 또는 따옴표로 감싸서 "Ship Your First Manage Agent")
```

> ### 💡 개념 돋보기: 터미널 명령어 `cd`와 `git clone`
> > **일상 비유: 이사와 현관문 열기**
> > - **`git clone`**: 인터넷 쇼핑몰에서 'DIY 가구 세트'를 시켜서 **현관 앞까지 배송받는 것**. (내 로컬 컴퓨터에 폴더가 생김)
> > - **`cd` (Change Directory)**: 배송 온 박스 앞에서 **"자, 이제 박스 뜯고 조립하러 방으로 들어갈게"** 하며 **작업 방(프로젝트 폴더) 안으로 들어가는 것**.
> > - **`ls` (List)**: 방 안에 들어와서 **"뭐가 들었나 보자"** 하고 **짐 목록 확인하는 것**.

### 2-3. 파이썬 가상환경 만들기 — '나만의 깨끗한 작업실' 분리하기
강연자분이 맥(Mac) 기준으로 두 줄, 윈도우용 한 줄을 보여주셨어요. 이건 **파이썬 가상환경(Virtual Environment)**을 만드는 과정이에요.

**맥/리눅스:**
```bash
python3 -m venv venv
source venv/bin/activate
```
**윈도우 (파워셸):**
```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
```

> ### 💡 개념 돋보기: 왜 가상환경(`venv`)을 만들까요?
> > **일상 비유: '공용 주방' vs '내 전용 주방'**
> > 파이썬을 그냥 전역(Global)으로 쓰면 **'공용 주방'**에서 요리하는 꼴이에요. 프로젝트 A는 '소금 1kg'이 필요한데, 프로젝트 B가 소금을 다 써버려서 '소금 10g'만 남겨뒀다면? 프로젝트 A는 망하겠죠. 라이브러리 버전 충돌이 바로 이겁니다.
> > **`venv`는 '내 전용 주방'을 하나 뚝딱 지어주는 마법**이에요. 이 방 안에는 내가 원하는 버전의 소금(라이브러리), 후추(패키지)만 딱 넣어둘 수 있어요. 다른 프로젝트랑 절대 안 섞이죠. `activate`는 그 전용 주방 **앞치마를 두르는 행위**예요. 프롬프트 앞에 `(venv)`라고 뜨면 "아, 지금 내 전용 주방에서 요리 중이구나" 알 수 있어요.

### 2-4. 필요 재료 설치하기 (`requirements.txt`)
앞치마 둘렀으면 이제 레시피에 적힌 재료를 사 와야죠. `requirements.txt`가 바로 **'장바구니 리스트'**예요.

```bash
pip install -r requirements.txt
```

이 명령어 한 방이면 `requests`, `anthropic`, `streamlit` 등 이번 워크숍에 필요한 모든 파이썬 패키지가 내 전용 주방(`venv`)에 착착 깔립니다.

### 2-5. 비밀 열쇠 넣기 (`.env` 파일과 API Key)
강연자분이 "QR 코드로 받은 무료 크레딧(Anthropic API Key)을 `.env` 파일에 넣으라"고 하셨어요. 이건 **'에이전트의 뇌(클로드 모델)를 쓰기 위한 출입증'**이에요.

프로젝트 폴더 최상위에 `.env` 파일을 만들고(없으면 새로 만드세요), 아래처럼 적어주세요.

```text
ANTHROPIC_API_KEY=sk-ant-api03-XXXXXXXXXXXXXXXXXXXXXXXX
```
*(XXXXX 부분에 본인 키를 넣으세요. 절대 깃허브에 올리면 안 돼요!)*

> ### 💡 개념 돋보기: API Key와 `.env` 파일
> > **일상 비유: 고급 레스토랑 '멤버십 카드'와 '지갑'**
> > - **API Key**: 클로드라는 **초특급 셰프를 내 주방에 불러쓰기 위한 '멤버십 카드'**예요. 이 카드 없으면 셰프가 요리(추론) 안 해줘요. 돈(크레딧)도 이 카드로 차감되죠.
> > - **`.env` 파일**: 이 중요한 카드를 **코드 속에 하드코딩(박제)하지 않고, 안전하게 보관하는 '내 지갑'**이에요. 코드(`app.py`)에서는 `os.getenv("ANTHROPIC_API_KEY")`처럼 "지갑에서 카드 꺼내 와"라고만 시키죠. 이렇게 해야 코드를 남에게 보여줄 때(깃허브 푸시) 카드 번호가 유출 안 돼요. **절대 공개 장소에 지갑 잃어버리지 마세요!**

### 2-6. 앱 실행! (`streamlit run app.py`)
자, 모든 준비 끝났어요. 이제 **'서빙 로봇(Streamlit)'**을 호출해 우리 에이전트 웹 페이지를 띄워볼까요?

## 3. 코드 뜯어보기: `agent.py` — 에이전트의 '뇌'와 '손' 설계도

강연자분이 화면을 좌우로 나누셨어요. 왼쪽은 **`agent.py` (우리가 채워갈 미완성 파일)**, 오른쪽은 **`agent_complete.py` (정답지)**. 우리는 정답지에서 조각을 하나씩 떼어다 왼쪽에 붙여넣으며 **에이전트가 어떻게 구성되는지 원리**를 배울 거예요.

자, 첫 번째 조각: **`Agent` 클래스 정의** 부분입니다.

```python
# agent.py (완성본에서 가져온 핵심 조각)
from claude_agent_sdk import Agent, Environment, Session, Skill, McpServer

# 1. 에이전트 정의: "너는 이런 성격이고, 이런 도구를 쓸 수 있어"
incident_agent = Agent(
    name="Incident Responder",           # 이름: 인시던트 해결사
    model="claude-3-5-sonnet-20241022",  # 뇌: 클로드 3.5 소네트 (최신 모델)
    instructions="""당신은 사이트 신뢰성 엔지니어(SRE)입니다. 
    인시던트가 발생하면 로그, 메트릭, 배포 내역을 조사하여 근본 원인을 찾고 해결책을 제안하세요.""",
    skills=[Skill(name="investigate_logs"), Skill(name="check_metrics"), Skill(name="review_deployments")],
    mcp_servers=[McpServer(name="observability")] # 관측 도구 서버 연결
)
```

이 코드 한 덩어리가 바로 **에이전트의 '페르소나(Persona)'와 '능력(Capabilities)'을 정의하는 신분증**이에요. 강연자분이 **"에이전트는 페르소나와 역량을 정의하는 곳이다. 모델, MCP 서버, 스킬, 에이전트 루프에서 활용할 다양한 컴포넌트..."**라고 설명하신 게 바로 이 부분이죠.

> ### 💡 개념 돋보기: `Agent` 클래스 — '슈퍼 인턴 채용 공고' 내기
> > **일상 비유: 구인 공고문 작성하기**
> > 내가 **"새벽 3시에 일할 슈퍼 인턴 구함"**이라고 공고 내는 장면이에요. 각 항목이 무슨 뜻인지 볼까요?
> > - **`name="Incident Responder"`**: **이름표**. "내 이름은 인시던트 해결사야."
> > - **`model="claude-3-5-sonnet..."`**: **뇌 스펙**. "머리는 클로드 3.5 소네트(최상위 모델) 쓸게요. 비싸지만 제일 똑똑하니까."
> > - **`instructions="..."`**: **업무 매뉴얼(Job Description)**. "너는 SRE(사이트 신뢰성 엔지니어야). 장애 나면 로그 보고, 메트릭 보고, 배포 기록 봐서 원인 찾고 고쳐. 말투는 전문적으로."
> > - **`skills=[...]`**: **자격증/특기**. "로그 조사하기(`investigate_logs`), 메트릭 보기(`check_metrics`), 배포 리뷰(`review_deployments`) 이 세 가지는 능숙하게 할 줄 알아야 해." (나중에 이 스킬들이 실제 파이썬 함수로 구현돼요.)
> > - **`mcp_servers=[McpServer(name="observability")]`**: **외부 도구 창고 열쇠**. "관측 도구(옵저버빌리티) 창고(`observability` 서버) 열쇠 줄게. 거기서 그라파나, 데이터독, 프로메테우스 같은 도구 꺼내 써." **MCP(Model Context Protocol)**가 바로 이 **'표준화된 도구 창고 인터페이스'**예요. "어떤 창고든 이 열쇠만 있으면 문 열 수 있게 해놓은 표준 규격"이죠.

## 4. `Environment` (환경) — 에이전트의 '손발'이 움직일 공간

에이전트(뇌)만 있으면 안 돼요. 뇌가 "로그 봐!"라고 명령해도 **실제로 로그 파일이 있는 서버, 컨테이너, 파일 시스템** 같은 **'물리적 공간'**이 필요하잖아요. 그게 **`Environment`**예요.

```python
# 2. 환경 정의: 에이전트가 실제 행동할 '컨테이너/샌드박스'
incident_env = Environment(
    name="incident-env",
    image="ghcr.io/anthropics/incident-response-env:latest", # 도커 이미지: 미리 세팅된 작업실
    # 이 안에는 kubectl, cli 도구, 로그 접근 권한 등이 다 깔려 있음
)
```

강연자분이 **"이전 것(에이전트)은 뇌이고, 이건 손(Environment)이다. 에이전트가 생각할 공간과 컨테이너를 줘서 대신 행동하게 하는 것"**이라고 하셨죠.

> ### 💡 개념 돋보기: `Environment` — '격리된 전용 작업실(샌드박스)'
> > **일상 비유: '폭발 위험 있는 실험실' vs '일반 사무실'**
> > 에이전트가 `kubectl delete pod` 같은 위험한 명령어를 실행할 수 있어요. 이걸 내 로컬 컴퓨터(내 노트북)에서 직접 돌리면? **내 컴퓨터가 망가져요.** 그래서 **도커 컨테이너라는 '격리된 실험실'**을 하나 빌려주는 거예요.
> > - **`image="..."`**: **"이 실험실엔 이미 공구(kubectl, aws cli, jq, curl)와 위험 물질(프로덕션 클러스터 접근 권한) 다 갖다 놨다"**는 뜻. `ghcr.io/...`는 도커 허브 같은 창고 주소예요.
> > - 이 환경 안에서 에이전트가 마음껏 `bash` 명령어 치고, 파일 지지고 볶아도 **내 노트북은 안전**해요. 이게 바로 강연자분이 강조한 **'뇌(에이전트)와 손(환경)의 분리(Decoupling)'**의 핵심 효과 중 하나 — **샌드박싱(Sandboxing, 격리)을 통한 보안**이죠.

## 5. `Session` (세션) — 뇌와 손을 잇는 '통신선'

뇌(에이전트)도 있고, 손(환경)도 있는데, 이 둘이 **어떤 작업 건으로 연결되어 있는지**, **대화 기록은 누가 기억하는지** 관리하는 게 **`Session`**이에요.

```python
# 3. 세션 생성: 에이전트 + 환경 = 실제 작동하는 '작업 단위'
session = Session(
    agent=incident_agent,
    environment=incident_env,
    # user_id="user-123" # 누가 시켰는지 식별자도 넣을 수 있음
)
```

강연자분 말씀: **"세션은 에이전트와 환경을 엮는 방식이다. 단일 세션은 환경 위에 뜬 에이전트 인스턴스를 가지며, 둘을 연결해 이벤트를 사용자에게 스트리밍하고 인간을 대신해 행동하게 한다."**

> ### 💡 개념 돋보기: `Session` — '업무 지시서 & 통화 연결'
> > **일상 비유: 콜센터 '상담 세션'**
> > - 고객(나)이 전화를 걸면 -> **세션 시작**.
> > - 상담원(에이전트 뇌)이 앉아 있고, 옆엔 전산 시스템(환경 손)이 있음.
> > - "고객님, 몇 번 문제로 전화하셨죠?" -> **컨텍스트(대화 기록) 유지**.
> > - 상담원이 전산 조회하고, 결과 말하고, 고객이 "아 네" 하면 -> **이벤트 스트리밍(실시간 응답)**.
> > - 통화 끊으면 -> **세션 종료**. (하지만 기록은 남음)
> > 
> > **클로드 매니지드 에이전트(Claude Managed Agents)의 마법:**
> > 강연자분이 **"클로드 매니지드 에이전트는 에이전트 루프가 서버 사이드에서 돈다"**고 하셨죠? 이 말이 무슨 뜻이냐면...
> > 
> > **일상 비유: '내 노트북에서 돌리는 로컬 상담원' vs '클라우드 콜센터 정규직 상담원'**
> > - **로컬(프로토타입)**: 내가 노트북 켜놓고 `python agent.py` 돌려야 함. 나 노트북 덮으면(잠들면) 상담원도 퇴근함. 내 와이파이 끊기면 상담원도 멈춤. **내구성(Durability), 신뢰성(Reliability) 내 책임.** -> **프로덕션 가기엔 너무 약함.**
> > - **클로드 매니지드(Server-side Loop)**: **"상담원을 우리(앤트로픽) 클라우드 데이터센터에 정규직으로 고용해놨음."** 내 노트북 덮어도, 브라우저 껐어도, 와이파이 끊겨도 **서버 쪽에서 상담원이 계속 일함**. 세션 상태(대화 기록, 환경 상태) 다 서버가 기억하고 보관해줌. **내가 안 챙겨도 되는 것들: 호스팅, 스케일링, 내구성, 신뢰성, 상태 관리.** -> **프로덕션 레디(Production Ready) 바로 가능!**
> > 
> > 이거 진짜 **혁신적**인 거예요. 예전엔 에이전트 루프(생각-행동-관찰 반복)를 내 코드(`while True: ...`)로 짜서 내 서버에서 돌려야 했거든요. 그걸 **완전히 서버 쪽으로 위임(Offload)**해버린 거죠.

## 6. 핵심 설계 철학: '뇌(루프)'와 '손(도구 실행)'의 분리 — 왜 이게 대박인가?

강연자분이 워크숍 들어가기 직전, **가장 중요하게 설명하신 부분**이에요. **"이전엔 에이전트 루프와 도구 실행이 한 박스(컨테이너)에 꽉 묶여 있었다(Strongly Coupled). 근데 우리는 이걸 떼어냈다(Decoupled)."**

### 6-1. 과거 방식: '뇌와 손이 한 몸' (Coupled Architecture)
> **일상 비유: '만능 해결사 1인 기업'**
> 사장(에이전트 루프)도 하고, 현장 작업(도구 실행)도 자기가 직접 다 함.
> - 장점: 지시 내리고 바로 행동하니까 빠름(지연 시간 낮음). 파일 시스템 바로 접근 가능.
> - 단점:
>   1. **보안 구멍**: 사장이 현장 나갈 때 **금고 열쇠(자격 증명, Credentials)**를 목에 걸고 나감. 현장에서 사고 치면 금고 털림.
>   2. **무거운 몸집**: 사장이 일하려면 **'사장실+공장' 합친 거대한 컨테이너**를 매 세션마다 띄워야 함. 컨테이너 뜨는 데 몇 초 걸림 -> **첫 토큰 시간(TTFT, Time To First Token) 느림**.
>   3. **확장성 꽝**: 사장이 한 명인데 일이 몰리면? 사장 복제하려면 거대한 공장째로 복제해야 함.

### 6-2. 클로드 매니지드 방식: '뇌는 본사, 손은 현장' (Decoupled Architecture)
> **일상 비유: '본사 전략가(뇌) + 현장 전문 기사단(손/환경)'**
> - **본사(서버 사이드 에이전트 루프)**: "상황 분석해. 다음엔 저 기사한테 '로그 뽑아와' 시켜." **생각만 함. 자격 증명 모름. 컨테이너 안 띄움.** 가볍고 빠름.
> - **현장(Environment/컨테이너)**: 기사들이 대기 중. 본사에서 "로그 뽑아와" 메시지 받으면 **자기 권한(샌드박스 안에서만 유효한 키)**으로 `kubectl logs` 실행하고 결과만 본사로 던져줌.
> - **통신**: 표준 프로토콜(MCP 등)로 주고받음.

> ### 💡 개념 돋보기: 디커플링(Decoupling)이 가져온 3가지 기적
> > 강연자분이 실제 측정 수치까지 말씀해주셨어요. **"P95 지연 시간 기준 TTFT(첫 토큰 시간) 90% 이상 단축"**
> > 
> > | 지표 | 과거 (Coupled) | 현재 (Decoupled) | 비유 설명 |
> > | :--- | :--- | :--- | :--- |
> > | **보안 (Security)** | 약함 (에이전트가 전체 권한 가짐) | **강력함 (샌드박스 격리, 자격 증명 암호화)** | 사장이 금고 열쇠 안 갖고 다님. 기사는 자기 방 열쇠만 가짐. |
> > | **지연 시간 (Latency/TTFT)** | 느림 (컨테이너 기동 대기) | **초고속 (90%↓, 루프만 돌면 됨)** | 본사 전략가는 몸만 오면 바로 생각 시작. 공장 안 지어줘도 됨. |
> > | **확장성/신뢰성** | 직접 구현해야 함 | **자동 관리 (서버 사이드)** | 기사 더 필요하면 본사가 자동 호출. 사장 아프면 본사에서 다른 전략가 투입. |
> > 
> > **이게 바로 "프로토타입을 프로덕션으로" 넘기는 마법의 열쇠**예요. 내 노트북에서 `streamlit run`으로 돌리던 장난감이, 코드 한 줄 안 고치고 **엔터프라이즈급 보안과 안정성**을 갖춘 서비스가 되는 거죠.

## 7. 실전 시뮬레이션: 인시던트 발생! 에이전트 작동 확인

자, 이제 `streamlit run app.py`로 띄운 웹 페이지로 가볼까요? 강연자분이 **"여기서 우리는 에이전트 상호작용을 시뮬레이션할 거다. 인시던트가 하나 터질 건데..."**라고 하시며 채팅창에 무언가 입력하셨을 거예요.

아마 이런 메시지였을 겁니다.

> **User:** `[P1-Critical] 결제 서비스 지연 시간 급증 (p99 > 5s). 에러율 12%. 즉시 조사 바람.`

우리가 만든 `incident_agent` 세션에게 이 메시지를 던지면, **서버 사이드 에이전트 루프가 돌기 시작**해요.

1.  **생각(Thought)**: "음, 결제 서비스 느리네. 내 매뉴얼(instructions)엔 로그, 메트릭, 배포 보라고 했지. 일단 스킬 `check_metrics` 써서 CPU/메모리 봐야겠다."
2.  **행동(Action - Tool Use)**: `check_metrics` 스킬 호출 -> **환경(Environment)** 안에서 `promql` 쿼리 날림.
3.  **관찰(Observation)**: 환경이 결과 돌려줌 -> "CPU 95%, 메모리 90%, 최근 배포 v2.3.1 이후 급증."
4.  **생각**: "아, 배포 직후네? `review_deployments`로 v2.3.1 내용 봐야지."
5.  **행동**: `review_deployments` 호출 -> 환경에서 `git log` 또는 ArgoCD API 조회.
6.  **관찰**: "v2.3.1에서 DB 커넥션 풀 사이즈 10 -> 100으로 변경됨. DB 연결 폭주로 보임."
7.  **최종 답변 생성**: 사용자(나)에게 **"근본 원인: v2.3.1 배포에서 DB 커넥션 풀 과다 설정. 해결책: 풀 사이즈 롤백 또는 20으로 조정. 롤백 원하시면 `kubectl rollout undo` 실행하겠습니다."** 라고 보고.

이 모든 과정이 **내 노트북이 아니라 클라우드 서버에서, 내 브라우저만 켜져 있으면 계속** 돌아가는 거예요. 내가 화장실 다녀와도, 노트북 덮어도 **세션은 살아있음**.

## 8. 마무리하며: 여러분은 이제 '에이전트 아키텍트'입니다

이번 챕터에서 우리는 정말 많은 걸 했어요.

1.  **문제 정의**: 새벽 3시 온콜의 고통 -> **자동화 대상 구체화**.
2.  **환경 세팅**: `git clone` -> `venv` -> `pip install` -> `API Key` -> `streamlit run`. **로컬 개발 환경 구축의 정석**.
3.  **코드 이해 (핵심 3요소)**:
    *   **`Agent`**: 뇌(모델) + 성격(Instruction) + 자격증(Skills) + 도구창고 열쇠(MCP).
    *   **`Environment`**: 손(컨테이너/샌드박스) + 공구(Docker Image) + 권한 격리.
    *   **`Session`**: 뇌와 손을 잇는 통신선 + 상태 기억 + 서버 사이드 영속성.
4.  **아키텍처 통찰**: **뇌-손 분리(Decoupling)**가 보안, 지연 시간, 신뢰성 모두를 잡는 **'은탄환(Silver Bullet)'**임을 이해.

강연자분이 마지막에 **"자, 이제 여러분 노트북에서 직접 돌려보세요. 안 되더라도 화면 보면서 따라오시면 돼요"**라고 하셨듯, **백 번 읽는 것보다 한 번 `streamlit run` 해보고, 채팅창에 "서버 다운됐어"라고 쳐보는 게 최고**예요.

에러 나면 에러 메시지 읽고, `agent.py` 열어서 `instructions` 한 줄 고쳐보고, `skills` 하나 추가해보고. 그렇게 **'내 에이전트'를 길들이는 과정** 자체가 진짜 공부입니다.

자, 이제 여러분의 터미널로 가세요. `streamlit run app.py` 치고, **나만의 새벽 당직 요정**을 깨워보세요. "얘, 인시던트 좀 봐줘"라고 말하면서요. 그 순간, 여러분은 더 이상 '코드 짜는 사람'이 아니라 **'AI 동료를 고용하고 지휘하는 매니저'**가 된 겁니다.
