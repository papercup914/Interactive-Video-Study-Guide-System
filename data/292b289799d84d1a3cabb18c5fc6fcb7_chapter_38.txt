# 서브 에이전트 도구화(Toolification): 루프 에이전트를 루트 에이전트 호출 가능한 도구로 변환

안녕하세요! 지난 시간에는 **'견고한 블로그 플래너(Robust Blog Planner)'**라는 이름의 **루프 에이전트(Loop Agent)**를 만들어, 기획안이 완벽해질 때까지 자동으로 '작성 → 검사 → 수정'의 사이클을 돌리는 방법을 배웠습니다. 마치 **'요리사가 요리를 하고, 수석 셰프가 맛을 보고, 다시 요리사가 고치는 과정'**을 무한 반복해서 '완벽한 한 접시'를 만들어내는 자동화 라인을 구축한 셈이죠.

자, 그런데 이제 우리는 **두 개의 거대한 자동화 라인**을 갖게 되었습니다.
1.  **견고한 블로그 플래너 (기획 전담 라인)**
2.  **견고한 블로그 라이터 (작성 전담 라인)** ← *이번 시간에 만들 친구입니다.*

이 두 라인을 **최종 책임자인 '루트 에이전트(Root Agent, 우리 프로젝트에서는 '블로거(Blogger)')**가 손쉽게 부려먹으려면(호출하려면), 이 복잡한 내부 구조를 **깔끔한 '도구(Tool)' 하나**로 포장해서 건네줘야 합니다. 이게 바로 오늘의 주제, **'서브 에이전트 도구화(Sub-agent Toolification)'**입니다.

---

## 1. 글쓰기 라인 구축: '견고한 블로그 라이터' 만들기

기획안이 통과되었다면, 이제는 진짜 글을 써야겠죠? 기획 때와 **똑같은 논리**로 '글쓰기 라인'을 만듭니다.

### ① 작가(Writer Agent) 고용하기
먼저 **'블로그 포스트 라이터(Blog Post Writer)'**라는 에이전트를 만듭니다. 얘한테는 이렇게 지시서를 줍니다.

> **"너는 전문 블로그 작가야. 사용자가 준 주제와 기획안(outline), 그리고 앞서 조사한 자료들(insights)을 바탕으로 본문을 써. 단순히 나열하지 말고 '어떻게(How)'와 '왜(Why)'를 설명하고, 필요하면 짧은 코드 조각도 넣어줘. 기획안의 제목 구조(Heading)를 정확히 따라야 해. 다 쓰면 `blog_post`라는 공유 창고(Shared State)에 저장해."**

여기서 **`blog_post`라는 공유 상태(Shared State)**가 중요합니다. 이건 **'작업대 위 완성된 원고 더미'**라고 보시면 됩니다. 작가 에이전트는 자기 일을 다 하고 나서 "자, 원고 여기 올려놨으니 가져가세요~" 하고 `blog_post` 슬롯에 결과물을 꽂아둡니다.

### ② 검수관(Checker Agent) 고용하기: '블로그 포스트 검증 체커'
작가가 글을 썼다고 바로 내보내면 안 되겠죠? 오타가 있을 수도, 구성이 빠졌을 수도 있으니까요. 그래서 **'블로그 포스트 검증 체커(Blog Post Validation Checker)'**라는 검수관을 둡니다.

이 친구의 일은 **`blog_post` 창고에 있는 원고를 꺼내 읽어보고**, 다음 기준을 통과하는지 확인하는 겁니다.

*   **도입부(Introduction)가 있는가?**
*   **기획안(Outline)의 섹션들과 맞춰져 있는가?**
*   **결론(Conclusion)이 있는가?**
*   **설명이 명확하고 이해하기 쉬운가?**

> **💡 개념 돋보기: 체커(Checker) 에이전트의 판단 기준**
> > 체커 에이전트는 **"통과(Okay)"** 또는 **"재시도(Retry)"** 둘 중 하나만 뱉습니다.
> > *   **"Okay"**: "완벽해! 출판해도 돼." → 루프 종료.
> > *   **"Retry"**: "이게 뭐야? 도입부도 없고, 3장 내용도 빠졌어. 고쳐와." → **수정 사항 리스트를 작가에게 다시 던져줌.**

### ③ 루프로 엮기: '견고한 블로그 라이터 (Robust Blog Writer)'
자, 이제 작가와 검수관을 **'루프 에이전트(Loop Agent)'**로 묶습니다. 이름이 바로 **'견고한 블로그 라이터(Robust Blog Writer)'**입니다.

이 루프의 동작 원리는 기획 때와 **완벽하게 동일**합니다.

1.  **작가**가 `blog_post`에 초안 작성.
2.  **체커**가 `blog_post` 읽고 검사.
3.  **"Okay"**면 → **루프 탈출 (성공!)**
4.  **"Retry"**면 → 체커가 지적한 수정 사항을 작가에게 전달 → **1번으로 돌아가 다시 작성 (최대 3회 반복)**

> **💡 개념 돋보기: 왜 '최대 3회'인가? (무한 루프 방지)**
> > 만약 작가가 실력이 너무 없거나, 체커 기준이 너무 높으면 영원히 "다시 해!"만 반복될 수 있습니다. 시스템이 멈추지 않게 **'최대 재시도 횟수(Max Retries = 3)'**라는 안전장치를 걸어둡니다. 3번 만에 안 되면 "인간님, 이건 제가 못 하겠어요. 개입 좀 해주세요"라고 에러를 띄우거나 상위 에이전트에게 도움을 요청하게 설계합니다.

## 2. 마법의 포장술: '도구화(Toolification)' - 복잡함을 감추고 단순함만 노출하기

자, 이제 우리는 두 개의 **'완성된 자동화 기계'**를 갖게 되었습니다.

1.  **기계 A: 견고한 블로그 플래너** (입력: 주제 → 출력: 검증된 기획안 `outline`)
2.  **기계 B: 견고한 블로그 라이터** (입력: 주제 + 기획안 + 자료 → 출력: 검증된 원고 `blog_post`)

이 기계들 내부엔 **작가, 체커, 루프, 공유 상태, 재시도 로직** 등 엄청나게 복잡한 회로들이 들어있습니다. 만약 **최종 보스(루트 에이전트 '블로거')**가 이걸 쓰려고 할 때마다 내부 회로를 다 꿰고 있어야 한다면 어떨까요? **"야, 너 기획안 짤 때 루프 3번 돌리고 체커가 Okay 할 때까지 기다렸다가 Shared State에서 outline 꺼내서..."** 이렇게 일일이 지시해야 한다면 보스는 미쳐버릴 겁니다.

그래서 우리는 **'도구화(Toolification)'**라는 마법을 씁니다.

### 🍳 일상 비유: '만능 리모컨' 혹은 '자판기 버튼'

상상해 보세요.
*   **도구화 전:** 커피 마시고 싶을 때마다 원두 갈고, 물 온도 맞추고, 탬핑하고, 추출 압력 조절하고... (바리스타가 되는 것)
*   **도구화 후:** **자판기 버튼 하나(Tool: `make_coffee`)** 누르면 → **맛있는 커피(Result) 나옴.**

**'견고한 블로그 플래너'라는 복잡한 루프 에이전트 전체를** → **`run_robust_planner`라는 '함수(Function) 도구' 하나**로 포장해 버리는 겁니다.
**'견고한 블로그 라이터'라는 복잡한 루프 에이전트 전체를** → **`run_robust_writer`라는 '함수(Function) 도구' 하나**로 포장해 버리는 겁니다.

### 기술적 구현: `AgentTool` 또는 `FunctionTool`로 감싸기

코드 레벨에서는 보통 프레임워크(ADK, LangGraph, AutoGen 등)에서 제공하는 **`AgentTool`**이나 **`FunctionTool`** 클래스를 사용합니다.

```python
# 의사코드(Pseudo-code) 예시

# 1. 복잡한 루프 에이전트 정의 (내부는 숨김)
robust_planner_loop = LoopAgent(
    sub_agents=[planner_writer, planner_checker],
    max_iterations=3
)

robust_writer_loop = LoopAgent(
    sub_agents=[post_writer, post_checker],
    max_iterations=3
)

# 2. 【핵심】 이 루프 에이전트들을 '도구(Tool)'로 변환 (포장)
# 이제 이건 그냥 "입력 넣으면 출력 뱉는 함수"처럼 행동함
planner_tool = AgentTool(agent=robust_planner_loop, name="run_robust_planner")
writer_tool = AgentTool(agent=robust_writer_loop, name="run_robust_writer")

# 3. 루트 에이전트('블로거')에게 도구 쥐어주기
root_agent = LlmAgent(
    name="Blogger",
    model="gemini-1.5-pro",
    tools=[planner_tool, writer_tool], # <--- 여기만 보면 끝!
    instruction="""
    너는 블로거야. 사용자가 주제를 주면:
    1. 먼저 run_robust_planner 도구를 호출해서 기획안을 만들어.
    2. 그 결과(outline)를 받아서 run_robust_writer 도구를 호출해서 본문을 써.
    3. 최종 결과물(blog_post)을 사용자에게 보여줘.
    """
)
```

> **💡 개념 돋보기: 캡슐화(Encapsulation)와 추상화(Abstraction)**
> > *   **캡슐화:** "내부에서 루프가 어떻게 돌든, Shared State를 어떻게 쓰든, 체커가 뭐라고 하든 **나몰라라**. 그냥 `planner_tool.run(topic)`이라고 호출하면 `outline`만 뱉어줘."
> > *   **추상화:** 루트 에이전트 입장에서 이 도구는 그냥 **'기획안 뽑아주는 마법 상자'**, **'글 써주는 마법 상자'**일 뿐입니다. **복잡도는 안으로 숨기고, 인터페이스는 극도로 단순하게.** 이게 소프트웨어 공학의 정수이자, 멀티 에이전트 시스템 설계의 핵심입니다.

## 3. 최종 조립: 루트 에이전트 '블로거(Blogger)' 탄생

이제 모든 준비가 끝났습니다. **최종 보스, 루트 에이전트 '블로거(Blogger)'**를 만듭니다.

얘는 **LLM 에이전트(대화형 AI)** 하나인데, 손에 **두 개의 강력한 도구(플래너 도구, 라이터 도구)**를 쥐고 있습니다. 시스템 프롬프트(Instruction)는 아주 심플합니다.

### 블로거의 지시서 (System Prompt)

> **"너는 전문 블로거 에이전트 '블로거'다. 사용자가 글감을 주면 다음 순서대로 실행해라.**
>
> 1.  **기획 단계:** `run_robust_planner` 도구를 호출하여, 주제에 맞는 **검증된 기획안(Outline)**을 만들어라. (이 도구는 내부적으로 알아서 3번까지 다시 쓰며 완벽한 기획안을 만든다.)
> 2.  **작성 단계:** 1번에서 받은 기획안(Outline)과 앞서 조사한 자료(Insights)를 가지고 `run_robust_writer` 도구를 호출하여, **검증된 완성 원고(Blog Post)**를 작성하라. (이 도구 역시 내부적으로 3번까지 다시 쓰며 완벽한 원고를 만든다.)
> 3.  **최종 보고:** 도구가 반환한 최종 `blog_post` 내용을 사용자에게 예쁘게 보여줘라."**

### 실행 시나리오 (사용자 관점)

**사용자:** *"요즘 뜨는 'RAG(검색 증강 생성)' 기술에 대해 초보자도 이해하기 쉽게 블로그 글 하나 써줘."*

**블로거(루트 에이전트) 머릿속 생각:**
> "오키, 주제는 'RAG'네. 일단 기획부터 해야지? 나한테 `run_robust_planner`란 도구가 있네? 이거 호출하면 기획안 나와. 인자(Argument)로 `topic='RAG'`만 넘기면 되겠네?"

**→ `run_robust_planner(topic="RAG")` 호출!**

*(백그라운드에서: 플래너 작가 작성 → 플래너 체커 검사 → "Retry!" → 작가 수정 → 체커 "Okay!" → `outline` 확정 → 루프 종료 → 결과 반환)*

**블로거:** "오, 기획안 나왔네. 제목: 'RAG의 원리', 1장: 벡터 DB란?, 2장: 임베딩이란?... 좋아. 이제 글 써야지. `run_robust_writer` 도구에다가 `topic='RAG'`, `outline=방금받은기획안`, `insights=자료조사결과` 넣고 돌리면 되겠네?"

**→ `run_robust_writer(topic="RAG", outline=..., insights=...)` 호출!**

*(백그라운드에서: 포스트 작가 작성 → 포스트 체커 검사 → "도입부 약함, Retry!" → 작가 수정 → 체커 "결론 보강 필요, Retry!" → 작가 수정 → 체커 "Okay!" → `blog_post` 확정 → 루프 종료 → 결과 반환)*

**블로거:** "짜잔! 완성된 원고(`blog_post`)가 돌아왔네. 사용자한테 마크다운으로 예쁘게 뿌려주면 끝!"

## 4. 전체 아키텍처 한눈에 보기 (요약도)

이렇게 해서 완성된 **계층형 멀티 에이전트 시스템(Hierarchical Multi-Agent System)**의 구조는 다음과 같습니다.

```text
┌─────────────────────────────────────────────────────┐
│           👑 ROOT AGENT: Blogger (LLM)              │
│  - Tools: [run_robust_planner, run_robust_writer]   │
│  - Instruction: "주제 받으면 플래너 → 라이터 순 실행"│
└──────────────┬──────────────────────┬────────────────┘
               │ Tool Call            │ Tool Call
               ▼                      ▼
┌─────────────────────────┐  ┌─────────────────────────┐
│ 🛠 TOOL: run_robust_    │  │ 🛠 TOOL: run_robust_    │
│    planner              │  │    writer               │
│  (AgentTool Wrapper)    │  │  (AgentTool Wrapper)    │
└───────────┬─────────────┘  └───────────┬─────────────┘
            │                            │
            ▼ (Internal Loop)            ▼ (Internal Loop)
┌─────────────────────────┐  ┌─────────────────────────┐
│  🔄 LOOP AGENT          │  │  🔄 LOOP AGENT          │
│  (Max 3 Iterations)     │  │  (Max 3 Iterations)     │
│                         │  │                         │
│  ┌─────────┐ ┌───────┐  │  │  ┌─────────┐ ┌───────┐  │
│  │ Writer  │▶│Checker│──┘  │  │ Writer  │▶│Checker│──┘
│  │(Planner)│ │(Plan) │     │  │ (Post)  │ │(Post) │
│  └────┬────┘ └───────┘     │  └────┬────┘ └───────┘
│       │   ▲  (Retry/Ok)    │       │   ▲  (Retry/Ok)
│       │   │                │       │   │
│       ▼   │                │       ▼   │
│  📦 Shared State: outline ◀┘  📦 Shared State: blog_post ◀┘
└─────────────────────────┘  └─────────────────────────┘
```

## 5. 핵심 정리: 왜 이렇게 복잡하게 만드나요?

초보자는 "그냥 LLM 하나한테 '블로그 써'라고 시키면 안 되나?"라고 생각할 수 있습니다. 하지만 **'도구화된 루프 에이전트'** 구조가 주는 압도적 이점이 있습니다.

| 관점 | 단순 LLM 단일 호출 (Naive) | 도구화된 루프 에이전트 계층 구조 (Pro) |
| :--- | :--- | :--- |
| **품질 보장** | 운에 맡김. 한 번에 완벽하길 기도. | **자동 검증 루프**로 품질 기준 미달 시 **강제 재작업**. |
| **복잡도 관리** | 프롬프트 하나에 모든 지시(기획, 작성, 검수, 코드, 형식)를 다 욱여넣어야 함. | **관심사 분리(SoC)**: 기획은 기획 에이전트, 작성은 작성 에이전트, 검수는 체커 에이전트. 각자 자기 일만 함. |
| **유지보수** | 프롬프트 수정 시 사이드 이펙트 예측 불가. | **모듈화**: "기획 기준 바꿔야지" → `Planner Checker` 프롬프트만 고치면 됨. "작성 톤 바꿔야지" → `Post Writer` 프롬프트만 고치면 됨. |
| **재사용성** | 이 프롬프트를 다른 프로젝트에 쓰기 힘듦. | **`planner_tool`, `writer_tool`**을 다른 루트 에이전트(예: '보고서 작성 봇', '논문 작성 봇')가 **그대로 가져다 씀**. |
| **디버깅** | "왜 이상하게 나왔지?" → 블랙박스. | "기획이 이상해" → 플래너 루프 로그 확인. "본문이 이상해" → 라이터 루프 로그 확인. **문제 지점 격리 용이.** |

> **💡 개념 돋보기: '신뢰할 수 있는 구성 요소(Reliable Components)'의 조합**
> > 루트 에이전트 '블로거'는 **"플래너 도구는 무조건 검증된 기획안을 준다"**, **"라이터 도구는 무조건 검증된 원고를 준다"**는 **신뢰(Contract/Interface)** 위에서 돌아갑니다. 내부에서 3번을 다시 쓰든 1번 만에 끝나든, 루트 에이전트는 **'결과물의 품질이 보장된 도구'**를 쓰는 것뿐입니다. 이게 **엔터프라이즈급 AI 에이전트 시스템**을 만드는 비결입니다.

## 마무리하며

오늘 우리는 **'서브 에이전트 도구화(Toolification)'**라는 강력한 설계 패턴을 배웠습니다.

1.  **루프 에이전트(자동 재시도 시스템)**를 만들어 **'신뢰할 수 있는 단일 작업 단위(기획, 작성)'**를 만듭니다.
2.  이 복잡한 루프 에이전트를 **`AgentTool`로 감싸서 '함수 도구'로 만듭니다.** (캡슐화)
3.  **루트 에이전트(오케스트레이터)**는 내부 구현을 전혀 모른 채, 단지 **도구 이름과 입력/출력 스펙만 보고** 이들을 레고 블록처럼 조립하여 거대 작업을 수행합니다.

이제 우리 시스템은 **"주제만 던지면 → 알아서 기획 짜고 검사하고 → 글 쓰고 검사하고 → 최종 본문 뱉어주는"** **완전 자동화된 블로그 생성 파이프라인**이 되었습니다.

다음 시간에는 이 시스템에 **'자료 조사(Research)'** 단계를 가장 앞에 붙여, **"주제만 주면 구글 검색/논문 읽고 → 기획하고 → 글 쓰는"** **완전체 자율 에이전트**로 진화시키는 방법을 알아보겠습니다. 기대해 주세요! 🚀
