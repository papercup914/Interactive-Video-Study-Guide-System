# Chapter 8. 기존 강점 영역에서의 성능 회귀 발생 패턴

> **학습 목표**: 이 챕터를 마치면, **'잘 작동하던 시스템의 핵심 강점을 그대로 둔 채 새로운 기능을 추가하려 할 때, 오히려 기존 강점이 무너지는 성능 회귀(Performance Regression) 현상'이 왜 발생하는지** 그 구조적 원인을 이해하고, **'뇌(추론)와 손(실행)의 분리'라는 아키텍처 패턴을 통해 이를 어떻게 예방하고 해결할 수 있는지** 실전 코드 수준에서 파악할 수 있게 됩니다.

---

## 1. 서론: "칼을 갈았는데 요리사가 다쳤다?" - 강점의 역설

여러분, 요리사에게 **'최고의 칼(강점)'**이 있다고 칩시다. 이 요리사는 칼 하나로 채 썰기, 다지기, 저미기 등 모든 작업을 척척 해냅니다. 그런데 어느 날, 주방장이 "요리사가 불을 쓰는 일도 같이 하게 하자"며 **'프라이팬(새로운 도구/권한)'**을 요리사의 다른 손에 쥐여줍니다.

문제는 여기서 터집니다. 요리사가 프라이팬을 다루느라 정신이 팔려 **칼질을 하던 손이 느려지거나(지연 시간 증가), 실수로 제 베어버리는(보안 사고) 일**이 벌어지는 겁니다. **기존 강점(칼질 실력)이 새로운 기능(불 다루기) 때문에 퇴보하는 현상**, 이게 바로 **'기존 강점 영역에서의 성능 회귀(Performance Regression in Existing Strength Areas)'**입니다.

이번 챕터에서 다룰 **Claude Managed Agents(클로드 매니지드 에이전트)**의 설계 여정은, 바로 이 **"칼(추론 엔진)과 프라이팬(도구 실행 환경)을 든 손을 분리하자"**는 결단에서 시작됩니다. 영상 속 발표자가 말한 **"에이전트 루프(뇌)와 도구 실행(손)의 긴밀한 결합(Tight Coupling)"**이 어떻게 강점을 좀먹었는지, 그리고 **'디커플링(Decoupling, 분리)'**이라는 수술이 어떻게 **90% 이상의 지연 시간 단축**과 **보안 강화**라는 두 마리 토끼를 잡았는지, 비전공자도 이해하기 쉬운 비유와 함께 아주 깊숙이 파헤쳐 보겠습니다.

## 2. 개념 돋보기 🧐: 핵심 용어, 일상 비유로 먼저 잡기

> **💡 개념 돋보기: 에이전트 루프 (Agent Loop) - "요리사의 머릿속 레시피 생각하기"**
> 에이전트가 **"상황을 보고(관찰) → 무슨 행동을 할지 결정하고(사고) → 도구를 호출하고(행동) → 결과를 다시 보는"** 과정을 무한 반복하는 사이클을 말합니다. 요리사가 "당근이 남았네? → 채 썰어야지 → 칼 들기 → 썰기 완료 → 다시 보기"를 반복하는 것과 똑같습니다.
>
> **💡 개념 돋보기: 도구 실행 (Tool Execution) - "요리사의 실제 손놀림(칼질, 불 조절)"**
> 에이전트가 결정한 행동을 실제 환경에서 수행하는 행위입니다. 파일 읽기, 코드 실행, API 호출, 데이터베이스 쿼리 등이 이에 해당합니다. 요리사로 치면 **'손'**에 해당합니다.
>
> **💡 개념 돋보기: 타이트 커플링 (Tight Coupling) - "뇌와 손이 한 몸에 딱 붙어있음"**
> 생각(루프)과 행동(도구 실행)이 **같은 프로세스, 같은 컨테이너, 같은 메모리 공간**에서 돌아가는 구조입니다. 요리사의 뇌와 손이 한 몸에 붙어 있어, 손이 화상을 입으면 뇌까지 충격을 받는 구조와 같습니다.
>
> **💡 개념 돋보기: 디커플링 (Decoupling) - "뇌는 본부에, 손은 현장에 분리 배치"**
> 생각(에이전트 루프/서버 사이드)과 행동(환경/컨테이너/샌드박스)을 **물리적, 논리적으로 분리**하는 아키텍처 패턴입니다. 뇌(클라우드 서버)는 안전하게 있고, 손(샌드박스 환경)만 위험한 현장에 보내는 구조입니다.
>
> **💡 개념 돋보기: TTFT (Time To First Token) - "첫 마디 꺼내기까지 걸리는 시간"**
> 사용자가 요청을 보냈을 때, 에이전트가 **첫 번째 응답 토큰(단어)을 내뱉기까지의 지연 시간**입니다. "요리사야, 당근 썰어!"라고 했을 때 "네!"라고 대답하기까지의 침묵 시간이라고 보시면 됩니다. P95(상위 5% 느린 케이스) 기준 90% 단축되었다는 건, 최악의 상황에서도 말이 빨라졌다는 뜻입니다.

## 3. 본론 1: 강점의 덫 - "모든 도구를 쥐여주니, 칼질이 느려지고 위험해졌다"

### 3.1 기존 패턴: '만능 요리사' 모델의 탄생과 한계

영상 초반, 발표자는 **"기존 많은 에이전트 하네스(프레임워크)에서는 에이전트 루프와 도구 실행이 강하게 결합(Tightly Coupled)되어 있었다"**고 회고합니다. 이 설계가 왜 처음엔 합리적이었을까요?

> **🍳 비유: '주방 올인원 요리사' 모델**
> 초창기 에이전트 설계는 **"요리사 한 명에게 주방 전체(파일 시스템, 터미널, 네트워크, 비밀번호 금고) 열쇠를 다 쥐여주고, 요리사 머릿속(루프)에서 바로 손(도구 실행)으로 연결되게 하자"**는 생각이었습니다.
>
> - **장점**: 요리사(에이전트)가 생각 즉시 행동으로 옮길 수 있어 **반응성이 빠르고 구현이 단순**합니다. `Claude Code`처럼 "내 컴퓨터 파일 다 뒤져서 고쳐줘" 같은 작업엔 여전히 이 방식이 최고입니다.
> - **이게 '강점'이었습니다**: **자율성(Autonomy)**, **즉각적 피드백(Immediate Feedback)**, **단순한 아키텍처(Simple Architecture)**.

### 3.2 강점이 독이 되는 순간: 성능 회귀의 트리거

하지만 **"자격 증명(Credentials), 보안, 샌드박싱"** 요구사항이 생기자, 이 '강점'이 **'아킬레스건'**으로 돌변합니다. 영상에서 발표자가 지적한 **제약 사항(Constraints)** 세 가지를 비유로 풀어봅니다.

#### ① 보안/자격 증명 누수 위험: "요리사 주머니에 금고 열쇠가 있다"
> **상황**: 에이전트가 사용자의 파일 시스템에 접근하려면 API 키, DB 비밀번호, SSH 키 같은 **민감한 자격 증명(Credentials)**이 필요합니다.
> **타이트 커플링 구조에서**: 에이전트 루프(뇌)와 도구 실행(손)이 **같은 컨테이너(같은 주머니)**에 있습니다. 해커가 도구 실행 환경(손)을 해킹하면, 뇌가 쥐고 있는 **자격 증명(금고 열쇠)까지 한 번에 털립니다.**
> **성능 회귀 포인트**: **"보안 강화하려다 보니, 에이전트마다 무거운 암호화/복호화 로직을 루프 안에 덕지덕지 붙여야 함 → 추론 속도 저하(강점인 '빠른 사고' 훼손)"**.

#### ② 샌드박싱(격리) 불가능: "요리사가 독극물 요리도 맨손으로 해야 함"
> **상황**: 사용자가 "이상한 스크립트 실행해줘"라고 시킬 수 있습니다. 악성 코드일 수도 있습니다.
> **타이트 커플링 구조에서**: 뇌와 손이 붙어 있으니, **손이 독극물(악성 코드)을 만지면 뇌(메인 프로세스)까지 오염**됩니다. 이를 막으려면 에이전트 프로세스 전체를 무거운 가상머신(VM)이나 컨테이너로 감싸야 합니다.
> **성능 회귀 포인트**: **"격리하려다 보니, 세션 하나 띄울 때마다 무거운 컨테이너를 통째로 부팅해야 함 → 세션 시작 지연 시간(TTFT) 폭증(강점인 '즉시성' 훼손)"**.

#### ③ 확장성/비용 폭증: "손님 한 명 오면 주방 하나 새로 짓기"
> **상황**: 동시 접속 사용자 1,000명이면 에이전트 세션 1,000개 필요.
> **타이트 커플링 구조에서**: 세션마다 **(뇌+손) 세트인 무거운 컨테이너**를 띄워야 합니다. 뇌(LLM 추론)는 공유해도 되는데, 손(도구 실행) 때문에 뇌까지 매번 새로 띄우는 낭비 발생.
> **성능 회귀 포인트**: **"리소스 낭비 → 비용 증가 → 스케일 아웃 지연 → 사용자 경험 저하"**.

> **💡 개념 돋보기: 성능 회귀(Performance Regression)의 정체**
> > **성능 회귀**란 "새 기능을 추가하거나 리팩토링한 후, **기존에 잘 작동하던 핵심 지표(속도, 안정성, 보안)가 오히려 나빠지는 현상**"을 말합니다.
> > 여기선 **"도구 실행 능력(새 기능/요구사항)을 지원하려다, 기존 강제로 에이전트 루프(기존 강점: 빠른 추론, 낮은 지연, 단순 구조)에 보안/격리/비용 부담을 떠안긴 것"**이 회귀의 본질입니다.

## 4. 본론 2: 수술 - "뇌(서버 사이드 루프)와 손(환경/샌드박스)의 완전 분리"

영상의 핵심 설계 결정: **"에이전트 루프를 서버 사이드(Server-side)로 올리고, 도구 실행 환경(Environment)을 별도 샌드박스로 분리하자."**

### 4.1 아키텍처 대수술: 뇌와 손의 이혼 절차

| 구성 요소 | 기존 (Tight Coupling) | 변경 후 (Decoupled / Managed Agents) | 비유: 요리사 시스템 |
| :--- | :--- | :--- | :--- |
| **뇌 (Agent Loop / Brain)** | 사용자 로컬/컨테이너 내 프로세스 | **클라우드 관리형 서버(Server-side)** | **본부 상황실(안전, 고성능 GPU, 영구 메모리)** |
| **손 (Environment / Hands)** | 뇌와 같은 컨테이너 내 도구 실행기 | **독립된 샌드박스 컨테이너(Sandboxed Container)** | **현장 출동 요원(일회용, 격리, 위험 감수)** |
| **자격 증명 관리** | 뇌 메모리/환경 변수에 평문/암호화 보관 | **뇌는 모름. 손(환경)이 필요할 때만 안전하게 주입** | **본부는 금고 위치 모름. 요원만 임무 시 열쇠 수령** |
| **세션 상태(Session)** | 프로세스 메모리(휘발성, 노트북 닫으면 끝) | **서버 사이드 영속 저장(Durable, Reliable)** | **본부 로그북에 자동 기록. 노트북 닫아도 이어짐** |

### 4.2 디커플링이 가져온 기적: 4대 강점 동시 회복 (영상 근거)

발표자는 이 분리로 **안전성(Safety), 신뢰성(Reliability), 지연 시간(Latency), 운영 편의성** 모든 게 좋아졌다고 강조합니다. 왜죠?

#### ① 지연 시간(Latency) 대폭 축소: "본부는 켜져 있으니, 요원만 보내면 됨"
> **영상 발언**: *"이전엔 세션마다 컨테이너 띄우느라 TTFT 지연 발생. 디커플링 후 **P95 기준 90% 이상 TTFT 감소** 달성."*
> **메커니즘 분석**:
> - **기존**: `사용자 요청 → 뇌+손 컨테이너 부팅(수초~수십초) → 루프 시작 → 첫 토큰` → **콜드 스타트(Cold Start) 지옥**
> - **신규**: `뇌(서버)는 24/7 가동 중(웜 상태) → 요청 오면 즉시 추론 시작 → 손(환경)은 비동기로 별도 준비/연결` → **뇌는 기다리지 않음**
> - **핵심**: **뇌의 '첫 생각(First Token)'을 손의 '준비 시간'과 분리(Decouple)시킴**. 사용자는 "네, 시작할게요"란 첫 마디를 **즉시** 들을 수 있습니다.

#### ② 보안/자격 증명 완벽 격리: "본부에 금고 열쇠 없음"
> **영상 발언**: *"에이전트가 실제 자격 증명에 접근 못 하게 디커플링으로 샌드박싱 구현. 암호화 없이도 자격 증명 보호 가능."*
> **메커니즘 분석**:
> - 뇌(서버 사이드 루프)는 **자격 증명을 모릅니다(Zero Knowledge)**. 그냥 "도구 호출해줘"라는 명령(JSON)만 내립니다.
> - 손(환경/샌드박스) 쪽에서 **권한 있는 사이드카(Sidecar)나 시크릿 매니저**가 안전하게 자격 증명을 주입해 도구를 실행합니다.
> - 해커가 손(샌드박스)을 털어도 **뇌(본부)엔 털 게 없습니다**. 강점인 '보안'이 아키텍처 레벨로 보장됩니다.

#### ③ 신뢰성/내구성(Reliability/Durability): "노트북 닫아도 요리 계속됨"
> **영상 발언**: *"루프가 서버 사이드라 복잡성 추상화. 노트북 닫거나 새로고침해도 모든 것 유지. 내구성/신뢰성 걱정 없음."*
> **메커니즘 분석**:
> - 기존 로컬 에이전트: 프로세스 죽으면 **세션 상태(대화 기록, 중간 결과, 도구 상태) 몽땅 증발**.
> - 매니지드 에이전트: **세션(Session) 객체**가 서버 DB/스토리지에 영속 저장. 클라이언트(노트북/브라우저)는 مجرد '뷰어(Viewer)'일 뿐.
> - **강점 회복**: "프로토타입 → 프로덕션" 갈 때 가장 큰 골칫거리인 **상태 관리(State Management), 재연결(Reconnection), 장애 복구(Failover)**를 프레임워크가 다 떠안아 줌.

#### ④ 확장성/비용 최적화: "뇌는 공유, 손만 필요만큼"
> - 뇌(LLM 추론 엔진)는 **스테이트리스(Stateless) 서비스**로 수평 확장(Scale-out) 용이. GPu 클러스터 공유.
> - 손(환경)은 **작업 종류/보안 등급별로 다른 이미지/사이즈**로 동적 프로비저닝(예: 단순 파일 읽기엔 작은 컨테이너, 빌드/테스트엔 큰 컨테이너).
> - **리소스 낭비 제로**. 강점인 '비용 효율성' 확보.

## 5. 본론 3: 코드 레벨에서 보는 '분리의 미학' - 실습 예제 분석

영상 후반, 발표자는 실습 저장소(`Ship Your First Managed Agent`)의 `agent.py` 파일을 보여주며 **프리미티브(Primitive, 기본 구성 요소) 3총사**가 어떻게 분리를 구현하는지 보여줍니다. 이 코드 구조가 바로 **성능 회귀를 막는 설계도**입니다.

### 5.1 3대 프리미티브: 뇌, 손, 연결고리

> **💻 코드 돋보기: `agent.py` 핵심 클래스 구조 (영상 기반 재구성)**

```python
# 1. 뇌 (Agent) - "성격, 능력, 모델, 도구 목록 정의. 실행 모름."
class Agent:
    def __init__(self, model: str, mcp_servers: list, skills: list, ...):
        self.model = model              # 어떤 LLM 쓸지 (Claude 3.5 Sonnet 등)
        self.mcp_servers = mcp_servers  # 연결할 외부 도구 서버 목록 (MCP 프로토콜)
        self.skills = skills            # 프롬프트 엔지니어링된 스킬/페르소나
        # 👉 주의: 여긴 '도구 실행 코드'가 없습니다. 오직 '정의'만 있음.

# 2. 손 (Environment) - "실제 실행 환경. 컨테이너, 파일시스템, 네트워크, 시크릿."
class Environment:
    def __init__(self, image: str, secrets: dict, resources: dict, ...):
        self.image = image              # 도커 이미지 (예: python:3.11-slim, node:20)
        self.secrets = secrets          # 이 환경에서만 쓸 비밀번호/키 (뇌 모름)
        self.resources = resources      # CPU/메모리/GPU 할당량
        # 👉 이 안에선 '생각' 안 함. 오직 '명령 받으면 실행'만 함.

# 3. 연결고리 (Session) - "뇌와 손을 이어주는 세션. 이벤트 스트리밍, 상태 저장."
class Session:
    def __init__(self, agent: Agent, environment: Environment):
        self.agent = agent              # 뇌 참조
        self.environment = environment  # 손 참조
        self.state = "INITIALIZING"     # 세션 상태 (서버 DB에 영속 저장됨)
    
    async def stream_events(self):      # 사용자한테 실시간 이벤트 쏴주기
        # 뇌가 생각 -> 도구 호출 결정 -> 손에게 위임 -> 손 결과 -> 뇌 다시 생각...
        # 이 루프가 '서버 사이드'에서 돕니다.
        pass
```

### 5.2 실습 시나리오: '3시 새벽 온콜(On-call) 악몽' 해결기

영상에서 발표자가 **"소프트웨어 엔지니어라면 3시에 깨우는 온콜 고통 알 것"**이라며 데모 시나리오로 든 **인시던트 대응 에이전트**가 이 분리의 위력을 보여줍니다.

| 단계 | 뇌 (Agent - 서버 사이드) | 손 (Environment - 샌드박스) | 세션 (Session) |
| :--- | :--- | :--- | :--- |
| **1. 알림 수신** | "PagerDuty 알림 옴. CPU 100%야. 뭐부터 볼까?" (추론 시작) | (대기 중) | 세션 생성, 상태 `RUNNING` 기록 |
| **2. 메트릭 조회** | `tool: query_prometheus(query="cpu_usage")` 호출 결정 | **프로메테우스 API 호출 실행** (네트워크, 인증 토큰 사용) | 이벤트 `TOOL_CALL` -> `TOOL_RESULT` 스트리밍 |
| **3. 로그 분석** | "로그 봐야지. `kubectl logs -n prod app-xyz`" | **쿠버네티스 클러스터 내부에서 kubectl 실행** (kubeconfig 시크릿 사용) | 중간 결과 사용자 대시보드에 실시간 표시 |
| **4. 배포 롤백** | "배포 v1.2.3이 원인. 롤백하자. `argo rollback`" | **ArgoCD CLI 실행하여 롤백 수행** (클러스터 관리자 권한 시크릿 사용) | 세션 상태 `COMPLETED`, 전체 히스토리 영구 저장 |
| **5. 보고서 작성** | "원인: 메모리 누수. 조치: 롤백. 후속: 코드 리뷰" 최종 요약 생성 | (작업 완료, 컨테이너 종료/재활용) | 사용자(엔지니어)는 **잠 계속 잠**. 아침에 보고서만 보면 끝. |

> **💡 여기서 성능 회귀가 없는 이유**:
> 1. **뇌는 '프롬프테우스 쿼리 문법'만 알지, '프로메테우스 비번' 모름** → 보안 회귀 없음.
> 2. **손(환경)은 'kubectl'만 실행할 줄 알지, '인시던트 대응 전략' 모름** → 역할 분리 명확.
> 3. **세션은 '상태'만 기억함** → 엔지니어 노트북 꺼져도, 네트워크 끊겨도 서버에서 이어감 → 신뢰성 회귀 없음.
> 4. **뇌(서버)는 이미 켜져 있음** → 알림 오자마자 "받았어, 분석 중이야" 첫 토큰 **즉시** 나감 → 지연 시간 회귀 없음.

## 6. 심화 토론: "분리가 정답인가? 트레이드오프는 없는가?"

모든 아키텍처엔 트레이드오프가 있습니다. 디커플링도 예외는 아닙니다. 성능 회귀를 막으려다 **새로운 회귀**를 부르지 않으려면 다음을 주의해야 합니다.

### 6.1 네트워크 지연(Network Latency) - "본부-현장 무전기 딜레이"
> - **문제**: 뇌(서버)와 손(샌드박스)이 네트워크로 떨어져 있으니, **매 도구 호출마다 네트워크 왕복 지연(RTT)** 발생.
> - **완화**: 동일 가용영역(AZ) 내 배치, 고성능 내부 네트워크, **스트리밍/비동기 프로토콜(gRPC, WebSocket)** 사용, 도구 호출 배치(Batching).
> - **영상 힌트**: 발표자가 "TTFT 90% 감소"라고 한 건 **뇌의 첫 응답** 기준입니다. **도구 실행 루프 전체 시간**은 네트워크 비용이 더해질 수 있습니다. 하지만 **"인간이 기다리는 체감 시간(첫 토큰)"을 줄인 것**이 UX상 핵심입니다.

### 6.2 상태 동기화 복잡도 (State Synchronization) - "본부 지도와 현장 현실 차이"
> - **문제**: 뇌가 가진 '파일 시스템 상태 모델'과 손(컨테이너)의 '실제 파일 시스템'이 다를 수 있음 (동시 수정, 외부 변경).
> - **해결**: **Event Sourcing(이벤트 소싱)** 패턴으로 모든 도구 실행 결과를 이벤트로 저장해 뇌가 상태를 재구성하게 하거나, **낙관적 락(Optimistic Locking)** 등 동시성 제어 필요.
> - **Managed Agents의 강점**: 이 복잡도를 **플랫폼 레벨(Session/Event Store)**에서 추상화해 줌. 개발자가 직접 맞출 필요 없음.

### 6.3 디버깅/관찰 가능성(Observability) - "분리되니 어디가 병목인지 모름"
> - **문제**: 로그/메트릭/트레이스가 **뇌(서버 로그), 손(컨테이너 로그), 네트워크(프록시 로그)**로 흩어짐.
> - **해결**: **분산 추적(Distributed Tracing, 예: OpenTelemetry)** 필수. `Session ID`를 `trace_id`로 공통 심어 전 구간 추적.
> - **영상 연결**: `Session.stream_events()`가 이벤트 스트림을 주는 게 곧 **관찰 가능성의 창구**입니다.

## 7. 요약 및 실전 체크리스트: 내 프로젝트에 적용하기

> **📋 실전 체크리스트: "우리 에이전트, 강점 지키고 회귀 없나?"**

| 검증 영역 | 체크 포인트 | 통과 기준 (Managed Agents 패턴 적용 시) |
| :--- | :--- | :--- |
| **🧠 뇌(루프) 보호** | 에이전트 루프 코드에 **도구 실행 로직, 시크릿, 파일 I/O, 네트워크 호출**이 섞여 있는가? | **아니오.** 루프는 순수 `모델 호출 → 도구 호출 결정(JSON)`만 함. 실행은 `Environment` 위임. |
| **🤲 손(환경) 격리** | 도구 실행 환경이 **에이전트 프로세스와 동일 컨테이너/호스트**인가? | **아니오.** 전용 샌드박스 컨테이너/VM 분리. 시크릿은 환경 변수/볼륨 마운트로만 주입. |
| **🔗 세션 내구성** | 사용자 브라우저/클라이언트 종료 시 **세션 상태(대화, 중간 결과) 보존**되는가? | **예.** `Session` 객체가 서버 사이드 DB/스토리지에 영속 저장. 재접속 시 복원. |
| **⚡ 지연 시간** | 새 세션 요청 시 **첫 토큰 응답(TTFT)까지 컨테이너 부팅 대기** 발생하는가? | **아니오.** 뇌(서버)는 상시 가동(Warm Pool). 손(환경)은 비동기 프리웜/지연 바인딩. |
| **🔐 보안 경계** | 에이전트 루프 메모리/코드에서 **API 키, DB 비번, 클라우드 자격 증명** 접근 가능한가? | **아니오.** 뇌는 자격 증명 **모름(Zero Knowledge)**. 손만 실행 시점에 권한 위임. |
| **📈 확장성** | 동시 사용자 증가 시 **뇌(LLM 추론) 리소스와 손(도구 실행) 리소스 독립 스케일링** 가능한가? | **예.** 뇌 = Stateless API 서버(HPA). 손 = Job Queue + K8s Job/Cluster Autoscaler. |

## 8. 마무리: "강점을 지키려면, 강점을 쥐고 있는 손을 놓아줘야 한다"

이번 챕터의 여정을 한 문장으로 요약하면 이렇습니다.

> **"에이전트의 강점(빠른 추론, 자율성)을 갉아먹던 보안/지연/신뢰성 이슈의 범인은, '뇌와 손을 한 몸에 묶어둔 타이트 커플링'이었다. 뇌(서버 사이드 루프)는 본부에서 안전하게 생각만 하게 하고, 손(샌드박스 환경)은 현장에서 위험하게 실행만 하게 **디커플링(분리)**하자, **강점은 더 날카로워지고(90% TTFT 감소), 약점은 방어막이 되었다(보안/내구성 확보)."**

이것이 바로 **'기존 강점 영역에서의 성능 회귀 발생 패턴'**을 **아키텍처 레벨에서 근절**한, Anthropic의 **Claude Managed Agents**가 보여준 설계 철학의 정수입니다.

여러분이 직접 에이전트를 만들거나, 기존 에이전트 시스템을 프로덕션 레벨로 올릴 때 **"이 로직은 뇌(루프)에 둘까, 손(환경)에 둘까? 시크릿은 누가 쥐고 있을까? 세션 끊기면 내 상태는 누가 지켜주나?"**라는 질문을 **매 코드 라인마다 던져보시길 바랍니다.** 그 질문이 곧 **성능 회귀를 예방하는 최고의 설계 도구**가 될 것입니다.
