# 📚 챕터 3. 순차적 에이전트(Sequential Agents): 조립 라인처럼 한 단계씩, 착실하게 움직이는 일꾼들

앞서 우리는 AI 에이전트가 단순히 대답만 하는 챗봇이 아니라, **'이유를 생각하고(Reasoning) → 행동하고(Acting) → 결과를 보고(Observing) → 다시 판단하는' 사이클**을 가진 똑똑한 비서라는 것을 배웠습니다. 그런데 이 '똑똑한 비서'들도 일하는 스타일이 제각각입니다. 어떤 비서는 **매뉴얼대로만 딱딱 맞춰 일하는 '원칙주의자'**이고, 어떤 비서는 **상황에 맞춰 융통성 있게 대처하는 '해결사'**죠.

오늘 배울 **순차적 에이전트(Sequential Agent)**는 바로 그 **'원칙주의자 비서'**, 즉 **조립 라인(Assembly Line) 방식**으로 일하는 친구들입니다. 자, 공장 견학 가듯이 한번 자세히 들여다볼까요?

---

## 🏭 1. 우리 집 주방에도 있는 '조립 라인'의 비밀

> **💡 개념 돋보기: 순차적 에이전트(Sequential Agent)란?**
> > **정해진 순서(Step 1 → Step 2 → Step 3...)대로 작업을 수행하는 에이전트 패턴입니다.**
> > 마치 공장의 컨베이어 벨트 위에서 부품이 순서대로 조립되듯, **이전 단계가 끝나야만 다음 단계로 넘어갈 수 있습니다.** 중간에 끼어들거나 순서를 바꾸는 건 불가능에 가깝습니다. **"예측 가능하지만 경직되어 있다"**가 최대 특징이자 장단점입니다.

여러분, **'김밥 말기'** 해보신 적 있으시죠? 김밥을 쌀 때 순서가 어떻게 되나요?
1.  **1단계:** 밥 짓기 (재료 준비)
2.  **2단계:** 당근, 시금치, 단무지 등 속재료 손질 및 볶기/데치기
3.  **3단계:** 김 위에 밥 펴기
4.  **4단계:** 속재료 올리기
5.  **5단계:** 김 말기 (말이질)
6.  **6단계:** 썰기 및 접시 담기

이 순서, **절대 바꿀 수 없죠?** "아, 오늘은 김부터 깔고 밥 나중에 올리자" 했다간 김이 다 찢어지고 난리 납니다. "속재료 안 볶고 바로 넣자" 하면 물 생기고 맛없죠. **반드시 1번이 끝나야 2번을 하고, 2번이 끝나야 3번을 합니다.** 중간에 "잠깐, 당근 대신 오이 넣을게요!" 하고 2단계로 되돌아갈 수도 없습니다. 이미 김에 밥 펴놨는데 어떻게 되돌아가겠어요?

**이게 바로 '순차적 에이전트'의 작동 원리입니다.**

*   **입력(Input):** "김밥 한 줄 말아줘" (사용자 요청)
*   **Step 1 (Agent A):** `재료_준비_도구()` 호출 → 결과: "밥, 김, 당근, 시금치... 준비 완료"
*   **Step 2 (Agent B):** `속재료_손질_도구(준비된_재료)` 호출 → 결과: "손질된 속재료들 완료"
*   **Step 3 (Agent C):** `김밥_말기_도구(밥, 손질된_속재료)` 호출 → 결과: "김밥 말림 완료"
*   **Step 4 (Agent D):** `썰기_도구(김밥)` 호출 → 결과: "완성된 김밥 한 접시"
*   **최종 출력(Output):** 사용자에게 "다 말았어요!" 전달

각 단계는 **독립적인 작은 에이전트(또는 함수/도구)**일 수 있습니다. 하지만 **이들을 잇는 '파이프라인(Pipeline)'은 단 하나, 일직선**입니다.

## 🤖 2. 왜 '예측 가능함'이 최고의 무기일까? (장점)

스크립트에서는 **"They're predictable but rigid(예측 가능하지만 경직되어 있다)"**라고 했습니다. 보통 '경직됐다'는 말을 부정적으로 쓰지만, 엔지니어링 관점에서 **'예측 가능하다(Predictable)'**는 것은 **엄청난 축복**입니다.

### 🎯 비유: "매뉴얼 대로만 하는 신입 사원 vs 알아서 척척 하는 베테랑"

상상해 보세요. 여러분이 **프랜차이즈 커피숍 사장**입니다.

*   **순차적 에이전트(신입 알바생 '철수'):** 레시피 매뉴얼 1페이지부터 10페이지까지 **한 글자도 안 틀리고 따릅니다.** "아메리카노 주세요" 하면 1) 컵 꺼내기 2) 얼음 넣기 3) 샷 뽑기 4) 물 붓기 5) 뚜껑 덮기 6) 건네기. **절대 실수 안 합니다.** "샷 두 번 뽑아주세요"라는 예외 요청만 없다면, 100잔 중 100잔 다 똑같은 맛, 똑같은 양, 똑같은 시간에 나옵니다. **디버깅(문제 찾기)도 쉽죠.** "왜 맛이 짰어?" → "아, 3번 단계에서 샷을 두 번 뽑았네? 코드 3번째 줄 고치면 돼." 끝.
*   **기타 에이전트(베테랑 '영희'):** 손님 얼굴 보고 "오늘 피곤해 보이시네, 샷 한 번 더 넣어드릴게요" 하고 융통성 있게 줍니다. 맛있긴 한데, **매번 맛이 다를 수 있습니다.** "왜 오늘은 연해?" 물어보면 "아, 원두 상태가 좀 그래서 물 양을 조절했어요"라 설명하는데, 이걸 코드로 고치려면 '영희의 직관'을 다 분석해야 하니 엄청 복잡합니다.

> **💡 개념 돋보기: 왜 '순차적'이 엔지니어링에선 사랑받을까?**
> > **1. 디버깅(Debugging)이 세상 쉽습니다.**
> > 문제가 생기면 "어? 3번 단계에서 에러 났네?" 하고 그 단계만 보면 됩니다. 전체 흐름을 추적할 필요가 없어요.
> > **2. 테스트(Test)가 모듈 단위로 가능합니다.**
> > 1단계 '재료 준비' 모듈만 따로 테스트하고, 2단계 '손질' 모듈만 따로 테스트하면 됩니다. 레고 블록 쌓듯 검증 가능하죠.
> > **3. 병렬 처리 최적화가 명확합니다.**
> > "1단계와 2단계는 서로 상관없네? 그럼 동시에 돌려서 시간 단축하자!" 같은 최적화 판단이 코드만 봐도 보입니다.
> > **4. 감사 추적(Audit Trail) & 규제 준수(Compliance)에 강합니다.**
> > 금융, 의료, 법률처럼 **"왜 이 결정을 내렸는지 단계별로 증명해야 하는 분야"**에서는 이 '일직선 로그'가 법적 증거가 됩니다. "1단계에서 신용조회 했고, 2단계에서 한도 계산 했고, 3단계에서 승인 냈음" 이 로그 하나가 소송에서 이겨줍니다.

## 🛑 3. 그런데 왜 '경직됐다'고 할까? (단점과 한계)

김밥 예시로 돌아가 볼까요? 손님이 **"저 당근 알레르기 있는데 당근 빼고 말아주세요"**라고 하면 어떨까요?

*   **순차적 에이전트(철수):** "죄송합니다. 제 매뉴얼 2단계는 '당근, 시금치, 단무지 손질'로 고정되어 있습니다. 당근을 빼는 옵션은 매뉴얼에 없습니다. 매뉴얼을 새로 짜오세요(코드 수정/재배포) 해야 합니다."
*   **결과:** 손님 기다리게 하고, 개발자 불러서 `step_2_prepare_ingredients()` 함수 안에 `if carrot_allergy: remove_carrot()` 로직 추가하고, 테스트하고, 배포하고... **수시간에서 수일 걸립니다.**

스크립트에서 **"Rigid(경직됨)"**이라고 표현한 건 정확히 이 지점입니다.

> **💡 개념 돋보기: 순차적 에이전트가 무너지는 순간들 (The "Rigid" Moment)**
> > **1. 예외 상황(Exception Handling)에 약합니다.**
> > "만약 API 호출 실패하면?" → `try-except`로 다음 단계로 넘기거나 멈춰야 하는데, 순차적 구조상 "실패했으니 1단계로 돌아가서 다른 API 써보자" 같은 **동적 우회(Dynamic Fallback)**를 짜려면 코드가 스파게티가 됩니다.
> > **2. 조건부 분기(Conditional Branching)가 하드코딩됩니다.**
> > "사용자 등급이 VIP면 3단계 건너뛰고 4단계로" 같은 로직을 넣으려면 파이프라인 정의 코드 안에 `if user.tier == 'VIP': skip_step_3()` 를 박아둬야 합니다. 분기 조건이 10개, 20개 생기면? **코드가 '이프(if) 지옥'이 됩니다.**
> > **3. 컨텍스트(Context) 공유가 단방향입니다.**
> > 1단계 결과가 2단계 입력, 2단계 결과가 3단계 입력... **뒤에서 앞으로 정보를 보낼 수 없습니다.** 3단계에서 "어? 이 데이터 1단계에서 좀 더 자세히 가져왔어야 했는데"라고 깨달아도 **이미 지나간 버스**입니다. 다시 처음부터 돌려야 해요.
> > **4. 인간의 개입(Human-in-the-loop)이 끼어들 틈이 없습니다.**
> > "2단계 결과 보고 제가 승인한 뒤 3단계 진행할게요" 같은 **중간 승인 프로세스**를 넣으려면 파이프라인을 2개로 쪼개고(1~2단계, 3~4단계), 중간에 큐(Queue)나 DB 상태 저장 로직을 직접 다 짜야 합니다.

## 🛠️ 4. 실전 코드 수준의 구현 상상하기 (Pseudo Code)

비전공자분들도 "아, 코드가 대충 이렇게 생겼구나" 감 잡으시라고 파이썬 비슷한 **의사코드(Pseudocode)**로 순차적 에이전트 파이프라인을 그려드릴게요. 어렵지 않아요, 그냥 **레시피 순서대로 적어놓은 것**뿐이니까요.

```python
# 순차적 에이전트 파이프라인 정의 (마치 김밥 레시피 카드처럼)

class SequentialKimchiAgentPipeline:
    def __init__(self):
        # 각 단계는 독립적인 '도구(Tool)' 또는 '작은 에이전트'라고 가정
        self.step_1_prep = PrepareIngredientsAgent()   # 1단계: 재료 준비 에이전트
        self.step_2_cook = CookIngredientsAgent()      # 2단계: 요리 에이전트
        self.step_3_roll = RollKimchiAgent()           # 3단계: 말기 에이전트
        self.step_4_cut  = CutAndServeAgent()          # 4단계: 썰기/서빙 에이전트

    def run(self, user_request: str) -> FinalKimchi:
        print(f"[시작] 주문 접수: {user_request}")
        
        # --- Step 1: 재료 준비 (입력: 주문, 출력: 재료꾸러미) ---
        # 이 함수가 끝나기 전엔 절대 Step 2로 못 감
        ingredients = self.step_1_prep.execute(order=user_request)
        print(f"[1단계 완료] 재료 준비됨: {ingredients.list}")
        
        # --- Step 2: 요리/손질 (입력: 재료꾸러미, 출력: 손질된재료) ---
        # Step 1의 결과물(ingredients)을 '그대로' 받아서 씀
        cooked_ingredients = self.step_2_cook.execute(raw_materials=ingredients)
        print(f"[2단계 완료] 손질 완료: {cooked_ingredients.status}")
        
        # --- Step 3: 말기 (입력: 손질된재료, 출력: 김밥줄기) ---
        # 여긴 '밥'이 필요할 수 있는데, 그건 Step 1 결과 안에 들어있어야 함
        # (만약 Step 1이 밥을 안 줬으면? 여기서 에러 터짐 -> 경직성의 예시)
        kimchi_roll = self.step_3_roll.execute(prepared_food=cooked_ingredients)
        print(f"[3단계 완료] 김밥 말림: {kimchi_roll.length}cm")
        
        # --- Step 4: 썰기/서빙 (입력: 김밥줄기, 출력: 최종접시) ---
        final_dish = self.step_4_cut.execute(roll=kimchi_roll)
        print(f"[최종 완료] 서빙 준비: {final_dish.plate_count}접시")
        
        return final_dish

# 실행
pipeline = SequentialKimchiAgentPipeline()
my_lunch = pipeline.run("참치김밥 2줄, 당근 빼고") 
# 💥 주의: 현재 코드엔 "당근 빼고" 처리 로직이 없음! 
# => 당근 들어간 김밥 나옴 (Rigid 함의 극치)
```

**이 코드에서 보이는 특징:**
1.  **`execute()` 메서드 체이닝:** `step_1` 결과 → `step_2` 입력 → `step_3` 입력... **데이터 흐름이 단방향 화살표(→) 하나뿐입니다.**
2.  **상태 저장 없음:** `self.memory` 같은 거 없습니다. 그냥 지역 변수(`ingredients`, `cooked_ingredients`...)로 흘려보낼 뿐이죠. 끝나면 다 날아갑니다.
3.  **제어 흐름 고정:** `if`, `for`, `while` 같은 제어문이 파이프라인 **밖(호출부)**에 있거나, **안에 하드코딩**되어 있습니다. 런타임에 동적으로 "아 2단계 건너뛰자" 못 합니다.

## 🏗️ 5. 그렇다면 언제 써먹어야 할까? (적절한 사용처)

"경직됐다니 안 쓰면 되는 거 아냐?" 하실 수 있는데, **세상 일 중 80%는 이 '경직된 순서'만으로도 충분합니다.** 오히려 융통성 부리다 사고 나는 게 더 무섭죠.

> **💡 개념 돋보기: 순차적 에이전트, 여기가 '맛집'입니다 (Best Fit Scenarios)**
> > **1. ETL / 데이터 파이프라인 (Extract → Transform → Load)**
> > "매일 새벽 3시, DB에서 데이터 뽑고(Extract) → 정제하고(Transform) → 데이터웨어하우스에 적재(Load)". 이거 순서 바뀌면 데이터 망가집니다. **무조건 순차적**이 정답입니다. Airflow, Dagster, Prefect 같은 도구들이 다 이 패턴 기반이에요.
> > **2. 문서 처리 워크플로우 (OCR → 요약 → 번역 → 저장)**
> > PDF 업로드 → 텍스트 추출 → 청크 분할 → 임베딩 생성 → 벡터 DB 저장. **이전 단계 출력이 다음 단계 입력으로 필수**인 경우. RAG(Retrieval-Augmented Generation) 인덱싱 파이프라인이 전형적입니다.
> > **3. CI/CD 배포 파이프라인 (Build → Test → Staging Deploy → Prod Deploy)**
> > 테스트 안 통과했는데 스테이징 배포하면 안 되죠. 프로덕션 배포 전 승인 단계(Human Gate)가 끼어들기)가 있어도 **단계를 쪼개서 순차적으로 연결**하면 됩니다.
> > **4. 규제가 강한 도메인의 결정론적 프로세스 (대출 심사, 보험 청구, 의료 진단 보조)**
> > "1. 신분증 확인 2. 소득 증빙 3. 신용 조회 4. 한도 산출 5. 승인/거절". **감사 로그 남기기 좋고, 규정 준수 증명하기 좋고, 실수 없음.** 여기가 순차적 에이전트의 꽃밭입니다.
> > **5. 단일 목적의 명확한 자동화 스크립트 대체**
> > "매일 아침 뉴스 크롤링 → 요약 → 슬랙 전송" 같은 크론잡(Cron Job) 대체용. 굳이 복잡한 추론 에이전트 안 써도 됨.

---

## 🧠 6. 핵심 요약: "순차적 에이전트 = 믿을 수 있는 '매뉴얼 인간'"

자, 오늘 배운 내용을 내 것으로 만들기 위해 **한 문장씩 입으로 읽어보며 정리**해 볼까요?

1.  **정의:** 순차적 에이전트는 **정해진 단계(Step 1 → 2 → 3...)를 예외 없이 순서대로 실행**하는 패턴이다. (스크립트: *"run step-by-step like an assembly line"*)
2.  **데이터 흐름:** **단방향(One-way)**이다. 앞 단계의 출력이 뒤 단계의 입력이 된다. 뒤로 되돌아갈 수 없다.
3.  **최대 강점 - 예측 가능성(Predictability):** **"넣은 대로 나온다."** 디버깅 쉽고, 테스트 쉽고, 로그 보기 좋고, 규정 준수에 최적이다.
4.  **최대 약점 - 경직성(Rigidity):** **"예외가 터지면 못 버틴다."** 조건부 분기, 동적 우회, 중간 피드백 반영, 컨텍스트 역참조 모두 **코드 수정(하드코딩) 없인 불가능**하다.
5.  **기억력(Memory):** **사실상 없다.** 파이프라인 실행 중간에 생긴 중간 값들은 지역 변수로만 존재하고, 파이프라인이 끝나면 휘발된다. (다음 챕터에서 배울 '상태를 가진 에이전트'와 대비됨)
6.  **쓰임새:** **순서가 생명이자 법칙인 작업(데이터 파이프라인, 문서 처리, 배포, 규제 준수 프로세스)**에서 **'믿고 쓰는 표준 템플릿'**으로 쓴다.

## 🚀 7. 다음 챕터 예고: "그럼 유연하게 대처하는 에이전트는 어떻게 만들지?"

순차적 에이전트(철수)는 매뉴얼만 보고 일하니 **'당근 알레르기' 같은 돌발 상황에 멘붕**옵니다. 하지만 현장에는 **"아, 손님 알레르기 있으시대요? 그럼 2단계에서 당근 빼고 오이 더 넣어서 3단계로 넘기세요!"**라고 **상황 판단해서 지시를 내리는 '반장(Supervisor)'**이나, **"내가 알아서 당근 대신 오이 넣을게요"** 하고 **자율 판단하는 '베테랑(Autonomous Agent)'**이 필요하겠죠?

다음 챕터에서는 이 **'경직됨'을 깨부수는 두 가지 패턴**, 바로 **계층적 에이전트(Hierarchical Agents: 반장 스타일)**와 **비순차/루프 에이전트(Non-sequential/Loop Agents: 베테랑 스타일)**의 세계로 떠나보겠습니다. 기대해 주세요! 👋
