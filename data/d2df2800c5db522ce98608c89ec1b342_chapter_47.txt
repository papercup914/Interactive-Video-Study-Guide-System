# 챕터 3. 기초 인프라(캐싱, 컨텍스트 관리, 루프 실행)는 플랫폼에 위임: "무거운 짐은 플랫폼에게, 우리는 '뇌'만 집중하면 된다"

---

안녕하세요, 여러분! 지난 챕터까지 우리는 '에이전트라는 똑똑한 비서'를 만들기 위해 **'두뇌(에이전트 정의)'**와 **'손(환경/도구)'**을 분리하고, 이 둘을 **'세션(작업 공간)'**으로 연결하는 법을 배웠습니다. 마치 레스토랑에서 **셰프(두뇌)**가 레시피를 고민하고, **주방(손/환경)**에서 실제로 요리하며, **주문표(세션)**가 이 둘을 이어주는 그림을 그렸죠.

그런데 여러분, 이 레스토랑을 실제로 열려면 셰프와 주방만 있으면 될까요? **전기, 가스, 수도, 환기 시설, 식재료 창고 관리, 위생 검사, 화재 보험...** 이런 '보이지 않는 기반 시설(인프라)'이 없다면 아무리 훌륭한 셰프라도 요리 한 그릇 내놓기 전에 문을 닫게 됩니다.

오늘 배울 **'기초 인프라 플랫폼 위임'** 이야기는 바로 이 **"보이지 않는 무거운 짐을 누가 질 것인가?"**에 대한 이야기입니다. 내 노트북(로컬 환경)에서 직접 에이전트 루프를 돌리고, 컨텍스트를 관리하고, 캐싱을 챙기는 건 **'직접 발전소 짓고, 수도관 깔고, 가스관 연결해서 식당 차리는 일'**이나 다름없습니다. 클로드 매니지드 에이전트(Claude Managed Agents) 같은 플랫폼은 이 모든 **'도시 기반 시설'을 이미 완벽하게 갖춘 '최첨단 푸드코트'**를 우리에게 무료로 빌려주는 것과 같습니다.

자, 그럼 이 '마법 같은 푸드코트'가 구체적으로 우리의 어떤 짐을 덜어주는지, **비전공자 눈높이에서 아주 낱낱이, 그리고 길게** 파헤쳐 보겠습니다.

---

## 1. '에이전트 루프 서버 사이드 실행'이란? - "내 노트북 꺼도 요리는 계속된다"

스크립트에서 발표자는 이렇게 말했습니다.

> *"Claude manage agent has the agent loop run server side. This means that a lot of the complexities that come with managing hosting and scaling are abstracted away, and when you close your laptop, or you hit hard refresh on your agent... everything is maintained..."*

### 🍳 일상 비유: **'내 집 주방' vs '클라우드 주방(Cloud Kitchen)'**

상상해 보세요.

*   **로컬 실행 (내 노트북에서 직접 돌리기) = 내 집 주방에서 장사하기**
    *   손님(유저 요청)이 오면 내가 직접 가스불 켜고(서버 실행), 재료 다듬고(컨텍스트 로드), 요리하고(추론), 그릇 치우고(메모리 정리) 해야 합니다.
    *   **치명적 단점:** 내가 화장실 가려고 **노트북 덮개를 닫는 순간(잠자기 모드)**, 가스불이 꺼지고 요리가 멈춥니다. 손님은 음식을 못 받고 기다리다 갑니다. 내가 정전돼서 노트북이 꺼지면? 영업 끝. 내 컴퓨터 성능이 안 좋아서 요리가 느리면? 손님은 짜증 나고 갑니다. 24시간 켜두려니 전기세(컴퓨팅 비용) 폭탄에, 팬 소음은 덤입니다.

*   **서버 사이드 실행 (플랫폼 위임) = 배달 전문 '클라우드 주방(다크 키친)' 입점하기**
    *   나는 **'레시피(에이전트 코드/프롬프트)'만 전달**하면 됩니다.
    *   **주방(플랫폼 서버)**은 24시간 365일, 정전 대비 비상 발전기까지 갖춘 최첨단 시설에서 돌아갑니다.
    *   내가 **집에 가서 자고(노트북 끄고), 샤워하고(새로고침), 여행 가 있어도** 주방은 꺼지지 않고 주문을 받아 요리(에이전트 루프 실행)합니다.
    *   손님이 몰려도(트래픽 폭증) 주방이 알아서 불판(서버/GPU)을 늘려줍니다(오토스케일링). 내가 신경 쓸 필요 없습니다.

> **💡 개념 돋보기: '에이전트 루프(Agent Loop)'가 뭐길래 이렇게 중요해?**
>
> > 에이전트 루프는 **에이전트의 '심장 박동'**과 같습니다.
> > 1.  **관찰(Observe):** 사용자 메시지, 도구 실행 결과, 환경 상태를 읽음.
> > 2.  **사고(Think/Reasoning):** LLM(뇌)에게 "이제 뭐 할까?" 물어봄 (프롬프트 + 히스토리 + 도구 스펙 전달).
> > 3.  **행동(Act):** LLM이 "이 도구 써!"라고 하면, 해당 도구(API, 코드 실행 등)를 실제로 실행함.
> > 4.  **반영(Reflect):** 실행 결과를 다시 컨텍스트(기억)에 저장하고 1번으로 돌아감.
> >
> > 이 **무한 루프(while True: ...)**가 **내 컴퓨터가 아닌 '플랫폼의 튼튼한 서버'에서 돈다**는 게 핵심입니다. 내 로컬에서 돌리면 내 컴퓨터가 이 무한 루프의 '엔진' 역할을 해야 하니, 내 컴이 꺼지면 심장이 멈춥니다. 플랫폼에 위임하면 **'영구 기관' 심장**을 빌려 쓰는 셈이죠.

## 2. 플랫폼이 떠맡아 주는 '보이지 않는 3대 짐': 캐싱, 컨텍스트 관리, 내구성

발표자는 "hosting and scaling", "durability, reliability" 등을 추상화해준다고 했습니다. 이건 개발자 용어로 치면 **'지옥의 3종 세트'**를 플랫폼이 다 해준다는 뜻입니다. 하나씩 일상 비유로 풀어볼게요.

### ① 캐싱(Caching): "매번 장 보러 가지 마세요, 냉장고 쓰세요"

*   **문제 상황:** 에이전트가 "우리 서비스 현재 상태 어때?"라는 질문을 100번 받으면, 매번 100번 다 데이터베이스 조회하고, API 호출하고, LLM에게 "이 데이터 분석해줘" 부탁할까요? **미쳤죠.** 돈(토큰 비용/시간) 다 날립니다.
*   **로컬에서 직접 구현하려면?** "Redis 서버 깔고, TTL(Time To Live) 설정하고, 캐시 무효화(Cache Invalidation) 로직 짜고, 캐시 미스 났을 때 폴백(Fallback) 처리하고..." **이거 별도 프로젝트급 일입니다.**
*   **플랫폼 위임 시:** 플랫폼이 **'초고속 냉장고(분산 캐시 레이어)'**를 이미 깔아놨습니다. "이 쿼리 결과 5분간 기억해둬" 한 마디면(혹은 자동으로) 끝. **우린 '냉장고 관리인' 안 뽑아도 됩니다.**

### ② 컨텍스트 관리(Context Management): "뇌 용량 무한 아님, '요약 비서'가 필요해"

*   **문제 상황:** 에이전트 루프가 50바퀴 돌았다고 칩시다. 대화 기록 + 도구 실행 로그 + 에러 메시지 + 시스템 프롬프트... 이걸 다 LLM에게 매번 보내면 **'컨텍스트 윈도우(입력 한도)' 초과**로 터지거나, 토큰 비용이 억 단위로 나옵니다.
*   **로컬에서 직접 구현하려면?**
    *   "슬라이딩 윈도우(최근 N개만 유지) 할까? 중요도 기반 필터링 할까? 벡터 DB에 임베딩해서 RAG로 뽑아쓸까? 요약 모델 따로 돌려서 압축할까?"
    *   이거 **'메모리 관리 운영체제'** 만드는 수준입니다. 버그 나면 에이전트 치매 걸립니다(앞뒤 안 맞음).
*   **플랫폼 위임 시:** 플랫폼이 **'베테랑 비서 실장님'**을 붙여줍니다. "사장님(LLM), 이건 3일 전 얘기라 굳이 안 알려드려도 돼요. 핵심만 3줄로 요약해놨으니 이거만 보세요." **자동 요약, 중요도 선별, 벡터 검색 연동**을 플랫폼 레벨에서 최적화해 줍니다. 우린 **"이 대화 중요해/안 중요해"** 정도만 힌트 주면 끝.

### ③ 내구성/신뢰성(Durability & Reliability): "요리하다 칼 떨어뜨려도, 불 꺼져도 요리는 이어져야 한다"

*   **스크립트 핵심 문장:** *"when you close your laptop... everything is maintained, and you don't have to worry about durability, reliability..."*
*   **로컬 실행의 악몽:**
    *   에이전트 루프 10번째 돌다가 **와이파이 끊김** -> 세션 증발, 처음부터 다시.
    *   도구 실행 중 **OOM(메모리 부족) 크래시** -> 중간 상태(체크포인트) 없음 -> 처음부터 다시.
    *   배포 서버 **새 버전 업데이트하려고 재시작** -> 돌고 있던 에이전트 강제 종료 -> 사용자 화면에 "Error" 뜸.
*   **플랫폼의 마법 (Stateful Serverless / Actor Model 같은 기술 쓰지만 우린 몰라도 됨):**
    *   플랫폼은 에이전트 루프의 **매 스텝마다 '스냅샷(체크포인트)'을 찍어 영구 저장소(DB)에 보관**합니다.
    *   내 노트북 꺼져도, 플랫폼 서버가 재부팅돼도, **"아, 아까 7번째 스텝까지 했네? 8번째부터 이어서 하자"** 하고 복구합니다.
    *   이걸 **'내구성 있는 실행(Durable Execution)'**이라고 하는데, 이거 직접 구현하려면 **Temporal, Cadence, Orkes** 같은 워크플로 엔진 공부하고, 상태 머신 짜고, 재시도 정책(Retry Policy) 정의하고... **몇 달 걸립니다.** 플랫폼은 이걸 **"공짜로, 기본으로"** 줍니다.

> **💡 개념 돋보기: 왜 '세션(Session)'이 그냥 연결 고리가 아니라 '생명줄'인가?**
>
> > 스크립트에서 *"A single session has a spun up agent instance within an environment... stream events back to your user"*라고 했죠?
> >
> > 이 **세션 객체**가 바로 **'영구 저장되는 작업 장부'**입니다.
> > *   로컬에서 돌리면: 이 장부가 내 램(RAM)에만 있음 -> 전원 나가면 증발.
> > *   플랫폼에서 돌리면: 이 장부가 **플랫폼의 분산 데이터베이스(예: PostgreSQL, Cassandra 등)에 실시간 동기화**됨.
> >
> > 그래서 **"세션 ID만 알면 언제든, 어디서든(다른 기기에서), 누구든(다른 개발자가) 이어서 볼 수 있고, 제어할 수 있다"**는 겁니다. 이게 바로 '신뢰성'의 정체입니다.

## 3. '두뇌와 손의 분리(Decoupling)'가 인프라 비용을 어떻게 아껴주는가? - "90% 지연 시간 감소의 비밀"

스크립트 후반부에 발표자가 **아주 중요한 비하인드 스토리**를 공개합니다. 이 부분이 바로 **"인프라 위임이 단순한 편의가 아니라 '성능/비용 혁신'이다"**를 증명하는 대목입니다.

> *"Previously, with a lot of agent harnesses, we saw the agent loop coupled tightly with tool execution... you had to spin up containers for every single session... With this now decoupled, our teams actually saw reductions in time to first token, along the lines of a over 90% reduction in TTFT for our P95 metrics on latency."*

### 🚛 일상 비유: **'이사 트럭' vs '고속열차(KTX)'**

#### **구 방식 (Coupled: 루프 + 도구 실행 = 한 컨테이너)**
*   **상황:** 손님 한 명(세션 하나) 오면 -> **전용 트럭(컨테이너) 한 대 배정** -> 트럭 안에 **운전기사(에이전트 루프/두뇌)** + **짐 싣는 인부들(도구 실행 환경/손)** + **짐(파일시스템, 크리덴셜)** 다 태움.
*   **문제점:**
    1.  **출발 대기 시간(콜드 스타트):** 트럭 시동 걸고, 인부 부르고, 짐 싣고... **이게 'Time To First Token(TTFT, 첫 토큰 생성 시간)'의 주범.** 손님은 문 앞에서 트럭 준비될 때까지 기다림.
    2.  **자원 낭비:** 손님이 "안녕" 한마디만 하고 가도 트럭은 왕복해야 함. 인부(도구 환경)는 놀고 있는데 기사(두뇌) 월급 주고 트럭 유지비 나감.
    3.  **보안 구멍:** 인부가 기사랑 같은 차 타니까, 기사 몰래 짐(크리덴셜/파일) 뒤질 수 있음 -> **샌드박싱 어려움.**

#### **신 방식 (Decoupled: 루프는 중앙 관제탑, 손은 원격 조종)**
*   **상황:**
    *   **두뇌(에이전트 루프)** = **중앙 관제탑(서버리스 함수/경량 프로세스)**. 엄청 가볍고, **항상 켜져 있음(웜 풀)**. 생각만 함.
    *   **손(환경/도구)** = **전국 곳곳의 물류 창고(샌드박스 컨테이너/VM)**. 필요할 때만 "창고 3번! 박스 옮기기 실행!" 하고 API 호출로 시킴.
*   **효과 (90% 지연 감소의 비밀):**
    1.  **TTFT 폭락:** 손님 오면 **관제탑(두뇌)은 이미 깨어있음**. 즉시 "생각" 시작 -> 첫 토큰 나옴. 트럭 시동 걸 시간 **0초**.
    2.  **비용 절감:** "파일 읽기" 하나 시키려고 무거운 컨테이너 안 띄워도 됨. 가벼운 함수 호출로 끝.
    3.  **보안 강화:** 관제탑(두뇌)은 **크리덴셜(열쇠) 모름**. 창고(손)만 열쇠 가지고 있음. 관제탑 해킹당해도 열쇠는 안전. **자격 증명 격리(Credential Isolation)** 완성.

> **💡 개념 돋보기: TTFT(Time To First Token)랑 P95가 왜 중요해?**
>
> > *   **TTFT (Time To First Token):** 사용자가 "헤이 클로드"라고 부르고 **첫 글자('네' 혹은 '알')가 화면에 뜨기까지 걸린 시간**.
> >     *   웹에서는 0.1초 차이도 '느리다/빠르다' 체감 갈림. 에이전트는 도구 쓰느라 원래 느린데, 여기서 **컨테이너 뜨는 시간(수초~수십 초)**이 붙으면 사용자 경험 **최악**.
> > *   **P95 (Percentile 95):** "상위 5% 느린 경우를 뺀, 나머지 95%의 사용자가 겪는 지연 시간".
> >     *   평균(Average)은 '부자 1명, 거지 99명' 있으면 평균 소득 높게 나옴. **P95는 '대다수 일반 사용자의 경험'**을 보여주는 **서비스 품질의 황금 지표**.
> > *   **90% 감소 의미:** 기존 P95가 10초였다면 -> **1초**. 기존 5초 -> **0.5초**. **'답답한 봇'에서 '즉시 반응하는 비서'로 등급 업.**

## 4. 실습 코드(`agent.py`, `environment.py`, `session.py`)가 이렇게 가벼운 이유

실습 부분에서 발표자가 말한 내용을 떠올려 보세요.

> *"So, let's go ahead and start off with this very first part, which is the agent... The next is the environments... Sessions are next... A key thing here... agent loop run server side... abstracted away..."*

여러분이 실습에서 `agent.py`에 **모델 이름, MCP 서버 주소, 스킬 목록**만 적고, `environment.py`에 **도커 이미지 이름, 환경 변수**만 적고, `session.py`에서 둘을 `session.create()` 한 줄로 묶는 이유. **그 뒤에 숨은 '인프라 코드 10만 줄'을 플랫폼이 이미 다 짜놨기 때문입니다.**

만약 여러분이 이걸 **직접 쿠버네티스(Kubernetes)에 올린다고 상상해 보세요.**

```yaml
# 여러분이 안 짜도 되는 가상의 인프라 설정들 (플랫폼이 다 해줌)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: agent-loop-runner
spec:
  replicas: 3 # 오토스케일링? HPA 설정 별도
  template:
    spec:
      containers:
      - name: agent-brain
        image: my-agent:latest
        env:
        - name: ANTHROPIC_API_KEY
          valueFrom: secretKeyRef... # 시크릿 관리
        resources:
          limits:
            memory: "4Gi" # OOM 터지면 재시작 정책?
            nvidia.com/gpu: 1 # GPU 할당?
      - name: tool-executor-sandbox # 손(환경) 분리용 사이드카
        image: sandbox:secure
        securityContext:
          runAsNonRoot: true
          readOnlyRootFilesystem: true # 샌드박싱
        volumeMounts:
        - name: empty-dir
          mountPath: /tmp
# ... Service, Ingress, ConfigMap, Secret, PVC, NetworkPolicy, PodDisruptionBudget ...
# 상태 저장을 위한 StatefulSet + PersistentVolume for Checkpointing...
# 분산 트레이싱(Jaeger), 로깅(ELK), 메트릭(Prometheus/Grafana) 연동...
# 블루/그린 배포, 카나리 릴리즈 파이프라인 (ArgoCD/Flux)...
```

**이 지옥 같은 YAML 지옥에서 우리를 구해준 게 바로 "플랫폼에 위임"입니다.**
우린 그냥 **파이썬 클래스 3개(`Agent`, `Environment`, `Session`)** 정의하고 끝낸 겁니다.

이 챕터의 핵심 메시지를 한 문장으로 담으면 이렇습니다.

> **"에이전트 개발의 본질은 '어떻게 생각할까(프롬프트/추론)', '어떻게 행동할까(도구/스킬)'를 설계하는 것이다. '서버 어떻게 켤까', '메모리 어떻게 아낄까', '꺼졌을 때 어떻게 복구할까' 같은 인프라 잡일은 플랫폼에게 맡기고, 우리는 '두뇌 설계자'에만 집중하자."**

### ✅ **이 챕터에서 꼭 기억해야 할 3가지 키워드**

1.  **Server-side Agent Loop (서버 사이드 에이전트 루프):** 내 컴퓨터 끄고 자도 에이전트는 일함. **'영구 심장' 장착.**
2.  **Decoupled Architecture (분리된 아키텍처):** 두뇌(루프)는 가볍게 중앙에서, 손(도구)은 무겁게 현장에서. **'90% 지연 감소', '보안 격리' 동시 달성.**
3.  **Abstracted Durability (추상화된 내구성):** 체크포인트, 상태 저장, 재시도, 스케일링... **'운영 지옥'을 '함수 호출 한 줄'로 해결.**
