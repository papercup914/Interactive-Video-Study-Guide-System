# 챕터 1. 기존 챗봇과의 차이점: 단일 응답 생성 vs 의사결정 및 행동 수행

안녕하세요! 여러분, 오늘부터 함께 **'AI 에이전트(AI Agent)'**라는 놀라운 세계로 여행을 떠나볼 거예요. 혹시 지금까지 챗GPT나 다른 AI 챗봇을 쓰면서 "대답은 잘하는데, **내가 시킨 일을 대신 해주는 건 아니네?**"라고 느껴보신 적 있으신가요? 예를 들어 "이번 주말 서울 날씨 알려줘"라고 물으면 "날씨가 맑고 20도입니다"라고 **대답만** 하죠. 하지만 **"이번 주말 서울 날씨 확인해서, 비 오면 우산 챙기라고 알림 설정해주고, 맑으면 근처 피크닉 장소 예약해줘"**라고 시키면? 기존 챗봇은 "알겠습니다!"라고 말만 하고 끝납니다. **직접 예약을 하거나 알림을 설정하는 '행동'은 못 하거든요.**

오늘 배울 **AI 에이전트**는 바로 이 지점에서 출발합니다. **"대답만 하는 입"**이 아니라, **"생각해서 행동하는 손과 발"**을 가진 소프트웨어라고 보시면 돼요. 자, 그럼 기존 챗봇과 AI 에이전트가 도대체 어떻게 다른지, 우리 일상생활에 비유해서 아주 자세히 뜯어보겠습니다.

---

## 1. 식당에서 생긴 일: '메뉴판만 읽어주는 알바생' vs '주문부터 서빙까지 다 해주는 매니저'

이해하기 쉽게 **식당** 상황을 상상해 볼게요.

### 상황 A: 기존 챗봇 (단일 응답 생성) = "메뉴판만 읽어주는 신입 알바생"
여러분이 식당에 앉아서 **"여기 김치찌개 맛있어요? 뭐가 들어갔어요?"**라고 물었어요.
*   **알바생(챗봇):** "네, 김치찌개에는 김치, 돼지고기, 두부, 파가 들어가고요, 매콤하면서 깊은 맛이 납니다. **이게 다예요.**" → **대답(응답) 생성 후 끝.**
*   여러분이 **"그럼 김치찌개 하나 주문이요!"**라고 해도, 이 알바생은 **"네, 알겠습니다! 김치찌개에는 김치, 돼지고기..."** 하고 메뉴 설명만 또 반복할 뿐, **주방에 주문서를 넣거나 음식을 갖다 주지 않아요.** 입으로만 "알겠어요" 하지, **행동(주문 접수, 서빙)은 하지 않는 거죠.**

### 상황 B: AI 에이전트 (의사결정 및 행동 수행) = "일 처리 다 해주는 베테랑 매니저"
같은 질문에 **"여기 김치찌개 맛있어요?"**라고 물었을 때.
*   **매니저(에이전트):** "네, 저희 김치찌개는 3년 묵은 묵은지로 끓여서 깊은 맛이 일품이에요. **손님, 드셔보시겠어요?**" → **판단(의사결정)**
*   여러분이 **"응, 하나 주문해줘"**라고 하면?
*   **매니저(에이전트):** 
    1.  주방에 **"김치찌개 1인분 주문 들어갑니다!"**라고 소리칩니다 (**도구 사용/Action: API 호출**).
    2.  주방에서 **"다 나왔어요!"**라고 하면 받아서 테이블에 갖다 줍니다 (**결과 확인/Observation**).
    3.  **"자, 여기 김치찌개 나왔습니다. 맛있게 드세요!"**라고 마무리합니다 (**다음 행동 결정/Next Step**).

**차이 느껴지시나요?** 기존 챗봇은 **'입'만 있고 '손발'이 없는 상태**예요. 반면 AI 에이전트는 **'뇌(추론)'로 상황을 판단하고, '손발(도구/Tool)'을 써서 실제 세계에서 일이 벌어지게 만듭니다.**

## 2. 핵심 차이점 3가지: "생각한다(Reason), 행동한다(Act), 적응한다(Adapt)"

영상 스크립트에서는 에이전트가 **"요청을 보고, 필요한 단계가 뭔지 파악하고, API를 호출하거나 코드를 실행하고, 결과를 보고 다음에 뭘 할지 결정한다"**고 설명하고 있어요. 이걸 세 단계로 쪼개서 비유해 드릴게요.

### ① 생각하기 (Reasoning): "어떻게 하지?" - 내비게이션의 '경로 탐색'
여러분이 내비게이션에 **"강남역까지 가자"**고 찍었을 때, 내비게이션이 가만히 있는 게 아니죠? **"현재 위치에서 강남역까지 최단 경로는 올림픽대로 타고 가는 거네? 근데 지금 올림픽대로 막히네? 그럼 강변북로로 우회하자."** 이렇게 **머릿속으로 시뮬레이션하며 최적의 경로를 '생각'**해냅니다.
*   **기존 챗봇:** "강남역은 서울특별시 강남구에 있는 지하철역입니다." (정보만 줌)
*   **AI 에이전트:** "지금 교통상황 보니 올림픽대로 막히니까 강변북로로 가세요. 5분 후에 우회전하세요." (상황 판단 → **의사결정**)

> **💡 개념 돋보기: 추론(Reasoning)이란?**
> > 단순히 저장된 지식을 꺼내 읽는 게 아니라, **주어진 목표(목적지)에 도달하기 위해 현재 상황(교통정보)을 분석하고, 여러 선택지 중 최적의 행동 순서(경로)를 논리적으로 짜내는 과정**입니다. 에이전트는 "무슨 말을 할까?"가 아니라 **"무슨 행동을 할까? 어떤 순서로 할까?"**를 고민합니다.

### ② 행동하기 (Acting): "실행하자!" - 내비게이션이 '엑셀/브레이크'를 밟는 자율주행차
생각만 하고 끝나면 소용없죠. 에이전트는 **실제 도구(Tool)를 써서 세상에 변화를 줍니다.**
*   **도구(Tool)란?** 에이전트가 쓸 수 있는 **'손발'**입니다. 날씨 API 호출하기, 파이썬 코드 실행해서 엑셀 파일 만들기, 구글 검색하기, 이메일 보내기, 데이터베이스 조회하기 등이 다 도구예요.
*   **비유:** 내비게이션이 "우회전하세요"라고 **소리만 내는 게 아니라, 핸들을 돌려서 차를 실제로 우회전시키는 자율주행차**가 된 겁니다.

> **💡 개념 돋보기: 도구 사용(Tool Use / Function Calling)이란?**
> > 에이전트가 **"내가 이 일을 하려면 날씨 정보가 필요하네? 그럼 '날씨 API'라는 도구를 써서 현재 기온을 가져와야겠다"**라고 판단하고, **실제로 코드를 실행해 외부 시스템과 통신하여 데이터를 가져오는 행위**입니다. 챗봇은 "날씨 API 주소가 ~~입니다"라고 알려주기만 하지만, 에이전트는 **직접 접속해서 JSON 데이터를 받아옵니다.**

### ③ 적응하기 (Adapting): "결과 보고 다시 생각하자!" - 요리사의 '간 보기'
이게 진짜 중요해요. 에이전트는 행동한 뒤 **결과를 보고** 다시 생각합니다.
*   **시나리오:** "비 오면 우산 알림 설정해줘"라는 명령을 받았다고 해볼까요?
    1.  **생각:** "날씨 확인해야지." → **행동:** 기상청 API 호출.
    2.  **결과(관찰):** API가 **"에러 났어요. 서버 점검 중입니다"**라고 돌려줬어요.
    3.  **적응 (다시 생각):** "아, 기상청 서버 안 되네? 그럼 **네이버 날씨 크롤링**하거나 **다른 날씨 API(Weather API)** 써서 다시 가져와야겠다." → **새로운 행동 실행.**
    4.  **최종 결과:** "비 온대요!" → 알림 설정 완료.

*   **기존 챗봇:** API 에러 나면? **"죄송합니다, 날씨 정보를 가져올 수 없습니다."** 하고 **멈춰요.** 사용자가 "그럼 다른 데서 찾아봐"라고 다시 시켜야 합니다.
*   **AI 에이전트:** **"어? 안 되네? 그럼 방법 바꿔서 다시 해보자!"**라고 **스스로 계획을 수정(Re-planning)해서 목표를 달성할 때까지 반복**해요.

> **💡 개념 돋보기: ReAct 패턴 (Reasoning + Acting)이란?**
> > 영상에서 언급된 유명한 논문 **'ReAct: Synergizing Reasoning and Acting in Language Models'**의 핵심 아이디어입니다.
> > **생각(Thought) → 행동(Action) → 관찰(Observation) → 생각(Thought) → 행동(Action)...** 이 루프를 계속 도는 거예요.
> > 마치 **요리사가 "간이 좀 싱겁네?(관찰) → 소금 좀 더 넣자(생각) → 소금 투입(행동) → 다시 맛봄(관찰) → 아 맞네!(종료)"** 하는 과정과 똑같습니다. 이 **'생각-행동-관찰'의 무한 루프**가 에이전트를 '똑똑한 비서'로 만들어주는 심장부입니다.

## 3. 한눈에 보는 비교표: 챗봇 vs 에이전트

| 특징 | 기존 챗봇 (단일 응답 생성) | AI 에이전트 (의사결정 및 행동 수행) |
| :--- | :--- | :--- |
| **역할** | **백과사전, 도서관 사서** (정보 제공자) | **비서, 매니저, 기사** (업무 수행자) |
| **입력** | 질문, 대화 | **목표, 미션, 복잡한 지시사항** |
| **처리 방식** | 입력 → **즉시 답변 생성 (One-shot)** | 입력 → **계획 수립 → 도구 실행 → 결과 확인 → 재계획 → ... → 최종 답변 (Multi-step Loop)** |
| **도구 사용** | ❌ 못 함 (도구 설명만 가능) | ✅ **직접 호출/실행 가능** (API, Code, Search 등) |
| **에러 대처** | "모르겠어요", "에러 났어요" 하고 멈춤 | **"다른 방법 써볼게요" 하며 우회 시도 (자율 복구)** |
| **메모리** | 대화 맥락만 기억 (단기) | **장기 기억 + 작업 진행 상태(State) 기억** |
| **비유** | **"레시피 책만 읽어주는 요리사"** | **"냉장고 보고 장 봐와서 요리까지 다 해주는 셰프"** |

## 4. 왜 지금 'AI 에이전트'가 뜨거운가? (영상의 핵심 포인트)

영상 도입부에서 **"단순히 이론만 배우는 게 아니라, 구글 ADK로 직접 첫 에이전트를 만들어 볼 것"**이라고 했죠? 과거에는 이런 '추론-행동-적응' 루프를 만들려면 복잡한 상태 머신(State Machine)이나 규칙 기반(Rule-based) 프로그래밍을 수개월에 걸쳐 짜야 했습니다.

하지만 **거대 언어 모델(LLM)**이 등장하면서, **'생각(Reasoning)' 역할을 LLM이 대신 해주게 된 것**이 혁명입니다.
1.  **LLM = 두뇌 (계획 짜기, 판단하기, 코드 짜기)**
2.  **Tools (API, Python, Search) = 손발 (실행하기)**
3.  **ADK (Agent Development Kit) = 신경계/뼈대 (이 둘을 연결하고 상태 관리해주는 프레임워크)**

이제 우리는 **"비 오면 우산 챙겨줘"**라는 자연어 한 줄로, 계획 짜기 → API 호출 → 에러 나면 재시도 → 알림 전송까지 **전부 자동으로 돌아가는 프로그램**을 며칠이 아닌 **몇 시간, 몇 분 만에** 만들 수 있게 되었습니다.

## 5. 마무리하며: 여러분이 만들게 될 '첫 번째 에이전트'

이 챕터의 핵심은 **"에이전트는 대답하는 기계가 아니라, 일을 처리하는 기계다"**라는 점입니다.
*   챗봇: **"뭐 해줄까?"** (수동적)
*   에이전트: **"이미 다 해놨어요. 확인해 보세요."** (능동적)

다음 챕터부터는 구글의 **ADK(Agent Development Kit)**라는 도구상자를 열어서, 이 '능동적인 일꾼'을 직접 코드로 조립해 볼 거예요. "생각-행동-관찰" 루프가 코드에서 어떻게 `Runner`, `Agent`, `Tool` 같은 객체로 구현되는지 아주 친절하게 뜯어보겠습니다.
