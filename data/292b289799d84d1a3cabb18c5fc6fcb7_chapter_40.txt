# 챕터 5. 루트 에이전트(Root Agent) 구현: 블로거(Blogger) — 지휘자, 완성된 요리를 식탁에 올리다

---

자, 지금까지 우리는 **'기획자(Planner)'**와 **'작가(Writer)'**라는 두 명의 핵심 전문가를 고용했고, 각각에게 **'검수관(Checker)'**을 붙여서 **'견고한 기획자(Robust Planner)'**와 **'견고한 작가(Robust Writer)'**라는 **'자동 재시도 시스템(Loop Agent)'**으로 업그레이드했습니다. 

이제 이 두 팀이 제각각 놀게 둘 수는 없죠? 누군가는 **"좋아, 이제 기획팀! 일해. 다 했어? 그럼 작가팀! 너도 일해. 다 했어? 그럼 최종 포장해서 손님(유저)에게 내놔."** 하고 **전체 흐름을 지휘**해야 합니다. 

이번 챕터에서 만들 **'루트 에이전트(Root Agent)'**, 이름하여 **'블로거(Blogger)'**가 바로 그 **총지휘자(지휘자, 매니저, 레스토랑의 지배인)** 역할을 맡게 됩니다.

---

## 1. 복잡한 주방, 심플한 주문서: '도구(Tool)'로 감추기 (Encapsulation)

우리가 앞서 만든 `견고한 블로그 기획자`와 `견고한 블로그 작가`는 내부적으로 꽤 복잡합니다.
- 기획자 안에는: `초안 작성기` → `검수관` → `루프(최대 3회 재시도)` 가 들어있죠.
- 작가 안에는: `본문 작성기` → `검수관` → `루프(최대 3회 재시도)` 가 들어있습니다.

이 복잡한 기계 장치를 **루트 에이전트(Blogger)에게 그대로 보여주면 안 됩니다.** 루트 에이전트는 "어떻게 기획서를 쓰는지", "어떻게 본문을 검수하는지" 알 필요가 없어요. 그냥 **"기획해줘"**, **"써줘"**만 알면 됩니다.

> **💡 개념 돋보기: 캡슐화(Encapsulation) & 도구(Tool)화**
> > **비유: 레스토랑의 '메뉴판'과 '주문 벨'**
> > 
> > 손님(루트 에이전트)이 "김치찌개 하나 주세요"라고 주문(도구 호출)하면, 주방(하위 에이전트 시스템)에서는 재료 손질, 육수 내기, 끓이기, 간 보기, 그릇 담기 등 복잡한 과정이 일어납니다. 하지만 손님은 그 과정을 몰라도 됩니다. **'주문 벨(도구/Tool)'만 누르면 '완성된 김치찌개(결과물)'가 나옵니다.**
> > 
> > 이번 챕터에서 우리는 **`견고한 기획자`**와 **`견고한 작가`**라는 복잡한 주방 기계들을 각각 **`planner_tool`(기획 도구)**과 **`writer_tool`(작성 도구)**라는 **'주문 벨'로 포장(래핑, Wrapping)합니다.** 이렇게 해야 루트 에이전트는 그저 버튼 두 개만 누르면 되는 아주 심플한 매니저가 될 수 있습니다.

---

## 2. '블로그 포스트 검수관(Validation Checker)' — 작가의 글, 빨간 펜으로 채점하기

루프 에이전트(견고한 작가) 안에는 **'작가'**만 있는 게 아닙니다. **'검수관(Validation Checker)'**이 꼭 붙어 있습니다. 스크립트에 나온 이 검수관의 역할, 아주 구체적으로 들여다봅시다.

이 검수관의 이름은 **`Blog Post Validation Checker`(블로그 포스트 유효성 검사기)**입니다. 이 친구가 하는 일은 **작가가 쓴 초안(`blog_post`)을 받아서 '합격/불합격'을 판정**하는 겁니다. 채점 기준은 딱 네 가지입니다.

1.  **도입부(Introduction)가 있는가?** — 글의 문을 열었나?
2.  **개요(Outline)와 섹션이 일치하는가?** — 기획서대로 썼나? (목차 3개라고 해놓고 2개만 썼으면 탈락)
3.  **결론(Conclusion)이 있는가?** — 글의 문을 닫았나?
4.  **명확한 설명(Clear Explanations)이 있는가?** — 그냥 단어 나열이 아니라, 독자가 이해할 수 있게 풀어썼나?

> **💡 개념 돋보기: 검수관의 판정 결과 — "OK" vs "Retry"**
> > **비유: 논문 심사위원 / 품질 검사(QC) 팀장**
> > 
> > - **통과 (OK):** "수고했어, 이 글은 출판해도 되겠어." → **루프 종료**, 상위 단계(루트 에이전트)로 결과물 전달.
> > - **실패 (Retry):** "이건 안 되겠어. **이유 3가지** 적어줄게. 고쳐와." → **피드백(수정 사항 리스트)과 함께 작가에게 되돌림(Loop)**.
> > 
> > 여기서 핵심은 **단순히 "아니오"라고만 하지 않고, **"뭐가 문제인지 구체적인 수정 사항(Fixes needed)을 리스트로 알려준다"**는 점입니다. 그래야 작가가 "아, 도입부가 없구나? 결론이 약하구나?" 알고 **똑똑하게 고쳐서 다시 제출**할 수 있으니까요. 이 과정을 **최대 3번** 반복합니다. 3번 다 실패하면? 그때는 "안 되겠네" 하고 에러를 뱉거나 사람이 개입하도록 설계하겠죠.

## 3. 루트 에이전트 '블로거(Blogger)'의 탄생: 두 개의 도구만 가진 지휘자

자, 이제 준비된 도구는 단 두 개입니다.
1.  **`planner_tool`** (견고한 기획자 — 개요 만들어주는 도구)
2.  **`writer_tool`** (견고한 작가 — 본문 써주는 도구)

루트 에이전트 **'블로거(Blogger)'**는 이 **두 개의 도구만 접근 권한(Access)**을 가집니다. 내부적으로 기획자가 루프를 돌든, 작가가 3번 퇴짜 맞든 **전혀 모릅니다.** 그냥 도구함에 있는 망치와 드라이버만 쓸 줄 알면 됩니다.

### 블로거에게 내려진 '업무 지시서(Instructions)'

스크립트에 나온 블로거의 지시사항(Instruction)은 아주 심플하고 명확합니다. **마치 요리 레시피의 순서처럼** 말이죠.

> **📋 블로거의 작업 순서 (Workflow)**
> 
> 1.  **사용자 토픽 접수:** "인공지능의 미래" 같은 주제가 들어옵니다.
> 2.  **1단계 — 기획 도구 호출:** `planner_tool`에게 토픽을 넘기며 **"개요 좀 짜줘"**라고 시킵니다. (기획팀이 루프 돌며 검수까지 다 끝낸 '확정 개요'를 받아옴)
> 3.  **2단계 — 작성 도구 호출:** 받은 '확정 개요'를 `writer_tool`에게 넘기며 **"이 개요대로 본문 써줘"**라고 시킵니다. (작가팀이 루프 돌며 검수까지 다 끝낸 '완성 본문'을 받아옴)
> 4.  **3단계 — 마무리 포장 (블로거의 고유 업무):** 도구가 해준 건 '본문'까지입니다. 블로거는 **직접** 다음을 덧붙입니다.
>     - **대체 제목 3개 (Three Alternative Titles):** "AI가 바꿀 내일", "미래를 여는 열쇠, AI", "우리의 삶 속으로 들어온 인공지능" 등 클릭을 유도할 매력적인 제목 후보들.
>     - **트윗용 훅 2개 (Two Tweet-length Hooks):** 트위터(엑스)나 스레드에 홍보용으로 올릴 **한 줄짜리 매력적인 문구** 2개. 예: "🚀 10년 뒤 직업의 50%가 사라진다? AI 시대를 살아남을 생존 전략 대공개! #AI #미래기술"
> 5.  **최종 결과물 반환:** 개요 + 본문 + 대체 제목 3개 + 트윗 훅 2개 = **완벽한 블로그 패키지**를 사용자에게 전달.

## 4. 왜 이렇게 설계했나? — '관심사 분리(Separation of Concerns)'의 마법

여러분, 혹시 **"그럼 블로거가 제목이랑 훅도 직접 쓰지, 왜 기획/작성은 도구로 뺐어?"** 라는 생각 안 드셨나요? 여기가 바로 **아키텍처(설계)의 핵심**입니다.

> **💡 개념 돋보기: 왜 루트 에이전트는 '도구'만 쓰게 하는가? (통제된 워크플로우)**
> > **비유: 건설 현장의 '현장 소장(루트 에이전트)' vs '하도급 전문 업체(하위 에이전트/도구)'**
> > 
> > - **현장 소장(블로거):** 전체 공정 관리, 발주처(유저) 소통, 최종 마감(제목/훅)만 챕니다. **벽돌 쌓기(기획), 미장 하기(작성) 같은 전문 기술은 모릅니다.** 알 필요도 없습니다.
> > - **전문 업체(플래너/라이터 도구):** "설계도면 주면 기초 공사 끝내드림(기획)", "기초 공사 끝났으면 올림 공사 끝내드림(작성)" **자신의 전문 분야만 완벽하게 책임집니다.** 내부적으로 인부(LLM 호출), 자재(프롬프트), 검수(체커), 재시공(루프) 다 알아서 합니다.
> > 
> > **이 설계의 장점:**
> > 1.  **단순함(Simplicity):** 블로거 코드는 `if topic: plan = planner(topic); draft = writer(plan); return polish(draft)` **겨우 이 정도**면 끝납니다. 버그 날 곳이 거의 없어요.
> > 2.  **교체 용이성(Swappability):** 나중에 `planner_tool`을 더 좋은 기획 에이전트(GPT-5 버전 등)로 **갈아끼워도 블로거 코드는 한 줄도 안 고칩니다.** 인터페이스(입력: 토픽, 출력: 개요)만 똑같으면 되니까요.
> > 3.  **디버깅 용이성:** "기획이 이상해" → `planner_tool`만 테스트하면 됨. "본문이 이상해" → `writer_tool`만 테스트하면 됨. "최종 포장이 이상해" → 블로거 코드만 보면 됨. **책임 소재가 확실합니다.**
> > 4.  **보안/권한 제어:** 블로거는 `planner_tool`, `writer_tool` **두 개만 호출 가능**합니다. 데이터베이스 지우기, 이메일 보내기, 외부 API 해킹 같은 위험한 도구는 **애초에 쥐어주지 않았습니다.**这就是 '통제된 워크플로우(Controlled Workflow)'의 힘입니다.

## 5. 전체 흐름 한눈에 보기 — 데이터의 여정 (Data Flow)

자, 이제 사용자가 **"요즘 뜨는 '에이전틱 워크플로우'에 대해 블로그 써줘"**라고 말한 순간부터 결과가 나오기까지, 데이터가 어떻게 흘러가는지 **한 단계 한 단계** 따라가 봅시다. 이게 바로 여러분이 나중에 직접 코드로 구현할 때 **디버깅 로그를 보며 "아, 지금 이 단계구나!"** 할 수 있게 해주는 지도입니다.

### 🗺️ 블로거 시스템 전체 실행 흐름도 (Step-by-Step)

| 단계 | 주체 (Actor) | 행동 (Action) | 입력 (Input) | 내부 처리 (Internal) | 출력 (Output) | 비고 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **0** | **User** | 요청 | `"Topic: Agentic Workflow"` | - | - | 시작점 |
| **1** | **Root Agent (Blogger)** | `planner_tool` 호출 | `topic` | - | - | "기획팀, 일해!" |
| **2** | **`planner_tool` (Robust Planner Loop)** | **자동 루프 시작** | `topic` | 1. `Planner` 초안 생성<br>2. `Planner Checker` 검수 (구조, 완성도)<br>3. 실패 시 피드백 주고 **재시도 (최대 3회)** | **`final_outline`** (검수 통과된 확정 개요) | 도구 내부에서 루프 돔. 블로거는 모름. |
| **3** | **Root Agent (Blogger)** | 결과 수신 & `writer_tool` 호출 | `final_outline` | - | - | "작가팀, 이 개요대로 써!" |
| **4** | **`writer_tool` (Robust Writer Loop)** | **자동 루프 시작** | `final_outline` | 1. `Writer` 본문 초안 생성<br>2. `Validation Checker` 검수 **(도입부, 개요일치, 결론, 명확성)**<br>3. 실패 시 **수정 사항 리스트** 주고 **재시도 (최대 3회)** | **`final_blog_post`** (검수 통과된 완성 본문) | 도구 내부에서 루프 돔. 블로거는 모름. |
| **5** | **Root Agent (Blogger)** | **후처리 (Post-processing)** | `final_blog_post` | **직접 수행 (LLM 호출 또는 템플릿):**<br>- 대체 제목 3개 생성<br>- 트윗 훅 2개 생성 | **`Final Package`**<br>{ outline, post, titles[3], hooks[2] } | 블로거의 고유 가치 창출 구간 |
| **6** | **User** | 최종 결과 수신 | `Final Package` | - | - | 완료! |

## 6. 실전 구현 시 꿀팁 (Implementation Tips for Beginners)

여러분이 나중에 파이썬(ADK, LangGraph, CrewAI 등)으로 이걸 짜실 때, **꼭 챙겨야 할 디테일**들을 미리 알려드립니다. 강의에는 안 나와지만 현업에서는 필수인 것들입니다.

### ① 도구(Tool) 인터페이스 설계: "입력/출력 타입을 엄격하게!"
`planner_tool`과 `writer_tool`은 **함수(Function)**나 **클래스 메서드**로 구현될 텐데, **타입 힌트(Type Hint)**를 꼭 넣으세요.
```python
# 예시 (Pydantic 모델 추천)
class Outline(BaseModel):
    title: str
    sections: List[Section] # 섹션 리스트

class BlogPost(BaseModel):
    outline: Outline
    content: str # 마크다운 본문

# 도구 시그니처
def planner_tool(topic: str) -> Outline: ...
def writer_tool(outline: Outline) -> BlogPost: ...
```
> **이유:** 블로거(루트 에이전트)가 LLM 기반이라면, **"이 도구는 문자열을 주면 Outline 객체를 준다"**는 걸 정확히 알아야 도구를 잘 호출합니다. `str` 넣고 `dict` 받으면 파싱 지옥 갑니다.

### ② 루프 에이전트의 '최대 재시도 횟수'와 '탈출 조건'
스크립트엔 "최대 3번"이라 나왔죠? 코드로는 이렇게 짜야 합니다.
```python
# 견고한 작가(Loop 내부 로직 개념도
max_retries = 3
current_attempt = 0
feedback = "최초 작성" # 처음엔 피드백 없음

while current_attempt < max_retries:
    # 1. 작가 호출 (피드백 포함해서 프롬프트 구성)
    draft = writer_agent.run(outline, feedback=feedback)
    
    # 2. 검수관 호출
    result = checker_agent.check(draft)
    
    if result.status == "OK":
        return draft # 성공! 루프 탈출
    
    # 3. 실패 시
    feedback = result.fixes_needed # "도입부 없음, 결론 보강 필요" 등
    current_attempt += 1

raise MaxRetriesExceededError("3번 시도했으나 품질 기준 미달")
```
> **포인트:** `feedback` 변수를 **이전 턴의 검수 결과**로 업데이트해줘야 작가가 "아, 그때 지적받은 거 고치면 되네?" 하고 **문맥을 이어서 수정**합니다. 이걸 안 해주면 매번 똑같은 엉뚱한 글만 씁니다.

### ③ 블로거의 '후처리(Post-processing)' — 프롬프트 엔지니어링 포인트
블로거가 마지막에 **대체 제목 3개, 훅 2개**를 만드는 건 별도의 LLM 호출이거나, 블로거 자신이 LLM이라면 **한 번의 프롬프트로 다 해결**할 수 있습니다.
> **프롬프트 예시 (블로거 내부 프롬프트):**
> ```
> 당신은 베테랑 블로그 에디터입니다. 다음 완성된 블로그 본문을 읽고 다음을 생성해주세요.
> 1. 클릭률(CTR)을 높일 수 있는 **대체 제목 3가지** (다양한 톤: 궁금증 유발형, 이득 제시형, 숫자/리스트형)
> 2. 트위터/스레드 홍보용 **한 줄 훅 2가지** (이모지 포함, 280자 내외, 해시태그 2~3개 필수)
> 
> [본문 내용]
> {final_blog_post}
> 
> 출력 형식: JSON (titles: list[str], hooks: list[str])
> ```
> 이렇게 **구조화된 출력(JSON)**을 강제하면 블로거가 결과를 파싱해서 최종 패키지 만들기 쉽습니다.

### ④ 로깅(Logging)과 관측가능성(Observability)
이 시스템은 **중첩된 루프(Loop inside Tool inside Agent)** 구조입니다. 콘솔에 찍히는 로그가 없으면 **"왜 30초째 안 끝나지? 무한 루프인가? 에러인가?"** 모릅니다.
- **필수 로그:** `[Planner Loop] Attempt 1/3`, `[Checker] Status: RETRY - Fixes: [...]`, `[Writer Loop] Attempt 2/3 Passed!`, `[Blogger] Generating titles...`
- **추천 라이브러리:** Python `logging` 모듈, 또는 `LangSmith`, `Weights & Biases`, `AgentOps` 같은 관측 툴 연동.

## 7. 요약하며 다음 단계로 — '에이전트 오케스트라'의 완성

자, 이번 챕터에서 우리는 **'분업과 협업의 완성체'**를 보았습니다.

1.  **전문성 분리:** 기획(Planner)과 작성(Writer)을 별도 에이전트로.
2.  **품질 보장:** 각 전문가 뒤에 검수관(Checker)과 재시도 루프(Loop Agent)를 붙여 **'견고함(Robustness)'** 확보.
3.  **복잡도 은닉:** 그 복잡한 시스템을 **`planner_tool`, `writer_tool`**이라는 **단순한 도구(Tool)**로 포장 (캡슐화).
4.  **지휘자 탄생:** 루트 에이전트 **`Blogger`**는 도구 2개만 호출하는 **심플한 워크플로우**로 전체를 지휘.
5.  **마무리 터치:** 도구가 못 하는 **'편집/마케팅 영역(제목, 훅)'**은 지휘자가 직접 수행하며 **최종 상품 가치** 높임.

이게 바로 **"하나의 큰 LLM에게 다 시키기(Monolithic Prompt)"**가 아니라, **"작고 검증된 에이전트들을 레고 블록처럼 조립해 신뢰할 수 있는 시스템 만들기(Modular Agentic Architecture)"**의 정석입니다.
