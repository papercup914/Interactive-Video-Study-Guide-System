# 챕터 5. 검증 실패 시 피드백을 포함한 프롬프트 재주입으로 품질 보장: "합격할 때까지 되돌려 보내는 깐깐한 편집장 시스템"

앞서 우리는 **'플래너(기획자) 에이전트'**가 블로그 글의 뼈대(아웃라인)를 짜고, **'체커(검수자) 에이전트'**가 그걸 보고 "합격(Okay)" 또는 "불합격(Retry)" 도장을 찍는 과정까지 살펴보았습니다. 그런데 여기서 끝나면 안 되겠죠? 체커가 "불합격"이라고 했는데, 플래너가 똑같은 실수를 반복하면 곤란하니까요.

이번 챕터에서는 **"불합격 판정을 받았을 때, 단순히 '다시 해'라고만 하지 않고, **'어디가 어떻게 틀렸는지(피드백)'를 구체적으로 적어서 플래너에게 다시 건네주는 방식(프롬프트 재주입)**으로 품질을 보장하는 루프(Loop) 시스템"**을 아주 자세히, 그리고 친근한 비유와 함께 파헤쳐 보겠습니다.

---

## 1. 식당 주방의 '품질 관리 루프'를 상상해 보세요

가장 이해하기 쉬운 비유는 **'고급 레스토랑의 주방과 검수 시스템'**입니다.

*   **플래너 에이전트 = 요리사 (조리 담당):** 주문서(사용자 요청)를 보고 요리(블로그 아웃라인)를 만듭니다.
*   **체커 에이전트 = 깐깐한 수석 셰프/품질 관리 매니저 (검수 담당):** 완성된 요리가 나가기 전에 플레이팅, 온도, 간, 재료 신선도 등을 체크합니다.
*   **공유 상태(Shared State) = 주방 위의 '작업대' 또는 '주문 티켓 보드':** 요리사가 만든 접시를 올려놓으면, 수석 셰프가 그걸 보고 평가하고, 평가서를 다시 작업대에 꽂아두는 공간입니다.
*   **루프 에이전트(Loop Agent) = 주방 총괄 매니저 (진행 담당):** "수석 셰프가 OK 할 때까지 요리사를 계속 부른다"는 규칙을 관리하는 사람입니다.

**상황 시나리오:**
1.  요리사(플래너)가 '스테이크 정식' 아웃라인을 만들어 작업대(State)에 올립니다.
2.  수석 셰프(체커)가 맛을 봅니다. **"고기가 너무 질기다(섹션 개수 부족), 소스가 없다(결론 누락)"** 라고 판단합니다.
3.  수석 셰프는 그냥 "다시 해!"라고 소리치지 않습니다. **'수정 지시서(피드백)'**를 정성껏 적습니다.
    > *"제목: 스테이크 정식 / 소개: 있음 / 본문 섹션: 현재 3개인데 4~6개로 늘려야 함 / 결론: 누락됨. 이 4가지 조건을 채워서 다시 올리세요."*
4.  이 수정 지시서가 작업대(State)에 **'피드백'이라는 이름으로 저장**됩니다.
5.  총괄 매니저(루프)가 "아직 OK 안 났네? 요리사 다시 불러!"라고 합니다. (최대 3번까지)
6.  요리사는 **이전 레시피(기존 프롬프트) + 수정 지시서(피드백)**를 합쳐서 **새로운 주문서(재주입 프롬프트)**를 받고, 정신을 바짝 차리고 다시 요리합니다.

이게 바로 **'검증 실패 시 피드백을 포함한 프롬프트 재주입(Re-prompting with Feedback)'**의 핵심입니다. 단순히 "다시 해"가 아니라, **"왜 틀렸는지, 어떻게 고쳐야 하는지"를 데이터로 실어 다시 던져주는 것**이죠.

## 2. 기술적 구현: '지시사항(Instruction)'과 '상태(State)'의 치밀한 춤

영상 스크립트를 보면, 이 과정이 어떻게 코드 레벨에서 구현되는지 힌트가 나옵니다. 하나씩 뜯어보면서 비유를 곁들여 설명해 드릴게요.

### 2-1. 체커(Checker)의 '엄격한 지시서(Instruction)' 설계: "기계처럼 판단해라"

영상에서는 체커 에이전트에게 다음과 같은 **엄격한 규칙(Instruction)**을 줍니다.

> *"If the outline in state has a title, an intro, four to six sections, and a conclusion, it must answer with the word 'okay.' If something is missing, it must answer with the word 'retry' and explain what's wrong."*

**번역 및 비유:**
> *"작업대(State)에 올라온 아웃라인이 **제목, 도입부, 4~6개의 본문 섹션, 결론**을 모두 가지면 **'okay'**라는 단어 **딱 하나만** 대답해라. 만약 하나라도 빠졌으면 **'retry'**라고 말하고 **뭐가 빠졌는지 설명**해라."*

*   **비유 - '자동 채점기' 혹은 '체크리스트 만점짜리 수석 셰프':**
    이 체커는 감성적으로 "음~ 느낌이 좋은데?" 하지 않습니다. **기계적인 체크리스트**만 봅니다.
    *   [ ] 제목 있음?
    *   [ ] 도입부 있음?
    *   [ ] 섹션 4개 이상 6개 이하?
    *   [ ] 결론 있음?
    *   **전부 예(Yes)면** → 출력: `"okay"` (도장 쾅!)
    *   **하나라도 아니오(No)면** → 출력: `"retry: 섹션이 3개뿐임, 결론 없음"` (빨간 펜으로 첨삭!)

이렇게 **출력 형식을 'okay' 또는 'retry + 사유'로 강제**하는 것이 중요합니다. 그래야 다음 단계인 루프 에이전트(또는 이를 제어하는 코드)가 **"아, 문자열에 'okay'가 들어있네? 멈추자"** 혹은 **"'retry'가 들어있네? 다시 돌려야지"**라고 **프로그램적으로 판단**할 수 있으니까요. 사람 말로 길게 쓰면 컴퓨터가 알아듣기 힘드니까, **'프로토콜(약속된 신호)'을 정해둔 것**입니다.

> **💡 개념 돋보기: 구조화된 출력(Structured Output) & 파싱(Parsing) 용이성**
> 에이전트 간의 소통에서 **'자연어'는 모호하지만, '약속된 키워드(okay, retry)'는 확실합니다.**
> 체커에게 "자유롭게 평가해"라고 시키면 "좋은 것 같아요 근데 섹션이 좀 적은 듯?"이라고 답할 수 있습니다. 그럼 루프 매니저(코드)가 이 문장을 읽고 "재시도인가? 통과인가?" 판단하려면 복잡한 자연어 처리(NLP)가 필요해집니다.
> **"딱 두 단어 중 하나로만 답해라"**라고 제약(Constraint)을 걸면, downstream(다음 단계) 로직이 `if "okay" in result:` 한 줄로 끝납니다. 이게 **엔지니어링적으로 매우 영리한 설계**입니다.

---

### 2-2. 플래너(Planner)의 '재도전 프롬프트' 구성: "피드백을 밥상에 올리기"

자, 체커가 `"retry: 섹션이 3개뿐이고 결론이 없습니다"`라고 작업대(State)에 적어놨습니다. 이제 루프 매니저가 플래너를 다시 호출합니다. 이때 플래너에게 주어지는 **입력 프롬프트(Prompt)**가 어떻게 변하는지가 이 챕터의 핵심입니다.

**최초 호출 시 프롬프트 (1차 시도):**
> "너는 블로그 플래너다. 제목, 도입, 4~6 섹션, 결론 있는 아웃라인 짜서 `blog_outline` 키로 상태에 저장해라."

**재호출 시 프롬프트 (2차 시도 - 핵심!):**
> "너는 블로그 플래너다. **이전 시도가 실패했다. 체커가 이렇게 말했다: 'retry: 섹션이 3개뿐이고 결론이 없습니다.'** 이 피드백을 반영해서 다시 짜서 `blog_outline` 키로 저장해라."

**비유 - 요리사에게 건네는 '수정된 주문서':**
*   1차: "스테이크 정식 만들어." → 요리사: (맘대로 만들어옴)
*   2차: **"방금 수석 셰프가 '고기 더 굽고 소스 뿌리라'고 했어. 그 피드백 반영해서 다시 만들어."**

이게 바로 **'피드백을 포함한 프롬프트 재주입(Re-injection)'**입니다. 단순히 루프를 도는 게 아니라, **이전 실행의 결과물(상태)과 평가 결과(피드백)을 컨텍스트(Context)로 주입**해서 다음 실행을 '더 똑똑하게' 만드는 것입니다.

> **💡 개념 돋보기: 컨텍스트 윈도우(Context Window)와 적은 샷(Few-shot) 효과**
> LLM(대형 언어 모델)은 **'즉시 학습(In-context Learning)'**을 합니다. 프롬프트에 **"이전 실패 사례 + 정정 지시"**가 함께 들어가 있으면, 모델은 "아, 저번엔 섹션 3개짜리 냈다가 혼났구나. 이번엔 5개로 채워야지"라고 **문맥상 추론**합니다. 별도의 파인튜닝(Fine-tuning)이나 가중치 업데이트 없이, **프롬프트 엔지니어링만으로 '학습' 효과를 내는 것**이죠. 이게 에이전트 루프의 강력한 힘입니다.

---

### 2-3. 루프 에이전트(Loop Agent): "최대 3번까지 기회 준다" (가드레일)

영상에서는 `robust blog planner`라는 이름의 **루프 에이전트**로 이 둘을 감쌉니다.

> *"The loop first runs the planner, then the checker, if the checker says 'okay,' we're done. If the checker says 'retry,' the loop runs the planner again with the same instructions. It can do this up to three times."*

**번역 및 비유:**
> *"루프는 먼저 플래너를 돌리고, 체커를 돌린다. 체커가 'okay'면 끝. 'retry'면 플래너를 다시 돌린다(같은 지시사항으로). 이걸 **최대 3번**까지 한다."*

*   **비유 - '3진 아웃(Three Strikes) 제도' 또는 '최대 3회 재시험 기회':**
    무한 루프(Infinite Loop)는 시스템을 다운시킵니다. 요리사가 아무리 해도 안 되면 주방이 마비되니까요. 그래서 **"기회는 3번만 준다"**는 **안전장치(Guardrail)**를 둡니다.
    *   1회차: 플래너 실행 → 체커 검사
    *   2회차 (재시도 1): 플래너 실행(피드백 포함) → 체커 검사
    *   3회차 (재시도 2): 플래너 실행(피드백 포함) → 체커 검사
    *   4회차 (재시도 3): 플래너 실행(피드백 포함) → 체커 검사 → **끝(성공이든 실패든 강제 종료)**

이 '최대 횟수(Max Iterations)' 설정은 **비용(Cost) 통제**와 **지연 시간(Latency) 방지**를 위해 필수적입니다. LLM 호출은 돈과 시간이 드니까요.

## 3. 데이터 흐름(Data Flow) 완벽 정복: State(상태)를 따라가는 여행

이 전체 과정을 **'공유 상태(Shared State)'**라는 하나의 화이트보드를 중심으로 누가, 뭘 쓰고, 누가, 뭘 읽는지 추적해 보겠습니다. 이게 이해되면 에이전트 아키텍처의 50%는 먹은 겁니다.

### 초기 상태 (Initial State)
```json
{
  "user_topic": "AI 에이전트 입문"
}
```

### 🔄 1회차 루프 (Iteration 1)

| 단계 | 액터 (Actor) | 행동 (Action) | 상태 (State) 변경 사항 | 비유 |
| :--- | :--- | :--- | :--- | :--- |
| **1** | **Loop Manager** | "플래너야, 일해라" | - | 매니저가 요리사 호출 |
| **2** | **Planner** | LLM 호출 → 아웃라인 생성 | `blog_outline`: `{title: "...", intro: "...", sections: [1,2,3], conclusion: null}` | 요리사가 요리 만들어 작업대에 올림 (섹션 3개, 결론 없음) |
| **3** | **Loop Manager** | "체커야, 검사해라" | - | 매니저가 수석 셰프 호출 |
| **4** | **Checker** | State의 `blog_outline` 읽음 → 지시사항대로 체크 → **실패 판정** | `checker_feedback`: `"retry: sections count is 3 (need 4-6), conclusion missing"` | 수석 셰프가 맛보고 빨간 펜으로 수정사항 적어 작업대에 붙임 |
| **5** | **Loop Manager** | `checker_feedback`에 `"okay"` 없음 → `"retry"` 있음 → **카운트 1 증가** → "플래너야, 다시 해" | `loop_count`: 1 | 매니저: "불합격! 피드백 봤지? 다시!" |

---

### 🔄 2회차 루프 (Iteration 2) - **핵심: 프롬프트 재주입 발생 지점**

| 단계 | 액터 (Actor) | 행동 (Action) | 상태 (State) 변경 사항 | 비유 |
| :--- | :--- | :--- | :--- | :--- |
| **1** | **Loop Manager** | 플래너 호출 **(중요: 프롬프트 구성 시 State의 `checker_feedback` 포함)** | - | 매니저: "요리사, 이 수정지시서(피드백) 보고 다시 해" |
| **2** | **Planner** | **입력 프롬프트 = 원래 지시사항 + "이전 피드백: `checker_feedback` 값"** <br> LLM 호출 → **수정된 아웃라인 생성** | `blog_outline`: `{title: "...", intro: "...", sections: [1,2,3,4,5], conclusion: "..."}` (덮어쓰기) | 요리사가 수정지시서 보며 섹션 5개, 결론 추가해 새 접시 올림 |
| **3** | **Loop Manager** | 체커 호출 | - | 수석 셰프 다시 호출 |
| **4** | **Checker** | State의 `blog_outline` 읽음 → 체크 → **성공 판정** | `checker_feedback`: `"okay"` | 수석 셰프: "완벽해! Okay!" 도장 쾅 |
| **5** | **Loop Manager** | `checker_feedback` == `"okay"` → **루프 종료 (Break)** | 최종 결과물 `blog_outline` 확정 | 매니저: "합격! 손님께 서빙해!" |

## 4. 왜 이 방식이 '품질 보장(Quality Assurance)'인가? (핵심 정리)

단순히 "LLM 한 번 호출해서 결과 받기(Single Shot)"와 이 **"플래너-체커-루프(Planner-Checker-Loop)"** 패턴의 차이는 **'검증 가능한 품질'**의 차이입니다.

| 비교 항목 | Single Shot (단일 호출) | Planner-Checker-Loop (이 챕터 패턴) |
| :--- | :--- | :--- |
| **신뢰도** | 운에 맡김. 프롬프트 잘 짜면 잘 나옴, 아님 말음. | **구조적 보장.** 체크리스트 통과할 때까지 강제 반복. |
| **에러 처리** | 에러 나면 사용자가 직접 수정하거나 다시 돌려야 함. | **자동 복구(Self-healing).** 피드백 루프가 알아서 고침. |
| **지시사항 복잡도** | 한 프롬프트에 "제목, 도입, 섹션 4-6, 결론, 마크다운, 톤앤매너..." 다 때려넣어야 함. | **관심사 분리(SoC).** 플래너는 '쓰기'만, 체커는 '규칙'만 신경 씀. |
| **디버깅** | 왜 틀렸는지 모름. | **체커의 피드백 로그**가 그대로 남음. 어디가 문제였는지 추적 가능. |
| **확장성** | 규칙 추가 시 프롬프트 전체 수정 필요. | 체커의 지시사항(Instruction)만 수정하면 됨. 플래너 건들 필요 없음. |

> **💡 개념 돋보기: '관심사 분리(Separation of Concerns)'와 '단일 책임 원칙(SRP)'의 적용**
> 소프트웨어 공학의 대원칙이 에이전트 설계에도 그대로 적용됩니다.
> *   **Planner Agent:** "어떻게 하면 멋진 아웃라인을 **잘 쓸까?**" (생성/창의성 담당)
> *   **Checker Agent:** "이 아웃라인이 **규격에 맞는가?**" (검증/논리/규칙 담당)
> *   **Loop Agent:** "이 둘을 **어떤 순서로, 몇 번 돌릴까?**" (제어/오케스트레이션 담당)
>
> 역할을 쪼개니 각 에이전트의 프롬프트(Instruction)가 **짧고 명확해집니다.** 프롬프트가 길면 모델이 지시사항을 놓치기 쉬운데(Attention Dilution), 역할을 나누니 **"섹션 4~6개 체크해"라는 한 가지 임무에만 집중**하게 되어 정확도가 비약적으로 올라갑니다.

## 5. 실무에서 주의할 '꿀팁'과 '함정' (Senior Developer's Advice)

이 패턴을 실무에 적용할 때 겪을 수 있는 시행착오를 미리 알려드릴게요.

### ① 피드백의 '구조화(Structuring)'가 생명입니다.
체커가 `"retry: 섹션이 부족해요"`라고 **자연어 문장**으로 뱉게 두면, 플래너가 이를 읽고 "아, 섹션 수를 늘리면 되겠네?"라고 **완벽하게 이해 못 할 확률**이 있습니다.
**→ 해결책:** 체커의 출력 형식을 **JSON**이나 **Key-Value**로 강제하세요.
```json
// 체커 출력 예시 (파싱하기 좋은 형태)
{
  "status": "retry",
  "errors": [
    {"field": "sections", "issue": "count", "current": 3, "required_min": 4, "required_max": 6},
    {"field": "conclusion", "issue": "missing"}
  ]
}
```
이렇게 구조화된 피드백을 플래너 프롬프트에 `json.dumps(feedback)`로 꽂아 넣으면, 플래너(LLM)가 **필드별로 정확히 무슨 짓을 해야 하는지 100% 이해**합니다.

### ② '상태 덮어쓰기(State Overwrite)' vs '히스토리 쌓기(History Accumulation)'
영상 예시처럼 `blog_outline` 키 하나를 계속 덮어쓰면(Overwrite) 메모리는 절약되지만, **"1차 때 뭐 썼는데 2차 때 어떻게 고쳤지?"** 비교 분석이 안 됩니다.
**→ 실무 팁:** `blog_outline_v1`, `blog_outline_v2`... 혹은 `outline_history: []` 리스트에 계속 `append` 해서 쌓아두세요. 디버깅할 때 **"아, 2차 때 결론을 추가했더니 3차 때 섹션이 빠졌네?"** 같은 패턴 분석이 가능해집니다.

### ③ 루프 카운트(Max Iterations) 설정의 미학
"최대 3번"이 정답은 아닙니다.
*   **단순 포맷 검증(섹션 개수, 필수 필드):** 2~3번이면 충분. (규칙이 명확하니까)
*   **복잡한 논리 검증(논리 흐름, 팩트 체크, 톤앤매너):** 5~10번 필요할 수도 있음. (주관적이라 수렴이 느림)
*   **비용 고려:** `Max Iterations * (Planner Cost + Checker Cost)` = 예상 최대 비용. 이걸 미리 계산하고 예산에 맞게 설정하세요.

### ④ '탈출구(Early Exit)' 조건 추가
체커가 `"okay"`라고 해도, 플래너가 **아예 엉뚱한 소리(할루시네이션)**를 해서 "제목: 오류, 소개: 오류..." 이렇게 채워넣고 체커가 "형식상 다 있네? Okay!" 할 수 있습니다.
**→ 해결책:** 체커 지시사항에 **`"내용의 질적 수준도 판단하라(예: 제목이 주제와 관련 있는가)"`**는 조항을 넣거나, 루프 매니저 레벨에서 **별도의 '품질 게이트(Quality Gate)' 에이전트**를 하나 더 두는 것도 방법입니다.

## 6. 마무리하며: "신뢰할 수 있는 AI 시스템을 만드는 가장 확실한 레시피"

이번 챕터에서 우리는 **'검증 실패 시 피드백을 포함한 프롬프트 재주입'**이라는 다소 거창한 제목이, 사실은 **엄마가 아이 숙제 검사해주며 "여기 틀렸어, 왜 틀렸는지 읽어보고 다시 풀어봐"라고 지도하는 과정**과 정확히 일치함을 보았습니다.

1.  **생성(Generate):** 플래너가 초안 작성.
2.  **평가(Evaluate):** 체커가 정해진 룰(체크리스트)로 채점.
3.  **피드백(Feedback):** 틀린 부분만 콕 짚어 알려주기.
4.  **재시도(Retry with Context):** 피드백을 컨텍스트로 주입하여 재생성.
5.  **반복(Loop):** 통과할 때까지(또는 횟수 다 될 때까지) 반복.

이 **Generate-Evaluate-Feedback-Retry Loop** 패턴은 **"LLM은 확률적으로 틀릴 수 있다"는 전제 하에, 결정론적(D deterministic)인 코드(루프, 파서, 상태 관리)로 그 불확실성을 감싸서 신뢰도를 끌어올리는** 가장 표준적이고 강력한 아키텍처 패턴입니다.

이제 여러분은 단순히 "프롬프트 잘 짜는 법"을 넘어, **"에이전트들을 어떻게 엮어서 스스로 검증하고 고치는 시스템을 만들까?"**를 설계할 수 있는 눈을 가지게 되셨습니다. 다음 챕터에서는 이 루프 시스템을 더 복잡한 멀티 에이전트 워크플로우로 확장하는 법이나, 병렬 처리(Parallel Processing)로 속도를 높이는 비법 등을 다뤄보겠습니다.
