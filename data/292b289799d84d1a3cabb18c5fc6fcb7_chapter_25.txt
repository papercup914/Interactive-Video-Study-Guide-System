# 📚 챕터 3: 워크플로우 에이전트로서의 루프 에이전트 개념 — "똑똑한 비서들이 주고받는 '완벽한 기획서' 만들기"

안녕하세요! 지난 시간에는 에이전트들이 서로 상태(State)라는 공용 노트를 통해 정보를 주고받는 **'순차 워크플로우(Sequential Workflow)'**의 기본 원리를 배웠어요. 마치 **릴레이 경주**에서 바통을 넘기듯, 한 에이전트가 일을 끝내면 다음 에이전트가 이어받는 방식이었죠.

이번 챕터에서는 그 흐름에 **'검토와 수정의 루프(Loop)'**라는 강력한 엔진을 다는 법을 배워볼 거예요. 제목은 거창하게 **"워크플로우 에이전트로서의 루프 에이전트 개념"**이지만, 쉽게 말해 **"실수하면 다시 시켜서라도 완벽하게 만드는 꼼꼼한 팀장 시스템"**을 코드로 구현하는 과정이라고 보시면 됩니다.

우리가 만들 예제는 **'블로그 글 기획 자동화'**예요. 그냥 "글 써줘"라고 시키는 게 아니라, **'기획자(Planner)'**가 초안을 짜고, **'검수자(Checker)'**가 빨간 펜으로 체크해서 통과할 때까지 돌려보내는 **'품질 관리 루프'**를 만드는 여정입니다.

자, 그럼 첫 번째 주자인 **'블로그 기획자(Blog Planner)'**와 깐깐한 **'개요 검수자(Outline Validation Checker)'**를 어떻게 채용하고 교육시키는지, 아주 디테일하게 들여다볼까요?

---

## 1. 첫 번째 직원 채용: '블로그 기획자 (Blog Planner)' — "뼈대만 딱 잡아주는 건축가"

가장 먼저 해야 할 일은 우리 팀의 **첫 번째 에이전트**를 정의하는 거예요. 이 친구의 역할은 딱 하나입니다. **사용자가 던진 '주제(Topic)'라는 덩어리를, 글쓰기 좋은 '구조화된 개요(Outline)'로 쪼개는 것**이죠.

```python
# 첫 번째 에이전트: 블로그 기획자
blog_planner = Agent(
    name="BlogPlanner",              # 이름표 붙이기
    model=os.getenv("MODEL_NAME"),   # 어떤 뇌(LLM) 쓸지 지정
    description="주제를 받아 블로그 글 개요를 작성하는 에이전트", # 인간용 설명
    instruction="""당신은 블로그 기획자입니다. 주어진 주제로 마크다운 형식의 개요를 작성하세요.
    반드시 다음 구조를 포함해야 합니다:
    1. 제목 (Title)
    2. 짧은 서론 (Introduction)
    3. 4~6개의 본문 섹션 (Sections) - 각 섹션은 불릿 포인트 포함
    4. 결론 (Conclusion)
    """,
    output_key="blog_outline"        # 💡 핵심! 결과물을 'blog_outline'이라는 키로 공용 노트(State)에 저장
)
```

### 🧐 개념 돋보기: `name`과 `description`, `instruction`의 차이

> **📋 [이력서 vs 업무 매뉴얼 vs 직함]**
> 
> 에이전트를 만들 때 이 세 가지를 헷갈리지 않으셔야 해요.
> 
> *   **`name` (이름): "BlogPlanner"** → **직함/명찰**입니다. 나중에 "야, BlogPlanner 너 좀 와봐"라고 부를 때 쓰는 **고유 식별자**예요. 중복되면 안 돼요.
> *   **`description` (설명): "주제를 받아 블로그 글 개요를 작성하는 에이전트"** → **이력서 한 줄 소개** 또는 **조직도 설명**입니다. 사람(개발자)이나 다른 에이전트가 "얘가 무슨 하는 애지?" 하고 볼 때 읽는 **메타데이터**예요. LLM이 동작하는 데 직접적인 영향을 주진 않아요.
> *   **`instruction` (지시문): "당신은 블로그 기획자입니다... 반드시 다음 구조를 포함해야 합니다..."** → **실제 업무 매뉴얼(시스템 프롬프트)**입니다. **이게 가장 중요해요!** LLM이 "아, 나 지금 기획자 역할을 해야지. 근데 형식은 마크다운이고 섹션은 4~6개로 해야지"라고 **생각(추론)하게 만드는 핵심 명령어**입니다.

---

### 🧐 개념 돋보기: `output_key` — "공용 서랍에 라벨 붙여 넣기"

> **🗂️ [출력 키(Output Key)는 '공용 노트의 폴더 이름'입니다]**
> 
> 코드 마지막 줄 `output_key="blog_outline"`을 보세요. 이게 이번 챕터의 **핵심 마법**이에요.
> 
> 1.  **BlogPlanner**이 열심히 개요를 짜서 답변을 뱉습니다.
> 2.  프레임워크(ADK 등)는 그 답변을 **그냥 화면에 띄우지 않고**, **세션 상태(Session State)라는 '팀 공용 노트'에 쏙 넣어버립니다.**
> 3.  이때 **"이 폴더 이름은 `blog_outline`이야"**라고 라벨을 붙여주는 게 바로 `output_key`예요.
> 
> **왜 이게 중요할까요?**
> 바로 **다음 주자(검수자)가 "내 차례네? 그럼 `blog_outline` 폴더부터 열어서 보자"** 하고 **자동으로 찾아갈 수 있게 되기 때문**이죠. 우리가 "야, 저기 서랍장에 있는 거 좀 줘"라고 일일이 말해줄 필요 없이, **약속된 키 이름만 알면 에이전트끼리 알아서 데이터를 주고받습니다.** 이게 바로 **'상태(State) 기반 협업'**의 정수예요!

---

## 2. 두 번째 직원 채용: '개요 검수자 (Outline Validation Checker)' — "빨간 펜 든 깐깐한 편집장"

자, 기획자가 개요를 써서 `blog_outline` 서랍에 넣어뒀어요. 이제 **검수자**를 불러야죠. 이 친구는 **글을 쓰지 않습니다.** 오직 **읽고, 판단하고, "통과(OK)" 또는 "실패(이유)"**만 외칩니다.

```python
# 두 번째 에이전트: 개요 검수자
outline_checker = Agent(
    name="OutlineChecker",
    model=os.getenv("MODEL_NAME"),
    description="작성된 개요가 규칙에 맞는지 검사하는 에이전트",
    instruction="""당신은 엄격한 편집장입니다. 공용 노트(State)에 저장된 'blog_outline'을 읽고 다음 기준을 모두 만족하는지 검사하세요.
    
    [필수 체크리스트]
    1. 제목(Title)이 있는가?
    2. 서론(Introduction)이 있는가?
    3. 본문 섹션(Sections)이 4개 이상 6개 이하인가? (불릿 포인트 포함)
    4. 결론(Conclusion)이 있는가?
    
    [판단 규칙 - 매우 중요!]
    - **모두 만족하면:** 다른 말 하지 말고 딱 한 단어 **"okay"**만 출력하세요.
    - **하나라도 빠지면:** "okay" 말고 **구체적으로 뭐가 빠졌는지, 왜 틀렸는지 설명**하며 "fail" 또는 오류 메시지를 출력하세요.
    """,
    # output_key가 없네요? -> 이 에이전트는 상태를 '쓰기'만 하지 않고 '읽고 판단'만 합니다.
)
```

### 🧐 개념 돋보기: 검수자의 `instruction` 설계 비법 — "판단을 코드로 박제하기"

> **⚖️ [LLM에게 '판단'을 맡길 땐 '이진법(Binary) + 사유'를 강제하세요]**
> 
> 검수자 에이전트의 `instruction`을 보면 **[판단 규칙]** 부분이 아주 구체적이죠?
> 
> *   **"만족하면 -> `okay` 한 단어만 출력"**
> *   **"불만족하면 -> 이유 설명 출력"**
> 
> 이걸 **'구조화된 출력(Structured Output)' 강제**라고 해요. LLM은 기본적으로 수다쟁이라 "네, 제목이 있고 서론도 있고... 좋네요! 통과입니다!"라고 길게 말할 수 있어요. 하지만 **다운스트림(다음 단계) 에이전트나 코드(파이썬 로직)가 이 결과를 받아서 `if result == "okay":` 같은 분기 처리를 하려면**, **출력 형식이 칼같이 고정되어 있어야 합니다.**
> 
> **비유하자면:**
> *   **나쁜 지시:** "잘했으면 잘했다고 말해줘." → 결과: "네, 아주 훌륭하게 잘 작성되었습니다!" (코드에서 `== "okay"` 비교 실패 😭)
> *   **좋은 지시:** "통과면 **무조건 `okay` 세 글자만** 뱉어." → 결과: `okay` (코드에서 `== "okay"` 비교 성공 🎉)
> 
> **이게 바로 '워크플로우 에이전트'를 만들 때 가장 중요한 노하우예요.** **사람이 읽기 좋은 말이 아니라, 기계(다음 로직)가 읽기 좋은 신호(Signal)를 출력하게 설계해야 합니다.**

## 3. 드디어 등장하는 '루프(Loop)'의 씨앗 — "OK 사인 떨어질 때까지 반복해"

자, 여기서 스크립트는 끊겼지만(`If something is missing, it must answer with...`), 우리는 **다음 그림**을 그릴 수 있어요. 이게 바로 **'루프 에이전트(Loop Agent)'** 개념의 시작입니다.

### 🔄 워크플로우 시나리오: "완벽해질 때까지 돌려보내기"

1.  **사용자:** "인공지능 역사에 대해 써줘."
2.  **BlogPlanner (기획자):** `blog_outline` 서랍에 초안 저장. (근데 섹션을 3개만 썼음 😅)
3.  **OutlineChecker (검수자):** 서랍 열어서 봄 -> "섹션 3개밖에 없네? **Fail! 섹션 4~6개로 늘려.**" 출력.
4.  **💡 루프 로직 (우리가 짤 코드):** "어? `okay`가 아니네? 그럼 **다시 BlogPlanner에게 가서 '검수자 피드백 반영해서 다시 써'라고 시키자.**"
5.  **BlogPlanner (재기획):** 피드백 보고 섹션 5개로 늘려서 `blog_outline` **덮어쓰기(Update)**.
6.  **OutlineChecker (재검수):** 다시 봄 -> "오! 다 맞네? **okay**"
7.  **루프 종료!** -> 다음 단계(본문 작성 에이전트)로 넘어감.

### 🧐 개념 돋보기: '루프 에이전트'란 무엇인가? — "자동으로 '다시 해' 버튼 누르는 매니저"

> **🔁 [Loop Agent = '조건 만족 시까지 반복 실행하는 워크플로우 컨트롤러']**
> 
> 우리가 흔히 아는 `while` 문이나 `for` 문이 **코드 레벨**의 루프라면, **에이전트 세계의 루프 에이전트(Loop Agent)는 '작업 단위'의 루프**를 관리해요.
> 
> **구조:**
> ```text
> [Loop Agent 시작]
>   ├─ 1. BlogPlanner 실행 (개요 생성/수정)
>   ├─ 2. OutlineChecker 실행 (검수)
>   └─ 3. 판단 로직: Checker 결과 == "okay" ?
>        ├─ True  -> Loop 탈출 (Break) -> 다음 단계로 Go!
>        └─ False -> 피드백 상태에 저장 -> 1번으로 돌아가기 (Continue)
> [Loop Agent 종료]
> ```
> 
> **일상 비유: "완성될 때까지 퇴근 없는 야근 루프"**
> *   **팀장(Loop Agent):** "김 대리(Planner), 기획안 올려. 박 대리(Checker), 검토해."
> *   **박 대리:** "김 대리, 섹션 수 부족해. 반려." (출력: `fail: 섹션 수 부족`)
> *   **팀장:** "그래? 김 대리, 박 대리 말 듣고 고쳐와." (상태 업데이트 후 재실행)
> *   **김 대리:** "수정했어요." (상태 덮어쓰기)
> *   **박 대리:** "오케이." (출력: `okay`)
> *   **팀장:** "좋아, 통과! 이제 디자인 팀(다음 에이전트) 넘겨."
> 
> 이 **'팀장 역할(판단 및 흐름 제어)'을 하는 것**이 바로 **Loop Agent(또는 Looping Workflow)**의 핵심입니다. **LLM이 스스로 "내가 다시 해야겠다"라고 판단하게 둘 수도 있고(ReAct 스타일), 외부 오케스트레이터(코드)가 `while` 돌리며 에이전트들을 호출할 수도 있어요.(ADK 스타일)** 이번 예제는 후자, **'코드가 루프를 돌며 에이전트들을 지휘하는 방식'**에 가깝습니다.

## 4. 왜 이렇게 복잡하게 '상태(State)'와 '루프'를 쓸까? — "한 방에 시키면 안 돼요?"

좋은 질문이에요. **"야, 너 블로그 기획하는데 제목, 서론, 섹션 4~6개, 결론 꼭 넣어서 완벽하게 한 번에 써!"**라고 **BlogPlanner 하나한테만 시키면 안 될까요?**

### 🧐 개념 돋보기: '단일 프롬프트' vs '멀티 에이전트 루프' — "천재 한 명 vs 검증 시스템"

> **🧠 [단일 프롬프트의 함정: "지시가 길어지면 LLM도 까먹는다"]**
> 
> *   **단일 에이전트(One-shot):** 프롬프트에 규칙을 100개 적어넣어도, LLM은 **'다음 토큰 예측'** 기계라 **뒤에 있는 규칙을 까먹거나, 앞의 규칙과 충돌**해서 **'환각(Hallucination)'**을 일으키기 쉽습니다. "섹션 4~6개" 규칙을 지킨다며 내용을 억지로 늘리다 **말도 안 되는 섹션**을 만들 수도 있어요.
> *   **멀티 에이전트 루프(Separation of Concerns):**
>     1.  **Planner(생성):** "창의적으로, 내용 풍부하게 쓰는 데만 집중해." (생성 특화)
>     2.  **Checker(검증):** "규칙만 딱 보고 기계적으로 체크해." (논리/검증 특화)
>     3.  **Loop(제어):** "통과할 때까지 무한 반복." (품질 보장)
> 
> **비유: 요리사와 위생 검사관**
> *   **단일 프롬프트:** 요리사에게 "맛있게 요리해. 근데 칼로리 500kcal 맞춰. 나트륨 200mg 이하. 알레르기 유발 물질 빼. 플레이팅 이쁘게. 10분 안에." → **요리사 멘붕, 결과물 망함.**
> *   **멀티 에이전트 루프:**
>     *   **요리사(Planner):** "맛있게 만드는 데만 올인!" → 요리 완성.
>     *   **영양사/위생검사관(Checker):** "이거 나트륨 초과야. 다시." (단호함)
>     *   **주방장(Loop):** "요리사, 영양사 말 듣고 다시 해." → 수정본 나옴.
>     *   **검사관:** "오케이, 합격."
> 
> **이게 바로 '워크플로우 에이전트' 패턴의 위력입니다.** **'생성(Creative)'과 '검증(Critical)'의 역할을 분리하고, 루프로 엮어서 '신뢰도(Reliability)'를 확보하는 것.** 이게 바로 우리가 이 복잡한 코드를 짜는 이유예요.

## 5. 실전 코드 조립 전, 머릿속 시뮬레이션 해보기

자, 이제 우리가 짜야 할 **파이썬 코드(오케스트레이션 로직)**의 큰 그림이 그려지시나요? 아직 코드를 안 보여드렸지만, **개념만으로도 흐름을 읽을 수 있어야 진짜 내공**이 쌓입니다.

```text
# 의사코드 (Pseudocode) - 머릿속으로 돌리세요!

# 1. 초기 상태 준비
state = {"topic": "인공지능 역사"}

# 2. 루프 시작 (최대 3번 시도 등 안전장치 필요)
for attempt in range(3):
    
    # Step A: 기획자 실행 -> state['blog_outline'] 생성/갱신
    blog_planner.run(state)  
    
    # Step B: 검수자 실행 -> state['check_result'] 에 "okay" 또는 "fail: 이유" 저장
    outline_checker.run(state)
    
    # Step C: 루프 제어 로직 (팀장의 판단)
    if state['check_result'].strip().lower() == "okay":
        print("✅ 개요 검수 통과! 루프 탈출.")
        break  # 루프 종료
    else:
        print(f"🔄 검수 실패 ({attempt+1}회차): {state['check_result']}")
        print("   -> 피드백 반영하여 기획자 재실행...")
        # state에 피드백 내용이 이미 들어있으므로, 다음 루프에서 기획자가 이를 봄
        continue

# 3. 루프 끝나면 다음 단계(본문 작성 등)로 state 넘기기
```

### 💡 여기서 포인트: **'상태(State)의 누적과 갱신'**

*   **`blog_planner.run(state)`** 호출 시: `state['blog_outline']` = **새로운 개요** (덮어쓰기)
*   **`outline_checker.run(state)`** 호출 시: `state['blog_outline']`을 **읽기만 함**. 결과는 `state['check_result']`에 저장.
*   **루프가 돌 때:** `state` 객체는 **계속 살아있음**. 그래서 2번째 루프에서 `blog_planner`가 실행될 때, `state` 안에는 **"이전 개요" + "검수자의 피드백(check_result)"**가 모두 들어있게 됩니다.
*   **Planner의 Instruction 수정 팁:** 실제 구현 시 Planner의 `instruction`에 **"만약 state에 check_result가 있으면, 그 피드백을 반영해서 고쳐 써."**라는 문구를 넣어주면 **완벽한 수정 루프**가 완성돼요!

**핵심 키워드 3가지, 가슴에 새기세요:**

3.  **Loop Control(상태 기반 반복)**: `while not okay: re-run` 패턴으로 **품질 보장 자동화**하기.
