# 자동 재시도 메커니즘: "retry" 판정 시 플래너 재실행 (최대 3회)

안녕하세요! 앞서 우리는 **'플래너(작성자)'**가 초안을 쓰고, **'체커(검수자)'**가 이를 꼼꼼히 검사하는 시스템을 만들었습니다. 그런데 여기서 아주 중요한 문제가 하나 남아 있습니다. 

> **"검수자가 '불합격(retry)' 판정을 내렸을 때, 도대체 어떻게 해야 할까?"**

단순히 "틀렸어!"라고 말하고 끝내버리면 아무런 소용이 없겠죠? 이번 챕터에서는 **검수자가 '재시도(retry)'를 외쳤을 때, 작성자를 다시 불러들여 자동으로 고쳐 쓰게 만드는 '자동 재시도 메커니즘(Automatic Retry Mechanism)'**이 어떻게 작동하는지, 그리고 왜 **'최대 3회'라는 안전장치**가 필요한지 아주 구체적으로 파헤쳐 보겠습니다.

---

## 1. "한 번 틀렸다고 포기할래?" - 무한 루프의 공포와 '최대 3회'의 지혜

가장 먼저 이해해야 할 것은 **'왜 하필 3회인가?'**입니다. 프로그래밍 세계에는 **'무한 루프(Infinite Loop)'**라는 무시무시한 괴물이 살고 있습니다.

### 일상 비유: 고집 센 요리사와 끝없는 주문
상상해 보세요. 손님(사용자)이 "김치찌개 주세요!"라고 주문했습니다.
1.  **요리사(플래너)**가 김치찌개를 끓여 내놓습니다.
2.  **매니저(체커)**가 맛을 보고 **"간이 안 맞아요, 다시 해오세요!(Retry)"**라고 합니다.
3.  요리사가 다시 끓여 내놓습니다.
4.  매니저가 또 **"김치가 너무 셔요, 다시!(Retry)"**라고 합니다.
5.  요리사가 또 끓입니다...
6.  **이게 밤새도록 계속된다면?** 식당 문 닫을 때까지 김치찌개만 끓이다 끝납니다. 다른 손님 주문은 받지도 못하죠.

이게 바로 **무한 루프**입니다. 조건이 충족되지 않으면(`okay`가 안 나오면) 영원히 `플래너 실행 -> 체커 검사 -> 플래너 실행 -> 체커 검사...`를 반복하게 되는 끔찍한 상황입니다.

### 개념 돋보기 🔍
> **무한 루프(Infinite Loop)란?**
> 종료 조건이 없거나, 종료 조건이 영원히 충족되지 않아 프로그램이 멈추지 않고 같은 작업을 끝없이 반복하는 현상입니다. 시스템 자원(CPU, 메모리)을 모두 소진시켜 전체 서비스를 마비시키는 주범입니다.

그래서 우리는 **"제발 좀 그만해! 최대 3번만 다시 해보고 안 되면 그냥 넘어가(또는 에러 처리해)"**라는 **최대 재시도 횟수(Max Retries = 3)**라는 **브레이크(안전장치)**를 걸어두는 것입니다. 이건 마치 **"수정 기회는 딱 3번만 줄게. 3번 다 틀리면 넌 자격 미달이야"**라고 엄포를 놓는 것과 똑같습니다.

---

## 2. 루프 에이전트(Loop Agent): 반복의 지휘자

이 자동 재시도 메커니즘의 핵심 열쇠는 바로 **`Loop Agent(루프 에이전트)`**라는 특별한 컨테이너(상자)입니다. 앞서 배운 `Sequential Agent(순차 에이전트)`가 "1번 하고 2번 하고 3번 하고 끝"이라면, `Loop Agent`는 **"안에 든 애들아, 내가 '그만' 할 때까지 계속 돌려!"**라고 명령하는 **반복 전용 상자**입니다.

### 일상 비유: 놀이공원의 '바이킹' 운영 요원
`Loop Agent`는 놀이공원 바이킹의 **운영 요원**과 같습니다.
*   **탑승객(데이터/상태)**: 바이킹에 탄 사람들.
*   **한 사이클(Planner -> Checker)**: 바이킹이 한번 왕복하는 것.
*   **운영 요원(Loop Agent)**: "자, 3바퀴만 돌고 내릴게요!"라고 정해놓고, 3바퀴가 돌거나 중간에 "멈춰!" 신호가 오면 브레이크를 거는 역할.

스크립트에서 **"To connect the planner and the checker, we wrap them inside a loop agent called robust blog planner."**라고 했죠? 이 말이 바로 **"플래너와 체커를 '로버스트 블로그 플래너'라는 이름의 루프 에이전트라는 큰 상자 안에 넣어버렸다"**는 뜻입니다.

### 개념 돋보기 🔍
> **Loop Agent (루프 에이전트) 구조**
> ```text
> [Loop Agent: "Robust Blog Planner"]  <-- 반복을 관리하는 큰 상자 (최대 3회 설정)
>     ├── [Agent 1: Planner (작성자)]   <-- 1순위: 초안 작성
>     └── [Agent 2: Checker (검수자)]   <-- 2순위: 검사 및 "okay" / "retry" 판단
> ```
> *   **실행 순서**: 플래너 실행 -> 체커 실행 -> (체커가 "retry"면) **처음(플래너)으로 돌아가기** -> 플래너 실행 -> 체커 실행 ... (최대 3회)
> *   **탈출 조건**: 체커가 **"okay"**라고 외치는 순간 즉시 루프 종료!

---

## 3. 체커의 '마법의 단어': "okay" vs "retry" - 신호등 시스템

이 루프가 돌아갈지, 멈출지를 결정하는 건 오로지 **체커(Checker)의 입**에 달려 있습니다. 체커는 복잡한 설명을 하지 않습니다. 그저 **단 한 단어**만 뱉습니다.

### 3-1. 초록불: "okay" (합격)
> **"상태(State)에 저장된 `blog_outline`을 보니 제목도 있고, 서론도 있고, 섹션 4~6개도 있고, 결론도 있네? 완벽해! `okay`"**

이 순간 **Loop Agent는 "임무 완료!"**를 외치며 루프를 **즉시 탈출(Break)**합니다. 뒤에 기다리고 있던 다음 에이전트(예: 본문 작성 에이전트)에게 제어권이 넘어갑니다.

### 3-2. 빨간불: "retry" (불합격 + 사유)
> **"음... `blog_outline`을 봤는데 섹션이 3개밖에 없어. 규칙은 4~6개야. 빠진 게 있으니 다시 써. `retry` - 섹션 개수 부족함."**

스크립트에는 *"If something is missing, it must answer with the word 'retry' and explain what's wrong."*라고 되어 있습니다. 체커는 그냥 "retry"만 던지는 게 아니라, **무엇이 잘못되었는지 설명(피드백)까지 붙여서** 상태(State)나 컨텍스트에 남겨줍니다.

### 일상 비유: 운전면허 시험관
*   **수험생(플래너)**: 운전해서 옴.
*   **시험관(체커)**: 
    *   합격 -> **"합격입니다(okay). 면허증 발급하세요."** -> 끝.
    *   불합격 -> **"불합격(retry). 이유: 좌회전 신호 위반, T자 주차 선 넘음. 다시 도전하세요."** -> 수험생은 이 피드백을 듣고 연습해서 다시 옴.

이 **'이유 설명'**이 있어야 플래너가 "아! 섹션 개수를 늘려야겠네?" 혹은 "제목 형식을 바꿔야겠네?" 하고 **제대로 고쳐 쓸 수 있습니다.** 그냥 "틀렸어"라고만 하면 플래너는 뭘 고쳐야 할지 몰라 헤매다 또 틀리게 되니까요.

## 4. 상태(State)를 통한 '릴레이 경주' - 바톤 터치의 기술

이 모든 과정이 매끄럽게 돌아가려면 **'공유 메모장(Shared State)'**이 필수적입니다. 루프가 돌 때마다 데이터가 초기화되면 안 되니까요.

### 시나리오: 3번의 도전 (최대 3회 루프 시뮬레이션)

자, 이제 **'로버스트 블로그 플래너(Loop Agent)'**가 최대 3회 회전하며 벌어지는 드라마를 1초 단위로 지켜봅시다.

#### 🎬 1회차 (첫 번째 도전)
1.  **Loop Agent**: "자, 1번째 시도 시작! 플래너야, 너 나와."
2.  **Planner**: (열심히 씀) -> `State['blog_outline']`에 저장: *"제목: AI, 서론: ..., 섹션 3개, 결론: ..."*
3.  **Loop Agent**: "자, 이제 체커야, 너 나와 검사해."
4.  **Checker**: (읽어봄) -> **"retry: 섹션이 3개뿐임. 4~6개 필요."** -> `State`에 피드백 저장.
5.  **Loop Agent**: (카운트: 1/3) "재시도 판정 났네? 아직 3번 안 됐으니까... **다시 플래너부터 시작!**"

#### 🎬 2회차 (두 번째 도전 - 피드백 반영)
1.  **Planner**: (State에 남은 **이전 초안 + 체커 피드백**을 보며) -> *"아, 섹션이 부족했구나? 하나를 더 추가하고, 하나 쪼개서 5개로 맞춰야지."* -> 수정된 아웃라인 저장.
2.  **Checker**: (다시 읽어봄) -> **"retry: 섹션 개수는 5개로 맞췄네. 근데 '결론' 부분이 없음. 결론 필수."**
3.  **Loop Agent**: (카운트: 2/3) "아직 기회 남았어. **다시 플래너로!**"

#### 🎬 3회차 (마지막 기회 - 운명의 순간)
1.  **Planner**: (피드백 보고) -> *"결론 넣고, 섹션 5개 유지하고... 완벽하게 고쳤어."* -> 최종본 저장.
2.  **Checker**: (꼼꼼히 검사) -> **"okay: 제목, 서론, 섹션 5개, 결론 모두 갖춤. 통과."**
3.  **Loop Agent**: (환호) **"okay 받았어! 루프 즉시 종료! 탈출!"** -> 다음 단계(본문 작성 에이전트)로 넘어감.

## 5. 만약 3번 다 실패하면? (최대 횟수 초과 시나리오)

여기서 궁금해지실 겁니다. **"3번 다 했는데도 체커가 'retry'만 외치면 어떡해?"**

### 개념 돋보기 🔍
> **최대 재시도 횟수 초과(Max Retries Exceeded) 처리 전략**
> Loop Agent는 내부 카운터를 가지고 있습니다. `max_iterations=3`으로 설정되어 있다면:
> 1.  3번째 루프가 끝나고 체커가 또 `"retry"`를 반환하면?
> 2.  Loop Agent는 **"더 이상 반복 불가(Max iterations reached)"** 예외를 발생시키거나, **마지막 상태(아직 불완전한 아웃라인)를 그대로 다음 단계로 넘기거나**, **에러 핸들링 에이전트**를 호출합니다.
> 3.  보통은 **"자동화 실패 알림(Slack, Email)"**을 보내고 **사람(개발자/운영자)이 개입**하도록 설계합니다.

### 일상 비유: 3번 불합격하면 '면허 취소' 혹은 '특별 교육'
운전면허 시험도 3번 떨어지면(국가마다 다름) 일정 기간 응시 제한이 걸리거나, 특별 교육을 이수해야 하죠. 우리 시스템도 **"AI가 3번이나 시도했는데 못 고쳤으면, 이건 사람이 봐야 해"**라고 **인간에게 에스컬레이션(Escalation, 이관)**하는 것이 정석입니다. 무한히 AI끼리 싸우게 두지 않는 것, 그게 **'로버스트(Robust, 견고한)'** 시스템의 핵심 철학입니다.

## 6. 왜 이 구조가 '로버스트(Robust - 견고한)'한가?

스크립트에서 이 루프 에이전트 이름을 **"Robust Blog Planner(견고한 블로그 플래너)"**라고 지은 데에는 다 이유가 있습니다.

### 1) 자기 치유 능력 (Self-Healing)
단순히 한 번 실행하고 끝나는 게 아니라, **결과물을 스스로 검증하고, 틀리면 스스로 고치는 과정**을 내장했습니다. 외부 개입 없이 "작성 -> 검사 -> 수정" 사이클을 자동으로 돕니다.

### 2) 예측 가능한 실패 처리 (Predictable Failure Handling)
*   **무한 루프 방지**: `max 3`이라는 명확한 상한선으로 시스템 다운 방지.
*   **명확한 계약**: 체커는 `okay` 또는 `retry` + 사유만 말하면 됨. 플래너는 피드백만 보고 고치면 됨. **인터페이스가 극도로 단순함.**

### 3) 상태 기반의 점진적 개선 (Iterative Improvement via State)
1회차 초안 -> 2회차 수정본 -> 3회차 최종본. **이전 시도의 기록(State)이 쌓이면서 점점 품질이 좋아집니다.** 이건 마치 **글쓰기의 '퇴고(推敲)' 과정**을 기계가 자동으로 수행하는 것과 같습니다.

## 7. 코드/설정 수준에서 보는 '루프 제어' 로직 (개념적 이해)

개발자가 아니어도 로직 구조는 알아두면 좋습니다. 대충 이런 모양새입니다.

```python
# 의사 코드 (Pseudo Code) 스타일로 이해하기

loop_agent = LoopAgent(
    name="RobustBlogPlanner",
    max_iterations=3,          # 🛑 안전장치: 최대 3바퀴
    sub_agents=[
        planner_agent,         # 1. 작성
        checker_agent          # 2. 검사
    ]
)

# 루프 에이전트 내부에서 대략 이렇게 돌아갑니다:
iteration = 0
while iteration < max_iterations:
    iteration += 1
    print(f"--- {iteration}번째 시도 ---")
    
    # 1. 플래너 실행 (이전 상태/피드백 참고하여 작성)
    current_outline = planner_agent.run(state)
    state['blog_outline'] = current_outline
    
    # 2. 체커 실행
    judgment = checker_agent.run(state)  # "okay" 또는 "retry: 이유"
    
    # 3. 판단 로직
    if judgment == "okay":
        print("✅ 검수 통과! 루프 탈출.")
        break  # 🏁 루프 즉시 종료
    else:
        print(f"❌ 재시도 필요: {judgment}")
        state['feedback'] = judgment  # 피드백 상태에 저장 -> 다음 플래너가 봄
        
        if iteration == max_iterations:
            print("🚨 최대 재시도 횟수 초과! 알림 발송 또는 예외 처리.")
            # handle_failure(state)
            break
```

이 로직에서 **`break`** 한 줄이 얼마나 소중한지 아시겠죠? `okay`를 만나는 순간 `while` 문을 박차고 나가는 **'탈출구'** 역할을 하니까요.

## 8. 요약하며: "믿고 맡기는 자동화의 완성"

이번 챕터에서 우리는 **'자동 재시도 메커니즘'**의 심장부인 **Loop Agent**와 그 작동 원리를 낱 원리를 해부했습니다.

1.  **Loop Agent**는 플래너와 체커를 감싸는 **반복 전용 컨테이너**다.
2.  **체커**는 `okay`(통과) 또는 `retry + 사유`(실패)라는 **명확한 신호**만 보낸다.
3.  **`retry` 시 플래너는 피드백을 읽고 '수정된 버전'을 다시 쓴다.** (상태 공유 필수)
4.  **최대 3회(Max Iterations)**라는 **브레이크**로 무한 루프를 원천 차단한다.
5.  3회 내 `okay`면 **성공적으로 다음 단계로**, 3회 초과면 **사람에게 이관(에러 처리)**한다.

이게 바로 **"한 번 실행해보고 틀리면 끝"**인 단순한 자동화와, **"스스로 검증하고 고쳐서 완성도 높은 결과물을 보장하는"** **견고한(Robust) 에이전트 시스템**의 결정적인 차이입니다.

이제 우리 시스템은 **"글 좀 써줘"**라고 시키면, **알아서 쓰고, 알아서 검사하고, 알아서 고쳐서, 3번 안에 합격점을 받아오는 '프로 작가 팀'**을 둔 셈이 되었습니다. 다음 챕터에서는 이 완벽해진 아웃라인을 받아 **'본문 작성 에이전트 팀'**이 어떻게 글을 써내려가는지 구경하러 가보겠습니다. 수고하셨습니다
