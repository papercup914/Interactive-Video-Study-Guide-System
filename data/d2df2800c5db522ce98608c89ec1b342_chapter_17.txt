# 챕터 3: 클로드 매니지드 에이전트의 3대 핵심 리소스 — 두뇌, 손, 그리고 연결고리

안녕하세요! 지난 시간에는 에이전트가 왜 '자율성'을 가져야 하는지, 그리고 클로드 매니지드 에이전트가 어떻게 우리의 새벽 3시 온콜(on-call) 악몽을 해결해 줄 수 있는지에 대해 이야기 나눴습니다. 이제 본격적으로 **'이 마법 같은 에이전트를 실제로 어떻게 만들까?'**라는 궁금증을 풀러 코드 속으로 들어가 볼 차례입니다.

강사님께서 화면에 띄워주신 `agent.py` 파일을 보니, 무언가 복잡해 보이지만 사실 **딱 세 가지 핵심 부품**만 알면 됩니다. 이 세 가지만 제대로 이해하면, 여러분도 "내 대신 서버를 고쳐주는 나만의 데브옵스 비서"를 만들 수 있어요. 자, 그럼 이 세 가지 주인공, **'에이전트(두뇌)', '환경(손)', '세션(연결고리)'**을 우리 일상 언어로 아주 낱낱이 파헤쳐 보겠습니다.

---

## 1. 에이전트(Agent) — "요리사의 레시피 노트이자 두뇌"

가장 먼저 등장하는 건 **`Agent`** 클래스입니다. 강사님은 이렇게 말씀하셨어요.
> *"에이전트는 페르소나(Persona)와 능력(Capabilities)을 정의하는 곳입니다. 모델, MCP 서버, 스킬, 에이전트 루프에서 활용할 다양한 컴포넌트들이 여기 들어갑니다."*

### 🍳 일상 비유: 미슐랭 3스타 셰프의 **'레시피 노트 + 두뇌'**

여러분이 **최고급 레스토랑의 오너 셰프**라고 상상해 보세요. 이 셰프(에이전트)에게는 **'레시피 노트(Agent 정의 파일)'**가 한 권 있습니다. 이 노트에는 다음과 같은 내용이 적혀 있죠.

1.  **페르소나(Persona = 성격/역할):** "너는 20년 경력의 한식 대가야. 손님이 매운 걸 못 먹으면 순하게, 아이에게는 부드럽게 조리해." → **시스템 프롬프트(System Prompt)**에 해당합니다.
2.  **모델(Model = 두뇌 회로):** "판단은 GPT-4o(또는 Claude 3.5 Sonnet) 최신 버전으로 해." → **어떤 LLM을 쓸지** 정하는 겁니다.
3.  **스킬(Skills = 특기 요리법):** "김치 담그기 스킬, 육수 내기 스킬, 플레이팅 스킬은 네가 마스터해둔 거야." → **미리 정의해둔 함수(Function/Tool) 들**입니다.
4.  **MCP 서버(MCP Servers = 식재료 창고/도구함):** "간장, 고춧가루, 칼, 도마는 저쪽 창고(MCP 서버)에 다 갖다 놨어. 필요하면 갖다 써." → **외부 도구나 데이터 소스에 접근하는 연결 정보**입니다.

**즉, `Agent` 객체는 "이 요리사(에이전트)는 누구이며, 뭘 할 줄 알고, 무슨 도구를 쓸 수 있는가?"를 정의한 **설계도이자 두뇌** 그 자체입니다.** 아직 요리를 시작하지 않았어요. 그냥 "준비된 셰프"가 서 있는 상태죠.

> **💡 개념 돋보기: 에이전트(Agent)의 정체**
> > **에이전트 = '생각하는 주체'의 정의서**
> >
> > 코드상으로는 `Agent` 클래스 인스턴스 하나입니다. 하지만 개념적으로는 **'누가(Persona), 어떤 머리(Model)로, 무슨 도구(Skills, MCP)로, 어떻게 생각할지(시스템 프롬프트)'를 총망라한 명세서**입니다. 이 친구는 아직 '일'을 하는 게 아니라, 일할 **'준비된 상태'**입니다.

## 2. 환경(Environment) — "요리사의 전용 주방이자 손(Hand)"

두 번째 주인공은 **`Environment`**입니다. 강사님의 비유가 정말 기가 막혔어요.
> *"이전 것(에이전트)이 에이전트의 '두뇌(Brain)'라면, 환경(Environment)은 에이전트의 '손(Hands)'입니다. 에이전트가 무엇을 실행할지 생각하고, 환경을 이용해 실제로 행동할 공간과 컨테이너를 갖는 것이죠."*

### 🍳 일상 비유: **'격리된 전용 주방(컨테이너/샌드박스)'**

아무리 천재 셰프(에이전트/두뇌)가 있어도, **주방(환경/손)**이 없으면 요리를 할 수 없습니다. 여기서 말하는 환경은 단순히 "부엌"이 아닙니다. **클라우드 위에 떠 있는, 격리된 나만의 전용 주방(Docker 컨테이너, VM, 혹은 원격 서버)**을 뜻해요.

이 주방의 특징은 이렇습니다.

*   **실행의 공간:** 셰프가 "양파 다져!"라고 생각(추론)하면, **주방의 칼과 도마(환경 내 도구/터미널/파일시스템)**가 실제로 움직여 양파를 다집니다.
*   **격리성(샌드박싱):** 강사님이 강조하신 **'보안(Credentials & Security)'** 이슈가 바로 여기 있습니다. 
    *   *옛날 방식(에이전트 루프 + 도구 실행 통합):* 셰프가 **집 전체(마스터 키, 금고, 침실 다 포함)**를 자유롭게 돌아다니는 격이었어요. 셰프가 실수하거나 해킹당하면 집 전체가 털립니다. (내 로컬 파일 시스템, AWS 키, DB 비번 다 노출)
    *   *클로드 매니지드 방식(두뇌와 손 분리):* 셰프(두뇌)는 **본관 사무실**에 있고, **주방(손/환경)은 별채**에 격리되어 있어요. 셰프는 인터콤(API)으로 "저기 냉장고에서 간장 좀 갖다 줘"라고만 시킵니다. 주방(환경)에는 **요리에 필요한 재료(권한 있는 토큰, 특정 폴더 접근권)만** 넣어둡니다. 설사 주방에서 불이 나거나 도둑이 들어도, 본관(에이전트/본체)과 금고(핵심 크리덴셜)는 안전하죠.
*   **상태 유지(Statefulness):** 주방은 셰프가 퇴근해도 그대로 있습니다. 냄비에 끓이던 육수(프로세스 상태, 파일 변경사항)가 식지 않고 유지돼요.

> **💡 개념 돋보기: 환경(Environment)과 '두뇌-손 분리'의 마법**
> > **환경 = 에이전트가 '물리적으로 행동하는 격리된 실행 컨텍스트'**
> >
> > 이 분리가 왜 혁신인가요?
> > 1.  **보안(샌드박싱):** 에이전트(두뇌)가 내 로컬 PC의 `~/.aws/credentials`나 `.env` 파일을 **직접 읽을 수 없습니다.** 환경(손)라는 별도 공간에서만 동작하니까요. "권한 최소화의 원칙"을 아키텍처 레벨에서 강제한 겁니다.
> > 2.  **지연 시간 단축(TTFT 감소):** 강사님 말씀대로 **90% 이상(P95 기준) 지연 시간 감소**를 가져왔습니다. 왜냐? 예전엔 "세션 하나 만들 때마다 무거운 주방(컨테이너) 통째로 띄워야 했거든요." 이제 두뇌(에이전트 루프)는 서버리스로 가볍게 돌아가고, 무거운 주방(환경)은 필요할 때만, 혹은 미리 띄워두고 재사용하니까 첫 토큰이 튀어나오는 속도가 번개처럼 빨라진 겁니다.

## 3. 세션(Session) — "주문표이자 셰프와 주방을 잇는 '인터콤'"

자, 천재 셰프(에이전트)도 있고, 최첨단 주방(환경)도 준비됐습니다. 그런데 **손님(유저)이 주문하면 어떻게 전달될까요?** 셰프가 주방에 가서 요리하고, 나온 음식을 손님에게 갖다 주는 **전체 흐름**을 관리하는 게 필요하죠. 그게 바로 **`Session`**입니다.

강사님 말씀:
> *"세션은 에이전트와 환경을 묶어주는 방법입니다. 단일 세션은 환경 위에 에이전트 인스턴스를 띄워서 둘을 연결하고, 이벤트를 사용자에게 스트리밍하며, 인간을 대신해 행동하게 만듭니다."*

### 🍳 일상 비유: **'주문표 + 서빙 로봇 + 인터콤 시스템'**

1.  **주문표(세션 생성):** 손님(유저)이 "서버 다운됐어, 고쳐줘!"라고 말하면, 시스템은 **새로운 주문표(세션 ID)** 하나를 끊습니다.
2.  **배정(연결):** 이 주문표를 들고 **"셰프님(에이전트 인스턴스), 3번 주방(환경) 가서 이 일 좀 해줘요"**라고 배정합니다. 이제 **셰프-주방 짝(세션)**이 성립됐습니다.
3.  **인터콤/스트리밍(이벤트 스트림):** 셰프가 주방에서 "지금 로그 보고 있어", "재시작 중이야", "고쳤어!"라고 중얼거리면(이벤트 발생), 인터콤(세션의 스트리밍 채널)을 통해 **실시간으로 홀의 손님(유저 UI)에게 전달**됩니다.
4.  **지속성(Durability):** 손님이 화장실 갔다 오거나(브라우저 새로고침), 심지어 식당 문 닫고 퇴근했다가 내일 와도(노트북 덮고 잠), **주문표(세션)는 살아있습니다.** 주방에서 육수 끓이던 불(프로세스)도 꺼지지 않아요. 클로드 매니지드 에이전트가 **서버 사이드에서 에이전트 루프를 돌리기 때문**이죠.

> **💡 개념 돋보기: 세션(Session)의 3가지 슈퍼파워**
> > **세션 = 에이전트 인스턴스 + 환경 인스턴스 + 양방향 통신 채널의 '결합체'**
> >
> > 1.  **결합(Binding):** 떠돌이 두뇌(에이전트)와 빈 껀트)와 놀고 있는 손(환경)을 **'한 쌍'으로 엮어줍니다.** 세션 없이는 둘은 서로 모릅니다.
> > 2.  **스트리밍(Streaming):** `yield` 제너레이터처럼, 에이전트의 사고 과정(Thinking), 도구 호출(Tool Call), 도구 결과(Tool Result), 최종 답변을 **조각조각 실시간으로** 유저에게 흘려보냅니다. "생각 중..." 스피너만 돌리는 게 아니에요.
> > 3.  **내구성(Durability & Reliability):** **"랩탑을 덮어도, 하드 리프레시해도 모든 게 유지됩니다."** 로컬에서 `python agent.py` 돌리면 프로세스 죽으면 끝이지만, 여기는 클라우드(서버사이드)가 세션 상태를 보관합니다. 프로토타입을 프로덕션으로 갈 때 가장 골치 아픈 '상태 관리/장애 복구'를 **플랫폼이 떠안아 준 것**입니다.

## 🎯 세 가지의 합주: "새벽 3시, 내 대신 일하는 흐름"

자, 이제 이 세 친구가 어떻게 **'새벽 3시 온콜 지옥'에서 우리를 구원하는지** 전체 흐름으로 엮어볼게요.

```mermaid
sequenceDiagram
    participant User as 나 (자고 있음 😴)
    participant Alert as 알람 시스템 (PagerDuty 등)
    participant Session as 세션 (매니저)
    participant Agent as 에이전트 (두뇌/셰프)
    participant Env as 환경 (손/격리된 주방)
    participant Infra as 인프라 (서버, DB, 로그)

    Alert->>Session: "서버 500 에러! 세션 생성해줘!"
    Session->>Agent: 에이전트 인스턴스 할당 (페르소나: SRE 전문가)
    Session->>Env: 환경 프로비저닝/재사용 (권한: kubectl, ssh, 로그 읽기만)
    Session->>User: (슬랙/이메일로) "사고 인지함. 분석 시작함..." (스트리밍 시작)
    
    loop 에이전트 루프 (서버사이드에서 무한 반복)
        Agent->>Agent: 생각: "에러 로그부터 봐야겠다."
        Agent->>Env: 도구 호출: `kubectl logs -n prod payment-svc`
        Env->>Infra: 실제 명령 실행 (격리된 공간에서)
        Infra-->>Env: 로그 텍스트 반환
        Env-->>Agent: 도구 결과 전달
        Agent->>Agent: 생각: "DB 커넥션 풀 고갈이네. 재시작 필요."
        Agent->>Env: 도구 호출: `kubectl rollout restart deployment/payment-svc`
        Env->>Infra: 재시작 명령 실행
        Infra-->>Env: 완료 응답
        Env-->>Agent: 결과 전달
        Agent->>Session: 최종 보고: "원인 파악 및 조치 완료. 모니터링 중."
    end
    
    Session->>User: (아침에 눈 떴을 때) "다 고쳤어요. 상세 리포트 여기 있어요." 😴➡️😊
```

### 이 흐름에서 빛나는 3대 리소스의 역할

| 리소스 | 역할 | 만약 이게 없다면? |
| :--- | :--- | :--- |
| **Agent (두뇌)** | **'무슨 생각을 할까?'** 정의. SRE 페르소나, 사용할 모델, `kubectl` 스킬, 런북 MCP 서버 연결 정보 보유. | "누가 나 대신 생각함?" → **내가 직접 생각해야 함 (새벽 3시 기상)** |
| **Environment (손)** | **'어디서 어떻게 실행할까?'** 제공. 실제 `kubectl` 바이너리, 클러스터 접근용 `kubeconfig`(권한 최소화), 임시 파일 저장소. 내 로컬 PC와 완전 격리. | "내 로컬에서 돌리면?" → **내 PC 켜놔야 함, 내 크리덴셜 노출 위험, 네트워크 끊기면 끝** |
| **Session (연결고리)** | **'누가 시키고, 누가 보고, 끝까지 책임질까?'** 관리. 알람 → 세션 자동 생성 → 스트리밍 리포트 → 내 랩탑 꺼져도 서버에서 지속 실행 → 내구성 보장. | "스크립트 하나 돌리면?" → **중간에 네트워크 끊기면 프로세스 죽음, 로그 유실, 재실행 수동, 히스토리 관리 안 됨** |

## 🛠️ 실습 전 체크포인트: `agent.py`에서 뭘 볼 것인가?

강사님께서 `agent.py` (미완성)와 `agent_complete.py` (완성본)를 나란히 띄워놓고, **한 조각씩 복사해 붙여넣으며 완성**해 나갈 거라고 하셨죠? 그때 여러분 눈여겨볼 **포인트 3가지**는 바로 이겁니다.

1.  **`Agent(...)` 생성 코드 찾을 때:**  
    `model=`, `system_prompt=`, `skills=[...]`, `mcp_servers=[...]` 이 네 가지가 채워지는지 보세요. **"아, 여기 셰프 이력서 쓰는 구나"** 생각하시면 됩니다.
2.  **`Environment(...)` 또는 환경 설정 코드 찾을 때:**  
    `docker_image=`, `resources=`, `env_vars=`, `tools=` 등이 보이면 **"아, 여기 주방 스펙(칼 몇 개, 가스불 세기, 냉장고 권한) 정하는 구나"** 하세요. 특히 `env_vars`에 **내 AWS 키 넣지 마세요!** 그건 주방 냉장고에 넣는 게 아니라, 금고(시크릿 매니저)나 MCP 서버 쪽으로 빼는 게 정석입니다.
3.  **`Session.create(...)` 또는 세션 시작 코드 찾을 때:**  
    `agent=my_agent, environment=my_env` 이렇게 둘을 **인자로 넘겨서 묶는 순간**이 세션 탄생입니다. 그리고 `session.stream_events()` 같은 걸로 이벤트 받아오는 코드가 있으면 **"아, 여기 인터콤 켜는 구나"** 하시면 돼요.

## 📝 마무리하며: 여러분의 '주방'은 이제 클라우드에 있습니다

오늘 배운 **에이전트(두뇌), 환경(손), 세션(매니저/인터콤)** 이 세 가지는 클로드 매니지드 에이전트의 **'생산성 3종 세트'**입니다.

*   과거: **"내 로컬에서 파이썬 스크립트 돌려서 서버 고치기"** → 내 랩탑 켜둬야 함, 내 키 노출, 네트워크 불안정, 로그 관리 직접 함.
*   현재 (Claude Managed Agents): **"클라우드에 셰프 두고, 별채 주방 빌려주고, 주문표(세션)만 던져두기"** → 내 랩탑 덮고 자도 됨, 키 안전함, 서버사이드라 안 죽음, 로그/히스토리 자동 저장.

다음 실습 시간에는 실제로 `streamlit run app.py`를 돌려서, **사고 난 서버를 고치는 이 흐름**을 직접 눈 앞에서 보게 될 겁니다. 강사님 말씀대로 **"마법 같은 순간"**을 함께 맞이해 봅시다. 준비되셨나요? 그럼 다음 섹션에서 코드 속으로 뛰어들어요! 🚀
