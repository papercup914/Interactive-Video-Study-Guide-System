# 챕터 3. 견고한 라이터 구성(Robust Blog Writer): 라이터와 체커의 루프 에이전트 래핑 (최대 3회 재시도)

자, 이제 설계도(계획)가 완성되었으니, 실제로 글을 쓰는 **'라이터(Writer)'**를 만들어 볼 차례입니다. 앞서 플래너(Planner)를 만들 때와 아주 비슷한 원리지만, 이번에는 **'글쓰기'**라는 구체적인 작업에 초점을 맞춥니다. 혹시라도 글이 엉성하게 나오면 자동으로 고쳐 쓰는 **'자동 퇴고 시스템'**을 장착하는 과정이라고 보시면 됩니다.

---

## 1. 라이터(Writer) 에이전트: "셰프에게 레시피와 재료를 주다"

먼저 **`blog_post_writer`**라는 에이전트를 만듭니다. 이 친구의 역할은 **"계획(아웃라인)을 보고, 실제 블로그 글을 써서 `blog_post`라는 저장소에 넣어두는 것"**입니다.

> **💡 개념 돋보기: 에이전트에게 '지시서(Instruction)' 주기**
> 에이전트를 만들 때 가장 중요한 건 **`instruction`(지시사항)**입니다. 이건 마치 식당 주방장에게 주는 **'메뉴얼'**이나 **'레시피 카드'**와 같습니다. "너는 이러이러한 사람이야, 이렇게 행동해"라고 정의를 내려주는 거죠.
>
> 이번 라이터의 지시서에는 이런 내용이 담겼습니다:
> *   **대상 독자:** 소프트웨어 엔지니어 (기초 설명 생략, 실전 인사이트 위주)
> *   **작성 스타일:** 어떻게(How) 하는지, 왜(Why) 하는지 둘 다 설명. 필요한 곳에 짧은 코드 조각 포함.
> *   **구조:** 앞서 만든 아웃라인의 목차 구조(헤딩 등)를 그대로 따를 것.
> *   **결과물 저장:** 완성된 초안을 공유 상태(`shared state`)의 `blog_post`라는 공간에 저장할 것.

**일상 비유로 이해하기:**
> **`shared state`(공유 상태)는 식당의 '주문서 보드'나 '공용 냉장고' 같은 곳입니다.** 플래너가 "이렇게 요리해!"라고 적은 주문서(아웃라인)를 보드에 붙여두면, 라이터 셰프가 그걸 보고 요리(글쓰기)를 해서 완성된 접시(블로그 초안)를 다시 보드의 `blog_post` 칸에 올려두는 것입니다.

---

## 2. 블로그 포스트 검증 체커(Validation Checker): "까다로운 미식가(품질 검사관) 등장"

글을 다 썼다고 바로 내보내면 안 되겠죠? **`blog_post_validation_checker`**라는 **체커(Checker) 에이전트**를 하나 더 만듭니다. 이 친구는 라이터가 쓴 글을 읽어보고 **"합격(Okay)"**이냐 **"재시도(Retry)"**냐를 판단하는 **품질 검사관** 역할을 합니다.

이 검사관이 보는 **체크리스트(검증 기준)**는 다음과 같습니다.

1.  **도입부(Introduction)가 있는가?** - 글을 여는 문단이 제대로 있는가?
2.  **목차와 섹션이 일치하는가?** - 아웃라인에 있던 소제목들이 본문에 다 있는가? 빠진 건 없는가?
3.  **결론(Conclusion)이 있는가?** - 글을 마무리하는 문단이 있는가?
4.  **설명이 명확한가?** - 그냥 코드만 던져놓은 게 아니라, 왜 이렇게 했는지 설명이 잘 되어 있는가?

> **💡 개념 돋보기: 체커의 판단 결과 - "Okay" vs "Retry + 수정 사항"**
> 이 체커는 단순한 합격/불합격만 알려주는 게 아닙니다.
> *   **통과 시:** `"okay"` 라는 한마디만 보냅니다. ( "잘했어, 그만해도 돼" )
> *   **실패 시:** `"retry"`라고 외치면서, **구체적으로 뭐가 잘못되었는지, 어떻게 고치면 되는지 '수정 사항 리스트'를 같이 알려줍니다.** ( "도입부가 없네? 첫 문단에 독자의 흥미를 끄는 훅(Hook)을 넣어. 그리고 3장 설명이 너무 어려우니 비유를 추가해." )

**일상 비유로 이해하기:**
> 이건 **'미슐랭 가이드 심사위원'**이나 **'편집장'** 같습니다. 셰프(라이터)가 요리를 내놓으면, 심사위원이 한 입 먹고 "이건 소금이 부족해", "플레이팅이 목차랑 안 맞네"라고 **구체적인 피드백을 적어서 돌려주는 것**입니다. 그냥 "맛없어" 하고 끝나는 게 아니라, **레시피 수정 가이드**를 준다는 점이 핵심입니다.

## 3. 루프 에이전트(Loop Agent)로 감싸기: "자동 퇴고 루프 만들기"

자, 이제 **라이터(글 쓰는 셰프)**와 **체커(검사하는 편집장)**가 준비되었습니다. 이 둘을 따로 놀게 하지 않고, **`robust_blog_writer`**라는 **하나의 '루프 에이전트(Loop Agent)'**로 묶어버립니다.

> **💡 개념 돋보기: 루프 에이전트(Loop Agent)란?**
> **"특정 조건이 만족될 때까지, 안의 작업을 무한 반복(또는 정해진 횟수만큼 반복)하라"**는 명령어를 가진 컨테이너(상자) 같은 에이전트입니다.
> *   안에는 **라이터 -> 체커** 순서로 들어갑니다.
> *   체커가 `"okay"`라고 하면 **루프 종료(탈출)**.
> *   체커가 `"retry"`라고 하면 **다시 처음으로 돌아가 라이터 실행(반복)**.

**작동 시나리오 (최대 3회 재시도):**

1.  **1차 시도:** 라이터가 글을 씀 -> 체커가 검사 -> **"Retry! (수정 사항: 도입부 약함, 2절 누락)"** -> 루프 계속.
2.  **2차 시도:** 라이터가 피드백 보며 고쳐 씀 -> 체커가 검사 -> **"Retry! (수정 사항: 코드 설명 부족)"** -> 루프 계속.
3.  **3차 시도:** 라이터가 다시 고쳐 씀 -> 체커가 검사 -> **"Okay!"** -> **루프 탈출! 성공!**
4.  *(만약 3번 다 실패하면?)*: 시스템 설정에 따라 에러를 내거나, 그때까지의 최고 결과물을 내보냅니다. (여기선 "최대 3회"로 안전장치를 뒀습니다.)

**일상 비유로 이해하기 - "자동 퇴고 머신":**
> 작가(라이터)가 초고를 쓰면, 편집자(체커)가 빨간 펜으로 수정 사항을 적어 돌려줍니다. 작가는 그걸 보고 고쳐서 다시 내고, 편집자는 다시 검사합니다. 이 **'쓰기 -> 검사 -> 고치기' 사이클**을 **사람이 개입하지 않고 기계가 알아서 3번까지 돌려주는 기계**를 만든 거라고 보시면 됩니다.
>
> *   **장점:** 사람이 밤새며 "이거 고쳐, 저거 고쳐" 할 필요 없습니다. 자고 일어나면 검증된 글이 완성되어 있습니다.
> *   **안전장치(최대 3회):** 무한 루프에 빠져 서버 비용만 날리는 걸 방지합니다. "3번 했는데도 안 되면 사람이 개입하자"는 뜻이죠.

## 4. 도구(Tool)로 포장하기: "루트 에이전트가 쓰는 만능 리모컨"

이제 **견고한 플래너(`robust_blog_planner`)**와 **견고한 라이터(`robust_blog_writer`)**라는 두 개의 강력한 **루프 에이전트**가 완성되었습니다. 하지만 이걸 최상위 보스인 **'루트 에이전트(Root Agent)'**가 쓰기 쉽게 만들어줘야 합니다.

그래서 이 두 루프 에이전트를 각각 **`Tool`(도구/기능)**로 **랩핑(Wrapping, 포장)**합니다.

> **💡 개념 돋보기: 에이전트를 도구(Tool)로 변환하기 (Agent as a Tool)**
> 복잡한 내부 로직(루프 돌고, 체크하고, 재시도하고...)을 **단순한 함수 하나**로 만들어 버리는 기술입니다.
> *   **이전:** 루트 에이전트가 "플래너 좀 돌려줘" -> 내부에서 루프 어떻게 돌지 직접 관리해야 함 (복잡함).
> *   **이후:** `robust_blog_planner`라는 **도구(함수)**가 생김. 루트 에이전트는 그냥 `run_robust_planner()`라고 **호출만 하면 됨**.
> *   **결과값:** 도구가 알아서 내부에서 루프 다 돌고, 검증 다 끝내고, 최종 완성된 **'계획'** 또는 **'블로그 글'**만 툭 뱉어줌.

**일상 비유로 이해하기 - "자판기 버튼" 또는 "만능 리모컨":**
> *   **루프 에이전트(내부):** 자판기 안의 복잡한 기계 장치(컵 꺼내기, 얼음 넣기, 커피 추출하기, 뚜껑 닫기, 꺼내주기). 고장 나면 다시 하고, 컵 없으면 채우고... 복잡한 과정이 숨어 있습니다.
> *   **도구(Tool)로 랩핑:** 바깥에 붙은 **'아메리카노' 버튼 하나**.
> *   **루트 에이전트(사용자):** 커피 마시고 싶으면 내부 기계가 어떻게 도는지 몰라도 **버튼만 누르면(도구 호출하면) 완성된 커피(결과물)가 나옵니다.**

이제 루트 에이전트는 **"블로그 글 써줘"**라는 명령 하나로, 계획 세우기(플래너 도구 호출) -> 글 쓰기(라이터 도구 호출)라는 복잡한 파이프라인을 **내부 사정 전혀 모른 채, 그냥 도구 두 번 호출로 끝낼 수 있게 된 것**입니다. 이게 바로 **모듈화(Modularization)**와 **추상화(Abstraction)**의 힘입니다.

## 5. 전체 흐름 정리: "자동화 공장 라인의 완성"

지금까지 만든 구조를 한눈에 보시죠.

```text
[사용자 요청]
      |
      v
[루트 에이전트 (오케스트레이터)]
      |---> 도구 1: robust_blog_planner (루프 에이전트)
      |        |---> Planner Agent (계획 작성)
      |        |---> Checker Agent (계획 검증: ok/retry)
      |        |---> (최대 3회 반복) -> 최종 계획(Outline) 확정 -> shared_state['outline'] 저장
      |
      |---> 도구 2: robust_blog_writer (루프 에이전트)
               |---> Writer Agent (글 작성: outline 보고 blog_post 초안 작성)
               |---> Checker Agent (글 검증: 구조, 도입, 결론, 설명 체크 -> ok/retry)
               |---> (최대 3회 반복) -> 최종 블로그 글 확정 -> shared_state['blog_post'] 저장
      |
      v
[최종 결과물 출력]
```

### 핵심 포인트 복습

1.  **분업과 협업:** 글 쓰는 애(Writer)와 검사하는 애(Checker)를 철저히 분리했습니다. **'쓰기'와 '평가'는 다른 뇌(에이전트)가 해야 잘 됩니다.** (사람도 글 쓸 땐 창의적으로, 퇴고할 땐 비판적으로 뇌를 다르게 쓰죠?)
2.  **루프(Loop)로 자동화:** "검사 -> 피드백 -> 수정" 사이클을 **코드로 고정(Loop Agent)**시켜 버렸습니다. 사람이 일일이 "다시 써" 할 필요 없습니다.
3.  **안전장치(Max Retries):** 무한 루프 방지를 위해 **최대 3회**로 제한했습니다. 3번 만에 안 되면 사람 손 타야 합니다.
4.  **도구화(Tooling)로 캡슐화:** 복잡한 루프 덩어리들을 **'버튼(Tool)'**로 만들었습니다. 덕분에 루트 에이전트는 "계획 세워" -> "글 써" 두 마디만 하면 됩니다.

## 마무리하며: 왜 이렇게 복잡하게 만드나요?

"그냥 LLM 한 번 호출해서 '블로그 글 써줘' 하면 안 되나?"라고 물으실 수 있습니다.

*   **단일 호출(One-shot):** 운이 좋아서 잘 나올 수도 있지만, **복잡한 기술 블로그처럼 구조와 깊이가 필요한 글은 십중팔구 엉성합니다.** (목차 누락, 설명 부족, 코드만 나열 등)
*   **이 구조(Multi-agent Loop):** **'품질 보증(QA) 프로세스'를 코드에 심어놓은 것**입니다. 셰프가 요리하고, 검식관이 검사하고, 불합격하면 다시 요리하게 만드는 **'자동화된 품질 관리 시스템'**을 만든 겁니다.

이제 루트 에이전트는 이 든든한 **두 개의 만능 도구(견고한 플래너, 견고한 라이터)**를 손에 쥐고, 사용자의 요청을 받아 **완성도 높은 기술 블로그 포스트를 자동으로 생산해내는 공장장**이 되었습니다. 다음 단계에서는 이 도구들을 루트 에이전트가 어떻게 호출하여 전체 오케스트레이션을 수행하는지 살펴보겠습니다. 수고하셨습니다!
