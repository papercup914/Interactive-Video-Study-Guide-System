# 챕터 7: 동일한 "okay"/"retry" 규칙 적용 및 구체적 수정 사항 피드백 – 글쓰기 자동화에도 '품질 검수 루프'를 달아주자

자, 지난 시간에는 **'계획 수립 에이전트(Planner)'**와 **'계획 검수 에이전트(Planning Checker)'**가 짝을 이루어, **"오케이(Okay)"**가 나올 때까지 **"다시 해(Retry)"**를 외치며 계획을 다듬는 **'강건한 플래너(Robust Planner)'** 루프를 만드는 법을 배웠습니다. 

이번 시간에는 바로 그 **성공적인 검증 루프 패턴을 '블로그 글쓰기' 단계에도 그대로 이식**하는 과정을 살펴보겠습니다. **"검증된 좋은 패턴은 재사용하라"**는 소프트웨어 공학의 대원칙을 실천하는 현장이죠. 더불어, 단순히 "통과/실패"만 알려주는 게 아니라 **"구체적으로 어디를 어떻게 고쳐라"**라고 **상세한 수정 피드백**을 주는 검수 에이전트의 위력도 함께 확인해 보겠습니다.

---

## 1. 새로운 주연 배우 등장: '블로그 작가(Blog Writer)' 에이전트

계획(Outline)이 완벽하게 검증되어 `blog_outline`이라는 창고에 잘 저장되었습니다. 이제 이 설계도를 바탕으로 **실제 블로그 글 초안**을 써줄 작가가 필요하겠죠? 여기서 **`Blog Writer`(블로그 작가) 에이전트**가 등장합니다.

> **💡 개념 돋보기: Blog Writer (블로그 작가 에이전트)**
> > **일상 비유: "미슐랭 셰프에게 주문서를 넘기는 주방장"**
> > 
> > 앞서 `Planner`가 **"손님 취향 분석 -> 메뉴 기획 -> 레시피(Outline) 작성"**까지 마쳤다면, `Blog Writer`는 그 **레시피(Outline)를 보고 실제로 요리(본문 작성)하는 셰프**입니다.
> > 
> > 이 셰프에게 주문서(Instruction)에는 이런 내용이 적혀 있습니다:
> > - **대상 손님:** "소프트웨어 엔지니어들임. 기초 설명(소금이 뭐냐, 프라이팬이 뭐냐) 생략하고, 실전 팁과 깊은 인사이트만 줘."
> > - **요리 스타일:** **"어떻게(How) 하는지만 쓰지 말고, 왜(Why) 이렇게 하는지 이유도 설명해줘."**
> > - **플레이팅(형식):** "짧은 코드 조각(Code Snippet)도 적절히 곁들여서, 설계도(Outline)의 목차 구조(Heading) 그대로 맞춰서 써줘."
> > - **결과물 보관:** "다 쓴 초안은 `blog_post`라는 창고에 넣어둬. 다음 공정(검수)이 가져갈 거야."

이 에이전트는 **공유 상태(Shared State)의 `blog_outline`을 읽어서**, 지시사항(Instruction)에 따라 **완성된 마크다운(Markdown) 블로그 포스트 초안**을 생성한 뒤, 다시 공유 상태의 **`blog_post`**에 저장하는 역할을 합니다.

## 2. 글쓰기에도 '품질 관리 팀' 배치: '블로그 포스트 검수기(Blog Post Validation Checker)'

자, 셰프가 요리를 내놨습니다. 근데 이 요리가 손님상에 나가도 될까요? **주방장(시스템)이 직접 맛보기엔 바쁘고, 객관적이지 못합니다.** 그래서 **전담 검수원(QA)**을 둡니다. 바로 **`Blog Post Validation Checker`(블로그 포스트 검증 검수기)** 에이전트입니다.

> **💡 개념 돋보기: Blog Post Validation Checker (블로그 포스트 검증 검수기)**
> > **일상 비유: "까다로운 미식가 비평가 / 식품 위생 검사관"**
> > 
> > 이 검수원은 `blog_post` 창고에 있는 초안을 꺼내 들고, **체크리스트**를 들고 하나하나 따져봅니다.
> > 
> > **📋 검수 체크리스트 (검수원의 머릿속 기준표)**
> > 1.  **도입부(Introduction)가 있는가?** (손님을 맞이하는 인사말, 글의 목적 설명)
> > 2.  **구성(Sections)이 설계도(Outline) 목차와 일치하는가?** (빠진 챕터는 없는가? 순서가 뒤바뀌진 않았는가?)
> > 3.  **결론(Conclusion)이 있는가?** (마무리 정리, 다음 액션 유도 등)
> > 4.  **설명이 명확한가?** (엔지니어 대상인데 너무 추상적이진 않은가? 코드 조각은 적절한가? Why가 빠져있진 않은가?)
> > 
> > **판정 결과는 단 두 가지!**
> > - ✅ **"Okay" (합격):** 모든 기준 통과. 다음 단계로 넘어가도 좋음.
> > - ❌ **"Retry" (불합격/수정 필요):** 기준 미달. **단순히 "다시 해"가 아니라, "구체적으로 무엇을 고쳐야 하는지(Fixes needed)" 리스트를 적어서 작가에게 돌려줌.**

이게 바로 지난 챕터에서 배운 **Planning Checker**와 **완전히 동일한 인터페이스(규칙)**입니다. "Okay"면 통과, "Retry"면 수정 사항 피드백. 이 **일관된 프로토콜** 덕분에 우리는 플래너 때 쓰던 **'루프 에이전트' 로직을 코드 한 줄 거의 안 고치고 그대로 재사용**할 수 있습니다.

## 3. 작가와 검수원을 '무한 루프(최대 3회)'로 묶기: '강건한 블로그 작가(Robust Blog Writer)'

이제 익숙한 그림이 그려집니다. **작가(Writer)** 와 **검수기(Checker)** 를 한 쌍으로 묶고, **"검수기가 Okay 할 때까지(최대 3번까지) 작가에게 다시 쓰게 시키는 루프"**를 만듭니다. 이것이 바로 **`Robust Blog Writer`(강건한 블로그 작가) 루프 에이전트**입니다.

> **💡 개념 돋보기: Robust Blog Writer (강건한 블로그 작가 루프)**
> > **일상 비유: "완벽주의 편집장과 집필 작가의 '핑퐁 게임' (최대 3세트)"**
> > 
> > 1.  **1세트:** 작가 초안 작성 -> 검수원 검토 -> **"Retry: 도입부가 약함, 3장 코드 예제 부족, 결론 없음"** -> 작가 수정
> > 2.  **2세트:** 작가 수정본 제출 -> 검수원 검토 -> **"Retry: 2장 설명이 여전히 추상적임, Why 설명 보충 필요"** -> 작가 재수정
> > 3.  **3세트:** 작가 최종본 제출 -> 검수원 검토 -> **"Okay! 합격!"** -> 루프 종료, 최종본 `blog_post` 확정
> > 
> > **핵심 포인트:** 검수원이 **"Retry"**를 외칠 때, **"어디가 틀렸는지(Fixes needed)"를 구체적으로 적어줍니다.** 작가는 이 '수정 지시서'를 보고 **"아, 2장에 Why 설명이 빠졌구나. 3장에 코드 스니펫 넣으랬지."** 하며 **정확하게 그 부분만 고쳐서** 다시 냅니다. 이게 그냥 "다시 해봐"랑은 차원이 다른 **'지시된 재시도(Guided Retry)'**입니다.

이 루프 에이전트 내부에서는 대략 이런 흐름이 코드로 돌고 있습니다 (의사코드 느낌):

```python
# Robust Blog Writer 내부 로직 (개념도)
max_attempts = 3
current_attempt = 0

while current_attempt < max_attempts:
    # 1. 작가 호출 (이전 피드백이 있으면 함께 전달)
    draft = blog_writer_agent.run(input_data={
        "outline": shared_state["blog_outline"],
        "previous_feedback": shared_state.get("last_checker_feedback") # 핵심! 이전 피드백 전달
    })
    shared_state["blog_post"] = draft # 초안 저장

    # 2. 검수원 호출
    validation_result = blog_post_checker_agent.run(input_data={
        "draft": shared_state["blog_post"]
    })

    # 3. 판정
    if validation_result.status == "okay":
        print("✅ 블로그 포스트 검수 통과! 최종본 확정.")
        break # 루프 탈출
    else: # "retry"
        current_attempt += 1
        print(f"❌ 검수 실패 ({current_attempt}/{max_attempts}회). 수정 사항: {validation_result.fixes_needed}")
        # 다음 시도를 위해 피드백 저장
        shared_state["last_checker_feedback"] = validation_result.fixes_needed
        
        if current_attempt >= max_attempts:
            print("🚨 최대 재시도 횟수 초과. 강제 종료하거나 사람 개입 필요.")
            break
```

## 4. '구체적 수정 사항 피드백(Fixes Needed)'의 마법 – 왜 이게 중요한가?

이번 챕터 제목의 후반부 **'구체적 수정 사항 피드백'**이 바로 이 시스템의 **'지능'**을 결정하는 핵심입니다. Planning Checker 때도 그랬지만, 여기서 다시 한번 그 위력을 짚고 넘어가야 합니다.

### 시나리오 A: 피드백이 없는 "그냥 Retry" (나쁜 예)
> **검수원:** "Retry. 글 별로야."
> **작가:** (당황) "어... 그럼 뭘 고치지? 도입부? 코드? 문체? 그냥 전체를 다시 쓸게요." -> **낭비, 방향성 상실, 무한 루프 위험**

### 시나리오 B: 구체적 피드백이 있는 "Retry + Fixes Needed" (좋은 예 - 우리 시스템)
> **검수원:** "Retry. 수정 사항:
> 1. **도입부:** 대상 독자(소프트웨어 엔지니어)에게 왜 이 글이 중요한지 'Hook'이 부족함. 첫 문단에 '이 기술이 배포 시간을 50% 단축시켰다'는 식의 임팩트 있는 문장 추가 바람.
> 2. **3번째 섹션(구현체):** Outline에 '비교 코드 포함'이라 되어 있는데 실제 코드 스니펫이 없음. `before/after` 비교 코드 블록 2개 삽입 필수.
> 3. **결론:** 마무리 문단 없음. '요약 및 다음 단계 예고' 섹션 추가 필요."
> 
> **작가:** (피드백 읽고) "아, 1번은 첫 문단 고치면 되고, 2번은 코드만 껴넣으면 되고, 3번은 결론만 쓰면 되네? **나머지 멀쩡한 2, 4, 5장 건드릴 필요 없구나!**" -> **정확한 수술, 토큰/시간 절약, 품질 수렴 속도 향상**

> **💡 개념 돋보기: 구조화된 피드백(Structured Feedback)의 힘**
> > **일상 비유: "수학 시험 채점 결과표" vs "빨간 펜으로 '틀렸음'만 적힌 시험지"**
> > 
> > - **단순 Retry:** 채점관이 **"틀렸음(F)"** 도장만 찍어줌. 학생은 어디서 틀렸는지 몰라 전 범위 다시 공부해야 함.
> > - **구체적 Fixes Needed:** 채점관이 **"3번 문제는 공식 오적용, 5번은 단위 미표기, 7번은 계산 실수"**라고 항목별로 적어줌. 학생은 **틀린 것만 골라서 고치면 됨.**
> > 
> > LLM 에이전트도 똑같습니다. **Context Window(기억 용량)**가 한정되어 있고, **생성 비용(토큰/돈/시간)**이 듭니다. **"전체 다시 써"** 하면 이전 잘 쓴 부분까지 망가뜨리며 새로 씁니다(일관성 깨짐 위험). **"3번 섹션 코드만 추가해"** 하면 **나머지 문맥 유지한 채 최소 수정**으로 고품질 결과물에 빠르게 수렴합니다.

## 5. 전체 파이프라인에서 이 단계가 갖는 의미: '계획-실행-검증'의 프랙탈 구조

자, 이제 우리 파이프라인의 모양이 갖춰지고 있습니다. **프랙탈(Fractal, 자기 유사성)** 구조라고 보시면 됩니다.

1.  **거대 루프 (전체 파이프라인):** `Planner Loop` -> `Writer Loop` -> `Reviewer Loop` (나중에 나옴) ...
2.  **중간 루프 (각 단계별):** `Robust Planner` (계획+검수 루프), **`Robust Blog Writer` (작성+검수 루프)**, `Robust Reviewer` (리뷰+검수 루프)...
3.  **미시 루프 (단일 에이전트 내부):** LLM이 토큰 하나 생성할 때마다 확률 분포에서 샘플링하는 과정...

**각 단계마다 "생성자(Generator) + 검증자(Validator) + 루프(Loop)"** 패턴이 **동일한 "Okay/Retry + 구체적 피드백" 프로토콜로 반복**됩니다.

*   **Plan 단계:** Planner(생성) + Planning Checker(검증) = **Robust Planner** ✅ (지난 챕터 완료)
*   **Write 단계:** Blog Writer(생성) + Blog Post Checker(검증) = **Robust Blog Writer** ✅ (이번 챕터 완료)
*   **Review 단계:** (다음 챕터 예고) Blog Reviewer(생성) + Review Checker(검증) = **Robust Reviewer** ⏳

이렇게 **모듈화되고 표준화된 '강건한 단위(Robust Unit)'들을 레고 블록처럼 쌓아 올려** 거대한 자율 에이전트 시스템을 만드는 것, 이것이 **마이크로서비스 아키텍처를 에이전트 세계에 가져온 '에이전트 오케스트레이션'의 정수**입니다.

## 6. 마무리하며: "신뢰하지만, 검증하고, 피드백하며, 반복하라"

이번 챕터에서 우리가 확인한 것은 크게 세 가지입니다.

1.  **패턴 재사용 (DRY - Don't Repeat Yourself):** 플래너 단계에서 검증된 **'생성-검수 루프' 패턴을 글쓰기 단계에 그대로 적용**했습니다. 코드 중복 없이, `Loop Agent`라는 추상화 레이어 덕분에 설정만 바꿔 끼우면 끝납니다.
2.  **인터페이스 표준화:** **`Checker` 에이전트의 출력을 `{"status": "okay/retry", "fixes": [...]}`** 형태로 통일했기에, **어떤 Checker든 Loop Agent가 알서 돌릴 수 있습니다.** 이게 '조립식 시스템'의 핵심입니다.
3.  **고품질 피드백의 경제성:** **"Retry"에 담긴 "Fixes Needed(수정 사항 리스트)"**가 **에이전트의 시행착오 비용을 획기적으로 줄여줍니다.** 이건 LLM 에이전트 공학에서 **가장 중요한 '프롬프트 엔지니어링 포인트'** 중 하나입니다. **"검수 프롬프트에 '구체적인 수정 사항 리스트를 JSON 배열로 출력하라'는 지시 한 줄 넣는 것"**이 시스템 전체의 성능을 결정합니다.

이제 **`blog_post` 창고에는 "검수관 도장(Okay) 찍힌, 품질 보증된 블로그 초안"**이 들어있습니다. 하지만 아직 끝난 게 아닙니다. 이 글을 **한 번 더 다듬고, 스타일 교정하고, 사람 눈높이로 최종 승인 받는 '리뷰 단계(Robust Reviewer)'**가 남아있습니다.

다음 챕터에서는 이 **최종 마무리 단계인 '강건한 리뷰어(Robust Reviewer)'**를 만들어, **"기계가 쓴 글 같지 않게, 사람이 쓴 듯 자연스럽고 완성도 높게"** 다듬는 과정을 배워보겠습니다. 지금까지 배운 루프 패턴의 **화룡점정(畵龍點睛)**이 될 것입니다. 기대하셔도 좋습니다!
