# 도구 접근 권한 제어: 플래너 도구, 라이터 도구만 노출하여 워크플로우 명확화

자, 이제 우리가 만든 정교한 부품들을 하나의 완성된 '시스템'으로 조립하는 마지막 단계에 왔습니다. 앞서 우리는 **'계획을 세우는 플래너(Planner)'**와 **'글을 쓰고 검수하는 라이터(Writer)'**를 각각 **'루프 에이전트(Loop Agent)'**로 감싸서, **자동으로 재시도하며 품질을 보장하는 튼튼한 모듈(Robust Planner, Robust Writer)**로 만들었습니다. 

이제 이 튼튼한 모듈들을 **'도구(Tool)'**라는 포장지에 싸서, 최종 보스인 **'루트 에이전트(Root Agent, 여기서는 Blogger)'**에게 건네주는 과정을 배워볼 차례입니다. 이 과정이 바로 **'도구 접근 권한 제어'**의 핵심이며, 복잡한 AI 시스템을 질서 있게 운영하는 비결입니다.

---

## 1. 복잡한 기계를 '자판기 버튼'으로 만들기: 도구(Tool) 래핑(Wrapping)

우리가 만든 `Robust Blog Planner`(강력한 플래너)와 `Robust Blog Writer`(강력한 라이터) 안을 들여다보면 엄청나게 복잡합니다. 플래너 안에는 "계획 짜기 -> 검사하기 -> 통과 못 하면 다시 짜기"라는 루프가 돌고 있고, 라이터 안에는 "글 쓰기 -> 검수하기 -> 통과 못 하면 다시 쓰기(최대 3회)"라는 또 다른 루프가 돕니다.

만약 최종 보스인 `Blogger` 에이전트가 이 내부 사정을 다 알아야 한다면 어떨까요? "아, 지금 플래너가 2번째 재시도 중이네? 그럼 내가 좀 기다렸다가...", "라이터가 지금 3번째 글 쓰는 중인데 검수 기준이 뭐지?" 라며 `Blogger`가 세세하게 간섭해야 한다면, `Blogger`는 본업(사용자 주제 받고 최종 결과물 주기)을 못 하고 관리자 노릇만 하게 됩니다.

> **💡 개념 돋보기: 캡슐화(Encapsulation)와 도구(Tool)화**
> 
> **비유: 고급 레스토랑의 '주문 벨'과 '주방'**
> 
> 손님(사용자)이 홀 매니저(`Blogger` - 루트 에이전트)에게 "스테이크 하나 주세요"라고 주문합니다. 홀 매니저는 주방으로 달려가서 "셰프님, 고기 굽기 시작하셨어요? 온도는요? 뒤집을 타이밍은요?"라고 간섭하지 않습니다. 대신 매니저는 **주방 호출 벨(도구, Tool)**만 누릅니다.
> 
> *   **플래너 도구(Planner Tool):** "메뉴 기획서 만들어 와" 버튼
> *   **라이터 도구(Writer Tool):** "요리 완성해 와" 버튼
> 
> 주방 안(내부 루프 에이전트)에서는 셰프(Planner/Writer)가 "고기가 질기네? 다시 구워", "간이 안 맞네? 다시 해" 하며 최대 3번까지 재시도(Loop)할 수 있습니다. 하지만 홀 매니저(`Blogger`)는 **오로지 "완성된 접시(결과물)"만 받으면 됩니다.** 이게 바로 **'도구로 감싸기(Wrapping as Tool)'**의 마법입니다. 복잡한 내부 로직(루프, 재시도, 검수)을 **'입력 -> 도구 호출 -> 출력'**이라는 **단순한 인터페이스**로 숨겨버리는 것이죠.

스크립트에서는 이렇게 말합니다.  
> *"Now we've wrapped each loop, the robust blog planner and the robust blog writer, as tools. This is what lets the root agent call them directly without worrying about what's happening inside."*  
> (이제 우리는 각 루프, 즉 강력한 플래너와 강력한 라이터를 도구로 감쌌습니다. 덕분에 루트 에이전트는 내부에서 무슨 일이 일어나는지 걱정하지 않고 직접 이 도구들을 호출할 수 있게 되었습니다.)

**이게 왜 중요할까요?**  
비전공자 입장에서 가장 큰 착각 중 하나가 **"AI 에이전트끼리 서로 다 알 수 있게 다 연결해줘야 하지 않나?"**라는 생각입니다. **절대 그렇지 않습니다.** 좋은 아키텍처는 **'모르는 게 약'**입니다. `Blogger`는 `Planner`가 내부적으로 LLM을 3번 호출하든, 5번 호출하든, 규칙 기반 검수를 하든 **전혀 알 필요가 없습니다.** 그냥 `planner_tool(topic)`이라고 호출하면 `outline`이 뚝 떨어지는 **블랙박스**여야 합니다. 그래야 `Planner` 내부를 나중에 고쳐도 `Blogger` 코드는 한 줄도 안 고쳐도 됩니다. 이것이 **'결합도(Coupling)를 낮추고 응집도(Cohesion)를 높이는'** 소프트웨어 공학의 정석이자, 멀티 에이전트 시스템 설계의 핵심입니다.

## 2. 심플한 레시피: 루트 에이전트(Blogger)의 지시사항 (Instructions)

도구라는 훌륭한 '주방 기구' 두 개(플래너 도구, 라이터 도구)를 장착한 `Blogger` 에이전트에게 우리는 이제 **'일하는 순서(Workflow)'**를 알려줘야 합니다. 스크립트에서 말하는 `instructions`(지시사항/시스템 프롬프트) 부분입니다.

> *"The instructions for Blogger are simple. When a user gives it a topic, first it calls the planner tool to make an outline, then it calls the writer tool to draft the full post, and finally it adds three alternative titles and two tweet-length hooks."*

**번역하며 뜯어보기:**
> "Blogger의 지시사항은 심플합니다. 사용자가 주제를 주면, **첫째**, 플래너 도구를 호출해 개요(outline)를 만듭니다. **둘째**, 라이터 도구를 호출해 본문 초안(full draft)을 씁니다. **셋째**, 대체 제목 3개와 트위터용 훅(hook) 2개를 덧붙입니다."

이게 다입니다. 정말 심플하죠? 복잡한 `if문`, `for문`, `try-except` 같은 프로그래밍 로직이 **프롬프트(자연어) 한 줄**로 끝납니다. 이것이 LLM 기반 에이전트의 위력입니다.

### 비유: 홀 매니저의 '업무 매뉴얼'
`Blogger`는 **아주 똑똑하지만 시키지 않으면 안 하는 신입 홀 매니저**라고 칩시다. 우리가 건네준 매뉴얼(Instructions)에는 이렇게 적혀 있습니다.

1.  **손님(사용자)이 주제(예: 'AI 시대의 글쓰기')를 말하면** -> **즉시 '플래너 도구 호출 벨'을 눌러 "이 주제로 목차 짜줘" 주문 넣기.**
2.  **주방(Planner)에서 '목차(Outline)'가 나오면** -> **그 목차를 들고 '라이터 도구 호출 벨'을 눌러 "이 목차대로 글 써줘" 주문 넣기.**
3.  **주방(Writer)에서 '완성된 글(Full Draft)'이 나오면** -> **매니저 본인이 직접 마무리 손질하기: "제목 3개 더 뽑고, 트윗용 한 줄 소개 2개 만들어 붙이기."**
4.  **손님에게 최종 결과물 서빙하기.**

여기서 **포인트 3번**을 보세요. "대체 제목 3개, 트윗 훅 2개" 만들기는 **별도의 도구가 없습니다.** `Blogger` 자신이 **자신의 머리(LLM 추론 능력)**로 바로 해냅니다. 왜냐? 이건 복잡한 검수 루프가 필요 없는, LLM이 가장 잘하는 '창의적 변형' 작업이니까요. **'도구로 뺄 일(복잡한 프로세스)'**과 **'직접 할 일(단순 생성)'**을 구분하는 것이 좋은 에이전트 설계의 감각입니다.

## 3. 철저한 출입 통제: "허락된 도구만 쓴다" (Access Control)

이 챕터의 하이라이트이자 보안/아키텍처 관점에서 가장 중요한 대목입니다.

> *"The root agent only has access to the two tools we exposed, the planner and the writer. So its workflow is clear and controlled."*

**번역:**  
> "루트 에이전트는 우리가 노출시킨(Exposed) 두 개의 도구, 즉 플래너와 라이터 **만** 접근할 수 있습니다. 그래서 그 워크플로우(작업 흐름)는 명확하고 통제됩니다."

### 비유: **'출입증(Access Card)' 시스템**

회사 건물(에이전트 시스템)에 `Blogger`라는 직원이 있습니다. 이 직원에게 **마스터 키(모든 도구 접근 권한)**를 주면 어떻게 될까요?
*   `Blogger`가 심심해서 `Checker`(검수 도구)를 직접 호출해볼 수도 있고,
*   내부 데이터베이스 툴을 건드려 볼 수도 있고,
*   `Planner` 안의 세부 프롬프트를 뜯어고치려 들 수도 있습니다.

그러면 시스템은 **카오스(Chaos)**가 됩니다. "계획 -> 작성 -> 검수"라는 정해진 파이프라인이 무너지고, 에이전트가 제멋대로 순서를 바꾸거나 불필요한 도구를 호출해 토큰(비용)만 낭비하게 되죠.

**그래서 우리는 `Blogger`에게 출입증을 딱 2개만 발급해 줍니다.**
1.  **출입증 A: `planner_tool`** (계획 세우기 전용)
2.  **출입증 B: `writer_tool`** (글 쓰기 전용)

`Blogger`의 가방(컨텍스트/사용 가능 도구 리스트)에는 **오직 이 두 장의 카드만 들어있습니다.** `checker_tool`, `database_tool`, `email_tool`... 이런 건 **카드 자체가 없습니다.** 애초에 호출하려 해도 **"Error: Tool not found(도구 없음)"** 에러가 납니다.

> **💡 개념 돋보기: 최소 권한 원칙 (Principle of Least Privilege) in Agent Design**
> 
> **비유: 수술실의 메스와 간호사**
> 
> 집도의(`Blogger` - 루트 에이전트)에게는 **메스(Planner Tool)**와 **봉합실(Writer Tool)**만 쥐여줍니다. 마취제 주사기(Checker Tool), 심전도 모니터(Internal Loop Logic), 수술실 조명 스위치(System Config)는 **간호사들(내부 서브 에이전트/루프)이 알아서 다룹니다.** 집도가 "마취 좀 더 주세요"라고 소리치면(도구 호출) 간호사가 알아서 처리하지만, 집도가 직접 마취제 병을 들고 주사 놓으러 다니면 수술 망칩니다.
> 
> **이 '도구 접근 제한'이 주는 3가지 선물:**
> 1.  **예측 가능성(Predictability):** `Blogger`는 무조건 `Planner` -> `Writer` 순서만 탈 수 있습니다. 엉뚱한 짓(예: 글부터 쓰고 계획 짜기)을 **구조적으로 원천 차단**합니다.
> 2.  **디버깅 용이성:** 문제가 생기면 "플래너 도구 탓인가? 라이터 도구 탓인가? 아님 블로거 지시문 탓인가?" **범위가 3개로 좁혀집니다.** 전체 코드베이스를 뒤질 필요 없습니다.
> 3.  **보안/비용 제어:** 불필요한 고비용 LLM 호출(내부 검수 도구 등)을 루트 에이전트가 실수로 남발하는 걸 막습니다.

## 4. 완성된 파이프라인: "주제만 주면 완성본이 나온다"

자, 이제 모든 조각이 맞춰졌습니다. 스크립트의 마지막 부분이 이 감동을 잘 요약합니다.

> *"You give it a topic, it plans, it writes, it checks, and then it gives you a polished blog post."*

**한 문장으로 보는 전체 흐름 (End-to-End Flow):**

1.  **입력 (Input):** 사용자 -> `Blogger` : **"'지속 가능한 다이어트'에 대해 블로그 글 써줘."**
2.  **1단계 - 계획 (Planning via Tool):** `Blogger` -> `planner_tool` 호출 -> 내부적으로 `Planner` + `Checker` 루프가 돌며 **검증된 목차(Outline)** 생성 -> `Blogger`에게 반환.
3.  **2단계 - 작성 (Writing via Tool):** `Blogger` -> `writer_tool` 호출 (목차 전달) -> 내부적으로 `Writer` + `Checker` 루프가 최대 3번 재시도하며 **검증된 본문(Draft)** 생성 -> `Blogger`에게 반환.
4.  **3단계 - 마무리 (Post-processing by Root):** `Blogger` 자신의 LLM 능력으로 -> **대체 제목 3개 + 트윗 훅 2개** 생성하여 본문에 붙임.
5.  **출력 (Output):** `Blogger` -> 사용자 : **"자, 여기 완성된 블로그 글이요! (목차, 본문, 대체 제목, 홍보용 트윗 포함)"**

이 모든 과정이 사용자 눈에선 **단 한 번의 대화**로 끝납니다. 내부에서 몇 번의 LLM 호출이 오갔는지, 몇 번의 재시도가 있었는지, 검수 프롬프트가 어땠는지는 **완벽히 은닉(Hidden)**되어 있습니다.

## 5. 다음 단계: 실전 실행 (ADK Web)

스크립트는 마지막에 이렇게 독려합니다.

> *"You've now successfully written your first agent script. The next step is to actually run it. Head into your terminal and launch it using this command with ADK web so you can view everything inside a simple UI."*

**번역:**  
> "이제 여러분은 첫 번째 에이전트 스크립트 작성을 성공적으로 마쳤습니다. 다음 단계는 실제로 실행해보는 것입니다. 터미널로 가서 ADK 웹 명령어로 실행하면, 간단한 UI 안에서 모든 과정을 눈으로 확인할 수 있습니다."

### 비유: **'시식회' 준비 완료**
지금까지 우리는 **주방 설계도(아키텍처)**를 그리고, **레시피(프롬프트/지시문)**를 짜고, **주방 기구(도구/루프 에이전트)**를 만들고, **출입증(권한 제어)**까지 발급했습니다. 이제 남은 건 **불 켜고 요리 시작하기(Run)**입니다.

`adk web` 명령어는 **'주방 CCTV 모니터'** 같은 역할을 합니다. 터미널에서 이 명령어를 치면 브라우저에 예쁜 대시보드가 뜨는데, 거기서:
*   "지속 가능한 다이어트"라고 입력하면(사용자 입력)
*   `Blogger`가 `planner_tool` 호출하는 로그(플래너 작동 중...)가 보이고
*   `Planner` 내부에서 `Checker`가 "목차 수정 필요"라며 루프 도는 모습(상세 트레이스)이 보이고
*   `writer_tool` 호출 후 `Writer`가 3번까지 재시도하는 긴박한 과정(디버깅 뷰)이 다 보이고
*   최종적으로 예쁘게 포장된 블로그 글이 화면에 렌더링되는 것까지 **한눈에** 볼 수 있습니다.

## 📝 요약하며 마무리: 이번 챕터의 핵심 3줄

1.  **복잡함은 안으로, 인터페이스는 밖으로:** `Loop Agent`(재시도 로직) -> `Tool`(단순 호출)로 감싸서 **루트 에이전트의 인지 부하를 제로(0)로 만드세요.**
2.  **루트 에이전트는 '지휘자'이지 '마이크로 매니저'가 아닙니다:** 자연어 지시문(Instructions)만으로 **"순서(Planner -> Writer)"**와 **"마무리(제목/훅)"**만 정의하세요. 어떻게(How)는 도구가 알아서 합니다.
