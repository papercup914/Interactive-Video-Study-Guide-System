# Chapter 3. Applied AI 팀의 역할과 고객과의 에이전트 구축 경험: 프로토타입을 넘어 '진짜 서비스'로 가는 여정

안녕하세요, 여러분! 지난 시간까지 우리는 '에이전트'라는 개념이 무엇인지, 그리고 클로드(Claude)가 어떻게 도구를 쓰고 사고하는지 기본 원리를 살펴보았습니다. 오늘은 이야기가 조금 더 깊어집니다. **"내 노트북에서는 잘 돌아가는데, 왜 서비스만 올리면 터질까?"**라는, 수많은 개발자를 밤잠 설치게 만드는 고전적인 문제에 대한 앤스로픽(Anthropic) Applied AI 팀의 치열한 고민과 해법을 들여다볼 차례입니다.

이 내용은 단순히 기술 문서를 읽는 것이 아닙니다. 실제 고객사들과 어깨동무하며 에이전트를 현장에 투입해 본 **'전장의 기록'**이자, **"어떻게 하면 에이전트를 장난감이 아닌 믿을 수 있는 동료로 만들까?"**라는 질문에 대한 답찾기 과정입니다. 자, 커피 한 잔 들고 편하게 따라오세요. 꽤 재미있는 비유들이 기다리고 있습니다.

## 1. 내 노트북을 덮어도 에이전트는 일한다: '서버 사이드 에이전트 루프'의 마법

여러분, 로컬(Local) 환경에서 파이썬 스크립트 돌려보신 적 있죠? `python agent.py` 치고 터미널 창 띄워놓고 뿌듯해하다가, 실수로 창을 닫거나 노트북 덮개를 닫으면? **쨍그랑!** 에이전트도 같이 죽어버립니다. 내가 띄워둔 스트림릿(Streamlit) 앱도, 에이전트가 생각하던 중간 상태(Context)도, 모두 휘발되어 버리죠.

이게 바로 **'프로토타입의 함정'**입니다. 내 컴퓨터에서는 '신'인데, 남들 쓰게 서버에 올리면 '유령'이 되어버리는 거죠.

> **💡 개념 돋보기: 프로토타입 vs 프로덕션 (Prototype vs Production)**
> > **프로토타입(시제품):** "내 기계에서만 돌아가면 돼." 내 노트북 터미널 위에서 내가 지켜보며 돌리는 상태. 전원 끄면 끝. 상태 저장 안 됨.
> > **프로덕션(실제 서비스):** "누가, 언제, 어디서 접속해도 24시간 365일 멀쩡해야 해." 내 노트북을 덮어도, 네트워크가 끊겨도, 사용자가 새로고침(F5)을 눌러도 **작업하던 그대로 이어서** 해야 함. 이를 **내구성(Durability)**, **신뢰성(Reliability)**이라고 부릅니다.

앤스로픽의 **클로드 매니지드 에이전트(Claude Managed Agents)**는 이 문제를 **'에이전트 루프(Agent Loop)를 서버 사이드(Server-side)에서 돌린다'**는 한 방으로 해결했습니다.

### 🍳 비유: '내 주방' vs '배달 전문 클라우드 주방'

*   **기존 방식 (클라이언트 사이드 루프):** 내 집 주방에서 요리하는 것과 같습니다. 내가 가스불 켜고(프로세스 실행), 재료 썰고(추론), 그릇 담고(응답) 다 해야 해요. 내가 외출하면(노트북 덮음) 요리 중단, 불 꺼짐, 음식 상함. 확장하려면 내 집 주방을 늘려야 하니 돈도 많이 들고 힘들죠.
*   **클로드 매니지드 에이전트 (서버 사이드 루프):** **'배민/쿠팡이츠 전용 클라우드 주방'** 같습니다. 나는 주문만 넣으면(요청 보내면), **서버라는 거대한 전문 주방에서 셰프(에이전트 루프)가 알아서 요리(사고-도구실행-관찰) 다 해줍니다.** 내가 집 가서 자고 있어도(노트북 덮음), 주방은 24시간 돌아가며 내 주문 건을 책임지고 완료합니다. 손님이 몰려도 주방 측에서 알아서 셰프 더 부르고 불 더 켜줍니다(자동 스케일링).

**핵심은 '추상화(Abstraction)'입니다.** 호스팅 어디서 할까, 서버 어떻게 늘릴까, 세션 끊기면 상태 어떻게 복구할까... 이런 **'귀찮고 어렵고 실수하기 좋은 인프라 잡일'을 앤스로픽이 다 떠안아 줍니다.** 개발자는 오직 **"에이전트가 무슨 일을 할까?(로직)"**만 짜면 됩니다.

> **💡 개념 돋보기: 서버 사이드 에이전트 루프 (Server-side Agent Loop)**
> > 에이전트의 핵심 두뇌 활동인 **"생각(Reasoning) → 도구 호출(Tool Use) → 결과 관찰(Observation) → 다시 생각..."** 이 무한 루프를 **개발자의 로컬 머신이 아닌, 앤스로픽의 관리형 클라우드 서버에서 실행**한다는 뜻입니다.
> > **왜 중요할까?**
> > 1.  **상태 영속성 (State Persistence):** 사용자가 브라우저를 껐다 켜도(F5), 세션 ID만 알면 **대화 기록, 툴 호출 이력, 중간 연산 결과**가 서버에 고스란히 남아 있습니다. "아까 어디까지 했지?" 할 필요 없음.
> > 2.  **무중단 운영:** 내 로컬 환경(와이파이, 배터리, OS 업데이트 재부팅)과 무관하게 에이전트는 서버에서 꿋꿋이 일함.
> > 3.  **확장성:** 사용자 100명이 동시에 써도 서버 측에서 컨테이너를 알아서 띄워줌. 개발자는 `docker-compose up` 같은 거 안 해도 됨.

## 2. '머리(두뇌)'와 '손(도구)'을 분리하라: 아키텍처의 대반전

자, 이제부터가 진짜 핵심입니다. 앤스로픽 Applied AI 팀이 고객사들과 부대끼며 **"아, 이대로는 안 되겠다"**고 뼈저리게 느껴 바꾼 **아키텍처 설계의 대전환** 이야기입니다.

기존 에이전트 프레임워크들(랑체인, 오토지니, 클로드 코드 초기 버전 등)은 대개 **'에이전트 루프(두뇌)'와 '도구 실행 환경(손)'을 한 몸(같은 컨테이너/프로세스)**으로 묶어놨습니다.

### 🍳 비유: '만능 해결사' vs '뇌와 로봇팔의 분리'

상상해 보세요.
*   **기존 방식 (강결합, Tight Coupling):** **'슈퍼맨 로봇'** 한 대가 있습니다. 머리(두뇌)도 달리고, 힘센 팔(도구 실행 환경)도 달렸어요. "파일 좀 읽어줘", "서버 재시작해줘", "DB 쿼리 날려줘" 뭐든 시키면 그 자리에서 바로 실행합니다. 편하죠? **근데 이 로봇이 해킹당하거나 실수로 `rm -rf /` (전체 삭제) 명령 내리면? 끝장납니다.** 내 컴퓨터 전체 권한을 이 로봇이 쥐고 있으니까요. 게다가 이 로봇 하나 부르려면 무거운 컨테이너 하나 통째로 켜야 하니 **부팅 시간(지연 시간)**이 깁니다.
*   **새 방식 (분리, Decoupling - Headless Architecture):**
    *   **뇌(Brain = Agent Loop):** **'전략가 장군'** 역할만 합니다. "상황 분석해 보니 3번 서버 재시작 필요해. 실행 부대에 명령 내려." **자체적으로 파일 시스템 접근 권한 같은 '손'은 전혀 없습니다.** 생각만 해요. 그래서 가볍고 빠릅니다.
    *   **손(Hands = Environment/Sandbox):** **'격리된 특수부대(샌드박스)'**입니다. 장군의 명령만 받아서 **철저히 격리된 감옥(샌드박스) 안에서만** 움직입니다. 실제 서버 비밀번호(자격증명/Credential) 모름. 내 로컬 파일 모름. 그냥 "명령어 `docker restart web-3` 실행해줘" 하면 샌드박스 안에서만 `stdout`/`stderr` 결과 텍스트만 뇌로 돌려줍니다.

**이 '분리'가 가져온 기적 같은 변화 세 가지:**

#### ① 보안 (Security): "장군에게 금고 열쇠를 주지 마라"
기존엔 에이전트가 내 파일 시스템, AWS 키, DB 패스워드 다 접근 가능했죠. **'프롬프트 인젝션(Prompt Injection)'** 공격 하나면 "아까 그 비밀 키 좀 출력해줘" 해서 다 털립니다.
> **분리 후:** 뇌(에이전트 루프)는 **자격 증명(Credentials)을 모릅니다.** 암호화된 채로 샌드박스에만 있거나, 아예 별도 보관소(Vault)에 있죠. 뇌는 "도구 실행해"라는 **추상적인 의도(Intent)**만 보냅니다. 해커가 뇌를 해킹해도 "비밀번호 줘" 해도 뇌가 모릅니다. **물리적으로 접근 권한이 분리되어 있으니 털릴 게 없습니다.** 이게 바로 **'샌드박싱(Sandboxing)'의 완성**입니다.

#### ② 지연 시간 (Latency): "장군은 텐트 치고 기다리지 않는다"
기존 방식: 사용자 요청 올 때마다 -> 컨테이너 띄우고(무거움) -> 에이전트 로드 -> 루프 시작 -> 첫 토큰 나옴. 이 **'콜드 스타트(Cold Start)'** 때문에 **TTFT(Time To First Token, 첫 토큰 도착 시간)**가 길었습니다. P95(상위 5% 느린 케이스) 기준으론 더 심하죠.
> **분리 후:** 뇌(에이전트 루프 프로세스)는 **서버에 항상 떠 있습니다(Warm).** 요청 오면 바로 "생각" 시작. 손(샌드박스)은 필요할 때만 가볍게 띄우거나 풀링(Pooling)해둔 걸 씁니다.
> **결과:** 앤스로픽 팀 측정 결과 **P95 TTFT가 90% 이상 단축**되었습니다. 사용자 입장에선 "어? 벌써 답이 나오네?" 체감 속도가 확 빨라진 거죠.

#### ③ 신뢰성 (Reliability): "손이 다쳐도 머리는 멀쩡하다"
샌드박스(손)에서 돌던 코드가 무한 루프 돌거나 메모리 터져서 컨테이너가 죽어도? **뇌(에이전트 루프)는 살아있습니다.** 그냥 "어? 손이 안 움직이네? 다른 손(새 샌드박스) 불러와야지" 하고 복구하면 그만입니다. 상태(Session State)는 뇌가 쥐고 있으니까요.

> **💡 개념 돋보기: 헤드리스 아키텍처 / 브레인-핸드 분리 (Headless Architecture / Brain-Hand Separation)**
> > **뇌 (Brain = Agent Loop / Control Plane):**
> > *   역할: 추론(Reasoning), 계획(Planning), 도구 선택(Tool Selection), 상태 관리(State Management).
> > *   특징: **Stateless에 가깝게 가볍게 유지**, 권한 없음(No Credentials, No FS Access), 고가용성(HA) 보장.
> > *   위치: 매니지드 클라우드 서버 (Always On).
> >
> > **손 (Hands = Environment / Execution Sandbox / Data Plane):**
> > *   역할: 실제 코드 실행, 파일 I/O, 네트워크 호출, CLI 명령 수행.
> > *   특징: **강력한 격리(Isolation)**, 일회용(Ephemeral) 가능, 권한 최소화(Least Privilege).
> > *   위치: 격리된 컨테이너/VM (On-demand or Pooled).
> >
> > **통신:** 뇌 ↔ 손 은 **표준화된 프로토콜(MCP 등)로만 대화**. "이 함수 실행해줘(arguments)" -> "결과/에러 돌아옴(result/error)".
> >
> > **왜 'Applied AI 팀의 경험'에서 나왔나?** 고객사들이 "에이전트 프로토타입은 만들겠는데, 보안 팀에서 승인 안 해줘요(권한 때문)", "지연 시간 때문에 실시간 서비스 못 써요", "에이전트 돌리다 컨테이너 터지면 세션 날아가요" 라는 **현장의 비명**을 듣고 설계한 해답입니다.

## 3. 실전: '새벽 3시 온콜(On-call) 악몽'을 에이전트에게 넘기기

이론은 이쯤 하고, Applied AI 팀이 **"이게 진짜 되네?"** 검증한 실전 예시를 볼까요? 워크샵에서 직접 돌릴 **'인시던트 대응 에이전트(Incident Response Agent)'**입니다.

### 🎬 상황극: 개발자의 악몽, 새벽 3시

> **장면:** 당신은 백엔드 엔지니어. 오늘 밤 **온콜(On-call, 당직)** 차례입니다. 자정 넘어 겨우 잠들었는데...
> **띠링~!** **`[P1 CRITICAL] API Error Rate 50% Exceeded - Payment Service Down`**
> **눈 비비며 노트북 열고:** 그라파나(Grafana) 대시보드 켜고 -> 로그 찾아 헤매고 -> 최근 배포 내역 확인하고 -> 쿠버네티스 파드 재시작 해보고 -> 슬랙에 "나 지금 보고 있어" 치고... **식은땀 나며 30분 씨름.**

이 **고통스럽고, 반복적이며, 실수하기 쉬운 과정**을 에이전트에게 맡겨보자! 가 이번 워크샵의 미션입니다.

### 🛠️ 워크샵 아키텍처 뜯어보기: `agent.py`의 세 가지 주역

제공된 레포지토리(`Ship Your First Managed Agent`)의 `agent.py`에는 방금 배운 **뇌-손-세션** 구조가 코드로 녹아 있습니다. 하나씩 요리조리 살펴볼까요?

#### ① 에이전트 (Agent) = **'두뇌 명세서 (Brain Spec)'**
```python
# agent.py (개념 코드)
agent = Agent(
    model="claude-3-5-sonnet-20241022", # 어떤 모델 쓸지 (지능 수준)
    instructions="당신은 시니어 SRE입니다. 인시던트 로그를 분석하고 근본 원인을 찾으세요.", # 페르소나 (성격/역할)
    mcp_servers=[...], # 쓸 수 있는 '외부 도구 상자' 목록 (MCP 서버들)
    skills=[...]       # 내장된 '특수 기술'들 (예: 로그 분석 스킬, 쿠버네티스 조작 스킬)
)
```
*   **비유:** **"구인 공고"** 또는 **"직무 기술서(JD)"**입니다. "우리는 이런 성격(페르소나), 이런 지능(모델), 이런 도구(MCP/스킬) 쓸 줄 아는 사람 뽑을게요."라고 정의만 해둔 상태. **아직 일은 안 합니다.** 그냥 설계도예요.

#### ② 환경 (Environment) = **'격리된 작업실 (The Hands / Sandbox)'**
```python
# environments.py (개념 코드)
env = Environment(
    type="docker", # 또는 "k8s", "cloud-vm"
    image="incident-response-env:latest", # 안에 kubectl, aws cli, python, jq 다 깔린 이미지
    secrets=["AWS_SECRET_KEY", "KUBECONFIG"], # 💡 뇌는 모름! 환경만 안전하게 주입됨
    network_policy="restricted" # 외부 인터넷 차단 등 보안 정책
)
```
*   **비유:** **'보안 검색대 통과한 깨끗한 작업실'**. 뇌가 "쿠버네티스 파드 재시작해" 하면, 이 방 안에 있는 `kubectl` 바이너리가 돌아가는 겁니다. **뇌(에이전트 프로세스)는 이 방 열쇠도 모릅니다.** 그냥 "방아, 이 명령 실행해" 하고 메시지만 던집니다. 방이 다치고(컨테이너 크래시), 더러워지면(상태 꼬이면) 버리고 새 방 만들면 그만.

#### ③ 세션 (Session) = **'두뇌와 손을 잇는 다리 (The Conductor)'**
```python
# sessions.py (개념 코드)
session = Session.create(
    agent_id=agent.id,
    environment_id=env.id,
    # 이 세션만의 고유한 대화 기록, 상태, 컨텍스트 윈도우를 가짐
)
```
*   **비유:** **'프로젝트 매니저(PM) 겸 통역사'**.
    1.  사용자(나) 요청 받음: "인시던트 ID `INC-2024-001` 분석해줘."
    2.  **세션**이 에이전트(두뇌) 깨워서: "이거 분석해. 도구 쓸 수 있어."
    3.  두뇌 생각: "음... 로그 봐야겠네. `get_logs` 도구 써야지." -> 세션에게 도구 호출 요청 보냄.
    4.  **세션**이 환경(손)에게: "야, `get_logs --incident-id=INC-2024-001` 실행해."
    5.  환경 실행 -> 결과(로그 텍스트) -> **세션**이 받아서 -> **두뇌**에게 "여기 결과야" 전달.
    6.  두뇌 분석 -> 최종 답변 -> **세션**이 사용자(나)에게 스트리밍으로 쏴줌.
    *   **중요:** 이 **세션 객체**가 **대화 히스토리(컨텍스트)**를 쥐고 있습니다. 내가 브라우저 끄고 자고 일어나서 같은 세션 ID로 접속하면? **"아, 아까 그 인시던트 분석하던 거 계속할게요."** 가능.

## 4. 직접 해보기: `streamlit run app.py` 마법의 순간

자, 이제 여러분 차례입니다. 강연자가 "자, 노트북 여세요"라고 한 그 순간으로 가봅시다.

### 단계 1: 레포지토리 복사하기 (내 작업장에 도면 가져오기)
```bash
git clone <제공된_URL>
cd "Ship Your First Managed Agent"
```
*   **비유:** 건축 도면(코드)과 자재 리스트(requirements.txt) 내 현장으로 가져오는 중.

### 단계 2: 파이썬 가상환경 만들기 (나만의 깨끗한 공구함 준비)
```bash
# Mac/Linux
python3 -m venv .venv
source .venv/bin/activate

# Windows
python -m venv .venv
.venv\Scripts\activate
```
*   **왜?** 내 컴퓨터 전역 파이썬 라이브러리 더럽히지 않고, 이 프로젝트만의 독립된 공간(샌드박스!) 만들기 위함. **개발자의 로컬에도 '격리' 습관 들이기!**

### 단계 3: 라이브러리 설치 (자재 창고 채우기)
```bash
pip install -r requirements.txt
```
*   `anthropic` SDK, `streamlit`, `mcp` 클라이언트 등 필요한 부품들 다운로드.

### 단계 4: 열쇠(API Key) 꽂기
```bash
cp .env.example .env
# .env 파일 열어서 ANTHROPIC_API_KEY=sk-ant-... 붙여넣기
```
*   **비유:** 클라우드 주방(매니지드 서버) 쓰려면 **회원 카드(API Key)** 필요. QR 코드로 받은 무료 크레딧 카드 꽂는 중. **절대 깃허브에 올리지 마세요! (.gitignore 확인 필수)**

### 단계 5: 실행! (불 켜고 장사 시작)
```bash
streamlit run app.py
```
*   터미널에 `Local URL: http://localhost:8501` 뜸. 브라우저에서 열면 **인시던트 대응 대시보드** 등장!

## 5. 화면 위에서 벌어지는 일: 에이전트의 '사고 과정' 구경하기

`app.py`를 열면 `streamlit`으로 만든 간단한 UI가 있습니다. "Run Agent" 버튼 누르면 오른쪽에서 **실시간 스트리밍**으로 에이전트가 일하는 모습이 보입니다.

### 🕵️‍♂️ 에이전트의 내면 독백 (Chain of Thought) 엿보기
매니지드 에이전트의 장점 중 하나는 **에이전트가 '왜 그렇게 생각했는지' 사고 과정(Thinking/Reasoning)을 실시간으로 스트리밍 해준다는 점**입니다. 화면에서 이런 흐름을 보실 겁니다.

1.  **사용자:** "인시던트 `INC-123` 분석해줘."
2.  **에이전트 (생각):** "음, 인시던트 ID 받았네. 먼저 그라파나에서 알람 상세 내역이랑 관련 메트릭 뽑아봐야겠다. `get_grafana_alert` 도구 쓸게." -> **[도구 호출: get_grafana_alert]**
3.  **환경 (실행):** 샌드박스 안에서 API 호출 -> JSON 결과 반환.
4.  **에이전트 (생각):** "아, 에러율 50%네. 최근 배포 `v2.3.1` 이후 급증했군. 쿠버네티스 파드 로그 봐야지. `kubectl logs` 쓸게." -> **[도구 호출: kubectl_logs]**
5.  **환경 (실행):** 샌드박스에서 `kubectl` 실행 -> 에러 스택 트레이스 텍스트 반환.
6.  **에이전트 (생각):** "`NullPointerException` at `PaymentProcessor.java:45`. 아, 신규 기능 플래그 `new_checkout_flow` 켜져서 구버전 코드랑 충돌 나네. 롤백 또는 플래그 끄기 권고해야겠다."
7.  **에이전트 (최종 답변):** 사용자에게 **요약 리포트 + 근본 원인(RCA) + 즉각 조치 가이드(런북) + 재발 방지 대책** 예쁘게 마크다운으로 뿅!

**이 모든 과정이** 내 노트북 터미널이 아닌 **클라우드 서버(뇌)**와 **격리된 컨테이너(손)** 사이에서 오가며 일어나고, **나는 브라우저에서 팝콘 먹으며 구경만 하면 됩니다.** 중간에 인터넷 끊겨도, 브라우저 껐다 켜도 **세션 ID만 있으면 이어서 볼 수 있죠.**

## 6. 마무리하며: Applied AI 팀이 우리에게 남긴 것

이번 챕터에서 우리는 단순한 코드 실습을 넘어, **'어떻게 하면 에이전트를 프로덕션급 무기로 만들까?'**라는 엔지니어링 철학을 배웠습니다.

1.  **인프라는 잊어라 (Server-side Loop):** 내 노트북 덮개 닫아도 에이전트는 일한다. 상태는 서버가 기억한다.
2.  **권한은 최소화하라 (Brain-Hand Separation):** 머리(뇌)에게 칼(자격증명/파일시스템) 주지 마라. 손(샌드박스)만 조심스럽게 쓰게 하라. 그래야 안전하고 빠르다.
3.  **세션이 곧 컨텍스트다 (Session as State):** 대화의 연속성, 디버깅, 감사(Audit) 로그... 모든 것의 열쇠는 **세션(Session)** 객체가 쥐고 있다.
4.  **실제 고통에서 출발하라 (Incident Response):** "새벽 3시 온콜" 같은 **진짜 아픈 문제(Real Pain Point)**를 자동화 타겟으로 삼아야 가치가 빛난다.

여러분이 오늘 `streamlit run app.py`를 치고 브라우저에서 에이전트가 척척 로그 분석하고 원인 찾아내는 걸 보신다면, 그건 단순히 "데모가 돌아간다"는 의미가 아닙니다. **"앤스로픽 Applied AI 팀이 수많은 고객사의 피눈물 나는 시행착오 끝에 정립한, 프로덕션 레디 에이전트 아키텍처의 모범 답안"**이 여러분의 로컬에서 구현되고 있는 겁니다.

자, 이제 여러분의 차례입니다. 레포지토리 클론하고, `.env`에 키 넣고, **내 손으로 첫 매니지드 에이전트를 띄워보세요.** 그리고 생각하세요. *"내 서비스에선 어떤 '새벽 3시 고통'을 이 친구에게 맡길 수 있을까?"*

다음 챕터에서는 이 에이전트에 **'기억력(Long-term Memory)'**을 심어주고, **'멀티 에이전트 협업(Multi-agent Collaboration)'**으로 확장하는 법을 배워보겠습니다. 기대하셔도 좋습니다. 수고하셨습니다! 👏
