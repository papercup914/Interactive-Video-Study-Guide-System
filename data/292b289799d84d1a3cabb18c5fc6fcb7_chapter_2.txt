# Chapter 3. ReAct 패턴 소개: 추론(Reasoning)과 행동(Acting)의 시너지

---

안녕하세요! 지난 챕터에서는 AI 에이전트가 단순히 대답만 하는 챗봇이 아니라, **스스로 판단하고(Reasoning) 실제 행동(Action)까지 하는 소프트웨어**라는 것을 배웠습니다. 그런데 "판단하고 행동한다"는 말이 어쩐지 막연하게 느껴지지 않으셨나요? "도대체 머릿속에서 무슨 생각을 하면서 행동을 결정하는 거지?"라는 궁금증이 드셨을 겁니다.

이번 챕터에서는 그 궁금증을 풀어줄, 현대 AI 에이전트의 **'두뇌 회로'**라고 불리는 **ReAct(Re+Act) 패턴**에 대해 아주 깊고 친절하게 파헤쳐 보겠습니다. 영상에서 소개된 논문 *「ReAct: Synergizing Reasoning and Acting in Language Models」*의 핵심 아이디어를, 어려운 수식이나 코드 없이 일상적인 비유로 완벽하게 이해시켜 드릴게요.

---

## 1. 왜 '한 번에 답하기'는 안 될까? - '즉석 요리사'와 '코스 요리 셰프'의 차이

영상 초반부에 이런 말이 나옵니다.
> *"Language models shouldn't just generate text in one go. They can actually reason step-by-step..."*
> (언어 모델은 한 번에 텍스트를 생성만 해서는 안 됩니다. 그들은 단계별로 추론할 수 있습니다.)

이게 무슨 말일까요? 비유로 시작해 볼게요.

### 🍳 비유: 즉석 떡볶이집 사장님 vs 미슐랭 3스타 셰프

**전통적인 LLM (챗봇) = 즉석 떡볶이집 사장님**
손님이 "매운 거 좋아해요, 알아서 주세요!"라고 주문하면, 사장님은 **생각할 틈도 없이** 바로 냄비에 고추장, 설탕, 떡, 어묵을 한꺼번에 쏟아붓고 불을 켭니다. "자, 다 됐어요! 드세요!" 한 번에 뚝딱 내놓는 거죠. 빠르고 편하지만, 손님이 "아, 저 알레르기 있는데..."라고 말하면 이미 늦었습니다. 국물 맛을 보며 조절할 기회가 없었으니까요.

**ReAct 패턴을 적용한 에이전트 = 미슐랭 3스타 셰프**
같은 주문을 받아도 셰프는 **한 번에 완성하지 않습니다.**
1.  **생각(Reasoning):** "손님이 매운 걸 좋아한다고? 근데 혹시 위장이 약하실 수도 있으니 베이스 육수부터 내고, 매운맛은 고춧가루가 아닌 직접 담근 고추기름으로 레이어를 쌓아야겠다. 먼저 육수 맛을 보자."
2.  **행동(Action):** 육수를 끓이고, 간을 본다. (도구 사용: 냄비, 국자, 간보기 스푼)
3.  **관찰(Observation):** "음, 육수가 좀 싱겁네. 여기다 간장 한 스푼 더 넣고, 고추기름으로 향을 내야지."
4.  **다음 생각(Next Reasoning):** 관찰 결과를 바탕으로 다음 행동을 계획한다.
5.  **최종 완성:** 단계별 검증을 거쳐 완벽한 한 그릇을 낸다.

---

> **💡 개념 돋보기: '한 번에 생성(One-shot Generation)'의 함정**
>
> 기존 LLM은 입력된 프롬프트를 보고 **확률적으로 가장 그럴듯한 다음 토큰(단어)을 쭉 이어 쓰는 것**이 전부입니다. 복잡한 문제(예: "서울에서 부산까지 기차로 가는데 중간에 대전 들러서 성심당 빵 사고, 대구에서 친구 만나고, 부산 도착해서 해운대 가기")를 한 번에 풀라고 하면, 중간 논리가 꼬이거나 환각(Hallucination)을 일으키기 쉽습니다.
>
> ReAct는 **"생각 → 행동 → 관찰 → 생각 → 행동..."** 이 루프를 돌게 하여, 거대한 문제를 **잘게 쪼개서(Decomposition) 검증하며 풀어나가게 하는 설계 패턴**입니다.

## 2. ReAct의 탄생: "생각만 하지 말고, 손도 좀 써봐!"

영상에서는 구글 연구자들이 발표한 **ReAct 논문**을 인용하며 이렇게 설명합니다.
> *"One of the clearest explanations comes from the research paper ReAct, synergizing reasoning and acting in language models."*
> (가장 명확한 설명 중 하나는 ReAct 논문, 즉 언어 모델에서 추론과 행동의 시너지에서 나옵니다.)

### 🧠 비유: '책상물림 박사' vs '현장 엔지니어'

*   **Reasoning만 하는 모델 (Chain-of-Thought):** 책상에 앉아서 이론만 빠삭한 박사님입니다. "이 기계 고치려면 나사 풀고, 기름 치고, 조이면 돼."라고 **생각만** 엄청 잘합니다. 그런데 정작 공구함이 어디 있는지, 나사가 녹슬어서 안 풀리면 어떡할지는 모릅니다. **현실 세계(외부 도구, API, 검색)와 단절**되어 있죠.
*   **Acting만 하는 모델 (전통적 봇):** 생각 없이 시키는 일만 기계적으로 하는 로봇팔입니다. "나사 풀어" 하면 풀고, "조여" 하면 조입니다. 근데 나사가 안 풀리는데 계속 힘으로 돌리다가 나사 머리가 뭉개집니다. **상황 판단(추론) 능력**이 없죠.
*   **ReAct (Reasoning + Acting):** **현장 베테랑 엔지니어**입니다. "나사가 안 풀리네?(관찰) → 그럼 WD-40 뿌리고 5분 기다렸다가 다시 풀자(추론 → 행동) → 아, 풀리네?(관찰) → 이제 기름 치고 조이자(추론 → 행동)." **생각과 행동이 실시간으로 교차**하며 문제를 해결합니다.

---

> **💡 개념 돋보기: ReAct라는 이름의 비밀**
>
> **Re**asoning (추론, 사고) + **Act**ing (행동, 행동) = **ReAct**
>
> 이 논문의 핵심 주장은 **"언어 모델에게 '생각해(Think)'라고만 시키지 말고, '행동해(Act)'라고 시키고, 그 결과(Observation)를 다시 '생각'에 반영하게 하자"**는 것입니다. 이 단순한 아이디어가 현재 모든 최신 AI 에이전트(AutoGPT, LangChain Agents, Google ADK 등)의 **표준 아키텍처**가 되었습니다.

---

## 3. ReAct 루프(Loop) 완전 해부: 에이전트의 '심장 박동'

영상 스크립트에서 에이전트의 작동 방식을 이렇게 묘사했습니다.
> *"It looks at your request, figures out what steps need to be taken, maybe calls an API, runs code, looks at the results and then decides what to do next."*
> (요청을 보고, 필요한 단계가 뭔지 파악하고, API를 호출하거나 코드를 실행하고, 결과를 보고, 다음에 무엇을 할지 결정합니다.)

이 문장 하나에 ReAct의 **전체 사이클**이 다 들어 있습니다. 이를 **'ReAct 루프(Loop)'**라고 부르며, 에이전트가 살아 숨 쉬게 하는 심장 박동과 같습니다. 단계별로 아주 느리게, 자세히 뜯어보겠습니다.

### 3-1. 단계 1: 입력 받기 & 상황 파악 (Input & Context)
> *"Looks at your request"*

사용자의 말("서울 날씨 어때?"), 이전 대화 기록, 그리고 에이전트가 가진 **도구(Tool) 목록(날씨 API, 검색, 계산기 등)**을 컨텍스트(Context)로 받아들입니다.

*   **비유:** 손님이 식당에 들어와 메뉴판을 보며 "추천 좀 해주세요"라고 말하는 순간. 셰프는 **손님 얼굴(컨텍스트), 오늘의 식재료(도구), 주방 상황(메모리)**을 한눈에 스캔합니다.

### 3-2. 단계 2: 추론 - 생각의 흔적 남기기 (Reasoning / Thought)
> *"Figures out what steps need to be taken"*

단순히 "날씨 API 쓰자"가 아닙니다. **내부 독백(Inner Monologue)**을 텍스트로 생성합니다.
> **"생각: 사용자가 서울 날씨를 물었다. 현재 내 도구 상자에는 '실시간 날씨 API'가 있다. 이 API는 '도시 이름'을 파라미터로 필요로 한다. 사용자는 '서울'이라고 했으니 파라미터는 'Seoul'로 정하면 되겠다. 이제 이 도구를 호출해야겠다."**

*   **핵심 포인트:** 이 **'생각(Thought)' 과정을 사용자나 개발자가 볼 수 있게 텍스트로 출력**하게 합니다. 이게 바로 **해석 가능성(Interpretability)**과 **디버깅**의 열쇠입니다.
*   **비유:** 셰프가 혼잣말하며 레시피를 짜는 과정. "오늘 돼지고기 상태가 좋으니 수육보다 보쌈으로 가야지. 된장찌개는 좀 싱거우니 새우젓으로 간 맞추고..." 이 생각을 종이에 적어두면 나중에 "왜 보쌈 했어요?"라고 물었을 때 설명 가능하죠.

### 3-3. 단계 3: 행동 - 도구 사용하기 (Action / Tool Use)
> *"Maybe calls an API, runs code"*

생각을 실행에 옮깁니다. 정해진 포맷(예: JSON)에 맞춰 외부 함수(Function Calling)를 호출합니다.
> **Action:** `get_weather(city="Seoul")`

*   **비유:** 셰프가 냉장고 가서 돼지고기 꺼내오고, 칼로 썰고, 냄비에 물 올리는 **실제 물리적 행동**. 생각만 해선 요리가 안 나옵니다. 반드시 **외부 세계(도구, 환경)와 인터랙션**해야 합니다.

### 3-4. 단계 4: 관찰 - 결과 마주하기 (Observation)
> *"Looks at the results"*

도구가 돌려준 결과값을 받습니다. 성공일 수도, 에러일 수도, 예상과 다를 수도 있습니다.
> **Observation:** `{"temperature": 15, "condition": "Rainy", "humidity": 80}`

*   **비유:** 끓는 육수 맛을 보고, 고기 익힘 정도를 확인하는 **감각 기관(미각, 시각, 촉각)**. "어? 간이 안 맞네(에러/예상과 다름)" 혹은 "완벽하네(성공)"를 아는 순간입니다.

### 3-5. 단계 5: 다음 결정 - 루프 반복 또는 종료 (Next Step / Loop)
> *"Decides what to do next"*

관찰 결과를 **다시 컨텍스트에 추가**하여 2번(추론)으로 돌아갑니다.
*   **경우 A (완료):** "날씨 정보를 다 받았으니 사용자에게 답변 생성하자." → **Final Answer 출력 후 종료.**
*   **경우 B (추가 필요):** "어? 비 오네? 그럼 우산 챙기라고 해야겠다. 근데 사용자 우산 있는지 모르니 검색해볼까? 아니면 그냥 우산 챙기라고 말해줄까?" → **다시 Thought 생성 → Action... (루프 지속)**

---

> **💡 개념 돋보기: ReAct 루프의 '마법의 가루' = 컨텍스트 누적 (Context Accumulation)**
>
> 이 루프가 도는 동안 **LLM의 입력 컨텍스트(대화 내역)는 계속 길어집니다.**
> `[System Prompt] -> [User Query] -> [Thought 1] -> [Action 1] -> [Observation 1] -> [Thought 2] -> [Action 2] -> [Observation 2] -> ... -> [Final Answer]`
>
> 마치 **수사관이 수첩에 단서를 계속 적어 나가는 것**과 같습니다. 이전 단계에서 무슨 생각을 했고, 무슨 행동을 했고, 결과가 어땠는지 **모두 기억(컨텍스트 윈도우 내에 유지)한 채로 다음 추론**을 하기 때문에, 실수를 스스로 수정(Self-correction)하거나 복잡한 멀티스텝 작업을 수행할 수 있는 것입니다.

## 4. 실전 시나리오로 보는 ReAct 흐름: "파리 여행 계획 짜줘"

자, 이제 추상적인 설명은 그만하고, 영상에서 예고한 **"첫 번째 AI 에이전트 만들기"**에서 우리가 겪게 될 상황을 시뮬레이션해 봅시다.

**사용자 요청:** *"이번 주말 파리 여행 갈 건데, 에펠탑 근처 맛집 예약 좀 해줘. 예산은 1인당 50유로 이내로."*

### 🔄 ReAct 에이전트의 머릿속 시뮬레이션 (Step-by-Step)

#### **Turn 1: 파악 및 1차 계획**
*   **Thought (생각):** "사용자는 파리 에펠탑 근처 맛집 예약을 원한다. 조건: 이번 주말, 1인 50유로 이하. 내 도구: `Google_Search`, `Maps_API`, `Restaurant_Reservation_API`. 먼저 '에펠탑 근처 맛집 리스트'를 검색해야겠다."
*   **Action:** `Google_Search(query="에펠탑 근처 맛집 추천 2024 주말 예약 가능")`
*   **Observation:** 검색 결과 10개 나옴. (르 쥘 베른 - 미슐랭/비쌈, 르 비스트로 파리지앵 - 40유로/가능, 카페 드 로옴 - 30유로/대기 긺...)

#### **Turn 2: 필터링 및 심화 조사 (추론의 깊이 들어감)**
*   **Thought (생각):** "검색 결과 봤다. '르 쥘 베른'은 에펠탑 2층이라 뷰는 좋지만 1인 200유로 넘음 -> 예산 초과 제외. '르 비스트로 파리지앵'은 40유로로 예산 내, 예약 가능 표시됨. '카페 드 로옴'은 싸지만 대기가 너무 김. 사용자는 '예약'을 원하니까 대기는 비추. '르 비스트로 파리지앵' 상세 정보(정확한 위치, 메뉴, 예약 가능 시간) 더 알아봐야겠다."
*   **Action:** `Maps_API(place_id="르_르 비스트로 파리지앵", fields=["opening_hours", "menu", "price_level"])`
*   **Observation:** 토요일 저녁 7시 예약 가능, 메뉴에 스테이크 프리츠 38유로, 와인 별도.

#### **Turn 3: 실행 (예약 시도)**
*   **Thought (생각):** "조건 완벽 부합. 에펠탑 근처, 예산 내, 주말 저녁 예약 가능. 이제 예약 API 호출해야지. 사용자 인원 수 안 물어봤네? 보통 2명 가정하고 진행하거나 물어봐야 함. 일단 2명으로 임시 예약 시도해보고, 사용자한테 확인받자."
*   **Action:** `Reservation_API(restaurant="르 비스트로 파리지앵", date="이번주 토요일", time="19:00", party_size=2)`
*   **Observation:** `{"status": "success", "confirmation_number": "PARIS-2024-001", "message": "예약 완료. 10분 전까지 도착 요망."}`

#### **Turn 4: 최종 답변 생성 (종료)**
*   **Thought (생각):** "예약 성공! 확인 번호 받았음. 사용자에게 식당 정보, 가격, 예약 확인 번호, 위치, 꿀팁(에펠탑 뷰 포인트) 정리해서 친절하게 답변하자."
*   **Final Answer:** (사용자에게 자연스러운 한국어로 정리된 여행 계획 전달)

---

> **💡 개념 돋보기: 왜 이 과정이 '시너지(Synergy)'일까?**
>
> 논문 제목이 *Synergizing Reasoning and Acting*입니다.
> *   **Reasoning만 했다면:** "음... 파리 맛집은 르 쥘 베른이 유명하지" 하고 **환각(Hallucination)**으로 비싼 곳 추천하거나, 예약 가능 여부는 모른 채 "전화해보세요"로 끝냄.
> *   **Acting만 했다면:** 검색 API에 "파리 맛집" 던지고 나온 첫 번째 결과(광고일 수도 있음) 바로 예약 시도 -> 예산 초과나 예약 불가로 실패.
> *   **ReAct (시너지):** **추론이 행동을 안내하고(어떤 API를, 어떤 파라미터로?), 행동의 결과가 추론을 교정한다(예산 초과 -> 제외, 예약 가능 -> 진행).** 이 **상호 보완적 피드백 루프**가 바로 시너지입니다.

## 5. ReAct 패턴, 코드로는 어떻게 생겼을까? (사전 예습)

이제 다음 챕터에서 **Google ADK**로 코드를 짤 건데, ReAct 루프가 코드 레벨에서 어떻게 구현되는지 구조만 살짝 엿보고 가시죠. 어렵지 않습니다. 우리가 본 흐름 그대로입니다.

```python
# pseudo-code 스타일 (개념 이해용)

class ReActAgent:
    def __init__(self, tools, llm):
        self.tools = tools      # 사용 가능한 도구들 (API, 함수들)
        self.llm = llm          # 생각하는 두뇌 (Gemini, GPT 등)
        self.history = []       # 추론-행동-관찰 기록장 (컨텍스트)

    def run(self, user_request):
        self.history.append(f"User: {user_request}")
        
        # 💓 ReAct 루프 시작 (최대 N번 반복 또는 종료 시까지)
        for _ in range(MAX_STEPS):
            
            # 1. Thought (추론): LLM에게 "지금 상황인데, 어떻게 할까? Thought/Action 형식으로 답해" 프롬프팅
            prompt = self._build_react_prompt(self.history)
            llm_response = self.llm.generate(prompt) # 예: "Thought: ...\nAction: search_weather(city='Seoul')"
            
            # 2. 파싱: LLM 답변에서 Thought와 Action 분리
            thought, action = self._parse_llm_output(llm_response)
            self.history.append(f"Thought: {thought}")
            
            # 3. 종료 조건 확인: Action이 "Final Answer"이면 루프 탈출
            if action.name == "Final Answer":
                return action.parameters['answer']
            
            # 4. Action (행동): 실제 파이썬 함수/호출 실행
            self.history.append(f"Action: {action.name}({action.parameters})")
            observation = self._execute_tool(action.name, action.parameters)
            
            # 5. Observation (관찰): 결과 기록
            self.history.append(f"Observation: {observation}")
            # 루프 반복 -> history가 계속 길어지며 다음 판단에 활용됨
```

> **💡 개념 돋보기: `_build_react_prompt` 안에는 뭐가 있을까?**
> 이 함수는 `System Prompt` + `Tool Descriptions` + `History(Thought/Action/Observation 반복)` + `Format Instructions("반드시 Thought: ... Action: ... 형식으로 답하세요")`를 합쳐서 만듭니다. 즉, **LLM에게 "너는 지금 ReAct 루프를 돌고 있어. 형식 지켜서 생각하고 행동해"라고 계속 상기시키는 역할**을 합니다. ADK 같은 프레임워크는 이 복잡한 프롬프트 엔지니어링과 파싱, 툴 실행을 **자동화(Abstraction)**해 줍니다.

## 6. 마무리하며: ReAct는 에이전트의 '운영체제(OS)'입니다

이번 챕터에서 우리가 배운 핵심은 세 가지입니다.

1.  **ReAct는 '생각(Reasoning)'과 '행동(Acting)'의 교차 루프다.** 한 번에 답하지 않고, 단계별로 쪼개서 검증하며 나아간다.
2.  **루프의 심장은 '컨텍스트 누적'이다.** 과거의 생각, 행동, 결과를 모두 기억하며 다음 판단을 내린다. 이게 '적응(Adapt)'을 가능하게 한다.
3.  **도구(Tool/API)는 에이전트의 '손발'이다.** 생각만 하는 뇌(LLM)에 손발(Tool)을 달아주고, ReAct가 그 '신경계' 역할을 하여 뇌가 손발을 제어하게 만든 패턴이다.

영상에서는 이 ReAct 패턴을 **Google ADK(Agent Development Kit)**라는 도구로 아주 쉽게 구현하는 방법을 보여줄 예정입니다. 이제 여러분은 **"아, 저 코드가 돌면서 Thought 찍고, Action으로 API 호출하고, Observation 받아와서 다시 Thought 찍는 거네?"** 하고 코드의 흐름을 **눈으로 그려가며** 보실 수 있게 되셨습니다.
