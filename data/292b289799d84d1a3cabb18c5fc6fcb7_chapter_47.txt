# 챕터 5. 실시간 서브 에이전트 협업 과정 모니터링: 플래닝, 검증, 작성, 재시도 과정 관찰

자, 드디어 우리가 직접 작성한 에이전트 코드를 실행해 볼 시간입니다. 지금까지는 설계도(코드)만 그려놨다면, 이제는 실제로 **'레스토랑을 오픈'**해서 손님(사용자)을 맞이하고 주방(에이전트 시스템)이 어떻게 돌아가는지 **CCTV(ADK Web UI)**로 생중계처럼 지켜보는 단계라고 보시면 됩니다.

---

## 1. 에이전트 실행: '주방 오픈' 알림 버튼 누르기 (터미널 명령어)

영상에서는 터미널(개발자의 검은 화면 창)에 다음과 같은 명령어를 입력하라고 안내합니다.

```bash
adk web
```

> **💡 개념 돋보기: `adk web` 명령어의 정체**
> 
> 이 명령어는 **"우리 레스토랑(에이전트 시스템)의 홀과 주방을 한눈에 볼 수 있는 대시보드(CCTV 모니터룸)를 로컬 컴퓨터에 띄워줘"**라고 ADK 프레임워크에 요청하는 것과 같습니다.
> 
> *   **백엔드(주방)**: 우리가 짠 파이썬 코드(플래너, 라이터, 체커 에이전트)가 돌고 있는 곳.
> *   **프론트엔드(홀/모니터룸)**: `adk web`이 자동으로 만들어주는 웹 페이지(보통 `http://localhost:8000` 같은 주소).
> 
> 이 명령어 한 방이면 복잡한 웹 서버 설정 없이, 내 로컬 컴퓨터 안에서 **'에이전트 전용 테스트 플레이그라운드'**가 즉시 열립니다.

명령어를 치고 엔터를 누르면 터미널에 이런저런 로그(서버가 뜨는 중이라는 신호)가 쭉 올라오다가, 결국 **"Running on http://127.0.0.1:8000"** 같은 문구가 뜹니다. 이게 **"자, 이제 손님 받을 준비 끝났습니다!"**라는 오픈 사인입니다.

---

## 2. 브라우저 접속: '모니터링 룸' 입장하기

이제 크롬이나 엣지 같은 브라우저를 열고, 터미널에 뜬 주소(`http://localhost:8000` 또는 `http://127.0.0.1:8000`)로 접속하세요.

짜잔! 화면이 뜨는데, 이게 바로 **ADK Web UI**입니다. 화려하진 않지만, **'에이전트의 머릿속을 투명하게 들여다볼 수 있는 X-ray 안경'** 같은 역할을 합니다.

화면 구성을 잠깐 살펴볼까요?
*   **왼쪽 사이드바**: 지금까지 대화한 히스토리나 세션 목록이 나옵니다. (카카오톡 채팅방 목록 같은 느낌)
*   **중앙 메인 화면**: 현재 선택된 에이전트와의 **대화 창**입니다. 여기가 우리가 "블로그 글 써줘"라고 주문하는 카운터입니다.
*   **오른쪽/하단 패널 (중요!)**: **이벤트 스트림(Event Stream) 또는 트레이스(Trace)**라고 부르는 영역입니다. **여기가 바로 우리가 지켜볼 '주방 CCTV' 화면입니다.**

> **💡 개념 돋보기: 왜 'ADK Web'을 쓰는가? (디버깅의 눈)**
> 
> 일반적인 챗봇(ChatGPT 등)은 "입력 -> 마법 -> 출력"으로 끝납니다. 중간에 무슨 생각했는지, 어떤 툴을 썼는지, 실수해서 다시 고쳤는지 **전혀 안 보입니다. (블랙박스)**
> 
> 하지만 ADK Web은 **'화이트박스'**입니다.
> *   "지금 플래너 에이전트가 계획 짜는 중이야 (생각 중...)"
> *   "이제 라이터 에이전트가 1번 섹션 쓰는 중이야 (타이핑 중...)"
> *   "어? 체커 에이전트가 '사실 관계 오류 발견!'이라고 되돌렸네? (재시도 트리거!)"
> 
> 이 모든 **중간 과정(Intermediate Steps)**이 실시간 로그로 찍혀 나옵니다. 비전공자 입장에선 **"아, AI가 단순히 답을 뱉는 게 아니라, 사람처럼 생각하고-쓰고-고치는구나"**를 눈으로 확인하는 최고의 학습 도구입니다.

영상 강사님은 이제 이 채팅 창에 이렇게 입력합니다.

> **"Generate a blog post on the top 10 use cases for AI agents."**
> (AI 에이전트의 상위 10가지 활용 사례에 대한 블로그 글을 생성해 줘.)

엔터를 치는 순간, **조용하던 주방이 요란하게 돌아가기 시작합니다.** 오른쪽 CCTV 패널(이벤트 스트림)에 로그들이 **실시간으로 폭포수처럼 쏟아져 내리기 시작**할 겁니다. 자, 이제부터가 핵심 관전 포인트입니다. 팝콘 각오하고 보세요.

## 4. 실시간 협업 과정 관전 포인트 4단계 (CCTV 해설)

화면 오른쪽(또는 하단)에 뜨는 로그들을 보며, 지금 주방에서 무슨 일이 벌어지는지 **요리사(에이전트) 별로 해설**해 드립니다.

### 🎬 Act 1. 기획 실장(Planner Agent) 등장: "밑그림 그리기"
가장 먼저 **`planner_agent`** 이름이 뜨면서 `function_call` 같은 로그가 찍힙니다.
*   **로그 내용 예시**: `{"topic": "AI agent use cases", "outline": ["Intro", "Use case 1: Customer Support", ... "Conclusion"]}`
*   **상황**: 기획 실장이 "손님, 'AI 에이전트 10가지 활용법' 주문받았습니다. 일단 목차부터 뽑겠습니다." 하고 **기획서(Outline/Plan)를 작성** 중입니다.
*   **비유**: 건축가가 설계도면을 그리는 중. "1층은 로비, 2층은 사무실..." 이렇게 큰 뼈대를 잡습니다. 이 단계에서 **'무슨 내용을, 어떤 순서로, 몇 단락으로 쓸지' 전체 큰 그림이 결정**됩니다.

> **💡 개념 돋보기: 플래너의 출력물 = '작업 지시서(Task Spec)'**
> 
> 플래너가 그냥 "열심히 써"라고 퉁 치지 않습니다. **구조화된 데이터(JSON)**로 내려줍니다.
> ```json
> {
>   "title": "Top 10 AI Agent Use Cases",
>   "sections": [
>     {"id": 1, "heading": "Customer Support Automation", "key_points": ["24/7", "Instant reply"]},
>     {"id": 2, "heading": "Code Generation", "key_points": ["GitHub Copilot", "Debugging"]},
>     ...
>   ]
> }
> ```
> 이 **'설계도면(JSON)'**이 있어야 다음 요리사(라이터)가 헤매지 않고 각 파트별로 분업해서 쓸 수 있습니다. 이게 **'구조화된 출력(Structured Output)'**의 힘입니다.

---

### 🎬 Act 2. 작가 팀(Writer Agent) 투입: "본문 쓰기 (분업 시작!)"
플래너의 설계도면이 떨어지자마자, **`writer_agent`**가 여러 번 호출되거나(병렬 처리), 순차적으로 호출되면서 `function_call: write_section` 같은 로그가 뜹니다.
*   **로그 내용 예시**: `Writing section 1: "Customer Support Automation"...`, `Writing section 2: "Code Generation"...`
*   **상황**: 작가 팀이 "아, 1번 섹션 '고객 지원 자동화' 쓰면 되네? 키워드는 24/7, 즉각 응답이네? 알겠습니다." 하고 **각 섹션별로 본문 초안(Draft)을 써내려 갑니다.**
*   **비유**: 설계도면 보고 목수들이 각 방 벽돌 쌓고, 전기 기사들이 배선 깔고, 도배사들이 벽지 바르는 중. **한 명이 다 쓰는 게 아니라, 섹션별로 나누어서 동시에(병렬로) 또는 순서대로 씁니다.** 이게 바로 **'서브 에이전트 분업(Delegation)'**의 위력입니다.

---

### 🎬 Act 3. 품질 관리 팀(Reviewer/Checker Agent) 등장: "검수 & 빨간 펜 긋기"
작가들이 "다 썼습니다!" 하고 내민 초안을 **`reviewer_agent`** (또는 영상에선 `checker` 같은 이름)가 받아서 읽기 시작합니다.
*   **로그 내용 예시**: `Reviewing draft...`, `Found issue: "Section 3 lacks specific statistics."`, `Suggestion: "Add Gartner 2024 data."`
*   **상황**: 품질 관리 팀장이 빨간 펜 들고 **"여기 3번 섹션 통계 수치 없는데? 근거 좀 대."**, **"5번 섹션 문장이 너무 딱딱해. 부드럽게 고쳐."**라고 **피드백(Feedback/Critique)을 적어서 돌려보냅니다.**
*   **비유**: 편집장이 기자 초안 보고 "이거 다시 써와" 하는 장면. **단순 맞춤법 검사가 아니라, '논리적 일관성', '사실 정확성', '톤앤매너' 등을 기준(Rubric)으로 평가**합니다.

> **💡 개념 돋보기: '평가 기준(Evaluation Rubric)'이 곧 실력이다**
> 
> 이 체커 에이전트에게 우리는 시스템 프롬프트로 **"이런 기준으로 채점해"라고 가이드라인(루브릭)을 줬을 겁니다.**
> *   정확성 (Factual Accuracy): 1~5점
> *   완성도 (Completeness): 계획 대비 누락 없는가?
> *   가독성 (Readability): 문장이 매끄러운가?
> 
> 이 **'채점표'가 없으면 체커는 "좋은데요?"라고만 하고 끝납니다.** 좋은 에이전트 시스템을 만들려면 **'좋은 결과물의 정의(채점표)'를 에이전트에게 심어주는 것**이 무엇보다 중요합니다.

---

### 🎬 Act 4. 재시도 루프(Retry Loop): "혼나고 다시 쓰는 작가" ⭐️ **하이라이트!**
자, 여기가 **이 챕터에서 가장 중요하게 봐야 할 장면**입니다.

체커가 "수정해"라고 피드백을 주면, 시스템은 **자동으로 다시 작가(Writer)에게 "이 피드백 반영해서 고쳐써"라고 시킵니다.**

*   **로그 흐름**:
    1.  `Reviewer` -> `Feedback: "Add stats to section 3"`
    2.  `Orchestrator` (자동) -> `Writer` 호출: `Input: {draft + feedback}`
    3.  `Writer` -> `Revised Draft` (수정된 초안 생성)
    4.  `Reviewer` -> `Re-evaluate` -> `Score: 4.5/5` -> `PASS!`

*   **비유**: 기자가 편집장한테 혼나고(리뷰), 자리에 앉아서 "아, 통계 넣으라고 했지?" 하고 **수정본(Revised Draft)을 다시 제출**하는 과정. 편집장이 "오케이, 합격!" 할 때까지 이 **'작성 -> 검수 -> 수정 -> 재검수' 루프**가 **자동으로, 무한 반복(또는 설정된 횟수만큼) 돌게 됩니다.**

> **💡 개념 돋보기: '재시도(Retry) 메커니즘' = 에이전트의 '근성(Grit)'**
> 
> 일반 LLM(챗GPT 등)은 한 번 답을 뱉으면 끝입니다. 틀려도 모릅니다.
> 하지만 **에이전트 시스템엔 'while 루프(While Loop)'가 심어져 있습니다.**
> ```python
> # 의사 코드 (Pseudo-code)
> while not approved:
>     draft = writer.write(plan)
>     feedback = reviewer.check(draft)
>     if feedback.is_pass: break
>     plan = plan + feedback # 피드백을 다음 입력에 포함
> ```
> 이 **'실패를 피드백 삼아 다시 시도하는 루프'** 덕분에, 에이전트는 **'한 번에 완벽하게'가 아니라 '점진적으로 개선하며(Iterative Refinement)' 결과물의 퀄리티를 보장**합니다. 이게 바로 **'신뢰할 수 있는 AI 시스템'**의 핵심 아키텍처입니다.

---

## 5. 최종 결과물 탄생: "폴리싱된 블로그 포스트"

이 루프가 몇 번 돌고 나서(보통 1~3회), 체커가 **"PASS: Quality threshold met."** 로그를 띄우면, 오케스트레이터(메인 에이전트)가 최종 취합된 마크다운/HTML 텍스트를 화면 중앙 채팅창에 **짜잔~ 하고 뿌려줍니다.**

영상에서는 "And that's it. You've built and run your first AI agent with Google's ADK."라며 마무리하지만, **우린 방금 '생각하고-쓰고-고치는' 자율 협업 시스템이 돌아가는 전 과정을 CCTV로 생중계 본 겁니다.**

## 6. 마무리하며: 이제 당신은 '에이전트 아키텍트'입니다.

이 영상 튜토리얼을 통해 우리가 겪은 여정을 정리해 보세요.

1.  **개념 이해**: "에이전트가 뭐야? 툴 쓰고, 계획 세우고, 기억하는 애잖아."
2.  **코드 구현**: `Agent` 클래스 만들고, `FunctionTool` 달고, `SequentialAgent`/`ParallelAgent`로 엮고, `Output Schema`로 출력 형식 강제하고.
3.  **실행 및 관찰**: `adk web`으로 띄우고, **플래닝 -> 작성 -> 검증 -> 재시도** 전 과정을 **트레이스 로그로 투명하게 확인**.

단순히 "블로그 글 하나 뽑았네"가 아닙니다. **'계획-실행-검증-개선'이라는 인간의 고차원적 업무 프로세스를, 코드 몇 백 줄로 '소프트웨어화'해서 자동화시켰다**는 게 핵심입니다.

> **💡 마지막 개념 돋보기: 이번 실습의 진짜 배움 (Takeaway)**
> 
> 1.  **분업(Decomposition)**: 큰일(블로그 작성)을 작은 단위(섹션 작성)로 쪼개서 서브 에이전트에게 위임했다.
> 2.  **계약(Contract)**: `Pydantic` 모델(Output Schema)로 "넌 이런 모양으로만 내놔"라고 **인터페이스를 강제**해서 에이전트 간 소통 오류를 원천 차단했다.
> 3.  **자기 수정(Self-Correction)**: `Reviewer` + `Retry Loop` 구조로 **"한 방에 완벽"이 아니라 "틀려도 고치면 돼"**라는 **회복 탄력성(Resilience)**을 시스템에 심었다.
> 4.  **관찰 가능성(Observability)**: `adk web` 덕분에 이 모든 과정이 **블랙박스가 아닌 글래스박스**로 열려 있다. (디버깅/개선 가능)
> 
> 이 4가지(**분업, 계약, 자기수정, 관찰**)만 챙겨도, 앞으로 어떤 복잡한 에이전트 시스템을 보더라도 **"아, 저긴 플래너네, 저긴 툴 호출이네, 저긴 리트라이 루프 도네"** 하며 구조를 꿰뚫어 볼 수 있게 됩니다.

**MCP(Model Context Protocol)**는 이 **'외부 서비스들을 에이전트가 쓸 수 있는 표준 툴 상자'로 포장해주는 통신 규약**입니다. 다음 챕터에서는 우리 에이전트에게 **"야, 이제 내 구글 캘린더 좀 봐줘", "슬랙으로 팀장님한테 보고 좀 해줘"** 같은 **현실 세계의 손발(액션)**을 달아주는 방법을 배울 겁니다.
