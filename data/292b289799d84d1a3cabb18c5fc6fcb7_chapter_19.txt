# 📚 챕터 3. 출력 키(Output Key) 설정: 공유 상태(Shared State) `'blog_outline'`에 저장하여 다음 에이전트와 데이터 연계

자, 지난 시간에는 우리 블로그 자동화 공장의 **첫 번째 일꾼, '블로그 플래너(BlogPlanner)'**를 채용했습니다. 이 친구의 임무는 사용자가 던져준 **'주제(Topic)'**를 받아서, 글을 쓰기 좋은 **'구조화된 개요(Outline)'**로 다듬는 것이었죠. 

그런데 여러분, 여기서 잠깐 멈춰서 생각해 볼 게 있습니다. **플래너가 열심히 개요를 짜놨는데, 이걸 누가 받아서 글을 쓸까요?** 바로 다음 순서인 '블로그 라이터(Writer)' 에이전트입니다. 그런데 이 두 에이전트는 서로 다른 방에서 일하는 별개의 인격체입니다. 플래너가 "자, 개요 다 짰어!"라고 외쳐도, 라이터가 그 종이를 받지 못하면 아무 소용이 없겠죠?

이번 챕터에서는 **플래너가 만든 소중한 결과물(개요)을 어떻게 라이터에게 안전하게 전달할 것인가?** 바로 그 **'데이터 전달의 다리'**를 놓는 기술, **`output_key` (출력 키)**와 **공유 상태(Shared State, 세션 상태)**에 대해 아주 자세히 파헤쳐 보겠습니다.

---

## 1. 🤔 왜 '출력 키'가 필요할까? – "비서에게 메모지를 건네주는 법"

> **💡 개념 돋보기: 에이전트 간의 벽, 그리고 '세션 상태(Session State)'라는 칠판**
> 
> ADK에서 각 에이전트(플래너, 라이터, 리뷰어 등)는 기본적으로 **독립적인 작업자**입니다. 마치 **각자 칸막이가 쳐진 독서실 책상**에 앉아 있는 것과 같아요. 플래너가 책상에서 개요를 다 적었다고 해도, 라이터 책상에는 자동으로 나타나지 않습니다.
> 
> 그래서 ADK는 **'공용 칠판(Shared State / Session State)'**이라는 공간을 제공합니다. 이건 **대화 세션(Session) 동안 살아있는 공유 메모장** 같은 겁니다. 누구나 여기에 적고, 누구나 읽을 수 있죠.
> 
> **`output_key`**는 바로 **"이 작업자가 일을 끝내고 나서, 결과물을 공용 칠판의 '몇 번 칸(어떤 키 이름)'에 적어놔라"**라고 지시하는 **이름표(라벨)**입니다.

### 일상 비유: 🍳 주방장의 레시피 카드와 공용 냉장고

상상해 보세요. 우리가 만드는 건 **'블로그 글 작성 레스토랑'**입니다.

1.  **헤드 셰프 (Planner Agent):** 손님이 주문한 '주제'를 보고, 오늘의 특선 요리(블로그 글)의 **레시피(개요/Outline)**를 짭니다.
2.  **조리 담당 (Writer Agent):** 레시피를 보고 실제 요리(본문 작성)를 해야 합니다.
3.  **공용 냉장고 (Shared State / Session State):** 주방 중앙에 있는 큰 냉장고입니다. 여긴 헤드 셰프도, 조리 담당도, 나중에 플레이팅 담당(Reviewer)도 모두 드나들 수 있습니다.

**문제 상황:** 헤드 셰프가 레시피 종이를 **자기 주머니에 넣고 끝내버리면?** 조리 담당은 "레시피가 어디 있어요?" 하며 요리를 못 합니다.

**`output_key` 해결책:** 헤드 셰프에게 **"다 만든 레시피는 공용 냉장고 선반 위 `blog_outline` 이라고 적힌 전용 바구니에 넣어두세요"**라고 규칙을 정해주는 겁니다. 그러면 조리 담당은 **"아, `blog_outline` 바구니만 열면 되네?"** 하고 바로 레시피를 꺼내 씁니다.

이게 바로 **`output_key="blog_outline"`** 한 줄의 마법입니다.

## 2. 🛠️ 코드 속으로: `LlmAgent` 생성자에서 `output_key` 지정하기

지난 챕터에서 우리는 `agent.py` 파일에 `BlogPlanner`를 만들기 위해 `LlmAgent`를 import 하고 인스턴스를 생성하기 직전까지 갔습니다. 이제 그 생성자 안에 **마법의 한 줄**을 추가할 차례입니다.

```python
# agent.py (계속 작성 중...)

from google.adk.agents import LlmAgent
# ... (이전 import들)

# 1. 블로그 플래너 에이전트 정의
blog_planner = LlmAgent(
    name="BlogPlanner",           # 에이전트 이름표
    model="gemini-2.0-flash",     # 사용할 두뇌(모델)
    instruction="""               # 업무 지시서 (프롬프트)
        당신은 전문 블로그 기획자입니다.
        사용자가 제공한 '주제(topic)'를 분석하여,
        블로그 글 작성을 위한 논리적인 구조의 개요(Outline)를 작성하세요.
        개요에는 제목 후보, 도입부, 본문 소제목별 핵심 내용, 마무리 구성 등이 포함되어야 합니다.
        마크다운 형식으로 깔끔하게 출력하세요.
    """,
    # 👇👇👇 바로 여기가 핵심! 출력 키 설정 👇👇👇
    output_key="blog_outline"     
)
```

### 한 줄 한 줄, 친절 해설

#### `output_key="blog_outline"` 이 한 줄이 하는 일

이 코드가 실행되어 `BlogPlanner`가 임무를 완수하면(즉, LLM이 개요 생성을 마치고 최종 답변을 내뱉으면), ADK 런타임(Runner)은 자동으로 다음과 같은 일을 **보이지 않는 백스테이지에서** 수행합니다.

1.  **결과물 가로채기:** 플래너가 뱉은 마지막 메시지(텍스트)를 낚아챕니다.
2.  **상태 저장소 접근:** 현재 실행 중인 **세션(Session)**의 `state` 딕셔너리(사전)에 접근합니다. (`session.state`)
3.  **키-값 저장:** `session.state["blog_outline"] = "플래너가 생성한 개요 텍스트 전체"` 라는 코드를 실행한 것과 똑같이 저장합니다.

> **💡 개념 돋보기: `session.state`는 파이썬 딕셔너리(dict)다!**
> 
> 혹시 파이썬의 `dict`(사전) 자료형을 아시나요? `{"키": "값"}` 형태로 데이터를 저장하는 그거요.
> ADK의 **Shared State(공유 상태/세션 상태)**는 정확히 **파이썬 딕셔너리**와 똑같이 생겼고, 똑같이 동작합니다.
> 
> *   **저장:** `state["blog_outline"] = "개요 내용..."`
> *   **조회:** `outline = state["blog_outline"]`
> *   **삭제/수정:** `del state["blog_outline"]` 또는 `state["blog_outline"] = "수정된 내용"`
> 
> 이 `state` 객체는 **대화 세션이 살아있는 동안** 메모리(RAM)에 유지됩니다. 사용자가 브라우저를 끄거나 세션이 타임아웃되면 사라지지만, 에이전트들이 주고받는 동안에는 **영구적인 공용 창고** 역할을 합니다.

## 3. 🔄 데이터 흐름의 전체 그림: 플래너 → (State) → 라이터

이제 `output_key`를 설정한 덕분에 데이터가 어떻게 흐르는지 **시퀀스 다이어그램**처럼 그려보며 확실히 이해합시다.

### Step 1. 사용자 입력 (User Input)
> **User:** "요즘 뜨는 '생성형 AI 생산성 도구'에 대해 블로그 글 써줘."
> → 이 메시지는 세션의 `user_content`로 들어옵니다.

### Step 2. 플래너 실행 (Planner Execution)
> **Runner**가 `BlogPlanner`를 호출합니다.
> 플래너는 `instruction`(지시사항)을 읽고, LLM(Gemini)에게 "주제: 생성형 AI 생산성 도구 -> 개요 짜줘"라고 요청합니다.
> LLM이 생각해서 개요 텍스트를 생성합니다.
> ```markdown
> # [개요] 생성형 AI 생산성 도구 완벽 가이드
> ## 1. 도입: 왜 지금 AI 도구인가?
> ## 2. 글쓰기 도구: Notion AI, ChatGPT, Claude 비교
> ## 3. 코딩 도구: GitHub Copilot, Cursor...
> ## 4. 마무리: 나만의 AI 워크플로우 만들기
> ```

### Step 3. 💥 `output_key` 마법 발동 (The Magic Moment)
> 플래너가 답변을 끝내자마자, ADK 프레임워크가 개입합니다.
> ```python
> # 내부적으로 이런 일이 자동으로 일어납니다.
> session.state["blog_outline"] = """# [개요] 생성형 AI 생산성 도구 완벽 가이드
> ## 1. 도입: 왜 지금 AI 도구인가?
> ## 2. 글쓰기 도구: Notion AI, ChatGPT, Claude 비교
> ## 3. 코딩 도구: GitHub Copilot, Cursor...
> ## 4. 마무리: 나만의 AI 워크플로우 만들기"""
> ```
> **이제 공용 칠판(State)에 `blog_outline`이라는 키로 개요가 저장되었습니다!** 플래너는 자기 할 일 다 하고 퇴근해도 됩니다.

### Step 4. 라이터 실행 (Writer Execution - 다음 에이전트)
> 이제 **순차 파이프라인(Sequential Pipeline)**이나 **루프 에이전트**에 의해 다음 차례인 `BlogWriter`가 호출됩니다.
> `BlogWriter`의 `instruction`(지시서)에는 이렇게 적혀 있습니다.
> > *"당신은 블로그 작가입니다. **세션 상태(state)의 `blog_outline` 키에 저장된 개요**를 읽고, 그에 맞춰 본문을 작성하세요."*
> 
> 라이터는 실행되자마자:
> ```python
> # 라이터 내부 로직 (또는 프롬프트 주입 시)
> my_outline = session.state.get("blog_outline") 
> # -> 위에서 저장한 그 개요 텍스트가 쏙 들어와 있습니다!
> ```
> 라이터는 개요를 **읽고** 바로 본문 작성을 시작합니다.

## 4. ⚠️ 초보자가 자주 하는 실수 & 꿀팁 (Best Practices)

### 실수 1: `output_key` 이름을 오타 내거나, 중복 사용하기
*   **상황:** 플래너는 `output_key="blog_outline"`로 저장했는데, 라이터 프롬프트에는 `state["blog_outlines"]`(s붙임)나 `state["outline"]`로 적음.
*   **결과:** `KeyError` 나거나 `None` 값이 들어와 라이터가 "개요가 없어요ㅠㅠ" 하며 헛소리(할루시네이션) 함.
*   **해결:** **이름은 무조건 통일!** 변수명 짓듯 신중하게, 그리고 `constants.py` 같은 데 상수로 빼서 관리하는 습관 들이기.

### 실수 2: 상태(State)가 이전 대화 턴의 찌꺼기로 더러워져 있는 경우
*   **상황:** 사용자가 두 번째 요청("이번엔 '강아지 산책' 글로 써줘")을 보냈는데, 세션이 그대로라 `state["blog_outline"]`에 **이전 글('AI 도구') 개요**가 그대로 남아있음.
*   **결과:** 플래너가 새 개요를 짜서 덮어쓰기 전, 라이터가 잠깐 옛 개요를 읽고 쓸 수 있음(경합 조건).
*   **해결:** 
    1.  플래너가 실행될 때 **무조건 새로 덮어쓰기** 하므로 보통 괜찮지만, 
    2.  확실하게 하려면 파이프라인 시작 전 `session.state.clear()` 또는 `del session.state["blog_outline"]`로 초기화하는 **'초기화 에이전트'**를 맨 앞에 두거나, `Callback`(`before_agent_callback`)에서 정리해주기.

### 꿀팁: `output_key` 없이 수동으로 상태 저장하기 (고급)
가끔 LLM 최종 답변이 아닌, **중간 계산 결과(JSON 파싱 등)**를 저장하고 싶을 때가 있습니다. 그때는 `output_key` 대신 **콜백(Callback)**이나 **도구(Tool)** 안에서 직접 `callback_context.state["my_key"] = value` 코드를 때려박습니다. 하지만 **플래너처럼 '최종 답변 자체가 결과물'인 경우는 `output_key`가 가장 깔끔하고 표준적**입니다.

## 5. 🧪 직접 해보기: 내 머릿속 시뮬레이션 돌리기

이제 `agent.py`에 코드를 다 치셨다고 칩시다. 터미널에서 `adk run` 혹은 `adk web`을 켜고 테스트해 볼 차례입니다.

1.  **입력:** `"파이썬 초보자를 위한 리스트 컴프리헨션 가이드"`
2.  **플래너 동작 중...** (콘솔에 로그 찍힘: `Running BlogPlanner...`)
3.  **플래너 완료:** 콘솔에 개요가 출력됨.
4.  **보이지 않는 곳:** `session.state["blog_outline"]`에 방금 그 개요가 저장됨. (디버거로 `session.state` 찍어보면 보임!)
5.  **라이터 동작 중...** (`Running BlogWriter...`)
6.  **라이터 완성:** 개요를 바탕으로 본문 작성 완료!

**💡 확인 포인트:** 만약 라이터가 쓴 글이 **"리스트 컴프리헨션"**이 아니라 **"파이썬 기초 문법"** 같은 엉뚱한 소리를 한다면? → **`output_key` 이름 불일치**거나 **프롬프트에서 state 읽는 법을 잘못 적음**을 의심하세요.

## 6. 📝 요약하며 다음 단계로

이번 챕터에서 우리는 **독립적인 에이전트들을 '팀'으로 엮어주는 접착제**, 바로 **`output_key`와 Shared State(세션 상태)**의 원리를 배웠습니다.

*   **`output_key="blog_outline"`** : 플래너의 결과물에 **"이름표"**를 붙여 **공용 창고(State)**에 보관하라는 명령.
*   **Shared State (`session.state`)** : 세션 동안 살아있는 **파이썬 딕셔너리 형태의 공용 메모장**.
*   **데이터 흐름:** `Planner` -> (자동 저장: `state["blog_outline"]`) -> `Writer` -> (자동 읽기: `state["blog_outline"]`)

이제 플래너가 개요를 `blog_outline`이라는 키로 공용 창고에 잘 넣어두었습니다. **다음 챕터에서는 이 창고에서 개요를 꺼내 읽고, 맛깔나는 본문을 써내려갈 '블로그 라이터(Writer) 에이전트'를 만들어 볼 차례입니다.** 라이터의 `instruction`(프롬프트) 안에서 `{{state.blog_outline}}` 같은 템플릿 문법을 써서 어떻게 상태 값을 주입하는지도 배울 거예요.

자, `agent.py` 파일을 닫지 마시고 그대로 두세요. 바로 이어서 **라이터 에이전트 코드**를 덧붙여 나갈 겁니다! 🚀
