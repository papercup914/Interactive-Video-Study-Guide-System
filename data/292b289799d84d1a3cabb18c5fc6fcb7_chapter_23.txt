# 📝 챕터 4. 출력 규칙 정의: 통과 시 "okay", 실패 시 "retry" 및 사유 반환

안녕하세요! 지난 시간에는 우리 에이전트 팀의 '첫 번째 주자'인 **'블로그 플래너(Blog Planner)'**를 채용하고, 이 친구가 **어떤 도구(모델)를 쓸지, 어떤 역할을 맡을지** 정해주는 시간(이름, 모델, 설명 설정)을 가졌습니다. 마치 신입 사원에게 "너는 기획팀이야, 너의 도구는 이 노트북이야, 네 임무는 기획안 쓰는 거야"라고 명함을 건네주는 과정이었죠.

자, 이제 명함도 줬고, 자리도 마련해줬습니다. 그럼 **"일해라!"** 하고 시키면 될까요? 안타깝게도 우리 에이전트 친구는 **'눈치'가 없습니다.** 그냥 "기획안 써"라고만 하면, 어떤 사람은 한 줄짜리 메모를 가져오고, 어떤 사람은 소설책을 써 오고, 어떤 사람은 엑셀 표로 만들어 올 수도 있습니다. 

그래서 **이번 챕터**가 정말정말 중요합니다. **"결과물을 이렇게, 정확히, 이 모양으로 내놔!"** 라고 **출력 규칙(Output Rule)을 칼같이 정해주는 작업**입니다. 이 규칙이 있어야만, 나중에 "이건 통과(okay)야" 혹은 "다시 해와(retry), 이유는 말이야..."라고 기계적으로 판단할 수 있는 기준이 생기거든요.

영상 속 강사님이 **"The important part of the introduction is, here we actually tell it what to produce..."(소개의 중요한 부분은, 여기서 실제로 무엇을 만들어내라고 시키느냐입니다...)**라고 강조하신 바로 그 부분! 지금부터 그 '출력 규칙 정의서'를 어떻게 작성하는지, 비전공자 눈높이에서 아주 낱낱이 파헤쳐 드리겠습니다.

## 1. 🍽️ 비유로 이해하기: "주문서 없는 주방" vs "레시피가 있는 주방"

상상해 보세요. 여러분이 **고급 레스토랑의 주방장(에이전트)**이라고 해볼까요?

*   **규칙이 없을 때 (프롬프트에 출력 형식 미지정):**
    손님(사용자)이 "맛있는 거 좀 줘"라고만 했습니다. 주방장 마음대로 **김치찌개**를 끓여 내놓을 수도 있고, **스테이크**를 구워 내놓을 수도 있고, 그냥 **라면**을 끓여 내놓을 수도 있습니다. 손님은 "난 스테이크 원했는데 왜 김치찌개야?"라고 화내겠죠. 이게 바로 **'출력 규칙 없는 에이전트'**의 비극입니다.

*   **규칙이 있을 때 (영상처럼 상세 지정):**
    손님이 **아주 구체적인 주문서(Instruction/Description)**를 내밀었습니다.
    > **"메인: 미디엄 레어 스테이크 200g, 사이드: 아스파라거스 구이 & 매시드 포테이토, 소스: 레드와인 소스, 플레이팅: 사각 접시 중앙 정렬, 온도: 60도 유지"**

    이제 주방장은 고민할 필요 없습니다. 그냥 **주문서대로만 만들면 됩니다.** 완성된 접시가 주문서와 100% 일치하면? **"Okay! 서빙해!" (통과)**. 스테이크가 탔거나, 아스파라거스가 없거나, 접시가 둥근 거라면? **"Retry! 다시 구워와! 이유: 굽기 정도 미달 / 사이드 누락 / 접시 규격 불일치" (실패 및 사유 반환)**.

**영상 속 'Blog Planner' 에이전트에게 우리가 준 '주문서'가 바로 이겁니다.**
> *"Markdown 형식의 아웃라인을 써줘. 제목(Title) 있어야 하고, 짧은 소개(Introduction) 있어야 하고, 본문은 4~6개 섹션(Sections)으로 나눠서 불릿 포인트(Bullet points)로 쓰고, 마지막에 결론(Conclusion) 꼭 넣어줘."*

이게 바로 **'통과(Okay)의 기준'**이자 **'실패(Retry)의 근거'**가 되는 **출력 규칙**입니다.

## 2. 🛠️ 실전 코드 분석: `Blog Planner`의 출력 규칙 심기

영상 스크립트를 보면 강사님이 `agent.py` 파일을 만들면서 `BlogPlanner` 에이전트를 정의하는 부분이 나옵니다. 여기서 **`instruction`(지시사항) 인자** 또는 **`description`(설명) 인자** 안에 이 규칙을 심어주는 모습이 보입니다. (코드상으로는 보통 `instruction` 파라미터에 긴 문자열로 넣거나, 별도의 프롬프트 템플릿으로 분리해서 넣습니다.)

가상의 코드 구조로 어떻게 생겼는지 들여다볼까요? (영상 내용을 바탕으로 재구성했습니다.)

```python
# agent.py 내부 - BlogPlanner 에이전트 정의 부분

from google.adk.agents import LlmAgent # 필요한 라이브러리 임포트

# 1. 블로그 플래너 에이전트 생성
blog_planner = LlmAgent(
    name="BlogPlanner",                    # 이름표 (식별용)
    model="gemini-1.5-pro",                # 사용할 뇌 (환경변수에서 가져옴)
    description="주제를 받아 구조화된 블로그 아웃라인을 작성하는 기획자", # 사람 읽기용 설명
    
    # 👇👇👇 여기가 핵심! '출력 규칙(주문서)'을 정의하는 instruction 부분 👇👇👇
    instruction="""
    당신은 전문 블로그 기획자입니다. 사용자가 준 '주제'를 받아 
    **반드시 아래의 엄격한 Markdown 형식**으로만 아웃라인을 작성하세요.
    
    [출력 필수 규칙 - 이 형식을 벗어나면 실패처리 됩니다]
    1. 최상단에 **# 제목 (Title)** 을 작성하세요.
    2. 제목 바로 아래에 **## 서론 (Introduction)** 섹션을 두고 2~3문장으로 주제를 소개하세요.
    3. **## 본론 (Body)** 섹션을 만들고, 그 아래에 **4개 이상 6개 이하**의 
       **### 세부 섹션(Section 1 ~ Section N)**을 만드세요.
    4. 각 세부 섹션 안에는 **최소 3개 이상의 불릿 포인트(- 또는 *)**로 핵심 내용을 채우세요.
    5. 맨 마지막에 **## 결론 (Conclusion)** 섹션을 두고 요약 및 마무리 멘트를 쓰세요.
    6. **절대 다른 텍스트(인사말, 설명, 코드 블록 표시 등)를 덧붙이지 마세요. 순수 Markdown 텍스트만 출력하세요.**
    """,
    
    # 👇👇👇 출력물 저장소 라벨 붙이기 (다음 챕터에서 자세히 다룹니다) 👇👇👇
    output_key="blog_outline" 
)
```

### 🔍 코드 속 규칙들의 의미 (비유 포함)

| 코드 속 규칙 | 일상 비유 | 왜 중요한가? (Okay/Retry 판단 기준) |
| :--- | :--- | :--- |
| **`# 제목` 필수** | 책 표지에 **책 제목** 없으면 책 아님. | 제목 없으면 **Retry** (이유: "최상위 헤더 누락") |
| **`## 서론` 2~3문장** | 면접 볼 때 **자기소개 1분** 정해져 있음. | 너무 길거나 없으면 **Retry** (이유: "서론 길이/형식 위반") |
| **본론 4~6개 섹션** | 건축 허가: **방 개수 4~6개**로 지으라고 함. | 3개면 **Retry** (이유: "최소 섹션 수 미달"), 7개면 **Retry** (이유: "최대 섹션 수 초과") |
| **불릿 포인트 필수** | 쇼핑 리스트에 **품목 없이 카테고리만** 적혀 있음. | 내용이 빈 껍데기면 **Retry** (이유: "세부 콘텐츠 불릿 포인트 없음") |
| **`## 결론` 필수** | 영화 보고 **엔딩 크레딧 없이** 불 켜짐. | 마무리가 없으면 **Retry** (이유: "결론 섹션 누락") |
| **Markdown 순수 텍스트만** | 제출 서류에 **낙서, 포스트잇, 클립** 붙여서 냈음. | 파싱(자동 읽기) 에러 나니 **Retry** (이유: "출력 포맷 오염 - 여분 텍스트 포함") |

> **💡 개념 돋보기: 왜 이렇게 까다롭게 정하나요? (구조화 출력의 힘)**
> 
> "그냥 '알아서 잘 써줘' 하면 안 되나요?" 라고 물으실 수 있습니다.
> LLM(거대 언어 모델)은 **'확률적으로 다음 단어를 예측하는 기계'**입니다. 규칙이 없으면 **'창의적(=랜덤)인 글'**을 씁니다. 
> 하지만 우리는 이 출력물을 **다음 에이전트(블로그 라이터)가 자동으로 받아서 글을 쓸 '데이터(원료)'**로 써야 합니다. 
> 다음 에이전트 입장에선 **"제목은 `state['blog_outline']`에서 `# `으로 시작하는 줄 찾아서 쓰고, 본문은 `### `으로 시작하는 섹션들 돌면서 쓰면 되겠네?"** 라고 **코드로 파싱(Parsing, 분석) 로직을 짜놔야 합니다.**
> 
> 만약 플래너가 어느 날 기분 좋아서 제목을 `## 제목` (샵 두 개)로 쓰거나, 본문 섹션을 `**섹션 1**` (볼드체)로 쓰면? **다음 에이전트 코드는 다 깨집니다.** (에러 나거나 엉뚱한 글 씀)
> 
> 그래서 **"출력 규칙 = 다음 단계 자동화를 위한 인터페이스 계약서"**입니다. 이 계약서(규칙)를 지키면 **Okay(통과)**, 어기면 **Retry(재시도)**시키는 검증 장치가 반드시 뒤에 따라붙어야 합니다.

## 3. ⚙️ "Okay"와 "Retry"는 누가 판단하나요? (검증 로직의 위치)

영상 스크립트에는 `output_key="blog_outline"`이라고만 나와 있지만, **"규칙을 어겼을 때 Retry 시키는 로직"**은 보통 다음 세 가지 레벨에서 구현됩니다. 비전공자분들은 이 구분을 아셔야 나중에 코드 짜실 때 헤매지 않습니다.

### 레벨 1: 프롬프트 레벨 (가장 약함, 하지만 가장 먼저)
*   **방법:** `instruction`에 *"규칙 어기면 다시 해라"*라고 적어두는 것.
*   **비유:** 직원에게 **"실수하면 혼날 줄 알아라"**라고 경고만 하는 것.
*   **한계:** LLM은 가끔 경고를 무시하고 실수합니다. (환각/할루시네이션)

### 레벨 2: 코드 레벨 - 출력 파싱 & 검증 (가장 표준적, 강력함) ⭐⭐⭐
*   **방법:** 에이전트가 토해낸 텍스트를 **파이썬 코드로 받아서(파싱), 정규식(Regex)이나 마크다운 파서로 구조를 검사**하는 함수(`callback` 또는 `after_model_callback` 등)를 달아둠.
*   **로직 예시 (의사코드):**
    ```python
    def validate_outline(output_text: str) -> dict:
        # 1. 제목 있나? (# 으로 시작하는 줄)
        if not re.search(r'^#\s.+', output_text, re.MULTILINE):
            return {"status": "retry", "reason": "제목(Header 1) 없음"}

        # 2. 섹션 개수 4~6개인가? (### 로 시작하는 줄 개수 세기)
        sections = re.findall(r'^###\s.+', output_text, re.MULTILINE)
        if not (4 <= len(sections) <= 6):
            return {"status": "retry", "reason": f"본문 섹션 수 오류: {len(sections)}개 (기준 4~6개)"}

        # 3. 결론 있나?
        if not re.search(r'^##\s*결론', output_text, re.MULTILINE):
            return {"status": "retry", "reason": "결론 섹션 없음"}

        # 모두 통과!
        return {"status": "okay", "data": output_text}
    ```
*   **비유:** **'품질 검사(QC) 직원'**이 완제품을 들고 와서 체크리스트(규칙)에 대조해 보는 것. 불량이면 **"불량 사유 적어서 재작업 지시서(Retry + Reason)"**를 생산 라인에 다시 꽂아 넣음.

### 레벨 3: 프레임워크 내장 기능 (ADK 등 최신 프레임워크)
*   **방법:** `output_schema` (Pydantic 모델 등)를 정의해서 **LLM이 애초에 JSON/구조화 객체로 뱉게 강제**하거나, 프레임워크 차원에서 `output_key`에 저장하기 전 검증 훅(Hook)을 제공하는 경우.
*   **비유:** **'자동화된 광학 검사기(AOI)'**가 컨베이어 벨트 위 제품 레이저로 스캔해서 불량 자동 선별.

> **💡 개념 돋보기: "사유 반환(Reason Return)"이 왜 생명이죠?**
> 
> 그냥 `"retry"`만 던지면 안 됩니다. **`"retry", "reason: 섹션 수 3개로 부족함"`** 이렇게 **구체적인 사유**가 붙어 있어야 합니다.
> 
> 왜냐구요? **에이전트(LLM)는 자신이 뭘 잘못했는지 모릅니다.** 그냥 확률적으로 단어 나열한 거예요.
> 우리가 **"야, 너 방금 섹션 3개만 썼어. 4개 이상 써야 해. 이유: 섹션 수 미달"**이라고 **피드백(사유)을 줘야**, 에이전트가 **"아! 내가 섹션 수를 덜 채웠구나? 그럼 하나 더 추가해서 다시 쓸게!"** 하고 **수정된 결과물**을 내놓을 수 있습니다.
> 
> 이 **'실패 -> 사유 전달 -> 재시도 -> 성공'** 루프를 **'자기 수정(Self-Correction) 루프'** 혹은 **'ReAct(Reasoning + Acting) 패턴'**이라고 부릅니다. 이 루프가 없으면 에이전트는 영원히 똑같은 실수를 반복하는 '고장 난 로봇'이 됩니다.

## 4. 🧩 영상 속 `output_key="blog_outline"`의 숨은 의미: "합격 도장 찍힌 것만 창고에 넣어라"

강사님이 **`output_key="blog_outline"`**이라고 설정한 부분을 보셨죠? 
> *"This means whatever this agent writes will be stored in shared state under that name..."* (이 에이전트가 쓴 건 뭐든 공유 상태(Shared State) 아래 그 이름으로 저장된다는 뜻...)

여기서 **중요한 전제**가 하나 있습니다. **"검증(Validation)을 통과한 결과물만 저장된다"**는 겁니다. (혹은 저장이 된 후, 다음 에이전트가 읽기 전에 검증해서 실패하면 예외를 터뜨리거나 상태를 롤백시킵니다.)

상상해 보세요. **'공용 창고(Shared State / Session State)'**가 있습니다.
*   **Blog Planner**가 일해서 결과물을 들고 옵니다.
*   **검사관(Validation Logic)**이 규칙서(Instruction)를 들고 체크합니다.
*   **통과 (Okay):** 검사관이 **"합격 도장(Okay)"** 찍고 창고 선반 `blog_outline` 칸에 넣어줍니다. 👉 **다음 에이전트(Blog Writer)는 안심하고 `blog_outline` 칸에서 재료 꺼내 씀.**
*   **실패 (Retry):** 검사관이 **"불합격 판정서(Retry + Reason)"**를 들고 플래너에게 되돌려보냅니다. 창고에는 **아무것도 안 넣음(또는 임시 보관 후 폐기).** 👉 **다음 에이전트는 실행조차 안 됨(또는 대기).**

이게 바로 **`output_key`가 가지는 책임감**입니다. "이 키로 저장된 건 **검증 완료된 깨끗한 데이터**다"라는 **신뢰의 보증수표**인 셈입니다.

> **✅ 에이전트 출력 규칙 정의 체크리스트 (초보자를 위한 실전 가이드)**

## 6. 🚀 다음 챕터 예고: "자, 합격된 아웃라인(`blog_outline`)을 들고 다음 주자 '블로그 라이터'에게 넘겨줘야 하는데... 어떻게 넘기나요?"

이제 **Blog Planner**는 **"Okay"** 도장을 받고 **`blog_outline`**이라는 이름표를 달고 **공용 창고(Shared State/Session State)**에 얌전히 앉아 있습니다. 

다음 챕터에서는 **"상태(State)라는 공용 창고 시스템을 어떻게 쓰고, 다음 에이전트(Blog Writer)는 이 창고에서 재료를 어떻게 꺼내 쓰는가?"** 즉, **에이전트 간 데이터 전달(State Management & Data Flow)**의 마법을 배워보겠습니다. 

"이전 에이전트가 쓴 글을 다음 에이전트가 어떻게 읽지? 복사 붙여넣기 하나?" 궁금하시죠? **절대 복사 붙여넣기 아닙니다.** 우아한 **'상태 기반 자동 전달'**의 세계로 여러분을 초대합니다. 다음 챕터에서 만나요! 👋
