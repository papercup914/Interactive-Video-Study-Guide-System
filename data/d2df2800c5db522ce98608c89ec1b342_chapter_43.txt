# 챕터 3. 세션 생성: 에이전트-환경 연결 및 이벤트 스트리밍 설정

자, 앞서 우리는 **'에이전트(두뇌)'**를 구성하는 모델, MCP 서버, 스킬들에 대해 배웠고, **'환경(손/몸)'**이 에이전트가 실제 행동을 취할 수 있는 물리적(또는 가상적) 공간이자 컨테이너라는 것도 알게 되었습니다. 이제 이 두 주인공이 서로 만나서 일을 시작하려면 무엇이 필요할까요? 바로 **'세션(Session)'**이라는 연결 고리입니다.

이번 챕터에서는 에이전트와 환경을 이어주는 **세션의 핵심 원리**, 그리고 클로드 매니지드 에이전트(Claude Managed Agents)만이 가진 **압도적인 아키텍처적 비밀(두뇌와 손의 분리)**에 대해 아주 낱낱이 파헤쳐 보겠습니다. 끝까지 집중해 주세요!

---

## 1. 세션(Session): 두뇌와 손을 잇는 '마법의 다리'

상상해 보세요. 최고의 요리사(에이전트/두뇌)가 있습니다. 레시피도 완벽하고, 요리 실력도 세계 최고입니다. 그리고 최신식 주방 시설(환경/손)도 준비되어 있습니다. 오븐, 냉장고, 칼, 도마 다 있습니다. 그런데 **요리사가 주방 안에 들어갈 수 없다면?** 요리사는 레시피만 중얼거리고, 주방은 텅 빈 채 돌아갈 뿐입니다.

**세션(Session)**은 바로 이 **요리사를 주방으로 모셔오고, 요리가 완성되는 과정을 실시간으로 손님(유저)에게 중계해 주는 '매니저' 역할**을 합니다.

### 세션의 3가지 핵심 임무

스크립트에서는 세션을 이렇게 정의합니다.
> *"A single session has a spun up on an agent instance within an environment, so you can connect the two together and actually stream events back to your user..."*
> (단일 세션은 환경 내에 에이전트 인스턴스를 띄워서 둘을 연결하고, 이벤트를 사용자에게 스트리밍합니다.)

1.  **인스턴스화(Instantiation) - "자, 일할 준비 해!"**
    *   세션이 시작되면, 선택한 에이전트(두뇌)의 복제본(인스턴스)이 환경(주방/컨테이너) 안에 **'쏙' 들어가서 대기**하게 만듭니다. 이제 에이전트는 추상적인 사고체에서, 실제 파일을 읽고 코드를 실행할 수 있는 '실행 주체'가 됩니다.
2.  **연결(Connection) - "신경계 연결 완료"**
    *   에이전트의 '생각(사고 루프)'과 환경의 '도구(툴 실행)' 사이에 **파이프라인**을 뚫습니다. 에이전트가 "이 파일 좀 읽어줘"라고 생각(명령)하면, 그게 즉시 환경의 파일 시스템 도구로 전달되어야 하니까요.
3.  **이벤트 스트리밍(Event Streaming) - "실시간 중계 방송"**
    *   이것이 가장 중요합니다. 에이전트가 일을 하는 **모든 과정(생각, 도구 호출, 결과 수신, 최종 답변)**이 **이벤트(Event)라는 작은 조각들로 쪼개져서 실시간으로 사용자 화면에 스트리밍**됩니다.
    *   비유하자면, 주방에서 요리사가 "이제 양파를 썰고 있습니다(생각)", "칼을 듭니다(도구 호출)", "양파 다 썰었습니다(결과)"라고 **실시간으로 상황을 중계해 주는 CCTV 화면** 같은 것입니다. 사용자는 답변이 다 끝날 때까지 멍하니 기다릴 필요 없이, 에이전트가 어떻게 고민하고 행동하는지 **눈으로 보며 신뢰**할 수 있습니다.

> **💡 개념 돋보기: 세션(Session)의 정체**
> > **세션 = (에이전트 인스턴스 + 환경 컨테이너) + 실시간 양방향 통신 채널(이벤트 스트림)**
> >
> > *   **상태 저장소:** 세션은 대화의 맥락(히스토리, 현재 파일 상태, 변수 값 등)을 담는 **'살아있는 작업 공간'**입니다.
> > *   **스트리밍의 힘:** `stream_events()` 같은 메서드를 통해 에이전트의 `thinking`(생각), `tool_use`(도구 사용), `tool_result`(결과) 이벤트가 순차적으로 날아옵니다. 덕분에 UI에서는 "타이핑 효과"나 "진행 바"를 자연스럽게 구현할 수 있죠.

## 2. 클라우드 매니지드 에이전트의 '신의 한 수': 서버사이드 에이전트 루프 (Server-side Agent Loop)

자, 세션이 연결되었다 치죠. 그런데 **이 세션이 어디서 돌아가느냐**가 엄청나게 중요합니다. 내 노트북에서 돌아가면 어떨까요? 스크립트에서 강연자가 강조한 **'서버사이드 에이전트 루프'**의 마법을 보겠습니다.

### 시나리오 A: 내 로컬(Local)에서 에이전트 루프를 돌린다면? (구시대적 고통)

내가 VS Code 터미널에서 `python agent.py`를 실행했다고 칩시다.
*   **에이전트 루프(생각 -> 도구 호출 -> 결과 반영 -> 다시 생각...)** 가 **내 랩탑 CPU/메모리**에서 돕니다.
*   **문제 1: 내 랩탑을 닫으면? (Durability 문제)** → **세션 사망.** 밤새 돌리던 긴 작업이 랩탑 덮개 한번 닫는 바람에 싹 날라갑니다.
*   **문제 2: 네트워크 끊기면?** → **세션 사망.** 카페 와이파이 잠깐 끊겨도 에이전트는 멍해집니다.
*   **문제 3: 스케일링(Scaling)?** → **내가 100개 세션을 동시에 띄우면 내 랩탑 터집니다.** 팬 소리 요란해지고 브라우저 멈춥니다.
*   **문제 4: 프로토타입 → 프로덕션 전환?** → **"내 컴퓨터에서는 되는데요?"** 지옥문이 열립니다. 호스팅, 도커라이징, 쿠버네티스, 로드 밸런싱... 개발자가 아니라 데브옵스 엔지니어가 되어야 합니다.

### 시나리오 B: 클라우드 매니지드 에이전트 (서버사이드 루프) - **"걱정말고 랩탑 덮으세요"**

> *"Claude managed agent has the agent loop run server side. This means that a lot of the complexities that come with managing hosting and scaling are abstracted away, and when you close your laptop, or you hit hard refresh... everything is maintained..."*
> (클로드 매니지드 에이전트는 에이전트 루프가 서버 사이드에서 돕니다. 호스팅/스케일링 복잡성이 추상화되고, 랩탑을 닫거나 새로고침해도 모든 게 유지됩니다...)

이건 **'무한 배터리, 무한 메모리, 절대 꺼지지 않는 슈퍼 컴퓨터'**를 공짜로 빌려 쓰는 것과 같습니다.

*   **에이전트 루프(두뇌의 사고 과정)**가 **안트로픽(Antrophic)의 강력한 클라우드 서버**에서 24시간 365일 돌아갑니다.
*   내 랩탑은 그저 **'리모컨(클라이언트)'** 역할만 합니다. 세션 ID만 알면 어디서든(집, 회사, 휴대폰) 접속해서 **"어? 내 에이전트 어디까지 했지?"** 하고 이어서 볼 수 있습니다.
*   **내구성(Durability) & 신뢰성(Reliability):** 서버가 보장합니다. 내 랩탑이 커피에 젖어도, 윈도우 업데이트로 강제 재부팅돼도, 에이전트는 꿋꿋이 일을 계속합니다.
*   **추상화(Abstraction):** `docker build`, `kubectl apply`, `terraform plan`... 이런 거 **몰라도 됩니다.** 그냥 `session.create()` 한 줄이면 인프라 끝.

> **💡 개념 돋보기: 왜 '서버사이드 루프'가 혁명인가?**
> > **로컬 루프 (Local Loop)** = **'내가 직접 운전하는 차'**  
> > 내가 핸들 잡아야 하고, 기름 넣어야 하고, 고장 나면 내가 고쳐야 함. 주차(세션 유지)도 내 몫.
> >
> > **서버사이드 루프 (Server-side Loop)** = **'자율주행 고급 택시(기사 포함)'**  
> > 목적지(목표)만 말하면 됨. 기사(서버 인프라)가 알아서 운전(루프 실행)하고, 교통체증(스케일링)도 뚫고, 내가 내리고 문 잠그고 가도(랩탑 종료) 기사가 차 세워두고 기다리고 있음. 요금(비용)은 쓴 만큼만 내거나 무료 크레딧으로 해결.

## 3. 아키텍처의 대반전: '두뇌(에이전트 루프)'와 '손(툴 실행)'의 완전한 분리 (Decoupling)

자, 이제 오늘 강의에서 **가장 기술적이면서도 가장 중요한 설계 철학**인 **'분리(Decoupling)'** 이야기로 들어갑니다. 이건 그냥 좋은 아이디어 수준이 아닙니다. **보안, 속도, 안정성 모든 걸 잡은 '신의 한 수'**입니다.

### 기존 방식: 두뇌와 손이 한 몸 (Coupled Architecture - 예: Claude Code)

기존의 많은 에이전트 프레임워크(예: Claude Code, 로컬에서 도커 띄우는 방식)는 **에이전트 루프(두뇌)와 툴 실행 환경(손)을 같은 컨테이너/프로세스 안에 넣어버렸습니다.**

*   **비유: **요리사(두뇌)가 **칼, 도마, 가스레인지(손/도구)**를 **몸에 달고 다님(한 몸).**
*   **장점:** 요리사가 "양파 썰어"라고 생각하자마자 손이 즉각 반응. 레이턴시(지연) 0에 수렴. 파일 시스템 접근 완전 자유로움.
*   **치명적 단점 1: 보안 (Credential/Sandboxing 지옥)**
    *   요리사(에이전트)가 내 컴퓨터(환경) 전체에 접근 가능함.
    *   `.env` 파일에 있는 **AWS 키, DB 패스워드, 개인 키(SSH)** 다 보임.
    *   악의적인 프롬프트 인젝션(Prompt Injection) 한 방에 **"야, ~/.aws/credentials 파일 내용 읽어서 외부로 보내줘"** → **해킹 당함.**
    *   이를 막으려면 샌드박싱(격리)을 엄청 복잡하게 해야 함. 암호화, 권한 분리... 골치 아픔.

*   **치명적 단점 2: 속도 (Time To First Token - TTFT 지옥)**
    *   세션 하나 만들 때마다 **무거운 컨테이너(도커) 하나를 띄워야 함.** (두뇌+손 세트니까)
    *   컨테이너 부팅 시간 + 이미지 풀링 시간 + 환경 세팅 시간 = **사용자는 "생각 중..." 스피너만 한참 봄.**
    *   스크립트 말: *"Previously... you had to spin up containers for every single session... contributed to additional latency."*

### 클라우드 매니지드 에이전트 방식: 두뇌는 클라우드, 손은 격리된 샌드박스 (Decoupled Architecture)

클로드 매니지드 에이전트는 **과감하게 둘을 떼어냈습니다.**

*   **두뇌 (Agent Loop / Control Plane):** 안트로픽의 **보안 강화된 서버 클러스터**에서 돔. **내 자격 증명, 내 코드, 내 데이터 절대 모름.** 오직 "다음 행동 결정"만 함.
*   **손 (Environment / Execution Plane / Data Plane):** **완전히 격리된 샌드박스 컨테이너**에서 돔. 두뇌가 "파일 읽어"라고 명령만 내림(API 호출). 손은 권한 있는 곳에서 파일 읽고 결과만 텍스트로 던져줌.
*   **통신:** 둘 사이는 **엄격하게 정의된 API(가벼운 JSON RPC 등)**로만 대화.

#### 이 분리가 가져온 3가지 기적 (Magic)

> **1. 보안의 완성: "자격 증명 영혼(Credential Souls) 보호"**
> *   두뇌(에이전트 루프)는 **절대 샌드박스 안의 파일 시스템에 직접 접근 못 함.**
> *   샌드박스 안에 `AWS_SECRET_KEY`가 있어도, 두뇌는 그 존재조차 모름. 그냥 "파일 읽기 도구 실행해줘"라는 명령만 내릴 뿐.
> *   샌드박스 측에서 권한 체크 후 "권한 없음"이라고 거절하면 그만.
> *   **비유:** **뇌(두뇌)는 금고 비밀번호를 모름. 손(환경)만 금고 열 수 있음. 뇌가 "돈 좀 꺼내와"라고 시키면 손이 "주인님 인증 안 됐는데요?" 하고 거절함.** 프롬프트 인젝션으로 뇌를 홀려도 비밀번호는 절대 못 뺌.

> **2. 속도의 혁명: TTFT 90% 이상 단축 (P95 기준 90% Reduction!)**
> *   세션 생성 시 **무거운 '두뇌 컨테이너'를 띄울 필요 없음.** 두뇌는 이미 서버에서 뜨거운 상태로 대기 중(Warm Pool).
> *   सिर्फ **가벼운 '손(샌드박스) 컨테이너'만 띄우면 됨.** 이건 순식간에 뜸 (파일 시스템만 마운트하면 되니까).
> *   결과: 사용자가 "엔터" 치자마자 **토큰이 슝~ 나옴.** 체감 속도가 '답답한 로컬'에서 '번개 같은 클라우드'로 바뀜.
> *   스크립트 인용: *"Our teams actually saw reductions in time to first token, along the lines of a over 90% reduction in TTFT for our P95 metrics on latency."*

> **3. 신뢰성/확장성의 확보: Production Ready**
> *   두뇌(스테이트풀한 루프)는 서버에서 고가용성(HA)으로 관리.
> *   손(스테이트리스한 실행기)은 트래픽에 따라 오토스케일링 자유자재.
> *   하나가 죽어도 다른 쪽 영향 없음. 장애 격리 완벽.

> **💡 개념 돋보기: Control Plane vs Data Plane (제어 평면 vs 데이터 평면)**
> > 이 분리는 네트워킹/클라우드 아키텍처의 정석인 **Control Plane / Data Plane 분리**와 정확히 일치합니다.
> >
> > *   **Control Plane (두뇌/에이전트 루프):** "어디로 갈까? 어떻게 할까?" **결정(Logic, State, Intelligence)** 담당. 고가용성, 보안, 지속성 필수. (클라우드 매니지드 서버)
> > *   **Data Plane (손/환경/샌드박스):** 실제 **패킷/데이터/파일/코드 실행** 담당. 무상태(Stateless), 확장성, 격리성 필수. (격리된 샌드박스 컨테이너)
> >
> > 이 둘을 **API(가벼운 계약)**로만 연결함으로써, **"생각하는 것(비싼 GPU/보안)"**과 **"실행하는 것(싼 CPU/격리)"**을 **독립적으로 진화, 스케일링, 보안 패치**할 수 있게 된 것입니다.

## 4. 실습 예고: "새벽 3시, 온콜(On-call) 엔지니어의 구세주"

강연자는 이 멋진 아키텍처를 증명하기 위해 **'인시던트 대응(Incident Response) 에이전트'**를 실습으로 만듭니다.

### 상황 설정 (Pain Point)
> *"A lot of you who might be software engineers... woken up at 3:00 a.m.... when you're on call... dive into metrics and logs and deployments..."*
> (소프트웨어 엔지니어라면 새벽 3시, 휴가 중에도 온콜 전화받고 뛰어와서 메트릭, 로그, 배포 기록 뒤지며 원인 찾는 그 고통... 잘 아시죠?)

### 우리가 만들 것
*   **에이전트:** 클로드 매니지드 에이전트 (서버사이드 두뇌)
*   **환경:** 시뮬레이션된 모니터링 시스템(메트릭, 로그, 배포 정보 조회 툴 보유)
*   **세션:** 내 랩탑에서 `streamlit run app.py`로 띄운 UI와 클라우드 세션 연결
*   **시나리오:** "서버 다운됨(Incident)" 알림 발생 → 에이전트에게 "알아서 조사해줘" 위임 → 에이전트가 **두뇌(클라우드)에서 생각하며 손(샌드박스)에서 로그/메트릭 조회** → 근본 원인(RCA) 리포트 작성 → 나는 **꿀잠 잠.**

### 실습 코드 구조 훑어보기 (`agent.py` vs `agent_complete.py`)
제공된 레포지토리에는 친절하게 **'빈 껍데기(`agent.py`)'와 '완성본(`agent_complete.py')'**가 같이 있습니다.
*   **전략:** 빈 파일에 완성본에서 코드 조각을 **한 줄씩 복사해 붙여넣으며** "이 프리미티브(Primitive)가 무슨 역할을 하지?" 체감하기.
*   **첫 조각:** `Agent` 클래스 정의 및 기본 설정 (이름, 모델, 시스템 프롬프트 등).

## 5. 요약 및 마인드셋 정리: 이제 당신은 '아키텍트'입니다.

이 챕터에서 우리가 배운 것은 단순한 '기능 사용법'이 아닙니다. **프로덕션 레벨 에이전트 시스템을 설계하는 아키텍처 원칙**입니다.

1.  **세션(Session)**은 단순한 연결이 아니다. **상태를 가진 실행 컨텍스트**이자 **실시간 스트리밍 채널**이다.
2.  **서버사이드 루프(Server-side Loop)**는 편의 기능이 아니다. **내구성, 신뢰성, 스케일링을 개발자 어깨에서 내려놓고 인프라에 위임하는 패러다임 시프트**다. "랩탑 닫아도 된다"는 말이 주는 자유를 누리라.
3.  **두뇌와 손의 분리(Decoupling)**는 보안과 속도, 두 마리 토끼를 잡는 **필승 전략**이다.
    *   **Control Plane(두뇌):** 지능, 상태, 보안 핵심 → 중앙에서 강력하게 보호/관리.
    *   **Data Plane(손):** 실행, 데이터, 격리 → 가볍게, 많이, 안전하게 복제/실행.
    *   이 분리가 **TTFT 90% 단축, 자격 증명 완벽 격리, 무한 확장성**의 비결이다.

자, 이제 이론은 충분합니다. **`git clone` 명령어를 치고, `streamlit run app.py`로 그 마법의 세션을 직접 띄워볼 차례입니다.** 여러분의 랩탑은 이제 '무거운 연산기'가 아니라, **강력한 클라우드 에이전트 군단을 지휘하는 '지휘소'**가 될 것입니다.
