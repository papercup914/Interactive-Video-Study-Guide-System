# 챕터 3. 플래너 → 체커 순차 실행 로직 구성: "초안 작성자"와 "깐깐한 검수자"의 완벽한 팀워크 만들기

자, 지난 시간까지 우리는 **'에이전트(Agent)'**라는 일꾼을 한 명씩 고용하는 법을 배웠습니다. 그런데 아무리 뛰어난 일꾼 한 명이라도, 중요한 일을 혼자 다 맡기면 실수가 생기기 마련이죠. 그래서 실제 업무 현장에서는 **'초안을 쓰는 사람(플래너)'**과 **'그걸 검수하는 사람(체커)'**을 짝지어 **순차적으로 일**하게 만듭니다.

이번 챕터에서는 **"블로그 글 개요를 짜는 플래너"**와 **"그 개요가 제대로 짜여졌는지 확인하는 체커"**를 **릴레이 경주처럼 순서대로 실행하는 로직**을 구성하는 방법을 아주 구체적으로 뜯어보겠습니다. 요리사가 요리하고, 주방장이 맛보고 내보내는 과정과 똑같다고 보시면 됩니다.

---

## 1. 첫 번째 주자: '블로그 플래너(BlogPlanner)' - 설계도 그리는 건축가

가장 먼저 등장하는 친구는 **`BlogPlanner`**라는 이름을 가진 에이전트입니다. 이 친구의 역할은 **"빈 종이에 블로그 글의 뼈대(개요)를 그리는 것"**입니다.

### 🏷️ 명함부터 제대로 파주자: 이름(Name)과 모델(Model)

```python
name="BlogPlanner",
model=os.getenv("DEFAULT_MODEL"), # 환경변수에서 모델 불러오기
description="블로그 포스트의 마크다운 개요를 작성하는 에이전트"
```

*   **`name="BlogPlanner"`**: 이 친구를 부를 때 헷갈리지 않게 **명찰**을 달아준 겁니다. 나중에 "야, 플래너 너 이리 와봐"라고 부를 때 이 이름을 씁니다.
*   **`model=...`**: 이 일꾼의 **'머리(뇌)'**가 될 거대 언어 모델(LLM)을 지정해주는 겁니다. `gpt-4o`인지 `gemini`인지, 우리 집 환경설정 파일(`.env`)에 적혀있는 기본값을 가져다 쓰겠다는 뜻이죠.
*   **`description`**: 인사팀에 제출하는 **'한 줄 소개'** 같습니다. "이 친구는 블로그 개요 짜는 애야"라고 다른 개발자(나중의 나)에게 알려주는 메모장입니다.

> **💡 개념 돋보기: 에이전트의 3대 필수 요소 (이름, 모델, 설명)**
> 에이전트를 만들 때는 **"누구야?(이름)", "머리는 뭐 써?(모델)", "무슨 일 해?(설명)"** 이 세 가지는 꼭 챙겨주세요. 그래야 나중에 수십 명의 에이전트가 북적대도 누가 누군지, 무슨 일을 하는지 한눈에 파악할 수 있습니다. 이건 마치 **'회사 조직도'**를 만드는 것과 똑같습니다.

---

### 📝 업무 지시서(Instruction): "이렇게 정확히 그려와!"

가장 중요한 부분입니다. 그냥 "개요 좀 짜줘"라고 말하면, 어떤 날은 목차만 달랑 주고, 어떤 날은 본문까지 다 써버리는 **'제멋대로인 신입사원'**이 될 수 있습니다. 그래서 **'업무 매뉴얼(Instruction)'**을 아주 구체적으로 적어줘야 합니다.

스크립트 내용을 보면 이렇게 지시하고 있습니다.

> **"마크다운 개요를 작성해줘. 구성은 다음과 같아:**
> 1. **제목(Title)**
> 2. **짧은 서론(Introduction)**
> 3. **본론 4~6개 섹션(Sections) - 각 섹션엔 불렛 포인트(Bullet points) 포함**
> 4. **결론(Conclusion)"**

이건 마치 **건축주(우리)가 건축가(플래너)에게 주는 설계 지침서**와 같습니다.
*   "방 3개, 화장실 2개, 거실 하나 만들어줘" 정도가 아니라,
*   **"현관 들어오자마자 왼쪽에 신발장(제목), 오른쪽에 거실(서론), 복도 따라 방 4~6개(본론 섹션), 제일 안쪽에 안방(결론) 배치하고, 각 방엔 붙박이장(불렛 포인트) 꼭 달아놔"** 라고 **치수까지 정해주는 것**입니다.

**왜 이렇게까지 자세히 적나요?**
LLM은 확률적으로 다음 단어를 예측하는 기계라, 제약 조건이 없으면 **'환각(Hallucination)'**을 일으켜 엉뚱한 형식으로 뱉어낼 수 있습니다. **"출력 형식을 강제(Constrained Output)"**함으로써, **다음 주자(체커)가 받아보았을 때 "아, 이건 제대로 된 개요구나" 하고 바로 알 수 있는 표준 포맷**을 보장하는 것입니다.

---

### 📦 아웃풋 열쇠(`output_key`): "이 서랍에 넣어둬!"

```python
output_key="blog_outline"
```

여기가 **이 챕터의 핵심 마법**이 숨겨진 곳입니다.

플래너가 열심히 개요를 다 썼습니다. 그럼 이 결과물을 어디에 둬야 할까요? 그냥 화면에 `print`만 하고 끝내면, **다음 순서인 체커가 "야, 개요 어디 있어? 못 봤는데?"** 하게 됩니다.

`output_key="blog_outline"` 이 한 줄이 하는 일은 이렇습니다.

> **"플래너야, 너 다 쓴 그 개요 종이 **'공용 서랍(Shared State)'**의 **`blog_outline`** 이라는 이름표 붙은 칸에 넣어놔. 그럼 다음 사람이 알아서 꺼내갈 거야."**

*   **Shared State (공유 상태/메모리)**: 우리 팀(에이전트들)만 볼 수 있는 **공용 화이트보드** 혹은 **공용 서랍장** 같은 공간입니다.
*   **`blog_outline`**: 그 서랍장 칸막이에 붙은 **라벨(이름표)**입니다.

이렇게 해두면 **플래너는 "저장"만 하고 퇴근**하면 되고, **체커는 "읽기"만 하면 되는 완벽한 인수인계**가 이루어집니다. 이메일로 파일 첨부해서 보내고, 확인하고, 답장하고... 그런 번거로움이 **코드 한 줄(`output_key`)**로 해결되는 겁니다.

> **💡 개념 돋보기: `output_key` - 팀플의 '구글 드라이브 공유 폴더'**
> 혼자 일할 땐 내 컴퓨터 폴더에 저장하면 그만이지만, **여러 에이전트가 릴레이로 일할 땐 '공유 저장소'가 필수**입니다. `output_key`는 **"이 작업의 결과물을 공유 폴더의 '이 폴더'에 저장해줘"**라는 명령어입니다. 이걸 안 적으면 플래너가 쓴 글이 허공으로 증발해서 체커는 빈손으로 일하게 됩니다. **꼭 챙기세요!**

---

## 2. 두 번째 주자: '아웃라인 검증 체커(Outline Validation Checker)' - 깐깐한 품질 관리 팀장

자, 플래너가 `blog_outline` 서랍에 개요를 넣어두고 갔습니다. 이제 **체커(Checker)**가 나와서 **검수**를 해야죠. 이 친구는 **새로운 글을 쓰지 않습니다.** 오직 **검사만** 합니다.

### 🕵️‍♂️ 지시사항(Instruction): "체크리스트 들고 다니며 검사해!"

이 체커의 지시사항은 **매우 엄격(Strict)**합니다. 스크립트를 보면 거의 **'알고리즘'** 수준으로 정해져 있습니다.

> **지시 내용:**
> 1. **공용 서랍(State)에서 `blog_outline`을 꺼내 봐.**
> 2. **체크리스트 확인:**
>    - 제목(Title) 있는가?
>    - 서론(Introduction) 있는가?
>    - 본론 섹션(Sections)이 **4개 이상 6개 이하**인가?
>    - 결론(Conclusion) 있는가?
> 3. **판정 결과 말하기:**
>    - **다 맞으면 → "okay" 한 마디만 말해.**
>    - **하나라도 빠졌으면 → "retry" 라고 말하고, 뭐가 빠졌는지 설명해.**

이건 마치 **공장 품질 검사(QC) 팀장**이 **체크리스트 클립보드**를 들고 컨베이어 벨트 위 제품을 검사하는 모습과 똑같습니다.

*   **합격(Okay)**: "좋아, 다음 공정으로 넘어가." (다음 에이전트에게 넘김)
*   **불합격(Retry)**: "이거 제목이 없네? 다시 가서 제목 붙여와." (플래너에게 다시 시킴)

**왜 "okay" / "retry" 두 단어만 쓰게 하나요?**
이건 **사람이 읽으라고 만든 게 아니라, '시스템(코드/오케스트레이터)'이 읽고 자동으로 판단하기 위해서**입니다.
*   코드 입장에서는 `if result == "okay": pass` / `elif result == "retry": loop_back()` 이렇게 **단순 비교문 하나만 짜면 끝나니까** 엄청 편합니다.
*   만약 "음... 제목이 없는 것 같아요. 다시 해보세요." 라고 길게 말하게 하면, 코드가 이 문장을 분석해서 '아, 실패했구나'를 파악하려면 또 다른 LLM을 써야 합니다. **비용도 들고, 복잡해지죠.** 그래서 **기계어 수준의 짧은 키워드**로 답하게 훈련시키는 겁니다.

## 3. 연결 고리: 플래너 → 체커, 어떻게 이어붙이나? (순차 실행의 비밀)

스크립트 마지막에 *"To connect the planner and..."* (플래너와 체커를 연결하려면...)라고 끊겨 있지만, 개념적으로는 이렇습니다.

우리는 지금 **순차 실행(Sequential Execution)** 파이프라인을 만드는 중입니다.

```mermaid
graph LR
    A[사용자 요청] --> B(플래너: BlogPlanner)
    B -- 작성 완료 --> C[공용 서랍 State<br/>(key: blog_outline)]
    C --> D(체커: OutlineChecker)
    D -- 검사 결과 --> E{판정}
    E -- "okay" --> F[다음 단계 진행<br/>(예: 본문 작성 에이전트)]
    E -- "retry" --> B[플래너에게 재시도 명령]
```

1.  **플래너 실행** → `output_key="blog_outline"` 으로 State에 저장.
2.  **체커 실행** → 자동으로 State에서 `blog_outline`을 읽어옴 (입력값으로 자동 주입됨).
3.  **체커 판단** → `"okay"` 또는 `"retry"` 반환.
4.  **오케스트레이터(지휘자)** 가 이 반환값을 보고:
    *   `"okay"`면 **다음 에이전트(본문 작성 등)**로 넘어감.
    *   `"retry"`면 **다시 플래너로 루프(Loop)**를 돌려 보냄. (이때 "뭐가 틀렸는지" 설명도 함께 넘겨주면 플래너가 고치기 훨씬 수월함).

이게 바로 **'자율적인 자기 수정(Self-Correction) 루프'**의 기본 구조입니다. 사람 손으로 "다시 해"라고 할 필요 없이, **체커가 퇴짜 놓으면 플래너가 자동으로 다시 쓰는 무한 루프(성공할 때까지)**가 코드 몇 줄로 완성되는 것입니다.

## 4. 실전 예시로 보는 전체 흐름 (시뮬레이션)

상상해 봅시다. 사용자가 **"'파이썬 입문자를 위한 리스트 컴프리헨션' 글 개요 짜줘"**라고 요청했습니다.

### 🎬 Scene 1: 플래너의 첫 번째 시도 (조금 대충 함)
플래너가 `blog_outline` 서랍에 넣은 내용:
```markdown
# 파이썬 리스트 컴프리헨션 완전 정복

## 소개
리스트 컴프리헨션은 파이썬의 강력한 기능입니다.

## 기본 문법
- [표현식 for 항목 in 반복가능객체]
- 조건문 추가하기

## 활용 예시
- 리스트 평탄화
- 딕셔너리 만들기

## 마무리
연습 많이 하세요.
```
*   **상태**: 섹션이 **3개**(기본 문법, 활용 예시, 마무리? 마무리는 결론이라 치고, 본론 섹션이 2개뿐임) → **기준 미달(4~6개 필요)**

### 🎬 Scene 2: 체커의 검수
체커가 서랍에서 꺼내 읽고 체크리스트 대조:
*   제목? **O**
*   서론? **O**
*   본론 섹션 4~6개? **X (현재 2개)**
*   결론? **O**

**체커의 출력:** `"retry: 본론 섹션이 4개 이상 6개 이하로 필요합니다. 현재 2개뿐입니다. '장점', '주의사항', '고급 기법', '실전 팁' 등으로 섹션을 늘려주세요."`

### 🎬 Scene 3: 플래너의 두 번째 시도 (피드백 반영)
플래너가 체커의 메시지(`retry` 사유)를 보고 다시 씀.
```markdown
# 파이썬 리스트 컴프리헨션 완전 정복
## 소개
...
## 1. 기본 문법 구조
- ...
## 2. 리스트 컴프리헨션의 장점 3가지
- 가독성, 성능, 파이썬다움
## 3. 자주 하는 실수와 주의사항
- 부작용, 복잡도 과다
## 4. 중첩 리스트 평탄화 기법
- ...
## 5. 딕셔너리/셋 컴프리헨션 확장
- ...
## 6. 실무에서 써먹는 실전 팁
- ...
## 결론
...
```
*   **상태**: 섹션 **6개** → **기준 충족!**

### 🎬 Scene 4: 체커의 최종 판정
**체커의 출력:** `"okay"`

### 🎬 Scene 5: 시스템의 다음 진행
오케스트레이터가 `"okay"` 받음 → **"통과! 이제 본문 작성 에이전트(BlogWriter)에게 이 개요(`blog_outline`) 넘겨줘."** → 다음 단계로 이동.

---

## 5. 요약하며: 왜 이 구조가 '좋은 설계'인가?

이 **플래너 → 체커** 구조가 단순히 "두 번 일시키는 것"이 아니라 **엔지니어링적으로 훌륭한 이유** 세 가지를 짚으며 마무리하겠습니다.

> **💡 개념 돋보기: 플래너-체커 패턴이 주는 3가지 힘**
>
> 1.  **관심사 분리 (Separation of Concerns)**
>     *   플래너는 **"창의성(Contents)"**에만 집중합니다. "어떤 섹션이 좋을까? 독자가 뭘 궁금해할까?"만 생각하면 됩니다. 형식 맞추는 스트레스 제로.
>     *   체커는 **"규격/품질(Format/Quality)"**에만 집중합니다. "제목 있나? 섹션 개수 맞나?" 기계적으로만 보면 됩니다.
>     *   한 명에게 "창의적으로 쓰되 형식도 완벽하게 맞춰"라고 하면 둘 다 망칩니다. **역할 분담이 답입니다.**
>
> 2.  **결정적 출력 (Deterministic Output) 유도**
>     *   LLM은 본질적으로 비결정적(Non-deterministic)입니다. 같은 질문을 해도 답이 달라집니다.
>     *   체커라는 **'필터'**검증 단을 하나 두는 것만으로, 시스템 밖으로 나가는 최종 결과물의 **신뢰도(Reliability)**를 비약적으로 높일 수 있습니다. "검수받은 문서"만 다음 단계로 가니까요.
>
> 3.  **자동 재시도 루프 (Automatic Retry Loop) 구현 용이**
>     *   `retry` 신호 하나면 **코드 단 3~4줄(while 루프)**로 "완벽해질 때까지 무한 반복" 로직을 짤 수 있습니다.
>     *   사람 개입 없이 **'완성도 높은 개요'가 보장된 상태에서만** 다음 비싼 작업(본문 생성, 이미지 생성 등)으로 넘어가니 **비용 절약**에도 직결됩니다.

## 📝 마무리 학습 포인트 체크리스트

이 챕터에서 꼭 기억해둘 **핵심 키워드**들입니다. 면접이나 실무에서 바로 써먹을 수 있게 입으로 한번 말해보세요.

1.  **`output_key`**: 에이전트 간 데이터 전달의 **'공유 메모리 키(Key)'**. 이거 없으면 릴레이 불가.
2.  **`Instruction` (지시문)**: LLM에게 **"출력 형식(Output Format)을 강제"**하는 유일한 수단. 구체적일수록 좋음.
3.  **Structured Output / Constrained Output**: "마음대로 쓰지 말고 **이 틀(Schema)에 맞춰서 써**"라고 강제하는 기법.
4.  **Validation Agent (검증 에이전트)**: 생성(Generation)과 검증(Validation)을 분리해 **품질을 보장**하는 디자인 패턴.
5.  **Retry Loop (재시도 루프)**: `retry` 신호 기반으로 **자동으로 품질을 높이는 피드백 루프**.
6.  **Shared State (공유 상태)**: 워크플로우 전체의 **'단일 진실 공급원(Single Source of Truth)'** 역할을 하는 공용 데이터 창고.
