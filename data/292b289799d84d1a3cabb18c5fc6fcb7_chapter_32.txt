# 챕터: 기초 설명 생략, 실용적 통찰 중심, How와 Why 동시 설명, 코드 스니펫 포함 지침

여러분, 지난 시간에는 AI 에이전트에게 "글쓰기 계획(Outline)을 짜라"고 시키는 **플래너(Planner)** 에이전트를 만들었습니다. 그런데 사람이든 AI든 처음부터 완벽한 계획을 짜기는 쉽지 않죠. "아, 이 부분을 빼먹었네?", "이건 대상 독자 수준에 안 맞는데?" 같은 실수가 나오기 마련입니다.

이번 챕터에서는 **'계획을 짜는 AI'와 '계획을 검수하는 AI'를 짝지어 무한 루프(최대 3회) 안에서 서로 피드백을 주고받게 만드는 '견고한 블로그 플래너(Robust Blog Planner)'**를 만드는 과정을 살펴봅니다. 그리고 이렇게 검증된 완벽한 계획서를 받아 **'실전 블로그 글쓰기 AI(Blog Writer)'**에게 넘겨 실제 마크다운 초안을 완성하는 전체 파이프라인의 앞단을 구축해 보겠습니다.

## 1. 왜 '검수 루프(Loop Agent)'가 필요한가? — "혼자 일하면 실수한다, 둘이 일하면 잡는다"

### 🍳 일상 비유: 요리사의 '레시피 검수 시스템'

여러분이 **헤드 셰프(Planner)**라고 상상해 보세요. 오늘 저녁 코스 요리의 레시피(Outline)를 짜야 합니다. 베테랑 셰프라도 바쁜 주방에서 정신없이 레시피를 적다 보면 "소금 양을 안 적었네", "디저트 와인 페어링이 빠졌네" 하는 실수를 할 수 있습니다.

이때 주방에 **'꼼꼼한 수석 부주방장(Checker)'**이 딱 서서 레시피를 보며 체크리스트를 대조한다고 해보죠.
*   **수석 부주방장:** "셰프, 메인 요리에 '소금 간' 단계가 누락되었습니다. 다시 적어주세요." → **Retry(재시도)**
*   **헤드 셰프:** (수정하여 다시 제출) "소금 5g 추가했습니다."
*   **수석 부주방장:** "좋습니다. **Okay(승인)**. 이제 조리팀에게 넘기세요."

이렇게 **'작성자(Planner)'와 '검수자(Checker)'가 역할 분담을 하고, "완벽해질 때까지(최대 3번) 되돌려 보내는 시스템"**이 바로 **루프 에이전트(Loop Agent)**의 핵심 원리입니다. AI도 마찬가지입니다. 한 번에 완벽한 출력을 기대하기보다, **'생성 → 평가 → 수정'의 사이클을 시스템적으로 강제**하면 결과물의 신뢰도가 비약적으로 올라갑니다.

> **💡 개념 돋보기: 루프 에이전트(Loop Agent)란?**
> > **특정 작업(플래닝)을 수행하는 에이전트와, 그 결과를 평가하는 에이전트(체커)를 하나의 루프(Loop) 구조로 묶은 상위 에이전트입니다.**
> > 
> > *   **동작 방식:** `플래너 실행 → 체커 평가 → "Okay"면 종료 / "Retry"면 피드백과 함께 플래너 재실행`
> > *   **안전장치:** 최대 반복 횟수(예: 3회)를 두어 무한 루프 방지.
> > *   **장점:** 단일 에이전트의 '환각(Hallucination)'이나 '누락'을 구조적으로 보완 가능.

## 2. 체커(Checker) 에이전트 설계: "엄격한 품질 관리자 만들기"

가장 먼저, 플래너가 짠 계획을 검수할 **'체커 에이전트'**를 정의해야 합니다. 이 친구는 성격이 아주 까다로워야 합니다. "음, 나쁘지 않네~" 하고 넘어가면 안 되고, **정해진 체크리스트 기준으로만 'Okay' 또는 'Retry'라는 단 두 가지 답만 내뱉도록** 프롬프트를 설계해야 합니다.

### 🛠️ 코드 스니펫: 체커 에이전트 정의 (Python / ADK 스타일)

```python
from google.adk.agents import LlmAgent

# 1. 체커 에이전트 생성
checker_agent = LlmAgent(
    name="blog_outline_checker",
    model="gemini-1.5-flash",  # 가볍고 빠른 모델로 충분
    instruction="""
    당신은 블로그 글 개요(Outline) 품질 검수관입니다.
    입력으로 받은 'blog_outline' 상태 값을 다음 기준에 따라 엄격히 평가하세요.

    [필수 평가 기준]
    1. 대상 독자(Software Engineers)가 명시되었는가?
    2. '기초 설명 생략', '실용적 통찰 중심', 'How/Why 동시 설명', '코드 스니펫 포함' 지침이 반영되었는가?
    3. 마크다운 헤딩 구조(H1, H2 등)가 논리적인가?
    4. 코드 예시가 들어갈 섹션이 명시되어 있는가?

    [출력 규칙 - 절대 준수]
    - 모든 기준 충족 시: **오직 "okay"라는 단어만** 출력하세요.
    - 하나라도 미흡 시: **오직 "retry"라는 단어와, 구체적으로 무엇이 잘못되었는지 한 줄로 설명**하세요.
    - 그 외 어떤 인사말, 설명, 마크다운 문법도 사용하지 마세요.
    """,
    output_key="check_result"  # 평가 결과를 'check_result' 상태 키에 저장
)
```

### 🧐 상세 해설: 프롬프트 엔지니어링 포인트

1.  **`output_key="check_result"`**: 체커의 답변("okay" 또는 "retry 사유")을 세션 상태(`session.state`)에 저장합니다. 나중에 루프 에이전트가 이 값을 읽어서 "계속할까? 멈출까?"를 결정해야 하니까요.
2.  **출력 제약 (`오직 "okay"만`, `오직 "retry"만`)**: LLM은 수다스럽습니다. "네, 알겠습니다. 검토해보니..."라고 장황하게 말하면 파이썬 코드에서 `if result == "okay":` 같은 판단을 할 수 없습니다. **출력 포맷을 강제로 단일 토큰/단어 수준으로 고정**시키는 것이 자동화의 핵심입니다.
3.  **평가 기준의 구체화**: "잘 썼나?"가 아니라 **"대상 독자 명시 여부", "코드 스니펫 섹션 존재 여부"** 같이 **기계적으로 판별 가능한 객관식 기준**으로 쪼개야 합니다.

## 3. 플래너(Planner) 에이전트 수정: "피드백을 받아먹을 줄 아는 에이전트로 업그레이드"

기존 플래너는 "계획 짜서 저장해"만 알았지, "너 이거 틀렸어, 고쳐와"라는 피드백을 받는 로직이 없었습니다. 루프 안에서 체커가 `"retry: 코드 스니펫 섹션이 빠졌음"`이라고 뱉으면, 플래너는 이 말을 **듣고(입력받고) 반영하여 다시 짜야** 합니다.

### 🛠️ 코드 스니펫: 피드백 수용형 플래너 프롬프트 수정

```python
planner_agent = LlmAgent(
    name="blog_planner",
    model="gemini-1.5-pro",  # 계획 짜기는 복잡하니까 더 똑똑한 모델
    instruction="""
    당신은 블로그 글 개요 작성 전문가입니다.
    사용자의 요청(주제)을 받아 'blog_outline' 상태 키에 저장할 마크다운 개요를 작성하세요.

    [작성 지침 - 필수 포함 사항]
    - 대상 독자: Software Engineers (기초 생략)
    - 스타일: 실용적 통찰, How와 Why 동시 설명, 짧은 코드 스니펫 포함
    - 구조: 논리적인 마크다운 헤딩(H1, H2, H3)

    [중요: 재시도 로직]
    만약 직전 실행에서 체커로부터 피드백(`check_result` 상태 값 참조)을 받았다면,
    해당 피드백 내용을 **반드시 반영하여 수정된 개요**를 작성하세요.
    예: 체커가 "retry: 코드 스니펫 섹션 누락"이라고 했다면, 개요에 '코드 예시' 섹션을 명시적으로 추가하세요.
    """,
    output_key="blog_outline"  # 최종 계획안 저장 키
)
```

> **💡 개념 돋보기: 상태(State) 기반 피드백 루프**
> > **에이전트 간 데이터 전달은 '공유 메모리(Shared State/Session State)'를 통해 이루어집니다.**
> > 
> > 1.  **Planner** → `state["blog_outline"]` 에 초안 저장.
> > 2.  **Checker** → `state["blog_outline"]` 읽고 평가 → `state["check_result"]` 에 "okay" 또는 "retry 사유" 저장.
> > 3.  **Planner (재실행 시)** → `state["check_result"]` 를 읽고 "아, 내가 뭘 뺐구나?" 파악 후 수정본 → 다시 `state["blog_outline"]` 에 덮어쓰기.
> > 
> > 이처럼 **상태(State)를 매개로 '쓰고 → 읽고 → 고치고 → 다시 쓰는' 순환 구조**를 만드는 것이 멀티 에이전트 시스템 설계의 정석입니다.

## 4. 루프 에이전트(Loop Agent)로 묶기: "자동화된 품질 보증 라인 완성"

이제 준비된 두 에이전트(`planner_agent`, `checker_agent`)를 **`LoopAgent`**라는 컨테이너에 넣습니다. ADK(또는 유사 프레임워크)에서 `LoopAgent`는 `sub_agents` 리스트에 담긴 에이전트들을 **순차적으로 반복 실행**하며, 종료 조건을 개발자가 정의한 로직(또는 에이전트의 출력)에 따라 제어합니다.

### 🛠️ 코드 스니펫: 루프 에이전트 구성 (개념적 구현)

```python
from google.adk.agents import LoopAgent, LlmAgent
# (위에서 정의한 planner_agent, checker_agent가 있다고 가정)

# 1. 루프 에이전트 생성
robust_blog_planner = LoopAgent(
    name="robust_blog_planner",
    max_iterations=3,  # ⚠️ 안전장치: 최대 3번만 반복 (무한 루프 방지)
    sub_agents=[
        planner_agent,  # 1순위: 계획 작성 (또는 수정)
        checker_agent   # 2순위: 검수 및 판정
    ],
    # 고급: 커스텀 종료 조건 로직을 넣을 수도 있으나,
    # 여기서는 checker_agent의 output_key("check_result")가 "okay"면
    # 프레임워크 레벨에서 자동으로 루프를 깨주도록 구현했다고 가정합니다.
    # (실제 구현 시에는 LoopAgent 내부 로직 또는 후처리 콜백으로 처리)
)

# 전체 파이프라인의 루트 에이전트로 등록
root_agent = robust_blog_planner
```

### 🔄 실행 흐름 시뮬레이션 (Step-by-Step)

자, 이 `robust_blog_planner`가 실행되면 내부적으로 무슨 일이 벌어질까요?

| 반복 회차 | Planner (작성자) 행동 | Checker (검수자) 판단 (`check_result`) | 루프 상태 |
| :--- | :--- | :--- | :--- |
| **1회차** | 초기 주제만 보고 개요 초안 작성 → `blog_outline` 저장 | 초안 검토 → **"retry: 대상 독자 명시 안 됨, 코드 스니펫 섹션 없음"** 저장 | **계속 (Iteration 2)** |
| **2회차** | `check_result` 읽음 → "아, 독자랑 코드 섹션 빠졌네?" → 수정본 작성 → `blog_outline` 덮어쓰기 | 수정본 검토 → **"retry: How/Why 설명 지침이 본문 구조에 반영 안 됨"** 저장 | **계속 (Iteration 3)** |
| **3회차** | 피드백 반영 → 최종본 작성 → `blog_outline` 덮어쓰기 | 최종본 검토 → **"okay"** 저장 | **🛑 종료 (Break Loop)** |

> **💡 개념 돋보기: `max_iterations=3`의 의미 — "기회는 세 번만"**
> > **LLM은 비결정적(Non-deterministic)이라 같은 지시에도 매번 다른 결과를 낼 수 있습니다.**
> > 
> > *   **1회차:** 대충 씀.
> > *   **2회차:** 고치려다 딴짓함.
> > *   **3회차:** 정신 차리고 제대로 씀.
> > 
> > 이렇게 **'재시도 횟수'를 하드코딩으로 제한**하는 것은 **비용 폭증(토큰 낭비) 방지**와 **무한 루프로 인한 시스템 행 방지**를 위한 필수적인 엔지니어링 안전장치입니다. "완벽할 때까지 해"가 아니라 **"최대 3번까지만 기회 줄게, 안 되면 에러 뱉어"**가 프로덕션 레벨 코드의 자세입니다.

## 5. 블로그 라이터(Blog Writer) 에이전트: "검증된 설계를 바탕으로 실전 코드 작성"

드디어 `robust_blog_planner` 루프가 `"okay"`를 받고 종료되었습니다. 이제 세션 상태(`state`)에는 **체커가 인증한, 흠잡을 데 없는 `blog_outline`**이 들어있습니다. 이걸 받아서 **실제 독자가 읽을 마크다운 블로그 포스트 초안**을 쓸 **`blog_writer`** 에이전트를 만듭니다.

이 친구는 플래너/체커와 달리 **루프가 필요 없습니다**. 계획이 이미 완벽하니까요. 그냥 "이 계획대로, 너의 필체로 써"라고 시키면 됩니다.

### 🛠️ 코드 스니펫: 블로그 라이터 에이전트 정의

```python
blog_writer_agent = LlmAgent(
    name="blog_writer",
    model="gemini-1.5-pro",  # 글쓰기는 창의성과 논리 모두 필요 → Pro 모델 권장
    instruction="""
    당신은 시니어 소프트웨어 엔지니어 대상의 기술 블로그 작가입니다.
    공유 상태(`state['blog_outline']`)에 저장된 **승인된 개요**를 읽고, 이를 바탕으로 **완성도 높은 마크다운 블로그 포스트**를 작성하세요.

    [작성 원칙 - 절대 준수]
    1.  **대상 독자:** Software Engineers. 기초 문법, 환경 설정, "Hello World" 류의 입문 설명 **절대 금지**.
    2.  **핵심 지향:** '어떻게(How)' 구현하는지 코드 레벨로 보여주되, '왜(Why)' 이 방식이 좋은지(트레이드오프, 대안 비교) 동시에 설명.
    3.  **코드 스니펫:** 설명 중간중간 ` ```python ... ``` ` 블록으로 **실행 가능하거나 복사해 쓰기 좋은 짧은 코드** 필수 포함.
    4.  **구조 준수:** 개요의 헤딩(H1, H2, H3) 구조를 그대로 따라가되, 내용을 살을 붙여 채우세요.
    5.  **톤앤매너:** 전문적이되 딱딱하지 않게, "우리 이거 이렇게 쓰면 편하더라" 하는 경험 공유 톤.

    완성된 초안은 `state['blog_post']` 키에 저장하세요.
    """,
    output_key="blog_post"  # 최종 블로그 초안 저장
)
```

### 🎯 프롬프트 설계 디테일: "기초 설명 생략"을 어떻게 강제하는가?

단순히 "기초 설명 하지 마"라고 쓰면 AI가 어디까지가 기초인지 모릅니다. 그래서 **구체적인 금칙 사항(Negative Constraints)**을 때려 박는 것입니다.
*   ❌ "파이썬 설치법", "변수란?", "함수 정의 방법", "import 하는 법"
*   ✅ "타입 힌트 활용 전략", "비동기 처리의 백프레셔 처리", "데코레이터 기반 미들웨어 패턴 구현"

이처럼 **'하지 말 것' 리스트를 구체적으로 나열**해야 LLM이 "아, 그럼 중고급 주제만 파고들면 되겠네?" 하고 정확히 알아듣습니다.

## 6. 전체 파이프라인 연결: "플래너 루프 → 라이터" 순차 실행

이제 두 개의 큰 덩어리(`robust_blog_planner`, `blog_writer_agent`)를 **순차 에이전트(Sequential Agent)** 또는 메인 파이프라인 로직으로 엮으면 끝입니다.

## 7. 마무리하며: "믿을 수 있는 자동화의 비결은 '검수 루프'와 '역할 분리'"

이번 챕터에서 우리는 **단일 프롬프트로 "블로그 써줘"라고 시키는 아마추어 방식**을 벗어나, **소프트웨어 공학의 '코드 리뷰(Code Review)' 문화를 AI 에이전트 세계에 이식**했습니다.

1.  **Planner (작성자)**: 창의성과 구조화 담당.
2.  **Checker (리뷰어)**: 객관적 기준(체크리스트) 기반 품질 보증 담당. **"Okay / Retry" 이진 판정**으로 자동화 인터페이스 통일.
3.  **Loop Agent (프로세스 매니저)**: "리뷰 통과할 때까지 최대 3번 반복"이라는 **비즈니스 로직(정책) 담당**.
4.  **Writer (구현자)**: 검증된 설계도(`blog_outline`)를 받아 **실제 산출물(Code/Markdown) 생성** 담당.

이 **'생성-검수-승인-구현'** 파이프라인이 갖춰지면, 여러분은 "주제만 던지면 알아서 검수된 고품질 초안이 나온다"는 **신뢰할 수 있는 AI 자동화 시스템**을 갖게 되는 것입니다.

다음 챕터에서는 이 `blog_post` 초안을 받아 **'에디터 에이전트'가 문체 교정, 오탈자 검수, SEO 메타 태그 생성**까지 해주는 **후처리 파이프라인**을 구축해 보겠습니다. 여러분의 `state['blog_post']`가 이제 진짜 배포 직전 상태가 되는 순간입니다. 기대하셔도 좋습니다! 🚀
